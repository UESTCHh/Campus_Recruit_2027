# 📘 TSN 高阶流控机制与交换机整机架构学习笔记

## 一、 PSFP 核心概念与目标

### 1.1 PSFP 的起源与背景

PSFP（Per-Stream Filtering and Policing，每流过滤与监管）起源于 **IEEE 802.1Qci** 协议，该协议是 TSN 标准家族中的重要成员，专门用于**入站流量的安全过滤与流量监管**。

**核心目标**：在数据包进入交换机内部交换矩阵之前，进行严格的身份验证、时间窗口检查和带宽限制，防止恶意攻击、终端故障或误配置导致的异常流量冲击网络。

**通俗理解**：PSFP 就像地铁站的"安检大闸"。每个进站乘客（数据包）都需要：
1. **查身份**：确认是否属于合法流
2. **查时间**：确认是否在规定时间窗口内到达
3. **查行李**：确认是否符合携带物品限制（带宽）

### 1.2 为什么需要 PSFP？

**问题场景**：
- 某些终端设备可能因软件故障产生海量突发流量
- 恶意攻击者可能发送大量伪造数据包
- 网络配置错误可能导致流量超过预留带宽
- 非时间敏感流量可能抢占关键流量的资源

**PSFP 的价值**：
- 在流量进入核心交换架构之前将其拦截
- 保护交换机极其宝贵的 RAM 缓存资源
- 确保关键流量的服务质量不被其他流量影响
- 提供网络可预测性和稳定性

### 1.3 PSFP 与其他 TSN 机制的关系

| 机制 | 协议标准 | 作用位置 | 核心功能 |
|------|---------|---------|---------|
| **PSFP** | 802.1Qci | 入端口 (Ingress) | 流过滤、门控、计量 |
| **TAS** | 802.1Qbv | 出端口 (Egress) | 时间窗口调度 |
| **CBS** | 802.1Qav | 出端口 (Egress) | 信用整形 |
| **CQF** | 802.1Qch | 出端口 (Egress) | 循环队列转发 |

## 二、 PSFP 核心组件与架构

### 2.1 PSFP 的三大核心组件

IEEE 802.1Qci 定义了 PSFP 的三级流水线，每个组件各司其职：

```
┌─────────────────────────────────────────────────────────────┐
│                    PSFP 三级流水线                           │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  第1级：流过滤器 (Stream Filter)                             │
│  ├── 功能：基于五元组等标识"查身份"                          │
│  └── 代码实现：底层分类器哈希表                              │
│                                                             │
│           ▼                                                  │
│  第2级：流门控 (Stream Gate)                                │
│  ├── 功能：基于时间表"查时间"                                │
│  └── 未在合法时间窗口到达的周期流将被直接丢弃                 │
│                                                             │
│           ▼                                                  │
│  第3级：流计量器 (Stream Meter)                             │
│  ├── 功能：基于令牌桶算法"查带宽"                            │
│  └── 超速数据将被丢弃或降级，实现"垃圾数据零入库"            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 流过滤器 (Stream Filter)

**功能**：基于数据包的特定标识识别其所属的流。

**流识别方式**：
- 源 MAC 地址 + VLAN ID
- 目标 MAC 地址 + VLAN ID
- IP 头部的五元组（源 IP、目标 IP、源端口、目标端口、协议号）
- TSN Stream ID

**关键概念：Stream Handle**
- 流过滤器将识别到的流映射到一个唯一的句柄（Stream Handle）
- 这个句柄用于索引后续的流门控和流计量器

```cpp
/**
 * @brief 流过滤器实现
 */
class StreamFilter {
private:
    std::unordered_map<StreamID, StreamHandle> streamTable_;
    
public:
    /**
     * @brief 识别流并返回流句柄
     * @param frame 收到的以太网帧
     * @return 流句柄，如果识别失败返回无效句柄
     */
    StreamHandle identifyStream(const EthernetFrame& frame) {
        // 提取流标识信息
        StreamID streamId = extractStreamID(frame);
        
        // 查找或创建流句柄
        auto it = streamTable_.find(streamId);
        if (it != streamTable_.end()) {
            return it->second;
        }
        
        // 流不存在，检查是否允许动态创建
        if (allowDynamicStreamCreation(streamId)) {
            return createNewStream(streamId);
        }
        
        return INVALID_HANDLE;
    }
};
```

### 2.3 流门控 (Stream Gate)

**功能**：基于时间表控制流的发送窗口，超出时间窗口的帧将被丢弃。

**门控状态**：
- **Open (开启)**：允许帧通过
- **Closed (关闭)**：帧被丢弃

**关键特性**：
- 门控状态由时间表（Schedule）决定
- 支持 IPV（Internal Priority Value）赋值，控制帧进入哪个硬件队列
- 时间表可以是周期性的，与全局时钟同步

```
门控状态时间表示例：

时间轴：0 ──────────────────────────────────────────────────►

门控状态：|──Open──│──Closed──│──Open──│──Closed──│──Open──│
          ↑
       周期起点
```

### 2.4 流计量器 (Stream Meter)

**功能**：基于令牌桶算法检查流量是否超过预留带宽。

**关键参数**：
| 参数 | 说明 |
|------|------|
| Committed Information Rate (CIR) | 承诺信息速率（带宽上限） |
| Committed Burst Size (CBS) | 承诺突发大小（令牌桶容量） |
| Peak Information Rate (PIR) | 峰值信息速率（可选） |
| Peak Burst Size (PBS) | 峰值突发大小（可选） |

**计量结果处理**：
- **Conforming (符合)**：帧被标记为绿色，正常转发
- **Excess (超量)**：帧被标记为黄色，可能降级处理
- **Violating (违规)**：帧被标记为红色，直接丢弃

## 三、 FRER 核心概念与目标

### 3.1 FRER 的起源与背景

FRER（Frame Replication and Elimination for Reliability，帧复制与消除）起源于 **IEEE 802.1CB** 协议，是 TSN 标准家族中用于**提供高可靠性冗余传输**的核心机制。

**核心目标**：用双倍的链路带宽换取 0% 的丢包率，解决单点物理链路故障问题。

**通俗理解**：FRER 就像快递的"双重保险"机制。重要文件快递时，快递公司会：
1. **发送两份副本**：通过两条不同路线发送
2. **消除重复**：收件人收到第一份后，第二份直接拒收
3. **确保到达**：只要有一条路线正常，文件就能送达

### 3.2 为什么需要 FRER？

**问题场景**：
- 单点物理链路故障导致通信中断
- 电磁干扰导致数据包损坏或丢失
- 网络拥塞导致关键数据包被丢弃
- 某些工业场景（如汽车网络）要求零丢包率

**FRER 的价值**：
- 提供毫秒级的故障恢复
- 消除单点故障的影响
- 保证关键流量的高可靠性传输
- 适用于汽车、航空等安全关键应用

### 3.3 FRER 的应用场景

| 应用领域 | 典型场景 | 可靠性要求 |
|---------|---------|-----------|
| **汽车网络** | 自动驾驶传感器数据传输 | 99.999% 可用性 |
| **工业自动化** | 机器人控制指令 | 零丢包率 |
| **航空电子** | 飞控系统数据 | 功能安全 ASIL-D |
| **电力系统** | 继电保护信号 | 毫秒级恢复 |

### 4.2 R-TAG（冗余标签）

R-TAG 是 FRER 的核心数据结构，位于以太网帧的 VLAN Tag 之后：

```
以太网帧格式（含 R-TAG）：

┌─────────┬─────────┬─────────┬─────────┬─────────┬─────────┐
│ DA/SA   │ R-TAG   │ VLAN    │ Length/ │ Payload │ CRC     │
│         │         │ Tag     │ Type    │         │         │
└─────────┴─────────┴─────────┴─────────┴─────────┴─────────┘
              ↑
        ┌─────┴─────┐
        │ Sequence  │  ← 16-bit 序列号
        │ Number    │
        └───────────┘
```

**Sequence Number（序列号）**：
- 16 位无符号整数（0 ~ 65535）
- 每个流独立维护
- 发送端递增分配
- 用于接收端识别重复帧

### 4.3 复制功能 (Replication)

**复制点（RepNode）的职责**：
1. 为每个输出帧添加 R-TAG，包含唯一的 Sequence Number
2. 通过多个物理上分离的路径发送副本
3. 维护 Sequence Number 的生成状态

```cpp
/**
 * @brief FRER 复制器实现
 */
class FRERReplicator {
private:
    uint16_t sequenceNumber_;  // 当前序列号
    std::vector<int> outputPorts_;  // 冗余路径端口列表
    
public:
    /**
     * @brief 复制并发送帧
     * @param frame 原始帧
     */
    void replicate(const EthernetFrame& frame) {
        // 为当前帧分配序列号
        uint16_t seqNum = sequenceNumber_++;
        
        // 创建带 R-TAG 的帧副本
        for (int port : outputPorts_) {
            EthernetFrame replicatedFrame = addRTAG(frame, seqNum);
            sendToPort(port, replicatedFrame);
        }
    }
};
```

### 4.4 消除功能 (Elimination)

**消除点（ElimNode）的职责**：
1. 维护已接收序列号的记录（历史窗口）
2. 对于每个到达的帧，检查其序列号
3. 第一个到达的帧被接收，后续重复帧被丢弃

**两种恢复算法**：

#### 4.4.1 Match Recovery Algorithm (MRA)

**原理**：只记录接收到的最高序列号

```
┌─────────────────────────────────────────────────────────────┐
│                  Match Recovery Algorithm                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  接收历史：序列号 5 已确认                                    │
│                                                             │
│  帧到达顺序：                                                │
│  1. Seq=5 → 最高，接收（更新历史）                          │
│  2. Seq=5 → 重复，丢弃                                      │
│  3. Seq=6 → 新最高，接收（更新历史）                        │
│  4. Seq=4 → 低于历史窗口，丢弃                               │
│                                                             │
│  限制：适用于间歇性流（帧间隔 ≥ 接收窗口差异）               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 4.4.2 Vector Recovery Algorithm (VRA)

**原理**：维护序列号历史向量

```
┌─────────────────────────────────────────────────────────────┐
│                 Vector Recovery Algorithm                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  历史窗口长度：frerSeqRcvyHistoryLength                     │
│  当前确认序列号：n                                          │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐    │
│  │  n+5  │  n+4  │  n+3  │  n+2  │  n+1  │   n    │    │
│  │   0   │   1   │   1   │   1   │   1   │   1    │    │
│  │ 未知  │ 已收  │ 已收  │ 已收  │ 已收  │ 已收   │    │
│  └─────────────────────────────────────────────────────┘    │
│                                                             │
│  接收判断：                                                  │
│  - 序列号在窗口内且已接收 → 重复，丢弃                       │
│  - 序列号在窗口内但未接收 → 新帧，接收                       │
│  - 序列号在窗口外 → 丢弃或更新确认序列号                     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

## 五、 帧抢占 (Frame Preemption) 详解

### 5.1 帧抢占的起源与背景

帧抢占（Frame Preemption）由 **IEEE 802.1Qbu** 和 **IEEE 802.3br** 两项标准联合定义。

**核心目标**：解决长帧传输造成的"传输阻塞延迟"，实现微观物理层的终极插队机制。

**通俗理解**：就像高速公路上，紧急车辆（救护车、消防车）可以通过"可变车道"绕过正在行驶的普通车辆。帧抢占允许高优先级帧在传输过程中"切断"低优先级长帧，立即发送，然后再恢复传输。

### 5.2 帧抢占的基本原理

```
┌─────────────────────────────────────────────────────────────┐
│                   帧抢占原理图                              │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  无帧抢占时：                                                │
│  ┌──────────────────────────────────────────────────────┐ │
│  │  低优先级长帧 (1500 bytes, ~12μs)                      │ │
│  │  ████████████████████████████████████████████████████ │ │
│  └──────────────────────────────────────────────────────┘ │
│       ──────────────────────────────────────────▶ 时间     │
│       高优先级帧必须等待长帧发送完成                         │
│                                                             │
│  ───────────────────────────────────────────────────────── │
│                                                             │
│  有帧抢占时：                                                │
│  ┌──────────────────────────────────────────────────────┐ │
│  │  低优先级长帧                                          │ │
│  │  ████████████████│← 高优先级帧插入 │███████        │ │
│  └──────────────────────────────────────────────────────┘ │
│       ──────────────────────────────────────────▶ 时间     │
│                    ↑                                        │
│                    切断点（可抢占边界）                     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 5.3 MAC 层双引擎架构

帧抢占通过在 MAC 层引入双引擎来实现：

| 引擎 | 全称 | 职责 | 处理帧类型 |
|------|------|------|-----------|
| **eMAC** | Express MAC | 处理紧急高优先级帧 | 快速帧 (Express Frame) |
| **pMAC** | Preemptable MAC | 处理普通可抢占帧 | 可被抢占帧 (Preemptable Frame) |

```
┌─────────────────────────────────────────────────────────────┐
│                  MAC 层双引擎架构                            │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  高优先级队列 ────────► eMAC ────────► 物理层 (PHY)         │
│         │                                                       │
│         │ 抢占控制                                             │
│         ▼                                                       │
│  ┌───────────────────────────────────────────────────────┐ │
│  │              MAC 合并子层 (MAC Merge)                  │ │
│  │                                                       │ │
│  │   接收 eMAC 和 pMAC 的帧，                            │ │
│  │   在物理层合并输出                                    │ │
│  └───────────────────────────────────────────────────────┘ │
│         ▲                                                       │
│         │                                                       │
│  低优先级队列 ────────► pMAC ────────►        │               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 5.4 抢占过程详解

**抢占的原子步骤**：
1. 高优先级帧（如工业控制指令）到达出口队列
2. MAC 检测到当前可抢占点（通常在 MAC 头之后）
3. 发送抢占控制帧，通知接收端即将发生抢占
4. 插入高优先级帧（Express Frame）
5. 高优先级帧发送完毕后，恢复被中断的长帧
6. 接收端依据抢占标识与序列号完成重组与校验

### 5.5 关键参数与限制

| 参数 | 说明 |
|------|------|
| Preemption Flag | 1 bit，标识帧是否可被抢占 |
| Express Frame Indicator (EFI) | 1 bit，标识是否为快速帧 |
| Guard Band | 12 bytes，保护带，防止 CRC 错误 |
| mPacket | 被分割后的最小可传输单元 |

## 六、 ATS (异步流量整形) 详解

### 6.1 ATS 的起源与背景

ATS（Asynchronous Traffic Shaper，异步流量整形）起源于 **IEEE 802.1Qcr** 协议。

**核心目标**：彻底摆脱对全局严格时间同步（IEEE 802.1AS）的依赖，为异步网络提供确定性延迟保障。

**通俗理解**：ATS 就像机场的"独立安检通道"。每个乘客（数据流）都有自己专属的安检设备（漏桶定时器），按自己节奏排队安检，不依赖统一的广播通知。

### 6.2 ATS 与其他整形器的区别

| 特性 | TAS | CBS | ATS |
|------|-----|-----|-----|
| 同步需求 | 需要 802.1AS 同步 | 无 | 无 |
| 调度单位 | 队列 | 队列 | **每条流 (Per-Flow)** |
| 延迟特性 | 极低且固定 | 有上限但波动 | 确定性的上界 |
| 适用场景 | 严格周期性流 | 突发性 AVB 流 | 异步混合流 |

### 6.3 ATS 的核心算法

ATS 基于**令牌桶算法**的变体，为每条流分配独立的漏桶定时器：

**关键参数**：
| 参数 | 说明 |
|------|------|
| Committed Information Rate (CIR) | 承诺信息速率 |
| Committed Burst Size (CBS) | 承诺突发大小 |
| MaxResidenceTime | 最大驻留时间 |

**调度算法**：
```
计算 eligibilityTime (最早可发送时间):
1. lengthRecoveryDuration = frameLength / CIR
2. emptyToFullDuration = CBS / CIR
3. schedulerEligibilityTime = BucketEmptyTime + lengthRecoveryDuration
4. bucketFullTime = BucketEmptyTime + emptyToFullDuration
5. eligibilityTime = max(arrivalTime, schedulerEligibilityTime)

如果 eligibilityTime <= arrivalTime + MaxResidenceTime:
    → 帧有效，发送
否则:
    → 帧无效，丢弃
```

/**
 * @brief PSFP 流计量器 (令牌桶)
 */
class PSFPStreamMeter {
private:
    struct TokenBucket {
        double tokens_;
        double lastUpdateTime_;
        double cir_;  // Committed Information Rate
        double cbs_;  // Committed Burst Size
    };
    std::unordered_map<StreamHandle, TokenBucket> buckets_;
    
public:
    enum class MeterResult { CONFORMING, EXCESS, VIOLATING };
    
    MeterResult evaluate(StreamHandle handle, const Packet& packet, double currentTime) {
        TokenBucket& bucket = buckets_[handle];
        
        // 更新令牌桶
        double elapsed = currentTime - bucket.lastUpdateTime_;
        bucket.tokens_ = std::min(bucket.cbs_, bucket.tokens_ + elapsed * bucket.cir_);
        bucket.lastUpdateTime_ = currentTime;
        
        // 检查是否超过承诺速率
        if (bucket.tokens_ >= packet.length()) {
            bucket.tokens_ -= packet.length();
            return MeterResult::CONFORMING;
        }
        return MeterResult::VIOLATING;
    }
};

### 9.2 FRER 仿真实现

```cpp
/**
 * @brief FRER 复制器
 */
class FRERReplicator {
private:
    uint16_t sequenceNumber_;
    std::vector<int> redundantPorts_;
    
public:
    void replicate(const Packet& packet, int streamId) {
        uint16_t seqNum = sequenceNumber_[streamId]++;
        
        // 通过冗余路径发送副本
        for (int port : redundantPorts_) {
            Packet replica = packet;
            replica.addRTAG(streamId, seqNum);
            sendToPort(port, replica);
        }
    }
};

/**
 * @brief FRER 消除器 (使用 VRA 算法)
 */
class FREREliminator {
private:
    struct RecoveryState {
        uint16_t recoverySeqNum_;
        std::vector<bool> history_;  // 历史窗口向量
        size_t historyLength_;
    };
    std::unordered_map<int, RecoveryState> streamStates_;
    
public:
    bool processFrame(const Packet& packet, int streamId) {
        uint16_t seqNum = packet.getSequenceNumber();
        RecoveryState& state = streamStates_[streamId];
        
        // 计算序列号相对于 recoverySeqNum 的偏移
        int16_t offset = calculateOffset(seqNum, state.recoverySeqNum_);
        
        // 检查是否在历史窗口内
        if (offset >= 0 && offset < static_cast<int16_t>(state.historyLength_)) {
            if (state.history_[offset]) {
                // 已接收过，重复帧，丢弃
                return false;
            }
            // 新帧，接收并更新历史
            state.history_[offset] = true;
            return true;
        } else if (offset >= static_cast<int16_t>(state.historyLength_)) {
            // 序列号比历史窗口更新，更新 recoverySeqNum
            state.recoverySeqNum_ = seqNum;
            std::fill(state.history_.begin(), state.history_.end(), false);
            state.history_[0] = true;
            return true;
        }
        // 序列号在历史窗口之前，丢弃
        return false;
    }
};
```

## 十、 面试高频问题与解答

### 10.1 PSFP 相关问题

#### Q1：PSFP 的三级流水线是什么？

**答案**：
1. **流过滤器 (Stream Filter)**：基于五元组等标识识别流的身份，返回 Stream Handle
2. **流门控 (Stream Gate)**：基于时间表检查是否在合法时间窗口内
3. **流计量器 (Stream Meter)**：基于令牌桶算法检查是否超速

#### Q2：PSFP 在 TSN 架构中的作用是什么？

**答案**：
- PSFP 位于 Ingress（入端口），是交换机的第一道安检防线
- 作用是防止异常流量（恶意攻击、终端故障、配置错误）进入核心交换架构
- 保护交换机宝贵的 RAM 缓存资源
- 确保关键流量的服务质量不被影响

### 10.2 FRER 相关问题

#### Q3：FRER 的核心原理是什么？

**答案**：
- **发送端复制**：为每个帧添加 R-TAG（包含 Sequence Number），通过多条冗余路径发送副本
- **接收端消除**：维护序列号历史窗口，第一个到达的帧被接收，后续重复帧被丢弃
- **关键数据结构**：R-TAG（冗余标签），包含 16-bit 序列号

#### Q4：FRER 有哪两种恢复算法？区别是什么？

**答案**：
- **Match Recovery Algorithm (MRA)**：只记录最高序列号，适用于间歇性流
- **Vector Recovery Algorithm (VRA)**：维护完整的历史窗口向量，能处理更复杂的场景
- MRA 实现简单但功能有限；VRA 更强大但需要更多状态

#### Q5：FRER 对网络拓扑有什么要求？

**答案**：
- 网络必须能够形成**环路**，以提供冗余路径
- FRER 本身不创建冗余路径，需要网络拓扑本身具有环路
- 常用于 Zonal 架构（区域架构），而非域控制器架构

### 10.3 帧抢占相关问题

#### Q6：帧抢占的原理是什么？

**答案**：
- 帧抢占由 IEEE 802.1Qbu 和 IEEE 802.3br 联合定义
- 在 MAC 层引入双引擎：eMAC（处理高优先级帧）和 pMAC（处理低优先级帧）
- 当高优先级帧到达时，可以"切断"正在传输的低优先级长帧
- 被切断的帧被分割成多个 mPacket，恢复后继续传输

#### Q7：帧抢占能带来什么好处？

**答案**：
- **延迟降低**：原本需要等待长帧（1500B，约 12μs）发送完成的高优先级帧，可以立即发送
- **抖动减小**：高优先级帧的延迟从"等待时间"变成"抢占操作时间"
- **带宽利用率提升**：与 TAS 结合时，可以大幅压缩保护频带

### 10.4 ATS 相关问题

#### Q8：ATS 与 TAS 的主要区别是什么？

**答案**：
| 特性 | TAS | ATS |
|------|-----|-----|
| 同步需求 | 需要 802.1AS 同步 | 无需同步 |
| 调度单位 | 队列 | 每条流 (Per-Flow) |
| 配置复杂度 | 高 (需要全局 GCL) | 低 (只需为每流配置漏桶) |
| 适用场景 | 严格周期性流 | 异步混合流 |

### 10.5 联合调度相关问题

#### Q9：TAS 和帧抢占如何协同工作？

**答案**：
- TAS 原本需要设置 Guard Band 防止长帧阻塞
- 引入帧抢占后，可以直接切断长帧，无需等待
- **效果**：大幅压缩 Guard Band，提升带宽利用率
- **原理**：帧抢占将长帧分割成多个片段，在片段间插入高优先级帧

#### Q10：PSFP 和 CBS 如何协同工作？

**答案**：
- CBS 位于 Egress（出端口），容易被海量突发流耗尽交换机内存
- PSFP 位于 Ingress（入端口），可以在流量进入核心架构前拦截超速帧
- **效果**：实现"防线前移"，保护交换机缓存资源
