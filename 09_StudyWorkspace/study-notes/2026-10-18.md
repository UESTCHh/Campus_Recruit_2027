## 三、C++ Stage 1：从相同二叉树到镜像比较

### 3.1 对称性的判定对象

一棵二叉树对称，表示根节点左右子树互为镜像：镜像位置的值相同，空孩子的位置也要互相对应。

```text
         1
       /   \
      2     2
     / \   / \
    3   4 4   3
```

对应关系：

- 根的左孩子与右孩子比较：2 对 2。
- 外侧比较：左子树的左孩子与右子树的右孩子，即 3 对 3。
- 内侧比较：左子树的右孩子与右子树的左孩子，即 4 对 4。

只有两个直接孩子的值相同，不足以证明整棵树对称。例如 `[1,2,2,null,3,null,3]` 两侧都有值为 3 的节点，但它们处于相同方向，整体不对称。

### 3.2 与 Day43 的递归方向对比

| 问题 | 第一对子问题 | 第二对子问题 |
| --- | --- | --- |
| LC100 相同的树 | `p->left` 对 `q->left` | `p->right` 对 `q->right` |
| LC101 对称二叉树 | `p->left` 对 `q->right` | `p->right` 对 `q->left` |

两者都需要先处理空指针，再比较节点值；差异在于递归时如何配对。

### 3.3 本地实验：mirror_compare_demo.cpp

下面是当天文件中 `main()` 及其辅助代码，后附 LeetCode 解法另列于下一节。

```cpp
#include <iostream>

using namespace std;

struct TreeNode {
    int val;
    TreeNode* left;
    TreeNode* right;

    TreeNode(int x)
        : val(x), left(nullptr), right(nullptr) {}
};

// 只比较一对节点是否相同
// 不递归，因此还不能用来判断整棵树是否对称
bool sameCurrentNode(TreeNode* p, TreeNode* q) {
    if (p == nullptr || q == nullptr) {
        return p == q;
    }

    return p->val == q->val;
}

int main() {
    /*
             1
            / \
           2   2
          / \ / \
         3  4 4  3
    */

    TreeNode n1(1);
    TreeNode n2(2);
    TreeNode n3(2);
    TreeNode n4(3);
    TreeNode n5(4);
    TreeNode n6(4);
    TreeNode n7(3);

    n1.left = &n2;
    n1.right = &n3;

    n2.left = &n4;
    n2.right = &n5;

    n3.left = &n6;
    n3.right = &n7;

    TreeNode* root = &n1;

    cout << boolalpha;

    // 两个直接孩子的值是否相同
    cout << "Root children match: "
         << sameCurrentNode(root->left, root->right)
         << '\n';

    // 外侧镜像位置
    cout << "Outer grandchildren match: "
         << sameCurrentNode(
                root->left->left,
                root->right->right)
         << '\n';

    // 内侧镜像位置
    cout << "Inner grandchildren match: "
         << sameCurrentNode(
                root->left->right,
                root->right->left)
         << '\n';

    // 错误方向：左对左
    cout << "Same-side grandchildren match: "
         << sameCurrentNode(
                root->left->left,
                root->right->left)
         << '\n';

    return 0;
}
```

运行结果：

```text
Root children match: true
Outer grandchildren match: true
Inner grandchildren match: true
Same-side grandchildren match: false
```

用户已确认实际编译运行成功。最后一项为 `false` 是刻意安排的方向对比：左边的 3 与右边的 4 并非镜像位置。

关键理解：

1. `sameCurrentNode()` 只检查当前两个位置，不递归，不能单独判断整棵树对称。
2. `p == q` 比较两个指针保存的地址值；在“至少一个为空”的分支里，只有二者都为空才为真。
3. `p->val == q->val` 必须在确认两指针均非空后使用。
4. 示例节点是 `main()` 内的局部对象，连接通过地址完成，没有 `new`，不需要手动 `delete`。

## 四、C++ Stage 2：LeetCode 101《对称二叉树》

### 4.1 当天实现

以下为当前文件中的 `Solution`，保留当天代码，不将后续建议冒充成已提交版本。

```cpp
class Solution {
public:
    bool isTwoSym(TreeNode* p, TreeNode* q){
        if(p == nullptr || q == nullptr){
            return p == q;
        }
        return (p -> val == q -> val) &&
            isTwoSym(p -> left, q -> right) &&
            isTwoSym(p -> right, q -> left);
    }
    bool isSymmetric(TreeNode* root) {
        TreeNode* p = root -> left;
        TreeNode* q = root -> right;
        return isTwoSym(p, q);
    }
};
```

验收：用户确认 Accepted。题目来源：[LeetCode 101 · Symmetric Tree](https://leetcode.com/problems/symmetric-tree/)。

### 4.2 递归函数的含义

`isTwoSym(p, q)` 表示“以 p、q 为根的两棵子树是否互为镜像”。

三部分必须同时满足：

```cpp
p->val == q->val
isTwoSym(p->left, q->right)
isTwoSym(p->right, q->left)
```

递归边界：

| p | q | 返回 | 原因 |
| --- | --- | --- | --- |
| 空 | 空 | `true` | 对应位置同时缺失 |
| 空 | 非空 | `false` | 镜像结构不一致 |
| 非空 | 空 | `false` | 镜像结构不一致 |
| 非空 | 非空 | 继续比较 | 先值，再外侧与内侧 |

`&&` 具有短路性质：当前值不同，后面的递归不会继续；外侧递归为假，内侧也不必执行。这不会改变最坏情况下的复杂度。

### 4.3 时间和空间复杂度

- 最坏时间复杂度 `O(n)`：比较所有镜像位置，工作量随节点数线性增长。
- 递归辅助空间上界 `O(h)`：由实际递归深度决定，h 为树高。
- 对称且较平衡的树，h 为 `O(log n)`；退化树的树高可达 `O(n)`，但此题面对某些明显不对称的退化输入会提前结束，因此 `O(h)` 是上界，不表示每种输入一定用满该空间。

### 4.4 已通过代码的边界

题目当前约束至少有一个节点，所以当天入口直接读取 `root->left`、`root->right` 能满足题目输入。若迁移到允许空树的通用函数，入口应补充：

```cpp
if (root == nullptr) {
    return true;
}
```

这是通用性建议，不代表已修改当天源文件。也不需要为了判断对称先翻转树：交叉比较即可完成判断，不改变原树。

### 4.5 补充复习题（整理内容，非缺失原回答）

- 为什么只比较 `root->left->val` 和 `root->right->val` 不够？还需比较所有后代的镜像结构和值。
- 为什么外侧和内侧必须用 `&&`？整棵树对称要求两个方向都满足；使用 `||` 会放过局部不对称。
- 为什么先判断空指针？避免解引用空指针，并判断结构是否匹配。
- 为什么“相同的树”代码不能原样用来判对称？相同树沿相同方向比较，镜像树必须交叉比较。

## 六、Go PUT：更新指定学生

### 6.1 请求语义

```http
PUT /students/1005
Content-Type: application/json

{"name":"Eva Updated","age":23}
```

这里的 1005 仅作为路径示例，不代表记录当前一定存在。资源 ID 由 URL 确定，请求体只提供要写入的 `name`、`age`。

当前接口要求这两个字段都有效，按完整提交可写字段的方式更新，并非只提交一个字段的 PATCH。省略 `age` 会得到整数零值，随后被业务校验拒绝；请求体携带 `id` 则会因未知字段而被拒绝。

### 6.2 当天 Handler 完整代码

```go
func updateStudentHandler(repo *StudentRepository) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		// 1. 解析路径中的学生ID
		studentID, err := strconv.Atoi(r.PathValue("id"))
		if err != nil || studentID <= 0 {
			writeJSON(
				w,
				http.StatusBadRequest,
				ErrorResponse{Error: "invalid student id"},
			)
			return
		}

		// 2. 定义PUT请求体
		// ID不从请求体读取，而是由URL路径确定
		var req struct {
			Name string `json:"name"`
			Age  int    `json:"age"`
		}

		// 3. 解码JSON
		decoder := json.NewDecoder(r.Body)
		// 它使解码器在遇到结构体不认识的 JSON 字段时返回错误
		decoder.DisallowUnknownFields()

		if err := decoder.Decode(&req); err != nil {
			writeJSON(
				w,
				http.StatusBadRequest,
				ErrorResponse{Error: "invalid JSON body"},
			)
			return
		}

		// 4. 校验数据
		if strings.TrimSpace(req.Name) == "" || req.Age <= 0 {
			writeJSON(
				w,
				http.StatusBadRequest,
				ErrorResponse{Error: "invalid student data"},
			)
			return
		}

		// 5. 根据路径ID构造待更新的学生记录
		student := Student{
			ID:   studentID,
			Name: req.Name,
			Age:  req.Age,
		}

		// 6. 调用Repository
		affected, err := repo.Update(student)

		if err != nil {
			log.Printf("Update failed: %v", err)

			writeJSON(
				w,
				http.StatusInternalServerError,
				ErrorResponse{Error: "internal server error"},
			)
			return
		}

		// 7. 判断学生是否存在
		if affected == 0 {
			writeJSON(
				w,
				http.StatusNotFound,
				ErrorResponse{Error: "student not found"},
			)
			return
		}

		// 8. 返回更新后的学生信息
		writeJSON(w, http.StatusOK, student)
	}
}
```

处理顺序：路径 ID 转换与校验 → JSON 解码 → 业务字段校验 → 构造 `Student` → `repo.Update()` → 检查错误及影响行数 → 返回 200 JSON。

### 6.3 Repository 更新实现

```go
func (r *StudentRepository) Update(student Student) (int64, error) {
	result, err := r.db.Exec(
		"UPDATE students SET name = ?, age = ? WHERE id = ?",
		student.Name,
		student.Age,
		student.ID,
	)
	if err != nil {
		return 0, err
	}

	return result.RowsAffected()
}
```

SQL 用 `?` 占位符和参数传值，不把客户端输入拼接为 SQL。`Exec()` 返回的 `sql.Result` 才能进一步调用 `RowsAffected()`；`Exec()` 没报错并不保证找到了目标记录。

当前代码中：

- 数据库执行错误或影响行数获取错误：Handler 返回 500。
- 正常执行但影响行数为 0：按此接口约定返回 404。
- 找到记录并执行更新：200 + 更新后的学生 JSON。

迁移到其他驱动时要确认“影响行数”是匹配行还是实际变化行等细节，不能把本例约定机械套用到所有数据库。

### 6.4 JSON 严格校验的范围

`DisallowUnknownFields()` 会拒绝结构体不认识的字段，例如 `id` 或拼错的 `agge`。它不等于完成所有输入校验：业务约束仍需另行判断；当前仅调用一次 `Decode()`，没有继续确认后续为 EOF，因此不能宣称已拒绝尾随的第二个 JSON 文档。请求体大小限制等也尚未加入。

官方依据：[encoding/json.Decoder](https://pkg.go.dev/encoding/json#Decoder)。

## 七、405 Method Not Allowed：路由排错

### 7.1 先确定失败层次

405 表示该目标不支持本次请求方法。在本例 ServeMux 中，若 `/students/{id}` 只有 GET 路由而没有 PUT 路由，PUT 会被路由层拒绝，尚未执行 JSON 解码或 SQL。

因此，不能看到 405 就修改 JSON、数据库数据或 SQL。先检查客户端请求是否确实为 `PUT /students/{id}`，以及正在运行的程序是否注册了这条方法和路径。

### 7.2 排查顺序

1. 确认请求方法、URL、端口。当前服务监听 `127.0.0.1:8081`。
2. 确认有 `mux.HandleFunc("PUT /students/{id}", updateStudentHandler(repo))`。
3. 确认已保存代码，并停止旧服务、从 Day44 目录重新启动；修改源码不会自动更新旧进程。
4. 确认发送请求的端口对应当前程序，避免实际上仍访问 Day43 的服务。
5. 查看 405 响应中的 `Allow`，辅助判断该路径支持哪些方法。

Go 新版 ServeMux 的模式包含方法、路径和通配符；`r.PathValue("id")` 从匹配的通配符中取得路径 ID。参考：[net/http.ServeMux](https://pkg.go.dev/net/http#ServeMux)。

关于原聊天这次 405 的具体截图、进程和最终根因，当前预览没有保留，故以上是排错机制整理，不编造“当时一定因为忘记重启”等结论。

## 八、Go DELETE：删除指定学生

### 8.1 请求与处理链

```text
DELETE /students/{id}
  → r.PathValue("id")
  → strconv.Atoi + 正数校验
  → repo.Delete(studentID)
  → Exec DELETE + RowsAffected
  → 有错误：500
  → 影响 0 行：404 + 错误 JSON
  → 删除成功：204，无响应体
```

这个接口只需路径 ID，不要求 JSON 请求体，因此不使用 `json.Decoder`。这与成功响应有没有 JSON 是两个独立问题。

### 8.2 当天 Handler 完整代码

```go
func deleteStudentHandler(repo *StudentRepository) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		// 1. 从URL路径获取ID
		idText := r.PathValue("id")

		// 2. 转换并校验ID
		studentID, err := strconv.Atoi(idText)
		if err != nil || studentID <= 0 {
			writeJSON(
				w,
				http.StatusBadRequest,
				ErrorResponse{Error: "invalid student id"},
			)
			return
		}

		// 3. 调用Repository删除学生
		affected, err := repo.Delete(studentID)
		if err != nil {
			log.Printf("Delete failed: %v", err)

			writeJSON(
				w,
				http.StatusInternalServerError,
				ErrorResponse{Error: "internal server error"},
			)
			return
		}

		// 4. 目标学生不存在
		if affected == 0 {
			writeJSON(
				w,
				http.StatusNotFound,
				ErrorResponse{Error: "student not found"},
			)
			return
		}

		// 5. 删除成功，不返回JSON响应体
		w.WriteHeader(http.StatusNoContent)
	}
}
```

### 8.3 Repository 删除实现

```go
func (r *StudentRepository) Delete(studentID int) (int64, error) {
	result, err := r.db.Exec(
		"DELETE FROM students WHERE id = ?",
		studentID,
	)
	if err != nil {
		return 0, err
	}

	return result.RowsAffected()
}
```

`RowsAffected()` 在 Repository 内调用；Handler 得到的是 `affected` 与 `err`，再决定 HTTP 响应。`DELETE ... WHERE id = ?` 即使没有匹配记录，也可能正常执行，所以必须区分“执行成功”和“确实删除记录”。

官方依据：[database/sql.Result](https://pkg.go.dev/database/sql#Result)。

### 8.4 204 为什么不能走 writeJSON()

204 表示已成功完成，且没有响应内容。当天 `writeJSON()` 内部会序列化数据并调用 `w.Write()`，因此不适用于 204。正确分支是：

```go
w.WriteHeader(http.StatusNoContent)
```

删除成功也可以按接口设计返回 200 并提供操作结果描述；并不是 DELETE 天生只能返回 204。当前已同步完成删除、没有内容返回，因此选择 204。

## 九、HTTP 状态码与幂等性

### 9.1 按失败层次区分状态

| 状态 | 当前项目示例 | 发生层次 |
| --- | --- | --- |
| 200 | GET 成功、PUT 成功并返回学生 | Handler 正常响应 |
| 201 | POST 创建成功 | Handler 创建响应 |
| 204 | DELETE 删除成功，无响应内容 | Handler 删除响应 |
| 400 | ID 非法、JSON 无效、字段校验失败 | 输入处理 |
| 404 | 合法 ID 没有对应记录；或没有匹配路径 | 数据查找或路由 |
| 405 | 路径可匹配，但请求方法不支持 | 路由 |
| 409 | POST 主键 / 唯一约束冲突 | 数据库错误经 Handler 映射 |
| 500 | 未预期的数据库等服务端错误 | 服务端 |

这些是当前代码和接口约定，不等于所有项目都必须采用相同错误分类。ServeMux 自动生成的 404 / 405 也不一定采用本项目 `ErrorResponse` 的 JSON 格式。

### 9.2 幂等性的准确表达

同一个请求执行多次，其预期资源效果应与执行一次一致。并非要求每次响应完全相同，也不是说第一次请求不能改变数据库。

删除的例子：

```text
开始：学生存在
第一次 DELETE → 学生不存在，204
第二次 DELETE → 学生仍不存在，404
```

两次请求后目标状态均为“该学生不存在”，因此不违背幂等性。日志等附带记录可以不同。

PUT 将字段设定为相同给定值，也符合幂等语义；如果实现为“每次将年龄加一”，重复请求会不断改变结果，便不符合这里的 PUT 语义。POST 一般不保证幂等；本例重复主键被拒绝，并不能推出所有 POST 都幂等。

以上说明以没有其他客户端在两次请求之间修改或重建目标资源为例。协议中的幂等保证不等于消除并发更新问题。

规范参考：[RFC 9110 §9.2.2 幂等方法](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)、[§9.3.5 DELETE](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.5)、[§15.3.5 204](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.5)、[§15.5.6 405](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.6)。

### 10.1 为什么 DELETE 不需要 json.Decoder？

**可复述答案：**本接口只从 URL 路径取得并校验学生 ID，没有需要解析的 JSON 请求体，所以不使用 `json.Decoder`。

### 10.2 为什么成功删除返回 204，而非必须 200 + 学生 JSON？

**用户原回答：**

> 因为DELETE的结果不需要返回响应体，所以不需要返回学生JSON，此时学生记录在数据库中已经不存在了

**订正：**符合当前接口设计。更准确地说，删除已经完成且无内容返回，选择 204；DELETE 也允许按设计用 200 返回操作结果。记录被删并不意味着服务端绝对无法返回删除前的信息。

**可复述答案：**当前接口删除成功后不返回内容，因此用 204；若接口约定返回删除结果描述，也可以使用 200。

### 10.3 为什么不能使用 writeJSON() 写 204 响应？

**用户原回答：**

> 因为设置了响应的header为204 No Content，不允许再写入JSON数据到响应体中。

**订正：**核心正确。204 是 HTTP 响应状态码，不是普通响应头字段；应称为“写入 204 状态”。当前 `writeJSON()` 会尝试写响应体，所以不适用。

**可复述答案：**204 不包含响应内容，直接调用 `w.WriteHeader(http.StatusNoContent)`，不要再调用写 JSON 的函数。

## 十一、检查5：用户原回答与逐题订正

### 11.1 两次 DELETE 分别 204、404，为什么仍幂等？

**用户原回答：**

> 幂等只要求相同请求的结果相同即可，即数据库的状态不发生变化，不要返回的响应也相同。

**订正：**已抓住“关注状态效果，不要求响应相同”的重点，但“数据库的状态不发生变化”容易误解：第一次 DELETE 会改变状态；准确要求是多次执行的预期效果与执行一次一致。原文“不要返回的响应也相同”按上下文理解为“不要求返回的响应也相同”。

**可复述答案：**第一次成功删除后资源不存在，再删一次资源仍不存在。虽然分别返回 204 和 404，重复执行没有改变最终预期效果，所以 DELETE 仍幂等。

### 11.2 为什么 repo.Delete() 后还要检查 RowsAffected()？

**用户原回答：**

> 因为要区分已有记录被删除和数据库无资源两种情况，分别根据这两种情况返回204和404对应的状态码

**订正：**结论正确。具体是 `repo.Delete()` 内部调用 `RowsAffected()` 并返回行数，Handler 检查 `affected == 0`，区分“没有报 SQL 错误但未删除记录”和“确实删除成功”。

**可复述答案：**SQL 正常执行不代表命中记录；用影响行数区分删除成功与目标不存在，分别映射 204、404，并单独处理数据库错误。

### 11.3 DELETE /students/abc 与 /students/9999 有何区别？

**用户原回答：**

> 前者是JSON解码错误，属于请求本身的问题，属于400 Bad Request，而后者虽然解码成功且数据校验成功，但数据库中无对应的资源与之匹配，所以属于资源找不到的问题，应返回 404 Not Found

**订正：**状态码判断正确，错误发生机制需要修正。

- `/students/abc`：`strconv.Atoi("abc")` 失败，是路径参数转换失败，没有发生 JSON 解码，也不会执行 DELETE SQL。
- `/students/9999`：路径参数能转换为合法正整数；**只有数据库确实不存在 ID=9999 时**，才因影响 0 行返回 404。数字本身不代表一定不存在。

**可复述答案：**abc 不是合法整数 ID，路径解析失败返回 400；9999 是合法 ID，若数据库没有对应学生，则返回 404。此 DELETE 不涉及 JSON 解码。
