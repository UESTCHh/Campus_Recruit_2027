## 二、C++ Stage 1：LeetCode 111《二叉树的最小深度》

### 2.1 题目与核心概念

题目地址：https://leetcode.cn/problems/minimum-depth-of-binary-tree/

最小深度定义：

**从根节点到最近叶子节点的最短路径上的节点数量。**

叶子节点必须同时满足：

```cpp
root->left == nullptr && root->right == nullptr
```

只有左孩子或者只有右孩子的节点都不是叶子节点。

本题容易与之前的 LC104《二叉树的最大深度》混淆。

LC104 中，通常可以直接使用：

```cpp
return 1 + std::max(leftDepth, rightDepth);
```

但 LC111 不能无条件改成：

```cpp
return 1 + std::min(leftDepth, rightDepth);
```

原因：空子树返回 0，但它不代表存在一条到达叶子节点的路径。

### 2.2 错误解法的反例

考虑二叉树：

```text
    1
   /
  2
 /
3
```

最小深度应为 3，因为唯一的根到叶路径是：

```text
1 → 2 → 3
```

如果根节点直接计算：

```cpp
1 + std::min(2, 0)
```

就会错误地得到 1。

错误原因不是 `min()` 函数本身，而是把不存在的右子树错误地当成了可选择的路径。

```cpp
    int rightH = maxDepth(root->right);

    return 1 + std::max(leftH, rightH);

    int rightH = maxDepth(root->right);

    return 1 + std::min(leftH, rightH);
}
```

### 2.4 Stage 1 理解检查

#### 检查题 1：叶子节点的定义

**问题：**

为什么示例 B 中的根节点 1 不能被认为是叶子节点？一个节点只有左孩子、没有右孩子，是否属于叶子节点？

**我的回答（准确原话）：**

> 因为根节点1有左孩子，不是左右孩子均为空指针的叶子节点。属于。

**订正：**

第一句话正确，最后的“属于”错误，与前面的定义矛盾。

正确结论：

只有左孩子、没有右孩子的节点不是叶子节点。

叶子节点必须左右孩子同时为空。

**相关示例：**

```text
    1
   /
  2
```

节点 1 不是叶子节点；节点 2 才是叶子节点。

**面试专用回答：**

二叉树的叶子节点是左右孩子均为空的节点。只要有任意一个非空孩子，就不能认为该节点是叶子节点。最小深度必须计算到真正的叶子节点，而不能把空子树当作有效路径。

#### 检查题 2：为什么不能直接使用 min()？

**问题：**

为什么 LC104 可以直接使用 `1 + max(leftH, rightH)`，但 LC111 不能在所有情况下直接使用 `1 + min(leftH, rightH)`？

**我的回答（准确原话）：**

> lc104问的是最大深度，在只有一棵子树的情况下，可以正确返回子树的高度作为最大深度，但是lc111用1 + min(leftH, rightH)会得到1，因为此时空孩子返回的高度为0，比另一棵子树返回的高度更小，所以最终深度为1，但这是不准确的，因为根节点不为叶子节点，所以它的深度绝对大于1。

**订正：**

核心理解正确。

更准确的说法是：当根节点不是叶子节点时，以该节点为根的树，其最小深度必然大于 1。

空子树深度为 0，但不代表存在一条到达叶子的最短路径。

**相关示例：**

```text
    1
   /
  2
 /
3
```

错误结果：

```cpp
1 + std::min(2, 0)  // 1
```

正确结果：3。

**面试专用回答：**

最大深度可以直接选择左右子树深度的最大值，而最小深度需要特殊处理只有一个孩子的节点。由于空子树不能构成到叶子的有效路径，单侧子树为空时必须沿另一侧继续计算。只有左右子树均存在时，才能取两者最小深度的较小值。

#### 检查题 3：独立推导递归规则

**问题：**

设计 `int minDepth(TreeNode* root)`，分别处理空节点、叶子节点、单侧子树和双侧子树。

**我的回答（准确原话）：**

> 1. 返回0 2.返回1 3.返回唯一的子树高度 + 1 4.返回两棵子树高度的较小值 + 1

**订正：**

四种情况的处理方向正确。

需要规范的是“子树高度”这个术语。本题递归函数返回的是子树的**最小深度**，不是 LC104 中的最大高度。

正确递归规则：

1. 空节点返回 0。
2. 叶子节点返回 1。
3. 只有一棵非空子树时，返回该子树最小深度加 1。
4. 左右子树均非空时，返回二者最小深度的较小值加 1。

**相关示例：**

```text
       1
      / \
     2   3
    /
   4
```

左子树最小深度为 2，右子树最小深度为 1。

根节点最小深度为：

```text
1 + min(2, 1) = 2
```

**面试专用回答：**

我采用递归解决最小深度问题。空树返回 0，叶子节点返回 1。若只有一棵非空子树，则继续沿该子树寻找叶子；若左右子树都存在，则取两棵子树最小深度的较小值再加 1。时间复杂度 O(n)，递归栈空间复杂度 O(h)。

## 三、C++ Stage 2：独立实现 LC111

### 3.1 用户独立编写的代码

以下为用户实际提交到对话中的有效实现，整理了排版：

```cpp
class Solution {
public:
    int minDepth(TreeNode* root) {
        if (root == nullptr) {
            return 0;
        }

        if (root->left == nullptr) {
            return 1 + minDepth(root->right);
        }

        if (root->right == nullptr) {
            return 1 + minDepth(root->left);
        }

        return 1 + min(
            minDepth(root->left),
            minDepth(root->right)
        );
    }
};
```

原消息中重复粘贴了两遍相同的 `Solution` 定义；这里只保留一份。实际提交结果由用户反馈为通过。

### 3.2 代码逻辑解析

这份代码不需要显式写出：

```cpp
if (root->left == nullptr &&
    root->right == nullptr) {
    return 1;
}
```

原因是：

对于叶子节点，左右孩子均为空，会先进入第二个判断：

```cpp
if (root->left == nullptr) {
    return 1 + minDepth(root->right);
}
```

而 `root->right` 也是 `nullptr`：

```cpp
1 + minDepth(nullptr)
= 1 + 0
= 1
```

所以叶子节点已经被正确处理。

这是本次代码的一个特点：**利用递归边界和条件判断的先后顺序，简洁覆盖全部情况。**

### 3.3 复杂度分析

**时间复杂度：O(n)**

每个非空节点最多进入一次 `minDepth()`，不存在对已计算子树的重复高度求解。

**空间复杂度：O(h)**

递归调用栈的最大深度由二叉树高度决定。

- 平衡树：O(log n)。
- 极端退化树：O(n)。

### 4.5 错误分析与订正

#### 问题一：HTTP 方法大小写错误

首次写成：

```go
mux.HandleFunc(
    "Get /students/{id}",
    studentByIDHandler(repo),
)
```

但实际测试请求使用：

```go
http.MethodGet
```

其值是大写的 `"GET"`。

Go 的路由方法匹配区分大小写。

正确修改：

```go
mux.HandleFunc(
    "GET /students/{id}",
    studentByIDHandler(repo),
)
```

**排错结论：** 路由注册的方法必须与请求的方法一致。

根据代码推断，原写法会造成方法匹配失败；由于未提供第一次失败的具体输出，不记录未经观察的实际错误状态码。

#### 问题二：没有检查数据插入错误

首次写成：

```go
repo.Create(Student{
    ID:   1001,
    Name: "Alice",
    Age:  20,
})
```

这样会忽略函数的返回结果。

如果插入失败，后续 GET 可能无法查询到预期数据，测试失败原因也会变得不清晰。

若实际方法签名为 `Create(Student) error`，应写成：

```go
err := repo.Create(Student{
    ID:   1001,
    Name: "Alice",
    Age:  20,
})
if err != nil {
    t.Fatalf("create student failed: %v", err)
}
```

如果实际 `Create()` 返回多个值，则按 `repository.go` 中的真实函数签名调整。

**排错结论：** 测试数据准备阶段出现错误时，应立即终止当前测试并报告原因。

#### 问题三：忽略 JSON 解码错误

首次写成：

```go
if json.NewDecoder(result.Body).Decode(&got); got != want {
    t.Fatalf("expected 1001 Alice 20 but got %v", got)
}
```

这里的 `if 初始化语句; 条件` 是合法 Go 语法。

真正的问题是没有检查 `Decode()` 返回的错误。

推荐写法：

```go
var got Student

err := json.NewDecoder(result.Body).Decode(&got)
if err != nil {
    t.Fatalf("decode response failed: %v", err)
}

want := Student{
    ID:   1001,
    Name: "Alice",
    Age:  20,
}

if got != want {
    t.Fatalf("expected %+v, got %+v", want, got)
}
```

由于当前 `Student` 的字段为整数和字符串，可以直接使用 `!=` 比较结构体。

**排错结论：** 既要验证 HTTP 状态码，也要检查响应体能否正确解析，以及业务字段是否正确。

#### 补充：及时关闭响应体

```go
result := recorder.Result()
defer result.Body.Close()
```

这是更规范的测试资源管理写法。

```text
GET /students/1001
       ↓
404 Not Found
```

**面试专用回答：**

HTTP 与数据库集成测试需要构造确定的测试数据，再通过接口访问数据库并验证结果。使用独立测试数据库可以避免历史数据干扰，使测试结果稳定、可重复。

### 检查题 2：为什么只验证 HTTP 200 不够？

**问题：**

如果测试返回 200，但 JSON 中的 `name` 错误，为什么测试仍然应该失败？只检查状态码能否证明接口完全正确？

**我的回答（准确原话）：**

> 因为测试返回200只能说明响应的状态码正确，但是不能说明响应体内容也正确，如果name错误，说明数据库实际插入的学生记录与预期不符，不能说明测试通过，测试应该失败，只检查http状态码不能证明GET接口完全正确。

**订正：**

核心结论正确。

但 JSON 中的 `name` 错误，不一定意味着数据库插入错误。

还可能是：

- Repository 查询或字段映射错误；
- Handler 构造响应时使用了错误字段；
- JSON 响应生成过程存在问题。

因此需要沿调用链进一步定位，不能仅凭响应字段错误就断定是数据库插入失败。

**相关示例：**

数据库实际内容：

```json
{"id":1001,"name":"Alice","age":20}
```

接口错误响应：

```json
{"id":1001,"name":"Bob","age":20}
```

即使返回 HTTP 200，测试也必须判定为失败。

**面试专用回答：**

HTTP 200 只能说明接口返回了成功状态，不能证明业务数据正确。集成测试应同时验证响应状态码、JSON 格式以及关键业务字段，才能发现数据查询、字段映射和响应构造过程中的问题。

## 八、今日易错点与工程经验

### 8.1 C++：不能把空子树当成到叶子的有效路径

错误思路：

```cpp
return 1 + min(leftDepth, rightDepth);
```

正确原则：

只有一侧子树时沿该侧继续计算；两侧都存在时再比较最小深度。

### 8.2 C++：高度、节点深度和最小深度要区分

- 节点深度：通常指从根节点到该节点的层次或路径长度，具体从 0 还是 1 开始取决于定义。
- 树的高度：描述该树从根向下的最长路径，在本课程中按节点数量计算。
- 最小深度：从根节点到最近叶子节点的最短路径上的节点数量。

### 8.3 Go：HTTP 方法大小写必须匹配

```go
"Get /students/{id}"  // 错误的请求方法大小写
"GET /students/{id}"  // 当前测试需要的正确写法
```

### 8.4 Go：不能忽略关键操作的 error

需要检查：

- 测试数据创建是否成功；
- JSON 解码是否成功；
- HTTP 状态码是否符合预期；
- 响应业务字段是否正确。

### 8.5 Go：测试失败时应沿执行链路排查

建议顺序：

```text
测试输入是否正确？
    ↓
HTTP 方法与路由是否匹配？
    ↓
Handler 是否执行正确分支？
    ↓
数据库准备是否成功？
    ↓
Repository 查询结果是否正确？
    ↓
响应状态码是否正确？
    ↓
JSON 是否符合预期？
```

这套排错顺序适用于今后的多数基础 HTTP 集成测试。
