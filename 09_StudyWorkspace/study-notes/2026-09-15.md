# 三、Stack 的核心语义

Stack：

```text
Stack
=
栈
```

最重要的规则：

```text
LIFO
=
Last In First Out
=
后进先出
```

例如依次：

```cpp
numbers.push(10);
numbers.push(20);
numbers.push(30);
```

逻辑结构：

```text
top
 ↓
30
20
10
```

最后进入：

```text
30
```

所以最先离开：

```text
30
```

这就是：

```text
Last In
↓
First Out
```


作用：


但：


```cpp
numbers.pop();
```

作用：

```text

```

```cpp

numbers.pop();
```

即：

```text
先读取
↓

```

# 五、空 Stack 的边界

空 Stack：

```text
empty
```

不能直接：

```cpp
numbers.top();
```

或者：

```cpp
numbers.pop();
```

因为这些操作要求 Stack 当前存在有效的栈顶元素。

在空 `std::stack` 上调用这些操作不满足其前置条件，程序行为不能依赖一个确定的异常或错误结果。

因此应先：

```cpp
if (!numbers.empty())
{
    ...
}
```

```cpp
#include <stack>

using namespace std;

int main()
{
    // Stack遵循：
    //
    // Last In First Out
    // 后进先出
    stack<int> numbers;

    cout << "=== empty stack ==="
         << endl;

    cout << boolalpha;

    cout << "numbers.empty() = "
         << numbers.empty()
         << endl;

    // push 10
    numbers.push(10);

    cout << endl;
    cout << "after push 10:"
         << endl;

    cout << "top = "
         << numbers.top()
         << endl;

    // push 20
    numbers.push(20);

    cout << endl;
    cout << "after push 20:"
         << endl;

    cout << "top = "
         << numbers.top()
         << endl;

    // push 30
    numbers.push(30);

    cout << endl;
    cout << "after push 30:"
         << endl;

    cout << "top = "
         << numbers.top()
         << endl;

    cout << "size = "
         << numbers.size()
         << endl;

    // top只读取，不删除。
    cout << endl;
    cout << "=== top does not remove ==="
         << endl;

    cout << "first top = "
         << numbers.top()
         << endl;

    cout << "second top = "
         << numbers.top()
         << endl;

    cout << "size after top = "
         << numbers.size()
         << endl;

    // 删除30。
    numbers.pop();

    cout << endl;
    cout << "=== after one pop ==="
         << endl;

    cout << "top = "
         << numbers.top()
         << endl;

    cout << "size = "
         << numbers.size()
         << endl;

    // 当前：
    //
    // 20
    // 10
    //
    // 再加入40、50。
    numbers.push(40);
    numbers.push(50);

    cout << endl;
    cout << "=== pop all elements ==="
         << endl;

    while (!numbers.empty())
    {
        cout << "pop value = "
             << numbers.top()
             << endl;

        numbers.pop();
    }

    cout << endl;

    cout << "=== final state ==="
         << endl;

    cout << "numbers.empty() = "
         << numbers.empty()
         << endl;

    cout << "size = "
         << numbers.size()
         << endl;

    return 0;
}
```

## 问题 1：Stack 的核心规则

### 我的回答

> LIFO，Last in First out，后进先出，即最后进入栈的元素最先出栈，栈顶永远保存最后进入的元素。

### 订正

完全正确。

核心：

```text
最后进入
↓
最先离开
```

### 相关示例

```text
push 10
push 20
push 30
```

得到：

```text
30 ← top
20
10
```

第一个出栈一定是：

```text
30
```

### 面试专用回答

> Stack 是一种 LIFO，也就是后进先出的数据结构。所有插入、删除和主要访问操作都集中在栈顶，因此最后压入栈中的元素会最先被处理。

## 问题 2：栈顶顺序

### 我的回答

```text
top是30

从栈顶到底部的顺序是30 20 10
```

### 订正

完全正确。

### 相关示例

```cpp
push(10);
push(20);
push(30);
```

逻辑：

```text
30
20
10
```

### 面试专用回答

> 连续压入 10、20、30 后，30 是最后进入的元素，所以它位于栈顶。从栈顶到底部依次是 30、20、10。

## 问题 3：`top()` 和 `pop()`

### 我的回答

> 前者是查看栈顶元素，会返回栈顶元素，而后者是删除栈顶元素即将栈顶元素出栈，没有返回值；

```cpp
int value = numbers.top(); 首先保存栈顶元素
numbers.pop(); 再将栈顶元素出栈
```

### 订正

完全正确。

### 面试专用回答

> `top()` 用于读取当前栈顶元素，但不会修改 Stack；`pop()` 用于删除栈顶元素，并且 C++ 的 `std::stack::pop()` 返回 `void`。因此如果既需要当前值又需要删除，应先调用 `top()` 保存元素，再调用 `pop()`。

---

## 问题 4：为什么不能 `int value = pop()`

### 我的回答

> 因为stack.pop();没有返回值，不能通过pop函数来保存栈顶元素，如果既要读取又要删除，应该

```cpp
int value = numbers.top();
numbers.pop();
```

### 订正

完全正确。

### 面试专用回答

> C++ 的 `std::stack::pop()` 返回类型是 `void`，只负责删除，因此不能直接通过返回值获得被删除元素。标准做法是先使用 `top()` 获取栈顶，再调用 `pop()` 删除。

## 问题 5：为什么 `while (!empty())` 可以安全弹空

### 我的回答

> 因为empty函数可以判断当前栈是否为空，是否还有元素，保证在有元素的情况下再调用pop和top函数，否则就是错误的操作

### 订正

完全正确。

每轮：

```text
先确认非空
↓
读取top
↓
pop
↓
元素数量减少1
```

最终：

```text
empty() == true
```

### 面试专用回答

> 循环每次都会先通过 `empty()` 保证 Stack 当前存在有效栈顶，再调用 `top()` 和 `pop()`。每次 `pop()` 都使元素数量减少一个，因此最终 Stack 为空并结束循环。

# 九、Container Adapter

`std::stack`：

```text
不是一种新的底层存储布局
```

而是：

```text
使用已有Container
↓

↓

```

准确来说：

> `std::stack` 内部拥有或使用一个底层 Container 对象，真正的元素存储能力由这个底层 Container 提供，而 `std::stack` 对外提供受限制的 LIFO 接口。

# 十三、C++ Day20 第二阶段完整代码

## `stack_adapter_demo.cpp`

```cpp
#include <deque>
#include <iostream>
#include <stack>
#include <vector>

using namespace std;

// 为了让同一个函数可以处理不同底层Container构造的Stack，
// 使用简单的函数模板。
template <typename StackType>
void printAndClear(
    StackType& numbers)
{
    while (!numbers.empty())
    {
        cout << numbers.top()
             << ' ';

        numbers.pop();
    }

    cout << endl;
}

int main()
{
    // 默认底层是deque。
    stack<int> defaultStack;

    defaultStack.push(10);
    defaultStack.push(20);
    defaultStack.push(30);

    cout << "=== default stack ==="
         << endl;

    cout << "top = "
         << defaultStack.top()
         << endl;

    cout << "pop order = ";

    printAndClear(defaultStack);

    // 显式deque。
    stack<int, deque<int>> dequeStack;

    dequeStack.push(10);
    dequeStack.push(20);
    dequeStack.push(30);

    cout << endl;

    cout << "=== deque based stack ==="
         << endl;

    cout << "top = "
         << dequeStack.top()
         << endl;

    cout << "pop order = ";

    printAndClear(dequeStack);

    // vector也可以作为底层。
    stack<int, vector<int>> vectorStack;

    vectorStack.push(10);
    vectorStack.push(20);
    vectorStack.push(30);

    cout << endl;

    cout << "=== vector based stack ==="
         << endl;

    cout << "top = "
         << vectorStack.top()
         << endl;

    cout << "pop order = ";

    printAndClear(vectorStack);

    cout << endl;

    cout << "=== adapter conclusion ==="
         << endl;

    cout << "different underlying containers, "
         << "same LIFO interface"
         << endl;

    return 0;
}
```

实验结果：

```text
=== default stack ===
top = 30
pop order = 30 20 10

=== deque based stack ===
top = 30
pop order = 30 20 10

=== vector based stack ===
top = 30
pop order = 30 20 10

=== adapter conclusion ===
different underlying containers, same LIFO interface
```

核心实验结论：

```text
Underlying Container可以变化
↓
Stack对外LIFO Interface保持不变
```

# 十五、为什么括号匹配适合 Stack

例如：

```text
([]){}
```

Stack 中不需要保存所有字符。

只保存：


# 十八、C++ Day20 第三阶段完整代码

## `valid_parentheses_demo.cpp`

```cpp
#include <iostream>
#include <stack>
#include <string>

using namespace std;

bool isMatchingPair(
    char opening,
    char closing)
{
    if (opening == '(' &&
        closing == ')')
    {
        return true;
    }

    if (opening == '[' &&
        closing == ']')
    {
        return true;
    }

    if (opening == '{' &&
        closing == '}')
    {
        return true;
    }

    return false;
}

bool isValidParentheses(
    const string& text)
{
    // Stack只保存当前尚未匹配的左括号。
    stack<char> brackets;

    for (char ch : text)
    {
        // 左括号直接入栈。
        if (ch == '(' ||
            ch == '[' ||
            ch == '{')
        {
            brackets.push(ch);
            continue;
        }

        // 当前是右括号，但没有左括号可以匹配。
        if (brackets.empty())
        {
            return false;
        }

        // 最近一个尚未匹配的左括号。
        char opening =
            brackets.top();

        // 类型不匹配。
        if (!isMatchingPair(
                opening,
                ch))
        {
            return false;
        }

        // 已完成匹配，从“未完成集合”中删除。
        brackets.pop();
    }

    // 所有左括号都应该完成匹配。
    return brackets.empty();
}

int main()
{
    string test1 = "()";
    string test2 = "([]){}";
    string test3 = "([)]";
    string test4 = ")(";
    string test5 = "((";

    cout << boolalpha;

    cout << "=== valid parentheses ==="
         << endl;

    cout << test1
         << " -> "
         << isValidParentheses(test1)
         << endl;

    cout << test2
         << " -> "
         << isValidParentheses(test2)
         << endl;

    cout << test3
         << " -> "
         << isValidParentheses(test3)
         << endl;

    cout << test4
         << " -> "
         << isValidParentheses(test4)
         << endl;

    cout << test5
         << " -> "
         << isValidParentheses(test5)
         << endl;

    return 0;
}
```

预期结果：

```text
=== valid parentheses ===
() -> true
([]){} -> true
([)] -> false
)( -> false
(( -> false
```

## 问题 4：为什么匹配成功必须 `pop()`

### 我的回答

> 因为匹配成功后说明将该符号定义为已分配符号从栈里弹出，因为栈只保存所有未匹配的左符号，如果不pop那么栈中的元素永远不会清空，以后每次遇到的右符号都只会和最近进入的左符号相匹配，产生与预期不符的结果

### 订正

核心正确。

```text
已匹配符号
```



> Stack 在该算法中保存的是“尚未匹配的左括号”。一旦栈顶左括号与当前右括号匹配成功，它就已经完成任务，必须 `pop()`；否则已经完成的对象仍留在 Stack 中，会干扰后续匹配。

完全正确。

## 问题 8：最终综合题

### 我的回答

> 因为多个请求可能关联多个Goroutine，如果并发任务同时触发requestCounter++的书写逻辑，很可能造成data race 问题，所以通过atomic.AddUint64(...)这样的原子操作安全地生成简单递增 ID

### 订正

完全正确。

### 面试专用回答

> Go HTTP Server 会并发处理请求，因此共享计数器可能被多个 goroutine 同时修改。如果直接 `requestCounter++`，可能产生 data race；使用 `atomic.AddUint64()` 可以原子地完成计数器递增。

## 问题 7：Middleware Before / After

### 我的回答

> requestIDMiddleware中处理request started和request finished的逻辑输出，而其包装的handler处理真实的业务逻辑即Handler执行

### 订正

方向正确，需要补：

```go
next.ServeHTTP(w, r)
```

是同步函数调用。

执行：

```text
before
↓
next.ServeHTTP
↓
Handler
↓
Handler return
↓
next.ServeHTTP return
↓
after
```

### 面试专用回答

> `next.ServeHTTP(w, r)` 是同步下游调用，所以它之前的代码会在请求进入下游前执行，而它之后的代码只有在下游 Handler 返回后执行，这就是 Middleware 洋葱模型中 before / after 的来源。

## 问题 8：为什么 Handler 看不到 Middleware 局部变量

### 我的回答

### 订正

完全正确。

另外：

```text
requestID
```

本身也是 Middleware 的局部变量。

Handler 不在它的变量作用域中。

### 面试专用回答

> Middleware 中的 Request ID 是局部变量，而标准 Handler 接口固定为 `ServeHTTP(w, r)`，不能额外增加 Request ID 参数。因此可以把它作为 request-scoped data 放进 Request Context，再让下游 Handler 从 `r.Context()` 获取。

# 三十一、Request-scoped Data

Request ID：

```text
只属于当前Request
↓
沿当前Request调用链传播
↓
Request结束后通常失去保存意义
```

所以属于：

```text
Request-scoped Data
```

不应该简单放：

```go
var currentRequestID string
```

否则并发时：

```text
Request A
→ currentRequestID = req-1

Request B
→ currentRequestID = req-2

Request A继续执行
→ 可能读到req-2
```

导致：

```text
跨Request覆盖
数据串扰
甚至Data Race
```

# 三十二、Context 传递 Request ID

定义：

```go
type contextKey string

const requestIDKey contextKey =
    "requestID"
```

写入 Context：

```go
ctx :=
    context.WithValue(
        r.Context(),
        requestIDKey,
        requestID,
    )
```

然后：

```go
r =
    r.WithContext(ctx)
```

再：

```go
next.ServeHTTP(
    w,
    r,
)
```

完整：

```text
Middleware局部requestID
↓
context.WithValue
↓
Child Context
↓
r.WithContext
↓
New Request
↓
next.ServeHTTP
↓
Handler
```

# 三十三、`context.WithValue()` vs `r.WithContext()`

```go
context.WithValue(...)
```

负责：

```text
基于旧Context
↓
创建Child Context
↓
增加Value
```

而：

```go
r.WithContext(ctx)
```

负责：

```text
基于旧Request
↓
创建携带新Context的Request副本
```

两者不是同一件事。

# 三十四、Handler 读取 Request ID

```go
value :=
    r.Context().
        Value(requestIDKey)
```

返回：

```text
any
```

所以需要：

```go
requestID, ok :=
    value.(string)
```

其中：

```text
requestID
→ string值
```

```text
ok
→ Type Assertion是否成功
```

相比：

```go
value.(string)
```

comma-ok：

```go
requestID, ok := value.(string)
```

可以避免类型不匹配时直接 panic。

因此进一步封装：

```go

    ctx context.Context,

```

统一处理读取与断言。

# 三十五、Go Day21 第二阶段闭卷题

## 问题 1：为什么 Request ID 属于 Request-scoped Data

### 我的回答

> 因为每个请求有自己唯一的一个标识符request id，并且随请求结束后程序应该丢弃该变量值，天然属于Request-scoped Data，而简单存进全局变量会造成当多个请求共用同一个request id的情况

### 订正

核心正确。

更准确：

```text
全局变量
→ 请求之间可能互相覆盖
→ 数据串扰
→ 并发时可能Data Race
```

### 面试专用回答

> Request ID 只属于一次 HTTP Request，并需要沿请求调用链传播，请求结束后通常无需继续保存，因此属于典型 request-scoped data。全局变量会让不同并发请求共享同一存储位置，容易发生覆盖、串扰甚至 data race。

---

## 问题 2：`WithValue` 与 `WithContext`

### 我的回答

> context.WithValue(...)由当前context派生一个新的context并将信息附带进context中

```text
r.WithContext(ctx) 产生一个新的请求副本，不会直接修改原Request本身，而是返回一个携带新Context的Request副本
```

> 不是同一件事

### 订正

完全正确。

### 面试专用回答

> `context.WithValue` 基于已有 Context 创建一个携带额外 value 的 Child Context；`r.WithContext(ctx)` 则返回一个携带该 Context 的 Request 副本。前者操作 Context 链，后者把新 Context 绑定回 Request。

---

## 问题 3：为什么只创建 Context 不够

### 我的回答

> 因为这时请求r并没有赋值新的附带信息的新请求，还是旧的不带信息的请求，Handler 还是拿不到 Request ID

### 订正

完全正确。

### 面试专用回答

> `context.WithValue` 只产生新的 Context，并不会自动修改当前 Request。如果仍把原来的 `r` 传给 `next.ServeHTTP`，下游仍看到旧 Context，因此必须先通过 `r.WithContext(ctx)` 得到新的 Request。

---

## 问题 4：为什么 `WithContext` 不是原地修改

### 我的回答

> r.WithContext(ctx)产生一个新的请求副本，不会直接修改原Request本身，而是返回一个携带新Context的Request副本，所以是将现有的旧请求赋值这个新的请求副本

### 订正

完全正确。

### 面试专用回答

> `Request.WithContext` 不原地修改原 Request，而是返回携带指定 Context 的 Request 副本，因此常见写法是 `r = r.WithContext(ctx)`，然后将新的 `r` 传给下游。

---

## 问题 5：为什么定义 Context Key 类型

### 我的回答

> 因为可能不同package会使用同一个key，造成key冲突

### 订正

正确。

### 面试专用回答

> Context Key 不推荐直接使用普通 string，因为不同 package 可能使用相同字符串而发生 Key Collision。通常定义私有自定义类型，使不同模块的 Key 在类型层面隔离。

---

## 问题 6：为什么需要 Type Assertion

### 我的回答

> r.Context().Value(requestIDKey)返回的是any不是string类型，所以需要先Assertion；为了防止出现panic

### 订正

完全正确。

### 面试专用回答

> `Context.Value` 返回 `any`，所以读取后需要 Type Assertion 恢复真实类型。直接 `value.(string)` 类型不匹配时可能 panic，因此通常使用 `requestID, ok := value.(string)` 的 comma-ok 形式。

---

## 问题 7：为什么三个日志得到同一个 ID

### 我的回答

> 就是正常的普通函数同步调用，middleware前置逻辑执行完后到next.servehttp(w，r)函数调用，等该函数返回后继续执行middleware后置逻辑，期间同一个 Request ID 通过context附带进请求r中进行逐层传递

### 订正

整体正确。

需要区分：

```text
Middleware before log
→ 直接使用局部变量requestID

Handler log
→ 从Context读取

Middleware after log
→ 再使用原局部变量requestID
```

### 面试专用回答

> Request ID 首先在 Middleware 中确定，因此 Middleware 的 before/after 日志可以直接使用局部变量；同时 Middleware 把同一个 ID 放进 Request Context，下游 Handler 再从 `r.Context()` 中读取，因此三个位置最终使用的是同一个 Request ID。

## 问题 8：为什么 Context 适合 Middleware → Handler

### 我的回答

> 因为context可以将信息附带进请求中，而Middleware 向下游 Handler 传递 Request-specific Data 时用请求附带信息是天然合适的，利用context就可以将Request-specific Data附带进请求中逐层传递

### 订正

完全正确。

但继续记住：

```text
Context不只是Value Container
```

还负责：

```text
Cancellation
Deadline
Request Lifecycle
```

### 面试专用回答

> Context 适合传递 Request ID，是因为 Request ID 属于当前请求生命周期内的 request-scoped data，并需要沿调用链传播。Middleware 可以把它写入 Request Context，下游 Handler 不需要改变标准接口就能读取；同时 Context 本身还承担 cancellation 和 deadline 等请求生命周期能力。

# 三十七、第三阶段完整 `main.go`

```go
package main

import (
	"context"
	"encoding/json"
	"errors"
	"fmt"
	"log"
	"net/http"
	"strconv"
	"sync/atomic"
)

type contextKey string

const requestIDKey contextKey =
	"requestID"

var requestCounter uint64

type ErrorResponse struct {
	Error     string `json:"error"`
	RequestID string `json:"request_id"`
}

type UserResponse struct {
	ID        int    `json:"id"`
	Message   string `json:"message"`
	RequestID string `json:"request_id"`
}

var errUserNotFound =
	errors.New("user not found")

var errStorageUnavailable =
	errors.New("storage unavailable")

func nextRequestID() string {
	number :=
		atomic.AddUint64(
			&requestCounter,
			1,
		)

	return "req-" +
		strconv.FormatUint(
			number,
			10,
		)
}

func requestIDFromContext(
	ctx context.Context,
) string {
	requestID, ok :=
		ctx.Value(
			requestIDKey,
		).(string)

	if !ok {
		return ""
	}

	return requestID
}

func writeJSONError(
	w http.ResponseWriter,
	r *http.Request,
	status int,
	message string,
) {
	requestID :=
		requestIDFromContext(
			r.Context(),
		)

	w.Header().Set(
		"Content-Type",
		"application/json",
	)

	w.WriteHeader(status)

	response :=
		ErrorResponse{
			Error:     message,
			RequestID: requestID,
		}

	err :=
		json.NewEncoder(w).Encode(
			response,
		)

	if err != nil {
		log.Printf(
			"[%s] encode error response: %v",
			requestID,
			err,
		)
	}
}

func writeJSON(
	w http.ResponseWriter,
	status int,
	value any,
) {
	w.Header().Set(
		"Content-Type",
		"application/json",
	)

	w.WriteHeader(status)

	err :=
		json.NewEncoder(w).Encode(
			value,
		)

	if err != nil {
		log.Println(
			"encode response:",
			err,
		)
	}
}

func requestIDMiddleware(
	next http.Handler,
) http.Handler {
	return http.HandlerFunc(
		func(
			w http.ResponseWriter,
			r *http.Request,
		) {
			requestID :=
				r.Header.Get(
					"X-Request-ID",
				)

			if requestID == "" {
				requestID =
					nextRequestID()
			}

			w.Header().Set(
				"X-Request-ID",
				requestID,
			)

			ctx :=
				context.WithValue(
					r.Context(),
					requestIDKey,
					requestID,
				)

			r =
				r.WithContext(ctx)

			log.Printf(
				"[%s] request started: %s %s",
				requestID,
				r.Method,
				r.URL.Path,
			)

			next.ServeHTTP(
				w,
				r,
			)

			log.Printf(
				"[%s] request finished",
				requestID,
			)
		},
	)
}

func findUserByID(
	id int,
) (UserResponse, error) {
	if id == 404 {
		return UserResponse{},
			errUserNotFound
	}

	if id == 500 {
		return UserResponse{},
			errStorageUnavailable
	}

	return UserResponse{
		ID:      id,
		Message: "user found",
	}, nil
}

func userHandler(
	w http.ResponseWriter,
	r *http.Request,
) {
	requestID :=
		requestIDFromContext(
			r.Context(),
		)

	log.Printf(
		"[%s] user handler started",
		requestID,
	)

	// Extract Input
	idText :=
		r.PathValue("id")

	// Parsing
	id, err :=
		strconv.Atoi(idText)

	if err != nil {
		log.Printf(
			"[%s] invalid user id: %q",
			requestID,
			idText,
		)

		writeJSONError(
			w,
			r,
			http.StatusBadRequest,
			"user id must be an integer",
		)

		return
	}

	// Validation
	if id <= 0 {
		log.Printf(
			"[%s] user id validation failed: %d",
			requestID,
			id,
		)

		writeJSONError(
			w,
			r,
			http.StatusBadRequest,
			"user id must be greater than 0",
		)

		return
	}

	// Business Logic
	user, err :=
		findUserByID(id)

	if err != nil {
		if errors.Is(
			err,
			errUserNotFound,
		) {
			log.Printf(
				"[%s] user not found: %d",
				requestID,
				id,
			)

			writeJSONError(
				w,
				r,
				http.StatusNotFound,
				"user not found",
			)

			return
		}

		log.Printf(
			"[%s] find user failed: %v",
			requestID,
			err,
		)

		writeJSONError(
			w,
			r,
			http.StatusInternalServerError,
			"internal server error",
		)

		return
	}

	user.RequestID =
		requestID

	writeJSON(
		w,
		http.StatusOK,
		user,
	)
}

func main() {
	mux :=
		http.NewServeMux()

	mux.HandleFunc(
		"GET /users/{id}",
		userHandler,
	)

	handler :=
		requestIDMiddleware(mux)

	fmt.Println(
		"server listening on http://localhost:8080",
	)

	err :=
		http.ListenAndServe(
			":8080",
			handler,
		)

	if err != nil {
		log.Fatal(err)
	}
}
```

# 四十三、发现重复逻辑时的判断框架

不要：

```text
看到两行代码重复
↓
立刻抽函数
```

应该：

```text
发现重复
↓
为什么重复？
↓
这是谁的职责？
↓
应该放在哪一层？
```

判断：

```text
所有Endpoint都需要？
→ Middleware
```

```text
所有Response都需要？
→ Response Helper
```

```text
Request生命周期相关？
→ Context
```

```text
Business / Data Logic？
→ Business Function
```

```text
HTTP语义转换？
→ Handler Error Mapping
```

```text
具体实现细节？
→ Helper Function
```

核心：

> 减少重复不是为了单纯减少代码行数，而是为了让相同职责集中到正确位置。

# 四十四、减少重复逻辑的面试专用回答

> 我不会单纯为了减少代码行数就随意抽函数，而是先按照职责判断重复逻辑应该放在哪一层。像 Logging、Request ID 这类多个 Endpoint 都需要的横切逻辑，我会放到 Middleware；JSON Response 的 Header、Status 和 Encoding 会抽成 Response Helper；Request ID 等 request-scoped data 通过 Context 传播，并封装 Context Getter；业务查询逻辑从 Handler 中拆出来，业务函数返回明确的 error，再由 Handler 统一做 HTTP Error Mapping。同时会使用统一 Response Struct、Sentinel Error 和 `errors.Is` 保持数据格式和错误语义一致。这样既减少重复，也能降低层之间耦合，让代码更容易维护和测试。
