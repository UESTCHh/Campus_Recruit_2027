# Part 3：Repository 层

文件：

```text
repository.go
```

作用：

```text
模拟一个耗时2秒的数据库查询
```

代码：

```go
package main

import (
	"context"
	"fmt"
	"time"
)

func FindUser(ctx context.Context, id int) (string, error) {
	fmt.Println("repository: start query")

	select {
	case <-ctx.Done():
		fmt.Println("repository: query canceled")
		return "", ctx.Err()

	case <-time.After(2 * time.Second):
		fmt.Println("repository: query finished")
		return fmt.Sprintf("user-%d", id), nil
	}
}
```

函数：

```go
func FindUser(
	ctx context.Context,
	id int,
) (string, error)
```

注意：

```text
ctx
```

放在函数：

```text
第一个参数
```

这是 Go API 中非常常见的 Context 使用约定。

# Part 4：Repository 为什么使用 select

Repository 模拟：

```text
一次正常需要2秒完成的查询
```

但同时需要响应：

```text
请求取消
timeout
deadline
```

所以不能简单：

```go
time.Sleep(2 * time.Second)
```

而是：

```go
select {
case <-ctx.Done():
	// 请求已经取消或超时

case <-time.After(2 * time.Second):
	// 查询正常完成
}
```

这里本质上同时等待：

```text
ctx.Done()
        vs
2秒工作完成
```

如果 Context 先结束：

```text
Repository立即停止工作
```

如果查询先完成：

```text
正常返回结果
```

# Part 6：模拟 Handler

文件：

```text
main.go
```

代码：

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

func main() {
	ctx, cancel := context.WithTimeout(
		context.Background(),
		700*time.Millisecond,
	)
	defer cancel()

	fmt.Println("handler: request started")

	profile, err := GetUserProfile(
		ctx,
		1001,
	)

	if err != nil {
		if errors.Is(
			err,
			context.DeadlineExceeded,
		) {
			fmt.Println(
				"handler: request timeout",
			)
			return
		}

		fmt.Println(
			"handler: error:",
			err,
		)
		return
	}

	fmt.Println(
		"handler:",
		profile,
	)
}
```

这里模拟：

```text
Handler收到一个请求
```

并给这次请求设置：

```text
700ms timeout
```

通过：

```go
context.WithTimeout(
	context.Background(),
	700*time.Millisecond,
)
```

创建一个带 deadline 的 Context。

# Part 8：为什么 Repository 原本需要 2 秒，却可以约 700ms 退出

Repository：

```go
time.After(2 * time.Second)
```

表示模拟工作正常需要：

```text
2秒
```

但是 Handler 创建的 Context：

```go
context.WithTimeout(
	context.Background(),
	700*time.Millisecond,
)
```

只有：

```text
700ms
```

生命周期。

时间线：

```text
0ms

Handler创建ctx
timeout = 700ms

↓

Handler调用Service(ctx)

↓

Service调用Repository(ctx)

↓

Repository开始等待：

ctx.Done()
vs
2秒查询

↓

700ms

Context deadline到达

↓

Done channel关闭

↓

Repository中的：

case <-ctx.Done():

立即变为可执行

↓

Repository停止查询

↓

return "", ctx.Err()
```

所以不需要继续等待完整：

```text
2秒
```

# Part 9：这里不是 Handler 主动 cancel

今天一个需要特别修正的概念：

不能说：

```text
Handler在700ms主动调用cancel()
```

当前程序是：

```go
context.WithTimeout(..., 700*time.Millisecond)
```

所以：

```text
700ms到达
↓
deadline自动触发
```

此时：

```go
ctx.Err()
```

得到：

```text
context deadline exceeded
```

对应：

```go
context.DeadlineExceeded
```

而之前实验中的：

```go
cancel()
```

是：

```text
主动取消
```

对应：

```go
context.Canceled
```

因此必须区分：

```text
主动 cancel()

→ context.Canceled
```

和：

```text
WithTimeout / deadline 到期

→ context.DeadlineExceeded
```

# Part 13：Context propagation

今天正式学习的核心概念：

```text
Context propagation
Context传播
```

即：

```text
上层收到Context
↓
继续将其传给下层
↓
下层继续传递
```

例如：

```go
func Handler(ctx context.Context) {
	Service(ctx)
}
```

```go
func Service(ctx context.Context) {
	Repository(ctx)
}
```

```go
func Repository(ctx context.Context) {
	Database(ctx)
}
```

形成：

```text
Handler
↓ ctx
Service
↓ ctx
Repository
↓ ctx
Database / API
```

这样：

```text
请求取消
timeout
deadline
```

可以沿整个调用链传播。

# Part 15：为什么 Context 通常不存入长期 Service struct

假设：

```go
type UserService struct {
	ctx context.Context
}
```

看起来好像可以省去每次传 Context。

但存在一个根本问题：

```text
Service生命周期
和
Context生命周期
不同
```

Service 对象可能：

```text
程序启动时创建
↓
长期存在
↓
同时服务很多请求
```

而 Context 一般代表：

```text
某一次具体请求的生命周期
```

例如：

```text
Request A
ctxA
timeout = 500ms
```

以及：

```text
Request B
ctxB
timeout = 5s
```

两个请求：

```text
deadline不同
取消时间不同
生命周期不同
```

甚至：

```text
A已经取消
B还在正常执行
```

因此不能让它们简单共享一个：

```text
Service.ctx
```

---

# Part 16：更合理的写法

Service 可以长期存在：

```go
type UserService struct {
	// dependencies
}
```

但请求 Context：

```go
func (s *UserService) GetUser(
	ctx context.Context,
	id int,
) ...
```

每次调用传入：

```text
当前请求自己的ctx
```

例如：

```text
Request A
↓
GetUser(ctxA, 1001)


Request B
↓
GetUser(ctxB, 1002)
```

所以可以记：

```text
Service
→ 通常是长期存在的对象

Context
→ 通常是request-scoped请求级数据
```

# Part 18：Service 为什么使用 %w

Service：

```go
return "", fmt.Errorf(
	"get user profile: %w",
	err,
)
```

加入业务上下文：

```text

```

但 `%w` 保留：

```text

```

形成：

```text

    ↓ unwrap

context.DeadlineExceeded
```

# Part 19：Handler 为什么还能 errors.Is

Handler：

```go
errors.Is(
	err,
	context.DeadlineExceeded,
)
```

即使 Service 已经：

```go
%w
```

包装错误，`errors.Is` 仍然会沿：

```text
error chain
```

检查。

因此能够判断：

```text
底层失败原因是不是：
context.DeadlineExceeded
```

这里不能说：

```text
errors.Is比较错误字符串
```

更准确：

```text
errors.Is沿error chain进行目标错误匹配
```

# Part 20：Context 向下，Error 向上

请求方向：

```text

   ↓
Service
   │

   ↓
```

```text

   ↑
```


## 问题 1

为什么：

```go
func GetUserProfile(
	ctx context.Context,
	id int,
)
```

收到 `ctx` 后应该：

```go
FindUser(ctx, id)
```

而不是：

```go
FindUser(
	context.Background(),
	id,
)
```

？

### 我的回答

因为随手的操作是重新创建一个新的context，原来的context没有传递下去，传递链断开了，后续操作得到的ctx不是原来的context，造成错误。

正确。

```text

```

```text
一条与原请求Context无关的新Context链
```

这样 Handler 上的：

```text
cancel
timeout
deadline
```

不能继续传播到 Repository 等底层操作。

### 我的回答

# Part 27：今天必须记住

```text
1. Context通常表示请求级生命周期。

2. Context需要沿调用链向下传播。

3. Service收到ctx后，通常继续把它传给Repository。

4. 不应该为了方便在调用链中随意重新context.Background()。

5. 重新Background会切断原有Context传播关系。

6. 上层timeout/cancel因此无法继续传播到底层。

7. Context通常作为函数第一个参数。

8. Service对象往往长期存在。

9. Context往往只属于一次请求。

10. 多个请求拥有不同Context。

11. 因此请求Context一般不长期保存在共享Service struct字段中。

12. Repository可以通过ctx.Done()及时感知取消。

13. ctx.Err()可以得到Context结束原因。

14. 主动cancel通常对应context.Canceled。

15. timeout/deadline到达通常对应context.DeadlineExceeded。

16. Service使用%w可以增加错误上下文，同时保留error chain。

17. Handler可以通过errors.Is判断底层错误。

18. errors.Is不是简单比较err.Error()字符串。

19. Context通常向下传播。

20. Error通常向上传播。
```

# Part 31：面试表达

## Context 为什么需要向下传递？

可以回答：

> `context.Context` 通常表示一次请求的生命周期，并携带 cancellation、deadline、timeout 等信息。因此 Handler 接收到 Context 后，需要继续传给 Service、Repository 以及数据库或外部 API 调用。如果中途重新使用 `context.Background()`，原请求的 Context 链会被切断，下层就无法感知上层请求已经取消或超时。

---

## 为什么 Context 通常作为第一个参数？

可以回答：

> Go API 通常约定把 `context.Context` 作为第一个参数，因为它属于当前调用的请求级控制信息。这样调用者可以清晰地把 Context 沿调用链继续向下传递。

---

## 为什么不通常把 Context 存进 Service struct？

可以回答：

> Service 往往是长期存在并被多个请求复用的，而 Context 通常属于某一次具体请求，不同请求可能有不同 deadline、timeout 和取消时间。因此请求级 Context 更适合作为方法参数传递，而不是长期保存在共享 Service 对象中。

---

## Context 如何和 errors.Is 配合？

可以回答：

> 底层操作在 Context 取消后可以返回 `ctx.Err()`。Service 可以使用 `%w` 包装错误并增加业务上下文，同时保留 error chain。Handler 最后使用 `errors.Is` 判断错误链中是否存在 `context.Canceled` 或 `context.DeadlineExceeded`，从而根据具体失败原因做处理。
