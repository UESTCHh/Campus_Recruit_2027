# 五、动态 Top K 为什么仍然使用 Min Heap？

核心算法和昨天没有变化：

```text

↓

```

Heap 中始终保存：

```text

```

因此：

```cpp

```

始终表示：

```text
当前Top K中最小的元素
=
当前第K大
=

```

所以今天真正的新知识点不是 Heap 更新规则，而是：

```text
Heap状态必须跨多次add()保存
```

# 八、构造函数直接复用 `add()`

实验类：

```cpp
class KthLargestTracker
{
private:
    int k_;

    priority_queue<
        int,
        vector<int>,
        greater<int>
    > minHeap_;

public:
    KthLargestTracker(
        int k,
        const vector<int>& nums
    )
        : k_(k)
    {
        for (int value : nums)
        {
            add(value);
        }
    }

    int add(int value)
    {
        if (
            static_cast<int>(
                minHeap_.size()
            ) < k_
        ) {
            minHeap_.push(value);
        }
        else if (
            value > minHeap_.top()
        ) {
            minHeap_.pop();
            minHeap_.push(value);
        }

        return minHeap_.top();
    }
};
```

构造阶段：

```text
nums中的元素
```

和之后：

```text
Stream中新到达的元素
```

本质上都是：

```text
又来了一个新元素
```

所以可以复用：

```cpp
add(value);
```

避免重新写另一套 Top K 初始化逻辑。

### 订正

核心完全正确。

```text

↓

↓
局部Heap可以销毁
```

```text

```

> 静态 Top K 通常在一次函数调用中处理完整输入，局部 Heap 在函数结束后即可销毁；数据流 Top K 需要在多次 `add()` 调用之间持续维护历史 Top K，因此 Heap 必须作为长期状态保存。

### 我的回答

### 订正

完全正确。

局部变量：


## 我的提问

除了：

```cpp
int add(int value)
```

其含义：


# 十二、两种 Top K 更新方式

## 方式 A：先比较门槛

```cpp
if (heap.size() < k) {
    heap.push(value);
}
else if (value > heap.top()) {
    heap.pop();
    heap.push(value);
}
```

含义：

```text
Heap没满
→ 直接加入

Heap已满
→ 和top比较

不够强
→ 直接拒绝

够强
→ 淘汰top后加入
```

---

## 方式 B：先 push，再 pop

```cpp
heap.push(value);

if (heap.size() > k) {
    heap.pop();
}
```

含义：

```text
所有人先参加竞争
↓
超过K人
↓
淘汰最弱者
```

---

## 正确性

两者都维护同一个不变量：

```text
Heap中始终保存当前最大的K个元素
```

因此正确性相同。

---

## 实际 Heap 操作差异

```text
Top 3 = 100 90 80
```

后续：

```text
1 2 3 4 5
```

方式 A：

```text

↓
全部不够资格

Heap修改：
0次
```

方式 B：

```text

↓
size > k

```

所以有：

```text

```

结果相同，但方式 A 的实际 Heap 操作更少。

个元素，

# 十五、Stage 2 检查

## 问题 1

为什么历史数据再多，单次 `add()` 仍然可以是 `O(log k)`？

### 我的回答

> 因为无论历史数据来了多少，当前只维护大小为k的min heap，只保存历史数据中前K大的元素，舍弃掉的剩余数据都是不会对前k大元素造成影响的数据，可以忽略，单次add只用判断目标值与topk门槛元素的大小关系即可，不用将历史数据全部搬出来一起判断，因为有大部分数据已经对结果没有什么影响了，是无用且重复的数据

### 订正

核心完全正确。

复杂度推导补充为：

```text
Heap最多K个
↓
Heap高度O(log k)
↓
push / pop最坏O(log k)
↓
单次add最坏O(log k)
```

而：

```text
已经落在Top K之外的历史元素
```

在当前“只添加、不删除”的问题模型中，不会重新成为 Top K。

### 相关示例

当前：

```text
Top 3 = 100 90 80
```

历史还有：

```text
70 50 3 2 1
```

以后只会继续添加新元素。

当前 Top K 门槛：

```text
80
```

只可能不变或者升高。

因此：

```text
70 50 3 2 1
```

以后也不可能重新进入 Top 3。

### 面试专用回答

> 数据流 Top K 只需要维护大小为 K 的 Min Heap，历史数据中已经落在 Top K 之外的元素不会再影响未来结果，因此无需重新扫描全部历史数据。由于 Heap 大小最多为 K，一次 `add()` 的最坏时间复杂度为 O(log K)。

完全正确。

即使数据流已经有：


Heap 最多仍然保存：

## 问题 4

比较：

```text
A：先比较top，必要时才修改Heap

B：先push，size > k再pop
```

### 我的回答

> 两者都正确地实时维护了前K大元素集合，但是A是利用设立门槛的方式，若与门槛比较之后没有进入TOPk集合的资格就直接放弃，不做任何操作，而B则是先直接放入TOPK集合中再通过top去掉最小值，每个新元素的判断都会造成1次push和1次pop，而A通过设立门槛比较的方式，可以直接抛弃掉很多很小的新元素 ，实际会减少很多次push+pop，实际 Heap 操作会更少

核心完全正确。

```text

```

```text

```

时只需要一次比较。

# 十七、局部变量、全局变量、成员变量

## 局部变量

```text
生命周期：
单次函数调用
```

问题：

```text
add结束
→ Heap销毁
```

不能保存历史状态。

---

## 全局变量

```text
生命周期：
整个程序
```

优点：

```text
可以跨多次add保存状态
```

问题：

```text
状态属于整个程序
而不是某个具体对象
```

如果多个追踪器共享同一个全局 Heap，就会互相污染。

---

## 成员变量

```text
生命周期：
与具体对象一致
```

同时：

```text
状态明确属于某个对象实例
```

因此：

```text
生命周期够长
+
状态归属明确
+
多个实例互不干扰
```

# 十九、我的 LeetCode 703 实现

### 我的回答

```cpp
class KthLargest {
private:
    priority_queue<int, vector<int>, greater<int>> minheap;
    int k_;

public:
    KthLargest(int k, vector<int>& nums) {
        k_ = k;

        for(int val : nums){
            add(val);
        }
    }

    int add(int val) {
        if(static_cast<int>(minheap.size()) < k_){
            minheap.push(val);
        }
        else{
            if(minheap.top() < val){
                minheap.pop();
                minheap.push(val);
            }
        }

        return minheap.top();
    }
};

/**
```

# 二十、为什么 Heap 更适合作为成员变量？

### 我的回答

> 如果作为add的局部变量，每次add函数调用完毕返回后局部变量就会销毁，生命周期结束，下次add又会重新创建一个空的minheap，不会沿用上次add后保存的topk数据，而虽然全局变量也能保存生命周期，但全局变量的生命周期是属于程序的，属于不同对象实例共享的一份数据，不利于对象实例之间的隔离性，假如要同时测两个不同数据流的TOPK数据，则其会共享这一份minheap，导致结果不准确，但作为成员变量将其生命周期绑定到具体的对象上则即可实现生命周期的延续性以及不同对象实例的隔断性，所以 成员变量设计更合理

### 订正

回答正确，而且已经同时包含：

```text
生命周期
状态归属
实例隔离
```

三个层次。

更标准的术语：

```text
不同对象实例的状态隔离
```

而不是“隔断性”。

可以总结为：

```text
局部变量
→ 生命周期太短

全局变量
→ 生命周期足够
→ 但默认属于整个程序

成员变量
→ 生命周期与对象一致
→ 状态明确属于具体实例
```

### 相关示例

```cpp
KthLargest a(3, numsA);
KthLargest b(5, numsB);
```

：

```text
a
├── k_ = 3
└── 自己的minheap
```

：

```text
b
├── k_ = 5
└── 自己的minheap
```

执行：

```cpp
a.add(100);
```

不会修改：

```text
b
```

的状态。

### 面试专用回答

> 如果 Heap 是 `add()` 的局部变量，它会在函数返回时销毁，无法保存历史状态。全局变量虽然生命周期足够长，但通常属于整个程序，不利于状态归属和多实例隔离。将 Heap 作为成员变量可以让它的生命周期与具体对象一致，同时让每个对象拥有自己独立的数据流状态，因此设计更合理。

# 二十五、如果不断整理全局变量，最后其实会重新发明“对象”

假设把：

```text
kA
heapA
```

整理成：

```cpp
struct TrackerState {
    int k;
    Heap heap;
};
```

已经把状态绑定在一起。

如果再把：

```cpp
add()
```

也放进 `struct`：

```cpp
struct TrackerState {
    int k;
    Heap heap;

    int add(int val) {
        ...
    }
};
```

实际上已经重新形成：

```text
有状态对象
```

所以成员变量不是为了“强行面向对象”。

而是因为：

```text
每条数据流
都有自己的一组状态
+
都执行同一种操作
```

天然适合对象模型。

---

## 面试专用回答

> 如果数据流数量固定，也可以为每条数据流分别定义独立的全局 Heap，这样技术上可以实现状态隔离。但这种方式需要人工管理每一组 `k` 和 Heap，数据流数量增加时扩展性和维护性较差。将状态作为类成员后，每个对象天然拥有独立状态，可以方便地创建任意多个实例，并通过同一套 `add()` 方法操作各自状态，因此封装性、状态归属和扩展性都更好。

# 二十六、C++ Day25 最终知识体系

```text
Static Top K
↓
一次性处理完整数据

Dynamic Top K
↓
数据持续到来
↓
Top K状态必须跨add()保存
```

算法：

```text
Top K Largest
↓
Size-K Min Heap
↓
top = 当前第K大
```

状态：

```text
局部变量
→ 生命周期太短

全局变量
→ 生命周期足够
→ 可以人工隔离
→ 但状态管理和扩展困难

成员变量
→ 生命周期与对象绑定
→ 自动按实例隔离
→ 状态和行为封装
```

复杂度：

```text
构造：
O(n log k)

单次add：
O(log k)

m次add：
O(m log k)

总时间：
O((n + m) log k)

额外空间：
O(k)
```

---

# 二十七、C++ Day25 易错点

1. Dynamic Top K 并没有更换 Heap 算法。

2. 真正变化的是 Heap 的生命周期。

3. `add()` 中的局部 Heap 无法保存历史状态。

4. 全局变量不是“不能用”，而是状态归属和扩展性较差。

5. 多份全局 Heap 可以人工实现隔离。

6. 成员变量能够让状态自然归属于具体实例。

7. 两种更新方式都正确：

```text
先比较门槛
```

和：

```text
先push再pop
```

8. 门槛版本通常可以减少实际 Heap 操作。

9. 单次 `add()` 最坏是：

```text
O(log k)
```

而不是：

```text
O(log n)
```

10. 数据流再长，Heap 仍然只保存：

```text
K个元素
```

因此空间：

```text
O(k)
```

> `io.ReadAll(r.Body)` 返回 `[]byte`，因为 HTTP Body 本质上是字节数据，并不保证一定是文本。它可能承载 JSON、图片、文件或其他二进制内容，因此字节切片是更通用的表示形式。

## 问题 3

为什么 `Content-Type: application/json` 不会自动变成 Go struct？

### 我的回答

> 因为Content-Type: application/json只是描述body内容形式的说明信息，真正让json格式数据转换成go struct数据的是handler通过Content-Type: application/json信息+Json decoder实现的

### 订正

核心正确。

更精确：

```text
Content-Type
→ 声明 / 描述Body的媒体类型
```

并不会自动执行：

```text
JSON
→ Go struct
```

真正解析的是：

```go
json.Decoder
```

或：

```go
json.Unmarshal
```

> `json.Decoder` 并不一定必须先手动读取 `Content-Type` 才能运行。

### 相关示例

即使：

```http

```

但 Body：

```text
hello
```

那么：

```text
Header声称它是JSON
```

但：

```go
json.Decoder
```

仍会解析失败。

### 面试专用回答

> `Content-Type: application/json` 只是描述 Request Body 的媒体类型，不会自动完成反序列化。应用层仍然需要使用 `json.Decoder` 或 `json.Unmarshal` 将 JSON 数据解析成 Go 数据结构。

## 问题 4

为什么 Query / Header 是结构化输入，而 Body 还需要业务代码解释？

### 我的回答

> 因为header、query、path这些都已经是成型的http定义好的结构内容，所以可以通过get直接读取对应的值，而r.body并不是一个成型的http定义好的结构内容，它可能是xml、图片、JSON、二进制文件等等，甚至不是一个完整的数据包，而是一个持续在发送的数据流，所以不能直接用Get直接通过key值来找对应的值

### 订正

正确。

最好记成：

```text
Path / Query / Header
→ HTTP层知道它们内部结构

Body
→ HTTP层只知道这里是一段主体数据
→ Body内部语义由应用层协议决定
```

### 面试专用回答

> `net/http` 可以直接解析 Method、URL、Query 和 Header，因为这些属于 HTTP 报文本身的结构；Body 内部属于应用层数据，HTTP 并不知道其中有哪些业务字段，因此业务代码需要根据 JSON、XML 等具体格式继续读取和解析。

# 五十、问题分析

这里不能直接得出：

```text
Go json.Decoder有问题
```

更可能需要检查：

```text
PowerShell中输入的字符串
↓
PowerShell如何把参数传给Windows原生curl.exe
↓
curl.exe实际发送的Body
↓
Server实际收到的r.Body
```

这些层之间是否完全一致。

Windows PowerShell 调用：

```text
curl.exe
```

时存在原生命令行参数转义问题的可能。

尤其 JSON 内部包含：

```text
"
```

双引号。

因此：

> 第一条 JSON 在 PowerShell 源代码中合法，并不能直接证明 Server 最终收到的 Body 与它完全相同。

当前没有通过 `/body` 输出实际请求体来最终确认，所以应记录为：

```text
高度怀疑 PowerShell → curl.exe 参数转义导致Body被破坏
需要通过服务端实际收到的Body进一步验证
```

不能把这一判断写成已经完全证实。

自然不是合法 JSON。

# 五十八、Go Day26 易错点

1. Header Name 和 Header Value 不要混淆。

2. `Content-Type` 是 Header Name。

3. `application/json` 是 Header Value。

4. `Content-Type` 描述 Body 格式，不是 Body 本身。

5. `r.Body` 不是 `string`。

6. `r.Body` 是可读取的数据流。

7. `io.ReadAll(r.Body)` 返回：

```go
[]byte
```

不是：

```go
[]bytes
```

8. Body 本身属于 HTTP Request，但 Body 内部业务格式不是 HTTP 固定定义。

9. Query / Header 可以结构化读取，是因为 HTTP 层能够理解其结构。

10. Body 内部可能是 JSON、XML、文件、图片或二进制。

11. `Content-Type: application/json` 不会自动把 JSON 转成 struct。

12. JSON Decode 需要：

```go
json.Decoder
```

或：

```go
json.Unmarshal
```

13. Struct 中用于 JSON Decode 的字段需要可导出。

14. `Decode(&req)` 中：

```text
&req
```

是：

```text
指针
```

不要描述成 Go 的“引用传递”。

15. Parse 成功不代表 Validation 成功。

16. 合法 JSON 不代表业务数据合法。

17. Windows PowerShell 调用 `curl.exe` 时需要注意 JSON 参数转义。

18. 调试时应该确认 Server 实际收到的 Body，而不是只看 Client 端输入。
