# 三、Reverse Linked List 要解决的问题

原链表：

```text
head
 ↓
10 → 20 → 30 → nullptr
```

要求反转成：

```text
head
 ↓
30 → 20 → 10 → nullptr
```

这里并不是：

```text
交换10、20、30的value
```

而是：

```text
修改节点之间next指针的方向
```

原：

```text
10.next = 20
20.next = 30
30.next = nullptr
```

反转后：

```text
10.next = nullptr
20.next = 10
30.next = 20
```

所以：

> Reverse Linked List 的本质是反转节点之间的连接关系，而不是修改节点中保存的数据。

# 四、为什么不能直接修改 `current->next`

假设：

```text
current
   ↓
10 → 20 → 30 → nullptr
```

如果直接：

```cpp
current->next = previous;
```

那么原来的：

```text
current->next
↓
node20
```

会被覆盖。

例如最开始：

```text
previous = nullptr
```

执行：

```cpp
current->next = previous;
```

就变成：

```text
10 → nullptr
```

而原来：

```text
20 → 30 → nullptr
```

的入口就丢失了。

因此修改之前必须：

```cpp
ListNode* nextNode = current->next;
```

先保存：

```text
剩余未处理链表的入口
```

然后才能安全修改：

```cpp
current->next = previous;
```

# 五、与昨天 Linked List 插入操作的联系

昨天插入节点：

```cpp
newNode->next = prev->next;
prev->next = newNode;
```

为什么必须先：

```cpp
newNode->next = prev->next;
```

因为：

```cpp
prev->next
```

还保存着原链表后半部分的入口。

如果先覆盖：

```cpp
prev->next = newNode;
```

再：

```cpp
newNode->next = prev->next;
```

实际上变成：

```cpp
newNode->next = newNode;
```

形成自环，并且丢失原后半链表。

今天 Reverse Linked List：

```cpp
nextNode = current->next;
current->next = previous;
```

是完全相同的思想：

> 如果某个指针当前保存着后续数据结构的重要入口，在覆盖这个指针之前必须先把原地址保存下来。

# 十、Reverse Linked List 每轮四步

最终可以把每轮固定成：

```cpp
nextNode = current->next;
current->next = previous;
previous = current;
current = nextNode;
```

抽象为：

```text
Save
↓
Reverse
↓
Move previous
↓
Move current
```

或者今天自己的理解：

```text
保存
↓
反转
↓
扩大已反转链表
↓
缩小未处理链表
```

其中：

```cpp
nextNode = current->next;
```

作用：

```text
Save
→ 保存剩余未处理链表入口
```

```cpp
current->next = previous;
```

作用：

```text
Reverse
→ 反转当前节点next指针
```

```cpp
previous = current;
```

作用：

```text
扩大已反转部分
```

```cpp
current = nextNode;
```

作用：

```text
进入下一待处理节点
```

```cpp
while (current != nullptr)
```

# 十四、`reverseList()` 核心函数

```cpp
ListNode* reverseList(ListNode* head)
{
    ListNode* previous = nullptr;
    ListNode* current = head;

    while (current != nullptr)
    {
        ListNode* nextNode =
            current->next;

        current->next =
            previous;

        previous =
            current;

        current =
            nextNode;
    }

    return previous;
}
```

调用：

```cpp
head = reverseList(head);
```

---

# 十五、为什么循环条件是 `current != nullptr`

`current` 表示：

```text
当前待处理节点
```

所以：

```text
current != nullptr
```

说明：

```text
还有未处理节点
```

而：

```text
current == nullptr
```

说明：

```text
未处理部分为空
```

即：

```text
所有节点已经完成反转
```

因此：

```cpp
while (current != nullptr)
```

正好覆盖整个链表。

# 十六、为什么返回 `previous`

原：

```text
head
 ↓
10 → 20 → 30 → 40 → nullptr
```

反转：

```text
40 → 30 → 20 → 10 → nullptr
               ↑
            old head
```

原来的：

```text
head = node10
```

反转后 node10 已经成为尾节点。

循环结束：

```text
previous = node40
```

所以：

```cpp
return previous;
```

返回新的链表入口。

---

# 十七、为什么调用处需要重新赋值

必须：

```cpp
head = reverseList(head);
```

而不能只：

```cpp
reverseList(head);
```

因为函数：

```cpp
ListNode* reverseList(ListNode* head)
```

中的 `head` 是一个指针值的副本。

函数内部会修改：

```text
节点的next关系
```

但外部 `head` 指针变量本身仍然保存：

```text
old head
```

如果不接收返回值：

```text
外部head
仍然指向node10
```

而 node10 已经是：

```text
新链表尾节点
```

因此必须：

```cpp
head = reverseList(head);
```

把新入口重新保存到 `head`。

# 二十三、Reverse Linked List 时间复杂度

链表有：

```text
n个节点
```

每个节点：

```text
只成为current一次
```

每轮只做：

```text

修改next
移动previous
```

## 问题 7

完整描述 Iterative Reverse Linked List。

### 我的回答

> 通过维护三个指针变量，previous 已反转链表部分的头节点 current 当前待处理的节点 nextNode 下一个将要处理的节点，先用next保存后续未处理的链表入口，保证后续反转操作可以连续进行，再让current -> next = previous实现反转，然后previous、current同步移动，直到current == nullptr即整个链表反转完毕，最后返回previous即反转链表的新头节点，时间复杂度度是O(n)，额外空间是O(1)

### 订正

完全正确，已经达到当前阶段面试回答要求。

标准整理：

> 迭代反转单链表时维护 `previous`、`current` 和 `nextNode` 三个指针，其中 `previous` 指向已反转部分的头节点，`current` 指向当前待处理节点。每轮首先保存 `current->next` 到 `nextNode`，避免修改指针后丢失剩余链表入口；然后执行 `current->next = previous` 完成当前节点的反转，再分别移动 `previous` 和 `current`。当 `current == nullptr` 时所有节点都已经处理完成，此时 `previous` 就是新的头节点。每个节点只处理一次，因此时间复杂度 O(n)，只使用固定数量指针，因此额外空间复杂度 O(1)。

# 三十二、`writeJSONError()`

核心：

```go
func writeJSONError(
	w http.ResponseWriter,
	status int,
	message string,
) {
	w.Header().Set(
		"Content-Type",
		"application/json",
	)

	w.WriteHeader(status)

	response :=
		ErrorResponse{
			Error: message,
		}

	err :=
		json.NewEncoder(w).Encode(response)

	if err != nil {
		log.Println(
			"encode error response:",
			err,
		)
	}
}
```

这个函数负责：

```text
Content-Type
↓
Status Code
↓
ErrorResponse
↓
JSON Encode
```

Handler 不需要每个错误分支都重复：

```go
w.Header().Set(...)
w.WriteHeader(...)
json.NewEncoder(...)
```

而只需要：

```text
发生什么错误？
应该是什么Status？
错误消息是什么？
```

# 三十三、为什么 Header / Status / Body 顺序重要

正确：

```text
Set Header
↓
WriteHeader(Status)
↓
Write Body
```

即：

```go
w.Header().Set(
    "Content-Type",
    "application/json",
)

w.WriteHeader(status)

json.NewEncoder(w).Encode(response)
```

如果 Body 已经开始写出，而此前没有：

```go
WriteHeader(...)
```

Go 会默认使用：

```text
200 OK
```

这可能导致：

```text
Body：
发生错误

Status：
200 OK
```

语义冲突。

因此固定：

```text
Headers
↓
Status
↓
Body
```

# 三十四、为什么 Error Response 后必须 `return`

例如：

```go
if err != nil {
	writeJSONError(
		w,
		http.StatusBadRequest,
		"user id must be an integer",
	)

	return
}
```

`return` 代表：

```text
结束当前Handler
对当前HTTP Request的后续处理
```

不是：

```text

```

如果不写：

```text
Parsing已经失败
↓
已经返回400
↓
程序仍继续Validation
↓
继续Business Logic
↓
甚至尝试再次写Response
```

这会造成错误处理流程混乱。

所以基本模式：

```text
Detect Error
↓
Write Error Response
↓
return
```

## 问题 8

Go HTTP API 错误处理面试题。

### 我的回答

> 首先统一响应的格式，防止成功和失败响应需要客户端用不同的解析方式处理，然后通过不同的错误类型映射成不同的状态码，使得客户端和服务端都能根据错误信息进行debug以及排查错误，日志诊断

### 订正

核心方向正确，但需要补：

```text
Request Processing
Parsing / Validation
Business Error
Handler Mapping
Server Log
return
```

标准回答：

> 在 Go HTTP API 中，我会先按照 Request Processing 的阶段处理错误，比如 Request 输入的 Parsing 或 Validation 失败通常属于客户端请求问题，可以映射成 `400 Bad Request`。进入业务逻辑后，底层函数只返回业务结果或 error，而不直接依赖 HTTP；Handler 根据 error 的语义进行 HTTP Error Mapping，例如资源不存在映射成 `404 Not Found`，服务器内部依赖失败映射成 `500 Internal Server Error`。
>
> 在 Response 层，我会统一错误响应格式，例如统一返回 JSON，这样客户端不需要为成功和失败维护完全不同的解析方式。对于 500 这类服务器内部错误，详细错误会记录在 Server Log 中供排障，而客户端只返回稳定且安全的错误信息，避免泄露内部实现细节。错误 Response 写出以后应该及时 `return`，结束当前 Handler 对本次 Request 的后续处理，避免继续执行后面的业务逻辑或者重复写 Response。

# 五十一、Go Day20 30 秒面试回答

> 我一般按照错误发生的语义来处理 HTTP API 错误。Parsing 和 Validation 这类客户端输入错误通常返回 400；资源不存在返回 404；服务器内部依赖或执行失败返回 500。底层业务函数只返回业务结果和 error，由 Handler 负责把 error 映射成 HTTP Status，再通过统一的 JSON Error Response 返回客户端。内部错误会在服务端记录详细日志，但不会把敏感实现细节直接暴露给客户端；错误响应写完后立即 return，结束当前请求的错误路径。
