## 问题 1：Binary Search 的前提

### 我的回答

> 前提是数据有序性；假设数据是升序排列的，如果当前中间元素的值小于目标值，说明中间元素以及排在中间元素前面的元素必定是不等于目标值的，所以可以排除[left, mid]区间内的所有元素。

### 订正

完全正确。

对于升序数组：

```text
numbers[mid] < target
```

意味着：

```text
对于所有 i <= mid：

numbers[i]
<= numbers[mid]
< target
```

所以：

```text
[left, mid]
```

全部可以排除。

因此：

```cpp
left = mid + 1;
```

Binary Search 的核心不是单纯“取中间位置”，而是：

```text
利用有序性
↓
根据比较结果
↓
一次安全排除一半搜索空间
```

## 问题 2：为什么闭区间二分使用 `left <= right`

### 我的回答

> 因为由于是闭区间二分所以当left==right时，区间还有一个候选元素待搜索，即下标为left==right的元素，这个元素可能就是目标值，所以要排查，当left > right时搜索结束，没有找到目标值

### 订正

完全正确。

闭区间：

```text
[left, right]
```

当：

```text
left == right
```

时仍然存在一个候选元素：

```text
[left, left]
```

所以仍需检查。

只有：

```text
left > right
```

时：

```text
搜索区间为空
```

因此：

```cpp
while (left <= right)
```

# 四、Two Pointers 复习

## 问题 4：Sorted Two Sum 为什么 `++left`

### 我的回答

> 因为当numbers[left] + numbers[right] < target时，说明当前搜索区间的左边界和右边界的组合值小于目标值，而右边界已经是当前搜索区间的最大值了，所以不能再让--right;这只会让组合值更小，而左边界可以往右移动寻找更大的最小值，即++left;，这样可以使得左边界和右边界的组合值变大。当前的左边界已经不能和任何右边界组合去等于目标值了，故需要改变

### 订正

完全正确。

如果：

```text
numbers[left] + numbers[right] < target
```

而 `right` 已经是当前最大的候选元素。

连：

```text
numbers[left] + 最大候选值
```

都小于 target。

那么：

```text
numbers[left]
```

不可能再和任何剩余元素组成答案。

所以可以安全：

```cpp
++left;
```

Two Pointers 的核心之一就是：

```text
每次移动指针
↓
都有充分理由
↓
永久排除一部分候选
```

## 问题 5：Fast / Slow Pointer

### 我的回答

```text
slow 已经处理的有效元素边界
fast 待处理的元素
```

> 因为数据是有序的，故重复元素都是连续存在的，所以当numbers[slow] != numbers[fast]时，说明fast对应的元素是一个有效的不重复元素，需要加入已处理的有效元素区间中，所以先让++slow;扩大区间，再让numbers[slow] = numbers[fast];把有效元素加进去；最后返回slow + 1，是因为下标都是从0开始的，而有效区间是[0, slow]一共slow + 1个元素，最后返回的是有效元素的个数。

### 订正

完全正确。

更严格：

```text
slow
→ 已处理有效区间 [0, slow] 的最后一个元素

fast
→ 当前正在检查的候选元素
```

发现新元素：

```cpp
numbers[slow] != numbers[fast]
```

执行：

```cpp
++slow;
numbers[slow] = numbers[fast];
```

最后有效区间：

```text
[0, slow]
```

长度：

```text
slow + 1
```

# 五、Sliding Window 复习

## 问题 6：Fixed Sliding Window

### 我的回答

> 因为每次窗口右移后改变的只有边界元素，旧窗口和新窗口的重叠部分不需要重新计算，只用计算新窗口移除的元素和移入的元素带来的影响即可

### 订正

完全正确。

核心：

```text
newWindowState

=

oldWindowState
- 离开窗口的元素
+ 新进入窗口的元素
```

Sliding Window 的本质：

```text
复用相邻Window之间的大量重叠计算
```

---

## 问题 7：Variable Sliding Window 为什么常要求正整数

### 我的回答

> 因为只有元素是正整数时，右边界扩张才能保证累加和是增大的，才能寻找更加符合条件的值，而左边界收缩才能保证整体值缩小的，才能寻找符合条件的最小长度；如果出现负数，那么这套简单的逻辑就不适用了，因为收缩和扩张都不能保证值是增大还是缩小

### 订正

完全正确。

正整数保证：

```text
right扩张
→ sum不会减小
```

以及：

```text
left收缩
→ sum不会增大
```

因此形成单调性。

如果存在负数：

```text
扩张不一定增大
收缩不一定减小
```

原来的决策逻辑失效。

## 问题 8：为什么 `for + while` 仍然是 O(n)

### 我的回答

> 因为每个元素最多移出窗口一次和进入窗口一次，n个元素每次查找最坏即O(n + n) = O(n)

### 订正

核心正确。

更准确：

整个算法过程中：

```text
right最多移动n次

left最多移动n次
```

所以总指针移动次数：

```text
<= 2n
```

因此：

```text
O(2n)
=
O(n)
```

而不是看到：

```cpp
for
{
    while
    {
    }
}
```

就机械认为 O(n²)。

# 六、Prefix Sum 复习

## 问题 9：`prefix[i]` 定义

### 我的回答

> 前i个元素的累加和；prefix[0] = 0是因为前0个元素的和本来就是0，因为没有元素；而prefix num解决的是[left，right]的连续区间多次求和问题，而求和公式即prefix[right + 1] - prefix[left]，而当right=n - 1时 right+1 = n这说明prefix数组需要支持下标为n的遍历，所以prefix的区间为[0, n]故有n+1个元素，prefix.size() = n + 1

### 订正

正确。

严格定义：

```text
prefix[i]
=
原数组前 i 个元素之和
```

所以：

```text
prefix[0]
=
前0个元素之和
=
0
```

需要表示：

```text
前n个元素之和
```

所以需要：

```text
prefix[n]
```

因此：

```text
prefix.size() = n + 1
```

更重要的是：

```text
prefix[0] = 0
```

使所有区间统一使用：

```cpp
prefix[right + 1] - prefix[left]
```

无需特殊判断：

```cpp
left == 0
```

---

## 问题 10：为什么两个 Prefix 相减得到区间和

### 我的回答

> prefix[right + 1]为前right + 1个元素的累加和，即numbers[0] + numbers[1] + ..... + numbers[left -1] + numbers[left] + ...... + numbers[right]，而prefix[left]为前left个元素的累加和，即numbers[0] + numbers[1] + ..... + numbers[left -1]，两者相减消除公共前缀项，即剩下numbers[left] + ..... + numbers[right]即闭区间[left, right]的累加和

### 订正

完全正确。

本质：

```text
大Prefix
-
小Prefix
↓
公共前缀抵消
↓
目标区间
```

即：

```cpp
prefix[right + 1] - prefix[left]
```

# 七、Difference Array 复习

## 问题 11：Difference 定义与恢复

### 我的回答

> 当前元素相较前一个元素的变化量；因为Difference Array记录的是相邻元素的变化量，而difference[0] = numbers[0], numbers[i] = numbers[i - 1] + difference[i],让difference array数组做区间的累加和可以正好将中间的加减项抵消掉，最后只剩numbers[i]即原数组元素值

### 订正

完全正确。

定义：

```text
difference[0]
=
numbers[0]
```

以及：

```text
difference[i]
=
numbers[i] - numbers[i - 1]
```

所以：

```text
difference[i]
```

表示：

```text
当前位置相对于前一个位置变化多少
```

累计：

```text
difference[0]
+ ...
+ difference[i]
```

中间项相互抵消，最终得到：

```text
numbers[i]
```

因此：

```text
Difference Array
↓ Prefix Sum
Original Array
```

## 问题 12：Difference Range Update

### 我的回答

```text
difference[left] += value; 代表从left开始做累加和后都会带有 +value的影响
difference[right + 1] -= value; 代表从right+1开始的累加和都撤销了 +value的影响
```

> 这样可以使得只有[left，right]区间的元素整体+value

### 订正

完全正确。

可以固定为：

```text
difference[left] += value
→ 在left开启影响

difference[right+1] -= value
→ 在right+1关闭影响
```

因此：

```text
[left, right]
```

恰好受到修改。

# 八、Linked List 复习

## 问题 13：vector vs Linked List Random Access

### 我的回答

> 因为vector是连续存储空间，可以直接用下标随机访问任意元素，即首地址 + i * sizeof[数据类型]，故O(1)；而链表并不要求连续存储空间，存储的元素之间是通过节点之间的逻辑关系相连的，通过指针查找下一个节点的位置，故若要随机访问需要从头节点开始一个一个地往下一个节点开始找，最坏情况下是O(n)

### 订正

概念完全正确。

vector：

```text
连续存储
↓
地址可以直接计算
↓
O(1)
```

Linked List：

```text
节点不要求连续
↓
只能沿next查找
↓
O(n)
```

书写上应是：

```cpp
sizeof(数据类型)
```

## 问题 14：链表插入顺序

### 我的回答

> 要插入新元素需要先保存插入位置后的链表位置，先将新元素将后面的链表位置相连，再将插入位置之前的节点接到该插入节点，即10 -> 20 -> 30 变为 15 -> 20 -> 30 再让 10 -> 15 -> 20 -> 30，如果反过来，此时prev的next就是newNode新节点了，再让newNode->next = prev->next;即newNode->next = newNode;会形成自环结构，并丢失了原来插入位置后的链表入口

### 订正

完全正确。

正确：

```cpp
newNode->next = prev->next;
prev->next = newNode;
```

如果反过来：

```cpp
prev->next = newNode;
newNode->next = prev->next;
```

第二句实际变成：

```cpp
newNode->next = newNode;
```

形成：

```text
self-loop
自环
```

同时丢失原链表后半部分入口。

## 问题 15：delete 后为什么不能继续访问

### 我的回答

> 因为先delete后该指针对应的内存空间已经被释放掉了，再通过current = current->next;去操作该内存空间是未定义行为，是错误的操作，正确的释放链表节点方式是 先temp = current->next; 再delete current; 再prev -> next = temp

### 订正

核心内存安全理解正确。

绝对不能：

```cpp
delete current;
current = current->next;
```

因为：

```cpp
delete current;
```

以后 `current` 成为：

```text
dangling pointer
```

再：

```cpp
current->next
```

属于：

```text
Undefined Behavior
```

需要区分两个场景。

删除单个已知中间节点：

```cpp
prev->next = current->next;
delete current;
```

释放整个链表：

```cpp
ListNode* nextNode = current->next;
delete current;
current = nextNode;
```

## 问题 16：Dummy Node

### 我的回答

> Dummy Node 的核心价值是解决边界（头节点）统一逻辑的问题，并没有降低总体复杂度，查找 / 删除某个指定值节点的总体复杂度还是 O(n)，因为不知道前驱节点的情况下，要查找/删除某个节点需要先找到该节点的位置，即需要从头节点开始一个一个遍历下一个节点，最坏情况下就是O(n)，增加Dummy Node不会帮助找到节点的位置，还是需要线性搜索遍历

### 订正

完全正确。

Dummy Node：

```text
不负责提高查找速度
```

而是：

```text
给原head提供虚拟前驱
↓
统一头节点和普通节点操作
↓
减少边界特判
```

因此：

```text
寻找目标节点
仍然可能 O(n)
```

## 问题 10：多个数组算法如何区分

### 我的回答

```text
有序 + 查找target
→ Binary Search

有序 + 两数之和
→ Two Pointers

连续窗口 + 固定长度
→ Fixed sized Sliding Window

连续窗口 + 满足条件后收缩
→ variable sized Sliding Window

大量任意区间求和
→ Prefix Sum

大量区间统一增量修改
→ Difference Array
```

### 订正

映射正确，但面试时应组织为完整的一段逻辑：

> 这些算法虽然很多都用于数组，但它们优化的重复工作不同。Binary Search 利用有序性每次排除一半搜索空间，适合有序数据中的查找；Two Pointers 利用两个有明确含义的指针逐步排除候选，例如有序数组 Two Sum；Sliding Window 适合连续区间不断移动或伸缩的问题，通过维护当前窗口状态避免重新计算；Prefix Sum 提前保存所有前缀累计状态，适合大量随机区间查询；Difference Array 则主要优化大量区间增量修改，每次只修改两个边界，最后统一恢复结果。因此选择算法时，应根据题目是否有序、是否具有连续窗口关系，以及是大量查询还是大量修改来判断。

    if(numbers[left] + numbers[right] == target){

vector<int>

pair<int, int>

return {left, right};

while (left < right)

    {
        return {left, right};
    }
    else if (sum > target)
    {
        --right;
    }
    else
    {
        ++left;
    }
}

# 二十二、Go HTTP Middleware 面试标准回答

> Go 标准库的 HTTP 处理体系是围绕 `http.Handler` 接口构建的。`http.Handler` 只要求实现 `ServeHTTP(w, r)` 方法，因此任何实现这个方法的类型都可以参与 HTTP 请求处理。普通的 Handler 函数本身不是 `http.Handler`，但是标准库提供了 `http.HandlerFunc` 这个函数类型，它实现了 `ServeHTTP`，因此可以把符合签名的普通函数适配成 `http.Handler`。
>
> Middleware 通常设计成 `func(http.Handler) http.Handler`，也就是接收一个下一层 Handler，再返回一个包装后的新 Handler。Middleware 可以在调用 `next.ServeHTTP(w, r)` 之前执行日志、认证等前置逻辑，调用 `next.ServeHTTP` 时把请求继续交给下一层 Handler，等下一层返回以后再执行后置逻辑。
>
> `ServeMux` 本身也实现了 `http.Handler`，所以它可以位于 Middleware Chain 的最内层。请求最终到达 `mux.ServeHTTP` 后，ServeMux 会根据 Method 和 Path 进行路由匹配，再调用具体的业务 Handler。
>
> 当存在多个 Middleware 时，可以通过不断包装形成类似 `logging(auth(mux))` 的结构。请求进入时按照外层到内层执行，而返回时按照内层到外层返回，因此形成 Onion Model。
>
> 如果 Middleware 需要把认证得到的 `userID`、Request ID 等请求级信息传给后面的 Handler，可以基于 `r.Context()` 创建新的 Context，然后通过 `r.WithContext(ctx)` 得到携带新 Context 的 Request，再继续调用 `next.ServeHTTP`，后续 Handler 就可以通过 `r.Context()` 获取这些 Request-scoped 数据。

# 二十三、Go HTTP Middleware 30 秒面试版

> Go HTTP Middleware 本质上是对 `http.Handler` 的层层包装。`http.Handler` 通过 `ServeHTTP` 定义统一的请求处理接口，普通函数可以通过 `http.HandlerFunc` 适配成 Handler，`ServeMux` 本身也实现了 Handler。Middleware 通常采用 `func(http.Handler) http.Handler` 的形式，内部在 `next.ServeHTTP` 前后执行通用逻辑，从而形成日志、认证等横切处理。多个 Middleware 可以组成 `logging(auth(mux))` 这样的调用链，请求从外向内执行、返回从内向外展开，形成洋葱模型；如果需要向后续 Handler 传递 userID、Request ID 等请求级数据，可以通过 Request 的 Context 传递。
