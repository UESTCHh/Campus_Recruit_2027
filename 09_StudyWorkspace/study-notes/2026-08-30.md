## 问题 4：Pointer Alias

### 我的回答

q依然存在，且q存储的是p本身的地址，q指向的是p本身的存储空间，p = nullptr只能将其置空，但它本身存储的空间依然存在，故q还是指向它并存储它的地址。

### 订正

这里理解错误。

代码：

```cpp
int* p = new int(10);
int* q = p;
```

不是：

```text
q → p → int
```

而是：

```text
p和q分别保存了相同的地址值
```

即：

```text
p ─────┐
       ↓
      [10]
       ↑
q ─────┘
```

执行：

```cpp
delete p;
```

后动态对象被销毁。

此时：

```text
p
q
```

都保存着原来的失效地址。

再：

```cpp
p = nullptr;
```

只会修改 `p` 自己。

最终：

```text
p → nullptr

q → 原来的失效地址
    dangling pointer
```

如果真正需要：

```text
q指向p这个指针变量
```

类型应该类似：

```cpp
int** q = &p;
```

必须记住：

```text
int* q = p;

→ 复制p里面保存的地址值
```

而不是：

```text
q指向p变量
```

## 问题 9：默认拷贝为什么危险

### 我的回答

会发生double free问题，即同一块内存空间资源被释放两次，出现错误。s1.age

### 订正

正确。


```text

        [20]
         ↑
s2.age ──┘
```

两个对象最终都尝试：

```cpp
delete age;
```

导致：

```text
double free
```

## 问题 1：为什么需要 Move

### 我的回答

因为当原对象有一大块动态资源时，深拷贝会重新申请一大块内存空间用来存放这块资源，不仅浪费内存空间，效率也低。Move则是直接将该动态资源的所有权交给新的对象，这样就不用重新申请一块内存，并且效率也高。

### 订正

正确。

```text
Copy
→ 创建新资源
→ 复制资源内容

Move
→ 转移已有资源所有权
```

Move 的主要价值：

```text
避免昂贵资源复制
```

## 问题 2：Move Constructor

### 我的回答

data = other.data;是移交该动态资源的所有权，而other.data = nullptr;是将原对象的指针置空，使其不再拥有该动态资源的所有权，这样析构的时候两个对象不会都释放同一块资源，造成double free问题。

### 订正

核心正确。

单独：


只是：

```text

```

真正完成 ownership transfer 的是：

```cpp
data = other.data;
other.data = nullptr;
```

两步组合。

## 问题 8：Self Assignment

```cpp
if (this == &other) {
```

## 问题 12：shared_ptr

### 我的回答

因为shared_ptr本身含有一个control block结构，存放对象所有者的个数，能够让多个只能指针共同管理一个对象，并且只有当该个数为0时被管理的对象才会被销毁

### 订正

核心正确。

更安全的描述：

```text
多个shared_ptr关联同一个control block
```

control block 中维护共享所有权相关状态。

当：

```text
strong/shared ownership count → 0
```

被管理对象被销毁。

对象销毁和 control block 自身销毁不是完全同一个概念。

## 问题 15：lock_guard

### 我的回答

因为该对象资源是自动管理生命周期的资源，在其所属的类中含有自动产生的构造和析构函数，在该代码块结束后会自动释放，符合RAII的思想。

### 订正

方向正确，但机制需要修正。

不是：

```text
编译器自动生成普通构造/析构
```

完成 lock/unlock。

而是：

```text
std::lock_guard类型自身实现了RAII语义
```

构造：

```text
lock mutex
```

析构：

```text
unlock mutex
```

## 问题 7：Collision

### 我的回答

哈希冲突，最终进入同一个bucket

### 订正

需要区分：



在同一个当前容器状态下：

```text

→ 相同bucket
```

但：

```text
相同bucket
↛
hash value一定相同
```

因为：

```text
hash value空间
远大于
bucket数量
```

所以不同 hash value 仍可能映射到同一个 bucket。

```go

```

解除阻塞。

关键不是：

```text

```

而是：

```text

```

## 问题 8：defer cancel()

### 我的回答

类似C++的RAII思想，因为程序可能在任何位置return，defer的作用是只要函数的生命周期结束了，就自动调用cancel函数释放掉context资源。

### 订正

核心正确。

可以类比：

```text
作用域退出时执行cleanup
```

但：

```text
Go defer
≠
C++ RAII
```

调用：

```go
defer cancel()
```

保证任何 return 路径最终都会调用 `cancel()`。

目的：

```text
及时释放派生Context关联的资源
例如timer
```

不是：

```text
释放cancel函数本身
```


# Go 当前重点强化点

## 1. Pointer Receiver 仍然是 Pass-by-Value

不能说：

```text
Go引用传递
```

而是：

```text
复制指针值
↓
复制后的指针仍指向原对象
```

---

## 2. Method Call 与 Method Set 不同

```go
sms.Send()
```

能够调用，

不代表：

```text
SMSNotifier
```

一定满足接口。

必须看：

```text
method set
```

---

## 3. Method Set 规则

固定：

```text
func (t T) M()

T   ✅
*T  ✅
```

```text
func (t *T) M()

T   ❌
*T  ✅
```

---

## 4. Fake

```text
Fake
≠
跳过被测业务逻辑
```

正确：

```text
真实执行被测Service
Fake替换外部依赖
```

---

## 5. Consumer-defined / Small Interface

Interface 应描述：

```text
Consumer真正需要的最小能力
```

而不是：

```text
Provider拥有的全部能力
```

---

## 6. errors.As 二级指针

固定：

```go
var validationErr *ValidationError
```

所以：

```text
validationErr
→ *ValidationError

&validationErr
→ **ValidationError
```

二级指针出现的原因：

```text
errors.As需要修改validationErr这个指针变量本身
```

不是因为错误对象本身是二级指针。

---

## 7. Context 本身不是取消信号

更加准确：

```text
Context
→ 请求生命周期控制信息的载体
```

它可以传播：

```text
cancellation
deadline
timeout
```

`Done()` channel 是下层观察 Context 结束的重要机制。

---

## 8. Cooperative Cancellation

Context：

```text
不会强杀函数
不会强杀goroutine
```

而是：

```text
Context状态发生变化
↓
Done关闭
↓
业务代码主动观察
↓
自己停止工作
```
