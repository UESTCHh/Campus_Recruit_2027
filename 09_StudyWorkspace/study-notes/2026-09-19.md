## 1. 从输入 URL 到浏览器显示内容的完整过程

### 我的理解

### 订正

整体理解正确。

更准确的过程：

```text
用户在浏览器输入URL
↓
浏览器Client构造HTTP Request
↓
浏览器发送Request
↓
HTTP Server监听对应端口并接收到Request
↓
Server把Request交给ServeMux
↓
ServeMux根据Request中的URL Path进行Route Matching
↓
找到对应Handler
↓
Handler读取Request并执行业务逻辑
↓
Handler通过ResponseWriter写Response
↓
HTTP Server将Response发送给Client
↓
浏览器读取Response
↓
根据Response内容进行展示
```

其中需要特别注意：

```text
Handler
```

并不是简单：

```text
return 一个Response对象
```

而是在 Go `net/http` 中通过：

```go
http.ResponseWriter
```

写响应。

# 三、为什么 Handler 可以直接读取 Request，却通过 ResponseWriter 写 Response？

## 1. 我的提问

> 为什么handler可以读到真实的请求request，却无法直接生成真实的response，而是要多此一举通过responsewriter间接地写response呢？

---

## 2. Request 为什么可以直接读取？

客户端已经把 Request 发过来了。

例如：

```http
GET /hello HTTP/1.1
Host: localhost:8080
```

HTTP Server 先完成：

```text
网络中的Request字节
↓
HTTP Server读取
↓
HTTP Server解析
↓
生成 *http.Request
↓
传给Handler
```

所以 Handler 执行时：

```go
r *http.Request
```

已经是 Server 解析好的请求对象。

Handler 可以直接读取：

```go
r.Method
r.URL.Path
r.URL.Query()
r.Header
r.Body
```

---

## 3. Response 为什么不同？

Handler 刚开始运行时：

```text
Request
→ 已经存在

Response
→ 还没有完成
```

Response 是 Handler 在运行过程中逐渐产生的。

例如：

```go
fmt.Fprintln(w, "hello")
fmt.Fprintln(w, "world")
fmt.Fprintln(w, "Go")
```

Handler 是逐步往 Response 中写内容。

所以 Go 给 Handler 的不是一个已经完成的：

```go
*http.Response
```

而是一个：

```go
http.ResponseWriter
```

用于写 Response。

---

## 4. ResponseWriter 可以理解为什么？

当前阶段可以理解为：

> Server 提供给 Handler 的 HTTP Response 输出通道。

即：

```text
Handler
↓
ResponseWriter
↓
HTTP Response
↓
HTTP Server
↓
Client
```

---

## 5. 为什么不强制 Handler return 一个完整 Response？

如果必须：

```text
Handler先生成整个Response
↓
return Response
↓
Server再发送
```

那么返回巨大文件或流式内容时会非常笨重。

ResponseWriter 允许：

```text
产生一点数据
↓
写一点

再产生一点
↓
再写一点
```

因此支持：

```text
Streaming
流式响应
```

同时 Handler 不需要直接管理：

```text
TCP连接
HTTP报文底层格式
网络发送细节
```

这些交给 HTTP Server。

---

## 6. Handler 与 Server 的职责

Handler：

```text
读取Request
↓
执行业务逻辑
↓
决定响应内容
↓
通过ResponseWriter写响应
```

HTTP Server：

```text
监听网络
↓
读取Request
↓
解析Request
↓
调用Handler
↓
处理Handler写入ResponseWriter的数据
↓
按照HTTP协议发送Response
```

---

## 7. ResponseWriter 不只写 Body

它主要可以操作：

```text
Response
├── Status Code
├── Header
└── Body
```

Header：

```go
w.Header().Set(
    "Content-Type",
    "application/json",
)
```

Status Code：

```go
w.WriteHeader(
    http.StatusNotFound,
)
```

Body：

```go
fmt.Fprintln(
    w,
    "not found",
)
```

---

## 8. 最核心记忆

```text
Request
→ Server已经解析好的输入

ResponseWriter
→ Server提供给Handler的输出通道
```

---

## 9. 面试专用回答

> `*http.Request` 表示已经由 Server 从网络中读取并解析完成的客户端请求，因此 Handler 可以直接读取它。Response 则是在 Handler 执行过程中逐步产生的，所以 Go 提供 `http.ResponseWriter`，让 Handler 写入 Status Code、Header 和 Body。这样既能让 Handler 与底层网络连接和 HTTP 协议细节解耦，也支持流式响应，最终由 HTTP Server 将 Response 发送给客户端。

# 八、C++ Day24 Stage 1 检查

## 问题 1

为什么找第 K 大时经常使用大小为 K 的 Min Heap？

### 我的回答

> 因为找第k大只用维护前k大的元素即可，不需要维护所有元素，而第k大即前k大元素中最小的那个，所以可以用大小为K的Min Heap，每次top都是前k大元素中最小的那个，让其与新元素相比较，若大，则新元素没资格进入前k大，若小，则将新元素加入前k大，而把作为门槛的第k大元素，即原来的top出队。

### 订正

核心完全正确。

比较时需要明确比较方向：

```text
newValue <= minHeap.top()
↓
新元素没有资格进入Top K

newValue > minHeap.top()
↓
新元素进入Top K
↓
pop旧top
↓
push新元素
```

### 面试专用回答

> 求第 K 大元素时只需要维护当前最大的 K 个元素。使用大小为 K 的 Min Heap 后，堆顶始终是 Top K 中最小的元素，也就是当前第 K 大和进入 Top K 的门槛。新元素大于堆顶时，淘汰旧堆顶并插入新元素。

## 问题 2

为什么整体最坏是 O(n log k)？

### 我的回答

> 首先所有元素都需要扫描一遍即O(n)，而每次扫描时前k个元素都会push一次即O(klog k) 后面n-k个元素最坏情况下都要push+pop，即O((n-k)logk) 所以最后的复杂度即O(klogk + (n-k)logk) = O(n logk)

### 订正

完全正确。

```text
前K个：
O(k log k)

剩余n-k个：
最坏O((n-k) log k)

总计：
O(n log k)
```

递增数组：

```text

```

之后几乎每个新元素都会：

### 面试专用回答

> 算法需要扫描全部 N 个元素。Heap 大小始终不超过 K，因此每次 `push` 或 `pop` 最坏为 O(log K)。最坏情况下后续元素都会触发一次删除和插入，所以整体时间复杂度为 O(N log K)。

# 十四、我的 LeetCode 215 Min Heap 实现

```cpp
class Solution {
public:
    int findKthLargest(vector<int>& nums, int k) {
        int n = static_cast<int>(nums.size());

        priority_queue<
            int,
            vector<int>,
            greater<int>
        > mh;

        for (int i = 0; i < n; i++) {
            if (i < k) {
                mh.push(nums[i]);
                continue;
            }

            if (mh.top() < nums[i]) {
                mh.pop();
                mh.push(nums[i]);
            }
        }

        return mh.top();
    }
};
```

---

```text
直接进入Min Heap
```

```text
→ 无法进入Top K
→ 忽略
```

：

```text
nums[i] > mh.top()
→ 新元素进入Top K
→ pop旧top
→ push新元素
```

最终：

```text
Heap
=
整个数组最大的K个元素
```

# 二十、LeetCode 215 面试专用回答

> 可以使用大小为 K 的 Min Heap 维护当前最大的 K 个元素，堆顶始终是 Top K 中最小的元素，也就是当前第 K 大。扫描每个元素时，如果 Heap 未满就直接加入；Heap 满后只有比堆顶大的元素才会进入，并淘汰旧堆顶。因此最终 `top()` 就是数组第 K 大。该方法时间复杂度为 O(N log K)，额外空间复杂度为 O(K)。如果进一步要求期望线性时间，可以使用随机化 Quickselect。

# 五十一、Stage 3 检查

## 问题 1

为什么：

```text
?page=abc
```

是 Parse 失败而不是 Required Check 失败？

### 我的回答

> 因为page变量有值“abc"并不是空，所以query()得到的不是空字符串所以Required Check成功，但是"abc"不是一个表示整数的字符串，所以atoi函数转换失败，所以Parse失败

### 订正

理解完全正确。

更精确：

```go
r.URL.Query().Get("page")
```

得到：

```text
"abc"
```

所以：

```text
Required Check
→ 通过
```

然后：

```go
strconv.Atoi("abc")
```

失败：

```text
Parse失败
```

### 面试专用回答

> `page=abc` 中参数存在且非空，因此 Required Check 可以通过；但 `abc` 不是合法整数表示，`strconv.Atoi` 会返回错误，因此这是 Parse 阶段失败。

---

## 问题 2

为什么 `page=-2` Parse 成功但 Validation 失败？

### 我的回答

> 因为虽然"-2"是一个表示整数的字符串，所以atoi函数转换成功，但是业务逻辑要求转换后的数据需要>0，而-2<0所以Validation失败。Parse主要是看参数是否是合法的表示整数的字符串并能够转换成功，而Validation是看转换后的数据是否满足业务逻辑

### 订正

完全正确。

```text
"-2"
→ 合法整数格式
→ Parse成功
```

：

```text
-2 < 1
→ 不符合page业务规则
→ Validation失败
```

### 面试专用回答

> Parse 负责将外部字符串转换为程序需要的数据类型，而 Validation 检查转换后的值是否符合业务约束。因此 `"-2"` 可以成功解析为整数 -2，但如果 page 必须大于等于 1，就会在 Validation 阶段失败。

---

## 问题 3

为什么 `http.Error()` 后通常要 `return`？

### 我的回答

> 因为这时已经返回错误响应了，后续操作应当立即停止，所以handler应该return并停止执行

### 订正

核心正确。

更准确：

```text
http.Error
→ 已经向ResponseWriter写错误Response
```

但 Handler 还没有自动结束。

必须：

```go
return
```

才能：

```text
停止后续Parse / Validation / Business Logic
```

### 面试专用回答

> `http.Error` 会通过 `ResponseWriter` 写入错误状态码和错误信息，但不会自动结束当前 Handler，因此通常需要立即 `return`，避免后续逻辑继续执行。

完整描述：

```text
?page=10
```

到：

```go
page int = 10
```

的流程。

### 我的回答

> ?page=10 -> r.URL.Query().Get("page") -> "10" -> required check -> Atoi("10") = 10, page int = 10 -> validation 10 >0 -> Bussiness logic

### 订正

完全正确。

标准流程：

```text
?page=10
↓

↓
.Get("page")
↓

↓
Required Check
↓
通过
↓
strconv.Atoi("10")
↓
10
int
↓
Validation
↓
10 >= 1

通过

```

> Handler 首先通过 `r.URL.Query().Get("page")` 得到字符串 `"10"`，通过 Required Check 后使用 `strconv.Atoi` 将其解析成整数 10，再验证其是否满足 `page >= 1` 的业务约束。全部通过后，再将解析后的 `int` 值交给业务逻辑使用。

# 五十四、Go Day25 易错点

1. `r.URL.Path` 是字段，不是 `r.URL.Path()`。

2. Query 不是：

```go
r.Query()
```

而是：

```go
r.URL.Query()
```

3. `RawQuery` 是原始字符串。

4. `Query()` 返回解析后的 Query Parameters。

5. Query Parameter 默认读取为 string。

6. `Get()` 在参数缺失时返回空字符串。

7. 只使用 `Get()` 无法严格区分：

```text
参数缺失
```

与：

```text
显式传空
```

8. 严格区分时可以使用：

```go
query.Has(...)
```

9. `Parse` 与 `Validation` 不是一回事。

10. `Atoi("-2")` 可以成功。

11. Parse 成功不代表业务值合法。

12. `http.Error` 写错误 Response，但不会自动结束 Handler。

13. `http.Error` 后通常需要：

```go
return
```

14. 浏览器页面看不到 400 文本不代表没有返回 400。

15. HTTP Status 可以通过：

```text
Browser Network
```

或：

```powershell
curl.exe -i
```

查看。

16. `Host` 从 HTTP 协议角度属于 Header，但 Go `net/http` 通常通过：

```go
r.Host
```

读取。
