2.1 DFS 和 BFS 的区别

示例：

        1
       / \
      2   3
     / \
    4   5

DFS 前序遍历：1 2 4 5 3，先向下深入再回溯。

BFS 层序遍历：1 2 3 4 5，按照从上到下、每层从左至右的顺序访问。

采用队列 queue<TreeNode*>，用 FIFO 确保先发现的节点先处理，并在弹出一个节点后，将其非空左右孩子依次压入队尾。

队列必须保留节点地址，才能继续访问节点的 left / right，而不仅仅是保存 val。

2.2 完整代码：bfs_demo.cpp

目录： D:\Campus_Recruit_2027\02_CPP_Notes\cpp-learning\day41-binary-tree-bfs

#include <iostream>
#include <queue>

using namespace std;

struct TreeNode {
    int val;
    TreeNode* left;
    TreeNode* right;

    TreeNode(int x) : val(x), left(nullptr), right(nullptr) {}
};

void bfs(TreeNode* root) {
    if (root == nullptr) {
        return;
    }

    queue<TreeNode*> q;
    q.push(root);

    while (!q.empty()) {
        TreeNode* current = q.front();
        q.pop();

        cout << current->val << " ";

        if (current->left != nullptr) {
            q.push(current->left);
        }
        if (current->right != nullptr) {
            q.push(current->right);
        }
    }
}

int main() {
    TreeNode n1(1), n2(2), n3(3), n4(4), n5(5);
    n1.left = &n2;
    n1.right = &n3;
    n2.left = &n4;
    n2.right = &n5;

    TreeNode* root = &n1;
    cout << "BFS: ";
    bfs(root);
    cout << '\n';
}

2.3 复杂度

时间 O(n)：每个节点最多入队、出队各一次，队列操作均摊 O(1)。

辅助空间 O(w)：队列保存待访问节点，w 表示树的最大层宽，最坏 O(n)。队列中可能同时包含当前层末尾和下一层开头，因此最大元素数不必精确等于 w，但在 O(w) 数量级内。

递归 DFS 空间 O(h)：h 表示树的高度，主要来自函数调用栈。平衡树约 O(log n)，链状树最坏 O(n)。

链状树 BFS 队列可以是 O(1)，而同一棵树上 DFS 的递归栈可以达到 O(n)。

2.4 检查 1｜为什么使用队列？

问题

为什么 BFS 更适合使用 queue，而不是 stack？

队列 FIFO 如何保证层序遍历？

为什么是 queue<TreeNode*>，而不是 queue<int>？

我的回答（原文）

为什么 BFS 更适合使用 queue，而不是 stack？因为最先遍历到的节点要优先处理，即需要先进先出，符合queue的语义，而stack是后进先出，不满足题目要求

队列的先进先出特性，是如何保证二叉树按照层序进行遍历的？每次处理时都是将队头取出并将其左右子节点入队，这样可以保证每层都是从左至右依次处理，并且是按一层一层依次往下处理

为什么这里使用 queue<TreeNode*>，而不是 queue<int>？因为每次处理时都是将队头取出并将其左右子节点入队，需要根据当前队列中的元素知道下次入队的元素，所以不能仅保存current->val，这样无法根据此元素知道current->left和current->right，无法将其左右子节点入队

订正

三问均正确。补充：保证同一层从左至右还依赖程序对每个节点先左孩子入队、再右孩子入队；反过来会产生从右至左的层序顺序。

相关示例

    1
   / \
  2   3

左先入队：1 2 3。

右先入队：1 3 2。

面试专用回答

BFS 使用先进先出的队列：每次弹出最早入队的节点，再把它的非空左右孩子按左、右顺序加入队尾，从而实现自上而下、同层从左到右的遍历。队列保存 TreeNode*，以便继续获取左右孩子地址。

2.6 检查 3｜BFS 复杂度

问题

为什么时间是 O(n)？

我的回答（原文）

为什么时间复杂度是 O(n)？因为每个节点入队一次，出队一次，处理时间都是O(1)，所以n个节点的复杂度就是O(1 * n) = O(n)

为什么空间复杂度不是一定为 O(1)？因为额外的空间负责度是依据队列的存储元素来决定的，当n=1时，队列最多存储一个元素，自然是O(1)，当n>1时，需要根据树的最大宽度来计算队列的最坏存储元素数量，即O(w)

订正

核心全部正确。w 是最大层宽，h 是树高。n > 1 时 BFS 也可能 O(1)，例如退化为链表的二叉树，因为每层只有一个节点；并非节点多就必然需要宽队列。

四、Go Stage 1｜sql.Result 与 RowsAffected

4.1 Exec 的返回值

result, err := db.Exec(
    "UPDATE students SET age = ? WHERE id = ?",
    22,
    1002,
)

result：类型 sql.Result，包含写操作的执行结果信息。

err：执行过程中有无数据库错误。

result.RowsAffected()：返回 (int64, error)，表示驱动报告的受影响行数。要检查它自身的错误。

result.LastInsertId()：在支持的驱动中取得插入标识；具体语义依驱动和数据库而定。

err == nil 不意味着一定有记录被更改或删除。 如 DELETE ... WHERE id = 9999 可正常执行，而受影响行数为 0。

if err != nil { return err }
if affected == 0 {
    // 例如按主键删除时，表示没有匹配的学生
}

面试专用回答

写操作首先检查 Exec 返回的错误，再检查 RowsAffected 是否可获取及影响行数；当受影响行数是 0 时，要结合 SQL 及业务语义区分“无匹配记录”和真正的数据库执行异常。

package main

import "database/sql"

type Student struct {
    ID   int
    Name string
    Age  int
}

type StudentRepository struct {
    db *sql.DB
}

func NewStudentRepository(db *sql.DB) *StudentRepository {
    return &StudentRepository{db: db}
}

func (r *StudentRepository) GetByID(id int) (Student, error) {
    var student Student
    err := r.db.QueryRow(
        "SELECT id, name, age FROM students WHERE id = ?",
        id,
    ).Scan(&student.ID, &student.Name, &student.Age)
    if err != nil {
        return Student{}, err
    }
    return student, nil
}

func (r *StudentRepository) List() ([]Student, error) {
    rows, err := r.db.Query(
        "SELECT id, name, age FROM students ORDER BY id",
    )
    if err != nil {
        return nil, err
    }
    defer rows.Close()

    students := make([]Student, 0)
    for rows.Next() {
        var student Student
        if err := rows.Scan(
            &student.ID, &student.Name, &student.Age,
        ); err != nil {
            return nil, err
        }
        students = append(students, student)
    }
    if err := rows.Err(); err != nil {
        return nil, err
    }
    return students, nil
}

func (r *StudentRepository) Create(student Student) error {
    _, err := r.db.Exec(
        "INSERT INTO students (id, name, age) VALUES (?, ?, ?)",
        student.ID, student.Name, student.Age,
    )
    return err
}

func (r *StudentRepository) Update(student Student) (int64, error) {
    result, err := r.db.Exec(
        "UPDATE students SET name = ?, age = ? WHERE id = ?",
        student.Name, student.Age, student.ID,
    )
    if err != nil {
        return 0, err
    }
    return result.RowsAffected()
}

func (r *StudentRepository) Delete(studentID int) (int64, error) {
    result, err := r.db.Exec(
        "DELETE FROM students WHERE id = ?",
        studentID,
    )
    if err != nil {
        return 0, err
    }
    return result.RowsAffected()
}

5.4 检查 4｜Update/Delete 返回值与 WHERE

问题

为什么 Update 返回 (int64,error)？

更新不存在的学生为什么可能 err=nil、受影响 0 行？

为什么 UPDATE/DELETE 必须小心 WHERE？

我的回答（原文）

为什么这次不再只返回 error，而是返回 (int64, error)？因为这次需要知道受到影响的行数，调用的RowsAffected返回值即(int64, error)

当修改一个不存在的学生时，为什么 Exec() 可能返回 nil 错误，而 RowsAffected() 返回 0？因为本身SQL语句执行成功，修改一个不存在的学生在SQL语句执行层面也算成功，修改一个不存在的学生等于修改0个学生成功。所以RowsAffected()返回 0，nil,受到影响的记录行数为0

为什么执行 UPDATE 和 DELETE 时尤其需要注意 WHERE 条件？因为不加where字段判断条件的话，UPDATE和DELETE会在数据库中的所有记录上执行，造成毁灭性的错误。

订正

三问全部正确。注意 WHERE 在语法上不是强制的，但根据 ID 修改/删除时必须正确提供业务条件。受影响 0 行在当前按主键操作示例中代表没有匹配的目标，并非执行异常。

相关示例

-- 只针对目标学生
UPDATE students SET age = 20 WHERE id = 1002;
DELETE FROM students WHERE id = 1002;

-- 危险：可能影响全表
UPDATE students SET age = 20;
DELETE FROM students;

面试专用回答

Update 和 Delete 使用 Exec 执行写操作，先检查错误，再通过 RowsAffected 获取影响行数，可以返回 (int64,error) 给调用者。若 WHERE 没有匹配记录，SQL 可以成功但影响 0 行；若遗漏 WHERE 则有误改、误删全表的风险。

5.5 检查 5｜CRUD / API / 数据库生命周期

问题

五个 Repository 方法对应哪些 CRUD？

为什么查询使用 Query/QueryRow，普通写操作使用 Exec？

:memory: 和 students.db 有什么不同？

我的回答（原文）

它们分别对应 CRUD 中的什么操作？Create()对应增，Delete()Delete()对应删，Update()对应改，GetByID()和List()对应查，总体就是增删改查。

为什么 GetByID() 和 List() 使用查询 API，而 Create()、Update()、Delete() 通常使用 Exec()？因为一般GetByID() 和 List()需要返回单行或多行结果集，而Create()、Update()、Delete()`通常不需要返回结果集。

当前 :memory: 数据库与之前文件型 students.db 有什么区别？前者是内存型数据库，生命周期绑定程序的生命周期，程序结束后就会被销毁，程序启动则会重新创建，而后者是文件型数据库，其生命周期实现了持久化，数据一般保存在硬盘内存中，不会随着程序的关闭而被销毁，且其他程序也可以共同访问该数据库，实现了数据的持久化。

订正

CRUD 对应关系和数据库 API 选择均正确。需要精确两处：

“硬盘内存”应改为磁盘存储（SSD/硬盘），不要与内存 RAM 混淆。

:memory: 数据库的生命周期依赖对应的 SQLite 底层连接，不只是抽象地依赖程序进程；每个新底层连接的 :memory: 通常是独立数据库。文件型 SQLite 使用磁盘文件保存数据，多进程可以访问，但并发写入受锁与事务限制。

补充：有些数据库支持写入语句 ... RETURNING ...，需要获取返回行时可能选用 Query/QueryRow；但当前 CRUD 例子中选用 Exec 完全恰当。

相关示例

// 内存型数据库：适合隔离、重复运行的教学实验
db, err := sql.Open("sqlite3", ":memory:")

// 文件型数据库：程序结束后仍可保留数据
db, err := sql.Open("sqlite3", "students.db")

面试专用回答

CRUD 分别对应 Create/Read/Update/Delete。普通 SELECT 通过 QueryRow/Query 读取单行/多行，普通 INSERT/UPDATE/DELETE 通常使用 Exec。SQLite :memory: 把数据库保存在内存中，与创建它的底层连接生命周期相关；文件型 SQLite 则通过磁盘数据库文件实现数据持久化。
