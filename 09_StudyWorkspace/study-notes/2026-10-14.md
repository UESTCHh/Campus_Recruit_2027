# 二、C++ Day40：递归与二叉树

## 2.1 二叉树的递归结构

一棵非空二叉树由 **根节点 + 左子树 + 右子树** 组成；左右子树仍然是二叉树，因此可以重复使用同一处理函数。

```text
        1
       / \
      2   3
     / \
    4   5
```

```cpp
void preorder(TreeNode* root) {
    if (root == nullptr) return; // 空子树是递归终止条件
    std::cout << root->val << ' ';  // 根
    preorder(root->left);          // 左子树：处理的是整棵左子树
    preorder(root->right);         // 右子树
}
```

- **前序**：根 → 左 → 右；上述树输出 `1 2 4 5 3`。
- **中序**：左 → 根 → 右；上述树输出 `4 2 5 1 3`。
- **后序**：左 → 右 → 根；上述树输出 `4 5 2 3 1`。
- 递归时间复杂度均为 **O(n)**，辅助栈空间为 **O(h)**（`h` 为树高）；最坏退化链为 O(n)，平衡树一般为 O(log n)。

### C++ Stage 1 检查 1：为什么适合递归？

**问题**：为什么二叉树天然适合递归？从树的结构与子树关系回答。

**我的回答（原文）**：

> 二叉树的结构即根节点+左子树+右子树天然适合递归，访问根节点的左子树或右子树时处理方式跟访问整颗二叉树的处理方式一样，故可以使用递归调用。

**订正**：✅ 正确。重要的是左右子树仍符合相同的二叉树定义；函数的职责是“处理以传入节点为根的整棵树”，而不仅处理单个孩子节点。

**相关示例**：`preorder(root->left)` 会完整处理左子树中所有节点，而不只打印左孩子本身。

**面试专用回答**：二叉树具有天然的递归定义：由根节点、左子树和右子树组成，左右子树又是二叉树。因此可将处理整棵树的问题拆成当前节点与左右子树的同类子问题。

### C++ Stage 1 检查 3：递归空指针判断

**问题**：为什么在 `preorder(TreeNode* root)` 开头写 `if (root == nullptr) return;`？

**我的回答（原文）**：

> 因为需要首先判断节点是否为空，即判断传进来的树是否为空树，否则就会访问空节点即无效对象，造成未定义行为，产生不可预期的结果。

**订正**：✅ 正确，并补充两层意义：①防止访问空指针；②作为递归边界，使叶子的空孩子分支返回上一层。

**相关示例**：`preorder(root->left)` 传入 `nullptr` 时立即 `return`；否则执行 `root->val` 将发生未定义行为。

**面试专用回答**：空节点是二叉树遍历的递归终止条件。先判断 `root == nullptr`，既避免空指针解引用，也确保递归可以正确结束。

## 2.2 二叉树递归遍历完整实验

**文件**：`day40-binary-tree-traversal/tree_traversal_demo.cpp`

```cpp
#include <iostream>

struct TreeNode {
    int val;
    TreeNode* left;
    TreeNode* right;
    explicit TreeNode(int x) : val(x), left(nullptr), right(nullptr) {}
};

void preorder(TreeNode* root) {
    if (root == nullptr) return;
    std::cout << root->val << ' ';
    preorder(root->left);
    preorder(root->right);
}

void inorder(TreeNode* root) {
    if (root == nullptr) return;
    inorder(root->left);
    std::cout << root->val << ' ';
    inorder(root->right);
}

void postorder(TreeNode* root) {
    if (root == nullptr) return;
    postorder(root->left);
    postorder(root->right);
    std::cout << root->val << ' ';
}

int main() {
    TreeNode n1(1), n2(2), n3(3), n4(4), n5(5);
    n1.left = &n2;
    n1.right = &n3;
    n2.left = &n4;
    n2.right = &n5;

    TreeNode* root = &n1;
    std::cout << "Preorder: "; preorder(root); std::cout << '\n';
    std::cout << "Inorder: "; inorder(root); std::cout << '\n';
    std::cout << "Postorder: "; postorder(root); std::cout << '\n';
}
```

## 2.3 LeetCode 104：二叉树最大深度

**问题**：以节点数计数，最长的根到叶路径包含多少节点？

```text
        3
       / \
      9   20
         /  \
        15   7
```

答案为 **3**。

**函数定义**：`maxDepth(root)` 返回以 `root` 为根的二叉树最大深度。

**递归边界**：空树不包含节点，返回 0。

**递归转移**：

```cpp
return 1 + std::max(maxDepth(root->left), maxDepth(root->right));
```

其中 `1` 是当前根节点贡献的一层；最大深度必须选择左右子树较深的一侧。

**复杂度**：访问每个节点一次，时间 **O(n)**；递归栈 **O(h)**，最坏 O(n)。

### C++ Stage 2 检查 4：为什么可以对左右子树调用同一函数？

**我的回答（原文）**：

> 因为root->left和root->right这两颗子树同样跟整颗二叉树一样具有相同的结构，也是一颗二叉树，当然可以和整颗树一样用同样的处理方式计算树的深度。

**订正**：✅ 正确。`maxDepth(root->left)` 表示左子树的**最大深度**，并非只测量左孩子一个节点。

**相关示例**：对根节点 3，其左子树深度为 1，右子树深度为 2，因此整体深度 `1 + max(1, 2) = 3`。

**面试专用回答**：函数定义为返回以当前节点为根的二叉树最大深度。左右子树自身也是二叉树，所以可以递归调用同一函数求左右子树深度，再通过当前节点合并答案。

### C++ Stage 2 检查 5：空树深度为什么是 0？

**我的回答（原文）**：

> 因为空树代表当前树没有节点，连树的根节点都没有，整棵树为空，当然深度应该定义为0

**订正**：✅ 正确。此处采用“沿最长根到叶路径的节点数”定义：空树深度 0，单节点树深度 1。

**相关示例**：只有根节点 8 的树，左右子树为空，深度 `1 + max(0,0) = 1`。

**面试专用回答**：当最大深度定义为根到叶最长路径的节点数时，空树不包含节点，深度为 0，这同时为递归提供正确的基本情况。

### C++ Stage 2 检查 6：公式中的 1 表示什么？

**我的回答（原文）**：

> 1代表当前树的根节点拥有的深度，即当前树不包括左右子树的纯深度，因为只有1个节点且一个节点占一层，所以深度为1

**订正**：✅ 正确，推荐简化表述为“当前根节点本身贡献的一层”。

**相关示例**：节点 9 的深度 `1 + max(0,0) = 1`，上层节点 3 再把自身的一层加进去。

**面试专用回答**：递归分别求得左右子树最大深度，选取其中较大值，再加上当前节点贡献的一层，因此返回 `1 + max(leftDepth, rightDepth)`。

### C++ 易错点

1. 一次递归调用处理的是一棵子树，而非仅一个孩子节点。
2. 空指针检查既是安全性检查，也是递归终止条件。
3. 递归栈空间是 O(h)，不是一概 O(1)。
4. 原课堂示例中直接 `new` 节点而未 `delete`，作为独立程序虽然退出时操作系统一般回收进程内存，但仍不应在可复用工程代码中保留这种资源管理缺陷；上方本地示例已修正。
5. **最小深度不能无条件套 `1 + min(left, right)`**：若某节点只有一个非空孩子，空孩子深度为 0，但最短根到**叶**路径必须沿着存在的孩子走。这是以后学最小深度时需特别区分的点。

## 3.2 从 Day39 普通函数到 Repository

Day39：

```go
func findStudentByID(db *sql.DB, studentID int) (Student, error)

```

Day40：

```go
type StudentRepository struct { db *sql.DB }

func NewStudentRepository(db *sql.DB) *StudentRepository {
    return &StudentRepository{db: db}

func (r *StudentRepository) GetByID(studentID int) (Student, error) { /*...*/ }

repo := NewStudentRepository(db)
```

`r` 是类型为 `*StudentRepository` 的方法接收者变量。Repository 保存外部的 `*sql.DB`，方法通过 `r.db` 复用数据库连接池管理对象。

### Go Stage 1 检查 1：Repository 保存什么？

**我的回答（原文）**：

> 1. `db *sql.DB` 保存的是什么？保存的是数据库连接池管理对象的指针
> 2. 为什么 Repository 要持有它？这样将其封装此结构中，作为Repository的结构体对象就可以直接调用它，而不用每次传入该参数。
> 3. 创建多个 `StudentRepository` 对象，是否就一定创建了多个底层数据库连接？不一定，都是复用同一个数据库连接池管理对象，只有在方法中真正进行数据库操作时才会创建数据库连接。

**订正**：✅ 基本完全正确；多个 Repository **仅在传入同一个 `*sql.DB` 时共享同一管理对象**。同一 `*sql.DB` 可以根据需要管理多个底层连接。`sql.Open` 本身不必立即建立连接。

**相关示例**：`repo1 := NewStudentRepository(db); repo2 := NewStudentRepository(db)`，二者共享同一个 db；若分别调用 `sql.Open`，则可能是不同的管理对象。

**面试专用回答**：Repository 持有外部注入的 `*sql.DB`，便于在多个方法间共享应用级连接池管理对象。底层连接由 `database/sql` 按需创建、复用及管理，不等于 Repository 对象数量。

### Go Stage 1 检查 2：方法接收者

**我的回答（原文）**：

> 1. `(r *StudentRepository)` 表示什么？当前方法的接收方是StudentRepository，即该方法属于StudentRepository，可以通过r.GetByID()调用该函数
> 2. 为什么方法内部能够使用 `r.db.QueryRow()`？因为db已经是r这个结构体的一个结构体成员了，并且在创建对象时，已经把之前创建好的共享数据库连接池管理对象赋值给了它，所以可以直接使用它。
> 3. 相比 Day39 的普通函数，调用方式发生了什么变化？Day39调用是用的findStudentByID(db, id)，每次调用都要传入db,而今天调用的是repo.GetByID(id)，只在创建 Repository 时传入一次

**订正**：✅ 完全正确。`r` 是接收者变量，`*StudentRepository` 是接收者类型；通过 `r.db` 可访问保存的依赖。实际调用用 `repo.GetByID(id)`，示例的 `r` 只是方法内部变量名。

**相关示例**：`repo := NewStudentRepository(db); student, err := repo.GetByID(1002)`。

**面试专用回答**：Go 使用方法接收者给结构体定义方法。把 DB 依赖注入 Repository 后，Repository 方法可以通过接收者访问它，而无须每次调用都传入数据库对象。

### Go Stage 1 检查 3：为什么不能在方法中关闭 DB？

**我的回答（原文）**：

> 因为数据库层只负责管理相关的数据库操作，不负责关闭数据库管理对象相关资源，数据库管理对象相关资源应在应用程序启动阶段创建，关闭阶段销毁

**订正**：✅ 正确。`db.Close()` 关闭整个 `sql.DB` 管理对象，放在 `GetByID()` 内会影响后续查询；而 `rows.Close()` 只关闭本次多行查询结果集，两者职责不同。

**相关示例**：在 `main()` 中 `defer db.Close()`；在 `List()` 中，`rows, err := r.db.Query(...)` 成功后 `defer rows.Close()`。

**面试专用回答**：`*sql.DB` 是应用级共享依赖，生命周期由应用入口和关闭流程管理；Repository 不应在单次方法调用中关闭它。但 Repository 创建的查询结果集等局部资源必须及时释放。

## 3.3 Go Stage 2：List 查询多行与资源管理

`GetByID(id) (Student, error)` 适合单条查询；`List() ([]Student, error)` 适合多条查询。

**单条查询**：

```go
err := r.db.QueryRow("SELECT id, name, age FROM students WHERE id = ?", studentID).
    Scan(&student.ID, &student.Name, &student.Age)
```

- `QueryRow` 返回 `*sql.Row`。
- `Scan` 读取首行并返回延迟错误；查无此行返回 `sql.ErrNoRows`。
- **`*sql.Row` 不提供 `Close()`；`Scan()` 在内部关闭结果集**。应及时调用 `Scan()`，不能创建 `Row` 后不处理。

**多条查询**：

```go
rows, err := r.db.Query("SELECT id, name, age FROM students ORDER BY id")
if err != nil { return nil, err }
defer rows.Close()

students := make([]Student, 0)
for rows.Next() {
    var s Student
    if err := rows.Scan(&s.ID, &s.Name, &s.Age); err != nil {
        return nil, err
    }
    students = append(students, s)
}
if err := rows.Err(); err != nil { return nil, err }
return students, nil
```

- `Query` 返回 `(*sql.Rows, error)`。
- `Next()` 逐行推进，`Scan()` 将当前行字段写入变量，`Err()` 检查迭代错误。
- `defer rows.Close()` 保障提前退出时也释放查询结果资源。正常遍历至结束时 `database/sql` 通常会自动关闭，但仍推荐显式 `defer`。
- 查询成功但**零行**：本实现返回 `[]Student{}` 与 `nil`，而不是 `sql.ErrNoRows`。

### Go Stage 2 检查 1：List 为什么返回切片？

**我的回答（原文）**：

> 1. 为什么返回 `[]Student`，而不是 `Student`？因为可能要返回多个学生的记录，用单个结构体变量不够，得用切片接收多个变量值
> 2. 为什么还要返回 `error`？因为Query()多行查询同样可能出现数据库连接失败、执行错误或读取结果失败。
> 3. 如果表中没有任何学生，`List()` 应该如何返回？这是否等于 `sql.ErrNoRows`？返回空切片和nil，和`sql.ErrNoRows`不一样。`Query()` 成功但表中没有学生时，`List()` 可以返回空切片和 `nil` 错误。这和 `QueryRow()` 查询不到记录时返回 `sql.ErrNoRows` 不一样。

**订正**：✅ 三问正确。函数使用 `students := make([]Student, 0)`，所以零记录时返回非 nil 的空切片；调用者检查长度为 0 即可。

**相关示例**：`students, err := repo.List(); if err == nil { fmt.Println(len(students)) }`，空表输出 0。

**面试专用回答**：多行查询返回结构体切片和 error，保存多条记录并报告查询/读取异常。成功执行但无匹配行通常返回空集合和 nil；与 `QueryRow().Scan()` 的 `sql.ErrNoRows` 区分。

### Go Stage 2 检查 2：Rows 的生命周期

**我的回答（原文）**：

> 1. 为什么这里需要 `defer rows.Close()`？因为Query()会产生Rows资源需要释放
> 2. 为什么不能替换成 `defer r.db.Close()`？因为数据库连接池管理对象的资源不应在数据库层创建和释放，应当放在应用启动和关闭阶段管理，否则一次查询就会关闭数据库连接，后续数据库操作则无法继续复用，导致操作失败
> 3. 如果查询结果有多行，为什么需要 `rows.Next()` 和 `rows.Scan()` 配合？
>
> 因为`rows.Next()`可以逐行遍历结果记录，而`rows.Scan()`可以将遍历得到的每行记录转换成Go需要的结果变量。

**订正**：✅ 三问正确。精准描述：`Next()` 移动到下一行并准备读取，`Scan()` 将当前行对应列写入目标；最后还应检查 `rows.Err()`。

**相关示例**：`rows, err := db.Query(...); if err != nil { ... }; defer rows.Close(); for rows.Next() {...}; if err := rows.Err(); err != nil {...}`。

**面试专用回答**：`Rows` 是一次查询结果集，调用者应及时关闭；`Next` 逐行推进，`Scan` 读入变量，`Err` 检查遍历错误。`db.Close()` 则关闭整个数据库管理对象，不是结果集释放的替代品。

### Go Stage 2 检查 3：Repository 方法的职责

**我的回答（原文）**：

> 1. 两个方法各自负责什么？前者负责查询单个学生的记录，后者负责查询全部学生的记录
> 2. 为什么两个方法可以共享同一个数据库连接池管理对象？因为两个方法均属于结构体Repository，而数据库依赖的数据库连接池管理对象已经被赋值给了结构体Repository的结构体变量db，故两个方法均可以使用内部的结构体变量db，共享同一个数据库连接池管理对象
> 3. 以后需要新增学生时，你认为可以给 `StudentRepository` 增加一个什么方法？它大致应该负责什么？Input()方法，大致应该负责传入一条学生记录的所以信息参数，并且在内部调用db的新增数据记录的Sql方法（使用Insert Into）新增一条学生记录。

**订正**：✅ 前两问正确，第三问设计思路正确；推荐将 `Input()` 命名为 `Create()` 或 `Insert()`，更准确体现数据库新增操作。普通 `INSERT INTO` 不返回行集时使用 `db.Exec()` 更合适。

**相关示例（预习，不属于 Day40 必做）**：

```go
    _, err := r.db.Exec(
        "INSERT INTO students (id, name, age) VALUES (?, ?, ?)",

```

**面试专用回答**：Repository 封装数据持久化操作，`GetByID` 查单条、`List` 查多条、`Create` 新增、`Update` 修改、`Delete` 删除。通过共享的 `*sql.DB` 执行数据库操作，提高复用性和可维护性。

### 额外追问：为什么 QueryRow 不用 defer Close？

**我的问题（原文）**：

> Query()会产生Rows资源需要释放，那么QueryRow()就不会产生相关资源吗？我看没有对应的defer close等操作

**订正 / 解释**：`QueryRow()` 同样涉及底层查询资源，但其 `*sql.Row` 的 `Scan()` 负责消费第一条记录和关闭内部查询结果集；没有向外暴露的 `row.Close()` 方法。`Query()` 返回 `*sql.Rows`，调用者可以自己遍历/中止，通常在取得 `Rows` 后 `defer rows.Close()`。**不要调用 `QueryRow()` 后长期不 `Scan()`**；`QueryRow` 的错误也会在 `Scan` 阶段体现。

**相关示例**：

```go
// 单行，调用 Scan 完成读取及资源清理
err := db.QueryRow("SELECT name FROM students WHERE id = ?", 1002).Scan(&name)

// 多行，必须处理查询结果集生命周期
rows, err := db.Query("SELECT name FROM students")
if err != nil { return err }
defer rows.Close()
```

**面试专用回答**：`QueryRow` 返回 `*sql.Row`，由 `Scan` 读取首行并清理内部结果集，因此不需要手动关闭 Row；`Query` 返回需要遍历的 `*sql.Rows`，调用者应及时 `Close` 并检查迭代错误。两者都需要正确处理数据库操作错误。

## 3.4 Go 可运行代码：repository.go

**文件**：`day40-go-repository/repository.go`

```go
package main

import "database/sql"

type Student struct {
    ID   int
    Name string
    Age  int
}

type StudentRepository struct {
    db *sql.DB
}

func NewStudentRepository(db *sql.DB) *StudentRepository {
    return &StudentRepository{db: db}
}

func (r *StudentRepository) GetByID(studentID int) (Student, error) {
    var student Student
    err := r.db.QueryRow(
        "SELECT id, name, age FROM students WHERE id = ?", studentID,
    ).Scan(&student.ID, &student.Name, &student.Age)
    if err != nil {
        return Student{}, err
    }
    return student, nil
}

func (r *StudentRepository) List() ([]Student, error) {
    rows, err := r.db.Query(
        "SELECT id, name, age FROM students ORDER BY id",
    )
    if err != nil {
        return nil, err
    }
    defer rows.Close()

    students := make([]Student, 0)
    for rows.Next() {
        var student Student
        if err := rows.Scan(&student.ID, &student.Name, &student.Age); err != nil {
            return nil, err
        }
        students = append(students, student)
    }
    if err := rows.Err(); err != nil {
        return nil, err
    }
    return students, nil
}
```

## 二、C++ 加练：LeetCode 104 二叉树的最大深度

### 练习 1：独立实现递归算法

#### 1. 问题

不参考之前的示例代码，独立实现：

```cpp
int maxDepth(TreeNode* root);
```

同时回答：

- 算法的时间复杂度是多少？
- 算法的空间复杂度是多少？
- 为什么可以使用递归解决？

#### 2. 我的原始回答

独立实现的代码：

```cpp
int maxDepth(TreeNode* root){
    if(!root) return 0;
    return 1 + max(maxDepth(root->left), maxDepth(root->right));	
}
```

复杂度与原理分析：

> 时间复杂度：O(n)
>
> 空间复杂度：O(1)
>
> 为什么递归成立：因为左子树和右子树具有和以root为根节点的二叉树同样的结构，都是根节点+左子树+右子树，所以可以用同样的逻辑求左子树和右子树的深度

#### 3. 订正

**（1）递归代码：正确。**

算法包含两个部分。

首先，设置递归终止条件：

```cpp
if (root == nullptr) {
    return 0;
}
```

空树没有节点，最大深度为 0。

其次，递归求出左右子树的最大深度：

```cpp
maxDepth(root->left);
maxDepth(root->right);
```

然后使用：

```cpp
1 + max(leftDepth, rightDepth);
```

计算当前整棵树的最大深度。

其中：

- `leftDepth`：左子树最大深度。
- `rightDepth`：右子树最大深度。
- `max()`：选择较深的那棵子树。
- `1`：当前根节点贡献的一层深度。

**（2）时间复杂度：O(n)，正确。**

递归过程中，每个节点只访问一次。

假设二叉树有 n 个节点，则需要处理 n 个节点，因此时间复杂度为：

**O(n)**

**（3）空间复杂度：O(1)，错误，需要订正。**

这是本次加练最重要的错误。

虽然代码没有显式创建数组、栈、队列等数据结构，但是递归调用本身需要使用函数调用栈。

例如：

```cpp
maxDepth(root->left);
```

每进行一次递归调用，系统都需要保存当前函数的执行状态。

递归深入多少层，调用栈就可能增长多少层。

因此：

**空间复杂度为 O(h)，其中 h 表示二叉树的高度。**

不同树形下：

| 二叉树结构 | 树高 | 空间复杂度 |
|---|---|---|
| 平衡二叉树 | O(log n) | O(log n) |
| 普通二叉树 | h | O(h) |
| 最坏情况：退化为链表 | O(n) | O(n) |

需要牢记：

**没有显式创建容器，不代表算法的空间复杂度就是 O(1)。递归调用栈同样属于额外空间。**

#### 4. 相关示例

考虑一棵退化为链表的二叉树：

```text
1
 \
  2
   \
    3
     \
      4
```

递归调用过程：

```text
maxDepth(1)
    |
    v
maxDepth(2)
    |
    v
maxDepth(3)
    |
    v
maxDepth(4)
    |
    v
maxDepth(nullptr)
```

递归进入下一层时，上一层函数尚未完成返回。

系统需要保存这些函数调用的信息。

所以这棵树的递归栈深度与节点数量成正比。

当树有 n 个节点且退化为链表时，额外空间复杂度达到 O(n)。

#### 5. 最终正确代码

```cpp
class Solution {
public:
    int maxDepth(TreeNode* root) {
        if (root == nullptr) {
            return 0;
        }

        return 1 + max(
            maxDepth(root->left),
            maxDepth(root->right)
        );
    }
};
```

说明：LeetCode 提供 `TreeNode` 定义，提交时只需要按照平台要求实现 `Solution`。

#### 6. LeetCode 提交结果

**题目：** LeetCode 104 — 二叉树的最大深度（Maximum Depth of Binary Tree）

**完成方式：** 独立编写递归解法。

**提交状态：Accepted（已通过）。**

**时间复杂度：O(n)。**

**空间复杂度：O(h)。**

本次提交说明已经能够独立使用二叉树递归思想解决最大深度问题。

需要继续巩固的是复杂度分析，尤其是递归调用栈的空间开销。

#### 7. 面试专用回答

> 二叉树的最大深度可以通过递归求解。首先判断当前节点是否为空，若为空则返回 0；否则递归求出左右子树的最大深度，再取两者的较大值并加上当前节点贡献的一层。由于每个节点只访问一次，时间复杂度为 O(n)。递归调用栈的最大深度等于树高，因此空间复杂度为 O(h)，平衡二叉树为 O(log n)，最坏情况下为 O(n)。

### 练习 2：手动推导递归过程

#### 1. 问题

给定二叉树：

```text
        1
       / \
      2   3
     /
    4
```

手动推导：

```cpp
maxDepth(root);
```

的递归计算过程，最终求出整棵树的最大深度。

#### 2. 我的原始回答

```text
maxDepth(1)

= 1 + max(
    maxDepth(2),
    maxDepth(3)
)

maxDepth(2)

= 1 + max(
    maxDepth(4),
    0
)

maxDepth(4) = 1 + max(0,0) = 1

maxDepth(3) = 1 + max(0,0) = 1

maxDepth(2) = 1 + max(1, 0) = 2

maxDepth(1)

= 1 + max(
    2,
    1
) = 1 + 2 = 3
```

#### 3. 订正

**完全正确。**

已经能够理解递归的两个过程：

**向下递归：不断拆分问题。**

```text
maxDepth(1)
    |
    +-- maxDepth(2)
    |       |
    |       +-- maxDepth(4)
    |
    +-- maxDepth(3)
```

**向上返回：逐层计算结果。**

```text
maxDepth(4) = 1
       |
       v
maxDepth(2) = 2

maxDepth(3) = 1

       |
       v
maxDepth(1) = 1 + max(2, 1)
            = 3
```

所以这棵二叉树的最大深度为：

**3**

#### 4. 相关示例

对于叶子节点 4：

```cpp
maxDepth(4)
= 1 + max(0, 0)
= 1;
```

对于节点 2：

```cpp
maxDepth(2)
= 1 + max(1, 0)
= 2;
```

对于根节点 1：

```cpp
maxDepth(1)
= 1 + max(2, 1)
= 3;
```

这说明递归算法不需要提前知道整棵树的深度，而是通过子问题的返回值逐步计算最终答案。

#### 5. 面试专用回答

> 二叉树递归会将当前问题拆分为左右子树的同类问题。递归向下直到遇到空节点，返回深度 0，再由叶子节点向上逐层计算，每一层取左右子树深度的最大值加 1，最终得到整棵二叉树的最大深度。

## 四、Go 后端面试表达训练

### 面试题 1：为什么不推荐在 Handler 中直接写 SQL？

#### 1. 问题

在实际 Go 后端项目中，为什么通常不建议将数据库 SQL 查询代码直接放进 HTTP Handler？

#### 2. 我的原始回答

> Handler主要负责HTTP层请求处理，并调用业务处理逻辑层Service，而Service又调用Repository层，真正的SQL语句执行在数据库Repository层，这样使不同层功能清晰划分，将功能解耦，使得后端这种分层设计让业务逻辑和数据访问分离，提高代码维护性和测试性

#### 3. 订正

回答正确。

已经能够区分：

**Handler：**

- 解析 HTTP 请求。
- 获取请求参数。
- 调用业务逻辑。
- 设置 HTTP 状态码。
- 返回 JSON 响应。

**Service：**

- 执行业务规则。
- 组织业务处理流程。
- 调用 Repository。
- 根据业务需求处理相关错误。

**Repository：**

- 执行 SQL。
- 操作数据库。
- 保存或查询数据。
- 返回数据访问结果。

需要注意，简单项目不一定需要强制引入完整三层，分层的目的应当是降低耦合，而不是单纯增加代码文件数量。

#### 4. 相关示例

```text
HTTP GET /students/1002
           |
           v
Handler
  解析请求参数
           |
           v
Service
  处理学生查询业务
           |
           v
Repository
  执行 SELECT SQL
           |
           v
Database
```

#### 5. 面试专用回答

> Handler 应当主要负责 HTTP 请求解析和响应，而 Service 负责业务逻辑，Repository 负责数据库访问。如果直接在 Handler 中写 SQL，会使 HTTP 层与数据持久化实现耦合，降低代码复用性和可维护性。合理的分层设计可以让职责更加清晰，也更方便测试和后续扩展。

### 面试题 2：为什么不为每个请求创建一个新的 `sql.DB`？

#### 1. 问题

为什么 Go 后端程序通常在应用启动时创建一个可共享的 `*sql.DB`，而不是每处理一次 HTTP 请求就重新创建？

#### 2. 我的原始回答

> 因为sql.DB是数据库连接池管理对象，不是一个数据库连接，而是管理数据库连接的，这个对象可以被不同的请求共享，当不同的请求需要一个数据库连接时，该对象就会动态创建一个数据库连接给请求使用，使用完毕后再归还给该对象供其他请求复用，所以不需要每个请求都创建一个数据库连接池管理对象，只在应用启动阶段创建一次就够了。

#### 3. 订正

核心回答正确。

需要进一步准确区分：

**`*sql.DB` 不是单个数据库连接，而是并发安全的数据库连接池管理对象。**

不过实际执行数据库请求时，不一定每次都创建新连接。

通常：

1. 优先复用可用的空闲连接。
2. 如果没有可用连接，并且配置允许，可以创建新的底层连接。
3. 如果连接数量达到上限，后续操作可能等待连接可用。
4. 数据库操作完成后，底层连接可以返回池中供其他操作复用。

因此，应当避免表述为“每次请求都创建一个新连接”。

#### 4. 相关示例

```text
             *sql.DB
                |
        数据库连接池管理
                |
       +--------+--------+
       |        |        |
      连接1    连接2    连接3
       |        |        |
      请求A    请求B    请求C
```

多个 Repository 也可以共享同一个 `*sql.DB`：

```go
db, err := sql.Open("sqlite3", dbPath)
if err != nil {
    log.Fatal(err)
}
defer db.Close()

studentRepo := NewStudentRepository(db)
```

这样 Repository 不负责重新创建数据库管理对象。

#### 5. 面试专用回答

> `sql.DB` 是并发安全的数据库连接池管理对象，而非单个数据库连接。后端应用通常在启动时创建并共享它，数据库操作通过连接池按需获取或复用底层连接，避免重复创建数据库管理对象和不必要的连接开销。应用还可以配置最大连接数、空闲连接数和连接生命周期。

### 面试题 3：`Query()` 和 `QueryRow()` 的区别是什么？

#### 1. 问题

说明两者适用场景、返回类型、结果读取方式与资源管理的区别。

#### 2. 我的原始回答

> 前者用于查询多行数据，返回多行结果集，并且需要搭配Next()和Scan()遍历所有行记录，并且返回的结果集Rows需要在请求完毕后及时手动销毁相关资源
>
> 后者用于查询单条数据，返回一行记录，可以直接用Scan遍历该行记录，查询不到数据时返回sql.ErrNoRows，并且Scan会在内部自动销毁相关资源，所以不用手动管理相关资源。

#### 3. 订正

整体正确，主要需要规范术语。

`Query()`：

- 返回 `*sql.Rows` 和 `error`。
- 适合处理多条查询记录。
- 使用 `rows.Next()` 移动到下一行。
- 使用 `rows.Scan()` 读取当前行字段。
- 建议使用 `defer rows.Close()` 及时关闭结果集。
- 遍历结束后检查 `rows.Err()`。

`QueryRow()`：

- 返回 `*sql.Row`。
- 适合预期单条结果的查询。
- 使用 `row.Scan()` 读取第一条记录。
- 没有匹配记录时，`Scan()` 返回 `sql.ErrNoRows`。
- `Scan()` 会处理内部查询结果集的清理，因此不需要手动调用 `Close()`。

特别注意：

`QueryRow()` 并不是不需要任何资源管理，而是内部结果集的清理由 `Scan()` 完成。

因此调用 `QueryRow()` 后应当及时调用 `Scan()`。

#### 4. 相关示例

**查询多条记录：**

```go
rows, err := db.Query(
    "SELECT id, name, age FROM students",
)
if err != nil {
    return
}
defer rows.Close()

for rows.Next() {
    // 使用 rows.Scan() 读取当前行
}
```

**查询单条记录：**

```go
var student Student

err := db.QueryRow(
    "SELECT id, name, age FROM students WHERE id = ?",
    1002,
).Scan(
    &student.ID,
    &student.Name,
    &student.Age,
)
```

#### 5. 面试专用回答

> `Query()` 适用于多行查询，返回 `*sql.Rows` 和 error，需要通过 `Next()` 和 `Scan()` 遍历读取，并及时关闭结果集。`QueryRow()` 适用于单行查询，返回 `*sql.Row`，通过 `Scan()` 读取第一条结果。如果没有匹配记录，`Scan()` 会返回 `sql.ErrNoRows`，同时负责内部结果集的清理。
