Go Package 边界、import 与测试范围

1. Module 和 go.mod 是什么关系？
答：Module是由go.mod管理的一组go packages，一个module一般对应一个go.mod文件，go.mod代表Module的边界，一个项目可能有多个go.mod所以区分不同module的方法就是找各自的go.mod，并且不受内外层的影响。
2. 一个 Module 能不能包含多个 Package？
答：可以，只要在当前Module所属目录下的所有Package均属于该Module，当然也可以没有1个Package。 
3. Module 根目录一定有 Package 吗？
答：不一定，可能在当前根目录只有go.mod文件没有其他.go文件，这时没有Package。
4. 同一个 Package 中的两个 .go 文件为什么不用互相 import？ 
答：因为都属于同一个Package，属于同一个Package的不同.go文件即该Package的功能划分文件，它们共同组成这个Package，属于同一个工作区域。
5. go test . 中的 . 指什么？
答：代表当前目录下的Package，会构建该目录下的测试文件，并运行测试函数，看是否与预期结果相符。

6. go test ./... 和 go test . 最大区别是什么？
答：前者会查找当前目录及其子目录所有的Package，而后者只会查找当前目录所属Package，跳过了子目录。

## 5. exported / unexported 实验

将：

```go
func Add(a int, b int) int
临时改成：
func add(a int, b int) int
之后，main.go 仍然调用：
calculator.Add(10, 5)
得到：
undefined: calculator.Add
这直接说明 Add 这个标识符已经不存在，因为函数已经被重命名为 add。
calculator_test.go 与 add.go 同属于：
package calculator
因此将测试改为：
got := add(10, 5)
后测试能够通过。
Package 可见性
Add()
→ exported
→ 可以作为 calculator Package 的公开 API
→ 其他 Package 可以通过 calculator.Add(...) 使用

add()
→ unexported
→ calculator Package 内部实现
→ 其他 Package 不能直接使用
exported 的边界是 Package，而不是单个 .go 文件。
API 设计
如果一个函数只服务于当前 Package 内部实现，优先保持 unexported。
只有真正需要提供给其他 Package 使用的能力，才作为 exported API。
