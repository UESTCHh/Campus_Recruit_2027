# 四、Linked List / Stack / Queue 本质区别

## 1. Linked List

Linked List 描述数据的连接方式。

例如：

```text
1 -> 2 -> 3 -> nullptr
```

核心：

```text
节点
next指针
连接关系
```

适合：

- 节点插入、删除
- 反转链表
- 合并链表
- 调整节点顺序

链表本身不规定元素必须先进先出或后进先出。

## 2. Stack

Stack 描述元素访问规则：

```text
LIFO
Last In First Out
后进先出
```

例如：

```text
push 1
push 2
push 3

pop 3
pop 2
pop 1
```

适合：

- 括号匹配
- 撤销操作
- 最近尚未处理的对象
- 单调栈

## 3. Queue

Queue 描述元素访问规则：

```text
FIFO
First In First Out
先进先出
```

例如：

```text
push 1
push 2
push 3

pop 1
pop 2
pop 3
```

适合：

- 按顺序处理任务
- 请求排队
- 过期元素清理
- BFS

## 4. 关键区别

```text
Linked List
→ 数据如何连接

Stack
→ 后进先出

Queue
→ 先进先出
```

Stack、Queue 规定访问规则，但并不限定必须通过某一种底层数据结构实现。

# 五、三种数据结构行为实验

文件：

```text
data_structure_behavior_demo.cpp
```

完整代码：

```cpp
#include <iostream>
#include <stack>
#include <queue>

using namespace std;

struct ListNode {
    int value;
    ListNode* next;
};

int main() {
    // 1. 链表头插法
    ListNode* head = nullptr;

    for (int x : {1, 2, 3}) {
        head = new ListNode{x, head};
    }

    cout << "Linked List (push front): ";

    ListNode* cur = head;

    while (cur != nullptr) {
        cout << cur->value << ' ';
        cur = cur->next;
    }

    cout << '\n';

    // 释放链表内存
    while (head != nullptr) {
        ListNode* nextNode = head->next;
        delete head;
        head = nextNode;
    }

    // 2. Stack
    stack<int> st;

    for (int x : {1, 2, 3}) {
        st.push(x);
    }

    cout << "Stack pop order: ";

    while (!st.empty()) {
        cout << st.top() << ' ';
        st.pop();
    }

    cout << '\n';

    // 3. Queue
    queue<int> q;

    for (int x : {1, 2, 3}) {
        q.push(x);
    }

    cout << "Queue pop order: ";

    while (!q.empty()) {
        cout << q.front() << ' ';
        q.pop();
    }

    cout << '\n';

    return 0;
}
```

编译：

```powershell
g++ -std=c++17 -Wall -Wextra -pedantic data_structure_behavior_demo.cpp -o data_structure_behavior_demo.exe
```

运行：

```powershell
.\data_structure_behavior_demo.exe
```

预期：

```text
Linked List (push front): 3 2 1
Stack pop order: 3 2 1
Queue pop order: 1 2 3
```

虽然链表头插法和 Stack 的输出相同，但原因不同。

链表输出 `3 2 1` 是因为选择了头插法。

Stack 输出 `3 2 1` 是因为遵守 LIFO。

# 六、Stage 1 检查记录

## 检查 1：为什么 Linked List 不等于 Stack？

**我的回答：**

> 因为链表这里实现的是头插法，但是链表还可以使用尾插法，那遍历顺序就会变成和queue一样，所以链表不在乎数据的进出规则是什么，它在乎的是数据通过什么样的结构组织在一起，而stack是因为它的接口明确规定只能按后进先出的方式弹出。

**订正：**

正确。

链表关注节点连接方式，而 Stack 关注元素访问规则。

**相关示例：**

链表使用尾插法可得到：

```text
1 -> 2 -> 3
```

使用头插法则得到：

```text
3 -> 2 -> 1
```

但 Stack 的 pop 顺序必须遵循 LIFO。

**面试回答：**

> Linked List 描述数据之间的连接方式，而 Stack 描述元素的访问顺序。链表可以用来实现 Stack，但链表本身不具有后进先出的操作约束。

## 检查 2：括号匹配为什么适合 Stack？

**我的回答：**

> 选stack，因为其后进先出的语义正好匹配最近进入的对象优先处理的情况，每次遇到右括号就取出最新进入的左括号进行匹配。

**订正：**

正确。

**相关示例：**

```text
{[()]}
```

左括号进入顺序：

```text
{
[
(
```

匹配时优先处理：

```text
(
[
{
```

**面试回答：**

> 括号匹配要求最近出现但尚未匹配的左括号优先匹配，符合 Stack 的后进先出特性。

## 检查 3：严格按到达顺序处理任务

**我的回答：**

> Queue，因为其先进先出的语义正好匹配最先进入的对象优先处理的情况，每次取出最先进入的任务进行处理，即可实现依次到达的任务严格按照到达顺序处理

**订正：**

正确。

**相关示例：**

```text
A → B → C
```

Queue 的出队顺序仍然是：

```text
A → B → C
```

**面试回答：**

> 如果任务必须按照到达顺序处理，应使用 FIFO 的 Queue。

## 检查 4：节点插入删除

**我的回答：**

> 题目要求明确说了需要修改节点之间的连接关系，所以重点更偏向节点与指针关系，要确定每个节点的指针和下一个指针指向。

**订正：**

正确。

**相关示例：**

```text
1 -> 2 -> 3 -> 4
```

删除节点3，需要让节点2直接指向节点4。

**面试回答：**

> 链表节点插入和删除主要关注前驱、当前节点和后继节点之间的指针连接关系，而非数据的先进先出或后进先出规则。

# 七、Stack 复习：LeetCode 20 有效括号

题目：

给定：

```text
([{}])
```

判断括号是否有效。

核心：

```text
最近进入的未匹配左括号
必须最先进行匹配
```

选择：

```text
Stack
```

栈中存放：

```text
尚未匹配的左括号
```

## 检查 1

**我的回答：**

> 适合，因为最后进入的左括号需要最先被处理，符合stack后进先出的语义

**订正：** 正确。

**面试回答：**

> 括号嵌套需要优先匹配最近出现的左括号，因此选择后进先出的 Stack。

## 检查 2

**我的回答：**

> stack保存的是所有待处理的左括号，而不是整个字符串

**订正：** 正确。

**相关示例：**

```text
stack = ['(', '[', '{']
```

只保存等待匹配的左括号。

**面试回答：**

> 栈中保存尚未匹配的左括号，每遇到右括号就检查栈顶是否能与其匹配。

## 检查 3

**我的回答：**

```text
读取 (
stack = (

读取 [
stack = ( [

读取{
stack = ( [ {

读取}
匹配stack.top() = {
匹配成功，stack.pop()
stack = ( [

读取]
匹配stack.top() = [
匹配成功，stack.pop()
stack = (

读取}
匹配stack.top() = )
匹配成功，stack.pop()
stack = empty
```

**订正：**

最后一步存在括号符号错误。

原始输入是：

```text
([{}])
```

最后读到的应该是：

```text
)
```

而不是再次读取 `}`。

此时栈顶是：

```text
(
```

而不是 `)`。

正确过程：

```text
读取 ( → push
stack = (

读取 [ → push
stack = ( [

读取 { → push
stack = ( [ {

读取 } → 与 { 匹配，pop
stack = ( [

读取 ] → 与 [ 匹配，pop
stack = (

读取 ) → 与 ( 匹配，pop
stack = empty
```

**面试回答：**

> 遍历字符串，遇到左括号入栈；遇到右括号时检查栈顶左括号是否匹配，不匹配则返回 false。遍历结束后，只有栈为空才表示所有括号正确匹配。

## 检查 4

**我的回答：**

> Queue的语义是先进先出，即最先进入的对象优先被处理，而括号匹配问题必须从内部往外部逐层匹配，即最后进入的对象优先被处理，所以不适合用Queue而适合用后进先出语义的Stack

**订正：**

正确。

**面试回答：**

> Queue 会先处理最早进入的左括号，而嵌套括号要求优先处理最近进入的左括号，因此 Stack 更符合问题的访问顺序。

# 八、单调栈复习：LeetCode 739 每日温度

题目：

```text
temperatures =
[73,74,75,71,69,72,76,73]
```

对于每一天，寻找未来第一个更高温度，并返回需要等待的天数。

关键不是简单的 LIFO，而是：

```text
Stack保存尚未找到更高温度的日期下标
```

新温度到来时，可能解决多个历史日期。

## 检查 1

**我的回答：**

> 保存的是还未找到较高温度日期的日期下标

**订正：**

正确。

保存下标而不是温度本身，是因为最终要求：

```cpp
answer[oldIndex] = currentIndex - oldIndex;
```

**面试回答：**

> 单调栈中保存尚未找到下一个更高温度的日期下标，新温度到来时尝试解决栈顶等待的日期。

## 检查 2

**我的回答：**

> 还没有找到更高温度的日期
>
> 已经找到答案的日期应该及时出栈，栈中只保存未处理的对象

**订正：**

正确。

**相关示例：**

```text
73 → 74
```

当74出现时，73已经找到未来第一个更高温度，因此可以出栈。

**面试回答：**

> 栈只保存尚未确定答案的日期。一旦某个日期找到未来第一个更高温度，就记录答案并将其出栈。

## 检查 3

**我的回答：**

> 读取：
> 73
>
> 此时：
> stack = 73
>
> 读取：
> 74
>
> 发生将73对应的下标0出栈，并写入答案1 - 0 = 1， 再将74对应的下标1入栈成为最近进入的未处理对象
>
> 1. 是否 push 74？是
> 2. 73 是否 pop？是
> 3. 为什么？每次处理完都要将已经处理完的对象出栈，再将未处理的对象入栈
>
> 最终：
> 73等待1 - 0 = 1天

**订正：**

逻辑正确。

但栈保存的是下标，因此更准确：

```text
读取73（index=0）
stack=[0]

读取74（index=1）
74 > temperatures[0]

answer[0]=1
pop 0

push 1
stack=[1]
```

**面试回答：**

> 遍历每一天，若当前温度高于栈顶下标对应的温度，就为栈顶日期计算等待天数并出栈。处理完后将当前日期下标入栈。

## 检查 4

**我的回答：**

> 每日温度要求解决
>
> 最近哪些元素还没有找到答案
>
> 适合stack最近进入的对象优先处理的情况，这里依然需要 LIFO，如果使用queue的先进先出，则无法满足找到未来第一个比今天温度高的日期的要求，比如75,71,69，这时新元素为72，理应先将69和71处理完再将72push进栈，但由于先进先出的语义，先处理的反而是75，这样72就失去能连续处理71和69的能力了。

**订正：**

核心思路正确。

对于：

```text
[75,71,69,72]
```

处理72前：

```text
栈底 → 栈顶
75,71,69
```

72出现：

```text
69 < 72 → 解决69
71 < 72 → 解决71
75 > 72 → 停止
```

普通 Queue 若将75放在队头，无法像单调栈这样直接从最近、最有可能被当前元素解决的候选开始处理。

不能说 Queue 在任何实现下绝对算不出答案；真正的问题是它不适合这种高效的单调候选维护。

**面试回答：**

> 单调栈能够从最近的未解决元素开始比较，并连续移除被当前元素解决的候选。通过维护单调性，每个元素最多入栈、出栈一次，因此能够在线性时间内完成问题。

## 检查 4

**我的回答：**

> 不用，因为第二遍的元素已经在第一遍遍历时就已经决定了去向，第二遍的元素只是起到处理第一遍中还未找到答案的待处理元素的作用，不是新的需要处理的元素。

**订正：**

在今天讨论的具体实现方案中正确。

可以：

```cpp
for (int i = 0; i < 2 * n; ++i) {
    int index = i % n;

    while (!st.empty() &&
           nums[st.top()] < nums[index]) {
        answer[st.top()] = nums[index];
        st.pop();
    }

    if (i < n) {
        st.push(index);
    }
}
```

第一遍建立未解决候选，第二遍只尝试解决剩余候选。

注意，这是一种实现方案，并不是所有循环单调栈写法都必须禁止第二遍入栈。

**面试回答：**

> 在只让第一遍建立候选的实现中，第二遍无需重新压入原始下标，只需要利用循环访问的元素解决第一遍剩余的候选，避免重复维护同一批元素。

# 十、拓展接触：LRU Cache

今天曾讨论：

```text
put(1,1)
put(2,2)
get(1)
put(3,3)
```

容量为2时，最久未使用的是2，应淘汰2。

LRU：

```text
Least Recently Used
```

关注最近访问顺序，而非单纯的插入顺序。

经典 O(1) 设计：

```text
HashMap + Doubly Linked List
```

HashMap 负责快速定位节点。

双向链表负责维护访问顺序、移动节点和淘汰尾部节点。

## 检查 1

**我的回答：**

> Linked List

**订正：**

在给出的 Linked List / Stack / Queue 选项中，选择 Linked List 是有依据的。

但经典 LRU Cache 的完整 O(1) 实现还需要：

```text
HashMap + Doubly Linked List
```

**面试回答：**

> LRU Cache 常使用 HashMap 与双向链表组合。HashMap 负责 O(1) 查找节点，双向链表维护访问顺序，支持 O(1) 移动和淘汰节点。

## 检查 2

**我的回答：**

> 因为每一个数据都可能随时被访问，不能通过数据进出的规则来处理待处理的对象，既要处理最近使用的数据应该保留的问题还要处理最久没有使用的数据应该被删除的问题

**订正：**

正确。

关键：

```text
最近访问顺序
≠
进入顺序
```

**面试回答：**

> LRU 需要根据动态访问顺序淘汰数据，因此不能仅根据数据进入容器的先后顺序决定淘汰对象。

## 检查 3

**我的回答：**

> 因为每一个数据都可能随时被访问，既要处理最近使用的数据应该保留的问题还要处理最久没有使用的数据应该被删除的问题

**订正：**

正确。

例如：

```text
put A
put B
put C
get A
put D
```

# 十一、Linked List 指针操作复习

文件：

```text
linked_list_pointer_demo.cpp
```

## 1. 插入节点

原始链表：

```text
1 -> 2 -> 3
```

在节点2之后插入节点4：

```text
1 -> 2 -> 4 -> 3
```

正确顺序：

```cpp
node4->next = node2->next;
node2->next = node4;
```

先保留后继关系，再修改前驱指针。

## 2. 删除节点

```cpp
node2->next = node4->next;
delete node4;
```

先断开节点连接，再释放动态分配的节点。

## 3. 完整代码

```cpp
#include <iostream>

using namespace std;

struct ListNode {
    int val;
    ListNode* next;
};

void printList(const ListNode* head) {
    const ListNode* cur = head;

    while (cur != nullptr) {
        cout << cur->val;

        if (cur->next != nullptr) {
            cout << " -> ";
        }

        cur = cur->next;
    }

    cout << '\n';
}

int main() {
    ListNode* node1 = new ListNode{1, nullptr};
    ListNode* node2 = new ListNode{2, nullptr};
    ListNode* node3 = new ListNode{3, nullptr};

    node1->next = node2;
    node2->next = node3;

    cout << "Original: ";
    printList(node1);

    // 在2后面插入4
    ListNode* node4 = new ListNode{4, nullptr};

    node4->next = node2->next;
    node2->next = node4;

    cout << "After insert: ";
    printList(node1);

    // 删除4
    node2->next = node4->next;
    delete node4;

    cout << "After delete: ";
    printList(node1);

    // 释放剩余节点
    ListNode* head = node1;

    while (head != nullptr) {
        ListNode* nextNode = head->next;
        delete head;
        head = nextNode;
    }

    return 0;
}
```

# 十五、LeetCode 933：Number of Recent Calls

## 1. 题目

每次调用：

```cpp
ping(t)
```

表示在时间 `t` 收到一次请求。

返回闭区间：

```text
[t-3000,t]
```

内的请求数量。

题目保证：

```text
t严格递增
```

所以请求时间自然有序。

## 2. 为什么用 Queue？

最早收到的请求最先过期。

```text
最早进入
→ 最先需要检查是否过期
```

符合Queue的 FIFO 规则。

维护队列时：

```text
新请求入队
↓
删除队头过期请求
↓
剩余元素数量就是答案
```

## 3. 我的独立实现

```cpp
class RecentCounter {
public:
    RecentCounter() {

    }

    int ping(int t) {
        this->q.push(t);
        while(q.front() < t - 3000){
            q.pop();
        }
        return q.size();
    }
private:
    queue<int> q;
};
```

## 4. 代码订正

实现正确。

因为：

```cpp
q.push(t);
```

先将当前请求入队，且当前请求必定满足有效区间，所以在正常题目约束下，`while` 判断时队列不会为空。

判断：

```cpp
q.front() < t - 3000
```

正确。

不能写：

```cpp
q.front() <= t - 3000
```

因为恰好处于左边界的请求仍然有效。

## 5. 相关示例

```text
ping(1)
队列：[1]
返回：1

ping(100)
队列：[1,100]
返回：2

ping(3001)
队列：[1,100,3001]
返回：3

ping(3002)
删除时间1
队列：[100,3001,3002]
返回：3
```

## 6. 我的复杂度回答

> 时间复杂度为O(n)
>
> 额外空间复杂度为O(n)

## 7. 复杂度订正

设一共调用了 n 次 `ping()`。

**总时间：**

每个请求最多：

```text
push一次
pop一次
```

所以 n 次调用总时间：

```text
O(n)
```

平均到每次：

```text
均摊 O(1)
```

对于固定3000毫秒窗口和严格递增整数时间戳，一次调用最多只需要清理有限数量的过期请求。

**空间：**

通用上界：

```text
O(n)
```

但根据本题特定约束，时间戳是严格递增的整数，有效窗口长度为3000毫秒，因此最多保留3001个时间戳。

更紧的表达：

```text
O(min(n,3001))
```

由于3001是题目固定常数，因此：

```text
O(1)
```

## 8. 面试回答

> 使用 Queue 保存最近3000毫秒内的请求时间。由于请求时间严格递增，过期请求总是位于队头。每次新请求入队后，持续删除小于 `t-3000` 的过期时间戳，然后返回队列长度。每个请求最多入队、出队一次，因此 n 次调用总时间 O(n)，单次均摊 O(1)。在题目的固定窗口和整数时间戳约束下，额外空间 O(1)。

# 十八、Request ID Middleware 原理

Middleware：

```go
func requestIDMiddleware(next http.Handler) http.Handler
```

主要步骤：

1. 生成 Request ID
2. 创建包含 Request ID 的派生 Context
3. 在响应头设置 `X-Request-ID`
4. 使用 `r.WithContext(ctx)` 向下游传递请求

例如：

```go
ctx := context.WithValue(
    r.Context(),
    requestIDKey{},
    id,
)

w.Header().Set("X-Request-ID", id)

next.ServeHTTP(w, r.WithContext(ctx))
```

这里：

```text
Context
→ 服务端内部传递Request ID

Response Header
→ 向客户端提供Request ID
```

注意：

`w.Header().Set()` 是设置响应头，不表示此时已经向网络发送了响应。

> 客户端通过 Request ID 标识发生问题的请求，服务端通过相同 ID 检索日志。这样即使多个并发请求产生相同错误码，也能够区分具体请求。

# 二十二、Go Day35 最终代码

文件：

```text
main.go
```

完整代码：

```go
package main

import (
    "context"
    "encoding/json"
    "fmt"
    "log"
    "net/http"
    "sync/atomic"
)

// requestIDKey用于Context中的Request ID。
// 自定义类型可避免与其他Context Key冲突。
type requestIDKey struct{}

// 教学用请求计数器。
// atomic支持并发请求下安全递增。
var requestCounter atomic.Uint64

// APIError是服务器内部错误模型。
type APIError struct {
    Status  int
    Code    string
    Message string
}

// errorResponse是对外JSON响应模型。
type errorResponse struct {
    Code    string `json:"code"`
    Message string `json:"message"`
}

// 预定义固定错误值。
var ErrInvalidName = APIError{
    Status:  http.StatusBadRequest,
    Code:    "INVALID_NAME",
    Message: "name is required",
}

// requestIDMiddleware为每个请求生成Request ID。
func requestIDMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(
        w http.ResponseWriter,
        r *http.Request,
    ) {
        // 生成Request ID。
        id := fmt.Sprintf(
            "req-%d",
            requestCounter.Add(1),
        )

        // 创建携带Request ID的派生Context。
        ctx := context.WithValue(
            r.Context(),
            requestIDKey{},
            id,
        )

        // 设置响应头，让客户端可以获取Request ID。
        w.Header().Set("X-Request-ID", id)

        // 向下游传递携带新Context的请求副本。
        next.ServeHTTP(w, r.WithContext(ctx))
    })
}

// writeError统一记录错误日志并输出HTTP错误响应。
func writeError(
    w http.ResponseWriter,
    r *http.Request,
    apiErr APIError,
) {
    // 从当前请求Context读取Request ID。
    requestID := r.Context().Value(requestIDKey{})

    // 记录服务端错误日志。
    log.Printf(
        "request_id=%v status=%d code=%s message=%q",
        requestID,
        apiErr.Status,
        apiErr.Code,
        apiErr.Message,
    )

    // 设置响应内容类型。
    w.Header().Set(
        "Content-Type",
        "application/json",
    )

    // 设置HTTP Status。
    w.WriteHeader(apiErr.Status)

    // 输出对外JSON错误Body。
    if err := json.NewEncoder(w).Encode(
        errorResponse{
            Code:    apiErr.Code,
            Message: apiErr.Message,
        },
    ); err != nil {
        // 响应已开始写入，此处只能记录日志，
        // 不能再尝试重新发送另一个HTTP Status。
        log.Printf(
            "request_id=%v encode_error=%v",
            requestID,
            err,
        )
    }
}

// helloHandler只负责请求与业务判断。
func helloHandler(
    w http.ResponseWriter,
    r *http.Request,
) {
    name := r.URL.Query().Get("name")

    if name == "" {
        writeError(w, r, ErrInvalidName)
        return
    }

    fmt.Fprintf(w, "hello %s\n", name)
}

func main() {
    mux := http.NewServeMux()

    mux.HandleFunc("/hello", helloHandler)

    // 先执行Middleware，再进入mux。
    handler := requestIDMiddleware(mux)

    log.Println(
        "server started at http://localhost:8080",
    )

    log.Fatal(
        http.ListenAndServe(":8080", handler),
    )
}
```

备注：

这里对 `json.Encode` 返回的错误增加了日志检查，属于较稳妥的工程写法；今天理解检查的核心仍是 Request ID 关联，不要求额外掌握复杂的 HTTP 写失败恢复机制。

当前 `req-1`、`req-2` 为教学用进程内编号，不能保证跨进程、跨重启的唯一性。

# 二十四、Go Stage 3 检查记录

## 检查 1

**我的回答：**

> 因为正确业务处理逻辑并没有调用writeError函数，所以不会在服务器端打印错误日志，因为此请求本身是正确请求，而客服端拿到的Request ID是在requestIDMiddleware中创建生成并提交给服务端的，是在业务处理逻辑handle前的公共逻辑就提交了的。

**订正：**

核心理解正确。

需要调整方向：

```text
Request ID由服务端Middleware生成
↓
写入Response Header
↓
随响应返回客户端
```

不是客户端将新生成的 ID 提交给服务器。

`w.Header().Set()` 仅设置响应头，实际发送发生在响应写出时。

**面试回答：**

> Middleware为所有请求生成Request ID，但只有进入错误分支并调用writeError时才会记录错误日志。因此正常请求拥有Request ID，却不会产生该函数的错误日志。

## 检查 2

**我的回答：**

> 仅根据code=INVALID_NAME无法判断这个错误信息属于哪个请求的，需要一个绑定到每一个不同请求上的标识性数据，所以需要Request ID非常合适，因为每个请求的Request ID都不同，将其写入日志中就可以根据这个不同的请求id区分不同的请求对应的信息。

**订正：**

完全正确。

Error Code：

```text
描述错误类别
```

Request ID：

```text
描述具体请求
```

二者用途不同。

**面试回答：**

> 相同的错误码可能在多个请求中出现，无法唯一定位某一次请求。Request ID 则用于关联具体请求，使客户端反馈和服务端日志能够对应。

## 检查 3

**我的回答：**

```text
客户端发起 /hello 请求
↓
Middleware生成请求id，将该数据附带进新创建的context中并创建一个携带该新context的请求副本r,利用该r继续请求调用链，最后提交请求id给客户端
↓
Handler
↓
判断发生了预定义的错误值ErrorInvalidname
↓
writeError将错误信息写入response中
↓
客户端收到 400 + X-Request-ID + JSON Error
↓
服务端能够通过同一个 Request ID 找到错误日志
```

**订正：**

整体正确。

预定义错误值名称：

```go
ErrInvalidName
```

不是：

```go
ErrorInvalidname
```

补充遗漏步骤：

```text
writeError
↓
从Context获取Request ID
↓
log.Printf记录错误日志
↓
WriteHeader设置HTTP Status
↓
JSON Encode输出错误Body
```

**面试回答：**

> HTTP 请求先经过 Request ID Middleware，生成并保存 Request ID。Handler 判断请求条件，发生错误时选择对应的 APIError，并调用 writeError。writeError从Context获取Request ID，将其和错误信息写入日志，再返回状态码和JSON响应。客户端通过响应头中的相同Request ID关联服务器日志。

# 二十六、今日易错点

## C++

**易错点 1：链表等于 Stack？**

错误。

链表是连接方式，Stack 是访问规则。

**易错点 2：链表插入先改前驱 next？**

可能覆盖原有连接，甚至形成自环。

应先连接新节点与原后继，再修改前驱。

**易错点 3：Queue 和 Stack 都能严格保持任务到达顺序？**

错误。

Queue 是 FIFO，Stack 是 LIFO。

**易错点 4：LC933 的过期判断使用 <=？**

错误。

有效区间包含左端点。

正确：

```cpp
q.front() < t - 3000
```

**易错点 5：有 while 就一定是 O(n²)？**

错误。

LC933 中每个请求最多入队、出队一次，因此 n 次调用总时间 O(n)，单次均摊 O(1)。

## Go

**易错点 1：不使用 Middleware 就不能正常处理业务？**

错误。

mux 和 Handler 仍可正常工作，只是失去了 Middleware 公共逻辑。

**易错点 2：Request ID 只属于错误请求？**

错误。

Request ID 标识一次请求，与是否成功无关。

**易错点 3：Context 中已经有 Request ID，就不需要 Response Header？**

不准确。

Context 服务于服务端内部调用链。

Response Header 服务于客户端获取 ID。

**易错点 4：Error Code 能唯一标识某次请求？**

错误。

Error Code 表示错误类别，Request ID 才用于关联具体请求。

**易错点 5：writeError只写HTTP Response？**

今天已经增加了：

```text
记录错误日志
写HTTP Status
输出JSON Body
```
