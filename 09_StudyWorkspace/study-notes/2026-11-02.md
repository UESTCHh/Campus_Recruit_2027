# 二、C++ 主线：LC104 二叉树的最大深度

## Stage 1：递归 DFS 求二叉树最大深度

### 1. 题目理解

LC104：Maximum Depth of Binary Tree。

求一棵二叉树的最大深度，即从根节点到最远叶子节点的最长路径所包含的节点数量。

注意：这里路径长度以节点数量计算，而不是边的数量。

特殊情况：

- 空树：深度为 0。
- 只有根节点：深度为 1。

### 2. 递归出口

```cpp
if(root == nullptr){
    return 0;
}
```

当前节点为空，说明这条路径没有节点，因此返回 0。

### 3. 递归关系

对于当前节点：

- 左子树最大深度：`maxDepth(root->left)`
- 右子树最大深度：`maxDepth(root->right)`
- 当前节点贡献一层深度。

因此：

\[
depth(root)=1+\max(depth(left),depth(right))
\]

### 4. 最终代码

```cpp
class Solution {
public:
    int maxDepth(TreeNode* root) {
        if(root == nullptr){
            return 0;
        }
        return 1 + max(
            maxDepth(root -> left),
            maxDepth(root -> right)
        );
    }
};
```

**LeetCode 提交结果：Accepted。**

### 5. 遍历思想

该方法属于 DFS 深度优先搜索，具体体现为后序遍历思想：

1. 递归计算左子树深度。
2. 递归计算右子树深度。
3. 处理当前节点，返回左右子树最大深度加一。

核心是先获得左右子树的结果，再计算当前节点的结果。

### 6. 复杂度分析

时间复杂度：

\[
O(n)
\]

每个非空节点只访问一次，每次处理为常数时间。

空间复杂度：

\[
O(h)
\]

主要来自递归调用栈，取决于树的高度。

- 平衡二叉树：O(log n)。
- 退化链表：O(n)。

注意：这里讨论的是辅助空间，不包含最终返回结果。

## Stage 2：DFS 与 BFS 空间复杂度对比

今天将之前学习的 LC102 层序遍历与 LC104 最大深度联系起来。

### 1. DFS 的空间复杂度

DFS 使用递归调用栈，沿着一条路径不断深入。

\[
S_{DFS}=O(h)
\]

其中 h 为树高。

### 2. BFS 的空间复杂度

BFS 使用队列保存当前层等待处理的节点。

\[
S_{BFS}=O(w)
\]

其中 w 为树的最大宽度。

### 3. 不同树形下的复杂度

| 树的形态 | DFS | BFS |
|---|---|---|
| 平衡二叉树 | O(log n) | O(n) |
| 完全二叉树 | O(log n) | O(n) |
| 退化链表 | O(n) | O(1) |
| 普通二叉树 | O(h) | O(w) |

### 4. 今日重点纠错

完全二叉树的 BFS 队列空间复杂度不是 O(log n)，而是 O(n)。

原因：

完全二叉树最后一层的节点数量可以达到接近 n/2。

BFS 处理倒数第二层节点时，会将最后一层节点陆续加入队列，因此队列最多可能保存 O(n) 个节点。

而 DFS 的递归调用栈主要取决于树高，完全二叉树的高度为 O(log n)。

对于退化链表：

- DFS 需要 O(n) 递归空间。
- BFS 队列最多保存一个节点，因此为 O(1)。

### 5. 面试专用回答

LC104 可以使用 DFS 或 BFS 实现。

DFS 更直接，因为最大深度可以表示为当前节点左右子树最大深度的较大值加一，因此可以使用递归后序遍历，先计算左右子树深度，再返回当前节点的深度。

BFS 则通过队列进行层序遍历，每遍历完一层，深度加一。

两种方法的时间复杂度都是 O(n)，因为每个节点最多访问一次。递归 DFS 的额外空间复杂度为 O(h)，取决于树的高度；BFS 的额外空间复杂度为 O(w)，取决于树的最大宽度。

### 2. 回顾 Go error

Go 中错误通过 `error` 接口返回。

```go
type error interface {
    Error() string
}
```

正常情况下，错误返回值为 nil。

发生错误时，返回非 nil 的 error。

### 3. 错误包装

使用 `fmt.Errorf()` 和 `%w` 包装原始错误：

```go
err := fmt.Errorf("query failed: %w", sql.ErrNoRows)
```

作用：

- 增加错误上下文。
- 保留原始错误。
- 保留错误链。
- 让上层继续使用 errors.Is() 和 errors.As() 判断底层错误。

### 4. `%w` 与 `%v` 的区别

| 对比 | %w | %v |
|---|---|---|
| 格式化错误 | 是 | 是 |
| 增加上下文 | 是 | 是 |
| 保留错误链 | 是 | 否 |
| errors.Is() 识别底层错误 | 可以 | 不可以 |
| errors.As() 提取底层错误类型 | 可以 | 不可以 |

示例：

```go
err1 := sql.ErrNoRows

err2 := fmt.Errorf("query failed: %w", err1)
err3 := fmt.Errorf("query failed: %v", err1)

errors.Is(err2, sql.ErrNoRows) // true
errors.Is(err3, sql.ErrNoRows) // false
```

## Stage 2：改造 Repository.GetByID()

### 1. 改造前

原来的 `repository.go`：

```go
if err != nil {
    return Student{}, err
}
```

存在的问题：

直接返回数据库错误，没有增加 Repository 层的操作上下文。

例如，发生错误时只看到：

```text
sql: no rows in result set
```

不容易从错误信息中判断具体是哪个 Repository 操作发生了问题。

### 2. 改造后

增加 fmt 依赖：

```go
import (
    "database/sql"
    "fmt"
)
```

错误返回逻辑：

```go
if err != nil {
    return Student{}, fmt.Errorf(
        "GetByID failed, studentID=%d: %w",
        id,
        err,
    )
}
```

注意：实际项目中应保留这一错误包装逻辑，不要将 `%w` 改成 `%v`。

### 3. 改造后的错误传递

例如查询不存在的学生 ID=9999：

```text
SQLite
  |
  | sql.ErrNoRows
  v
Repository.GetByID(9999)
  |
  | fmt.Errorf(... %w ...)
  v
包装后的错误
  |
  v
Handler
  |
  | errors.Is(err, sql.ErrNoRows)
  v
识别为记录不存在
  |
  v
HTTP 404 Not Found
```

这体现了不同层级的职责分离：

- Repository：增加数据库操作上下文。
- Handler：根据错误类型决定 HTTP 状态码。
- errors.Is()：识别错误链中的底层错误。

### 4. Handler 原有逻辑不需要修改

之前的 Handler：

```go
if errors.Is(err, sql.ErrNoRows) {
    writeJSON(
        w,
        http.StatusNotFound,
        ErrorResponse{Error: "student not found"},
    )
    return
}
```

Repository 使用 `%w` 包装错误后，Handler 依然能够正确识别底层的 `sql.ErrNoRows`。

因此不需要修改 Handler 的错误判断逻辑。
