# 二、C++ Stage 1：LC226 翻转二叉树——递归原理复习

题目：LeetCode 226《翻转二叉树》  
题目链接：https://leetcode.cn/problems/invert-binary-tree/

## 2.1 题目、镜像关系和基本模型

原始二叉树：

```text
          4
        /   \
       2     7
      / \   / \
     1   3 6   9
```

正确翻转后：

```text
          4
        /   \
       7     2
      / \   / \
     9   6 3   1
```

翻转要求每个非空节点都交换其左、右孩子。只交换根节点不能得到整棵树的镜像。

### 理解题 1：为什么只交换根节点的左右孩子不够？

**问题：** 若根节点为 4，左、右孩子分别为 2、7，为什么仅交换根节点不够？

**我的回答（准确原话）：**

> 只交换根节点的左右孩子不够，是因为左右孩子如果不是叶子节点，则也会有它们自己的左右孩子，所以需要递归处理每个非空节点，让每个节点都实现左右孩子互换，否则最终会出现根节点以及它的左右孩子这两层实现了镜像，但是再下层的节点却不能满足翻转的要求、，即无法根据一条竖线使得原树和翻转树实现对称。

**订正：核心正确。** 一个节点的左右指针交换只解决它自身这一层的相对方向；原有两棵子树内部的左右关系不会因此自动翻转。只有递归到每一个非空节点，才能完成全树镜像。

**相关示例：** 若只交换根节点，左右大子树互换位置，但原来节点 7 的孩子仍为左 6、右 9，正确翻转应为左 9、右 6。

**面试专用回答：**

> 翻转二叉树必须对每个非空节点交换左右子树。只交换根节点仅改变两棵大子树的位置，不能改变子树内部结构；递归遍历并交换每个节点后才能得到整棵树的镜像。

### 理解题 2：先交换再递归，还是先递归再交换？

**问题：** A. 先交换当前节点左右孩子，再递归；B. 先递归翻转两棵子树，再交换当前节点左右孩子。两种方案是否都成立？

**我的回答（准确原话）：**

> 都能完成，因为翻转操作是左右两棵整树翻转，不会影响到树中节点顺序，所以无论是从上到下翻转，还是从下到上翻转都可以实现每个节点的左右子树翻转。

**订正：结论正确，原因需精确。** 对于当前节点，父节点交换左右孩子的操作与两棵子树内部各节点的翻转操作可以交换顺序，最终都会把每一个节点的左右孩子交换恰好一次。这里不宜笼统说「不影响树中节点顺序」：翻转恰恰改变了左右相对位置，只是不改变节点集合和节点自身的值。

**相关示例：**

```cpp
// 方案 A：先交换当前节点，再递归两棵（已经互换位置的）子树
std::swap(root->left, root->right);
invertTree(root->left);
invertTree(root->right);

// 方案 B：先递归原左右子树，再交换当前位置
invertTree(root->left);
invertTree(root->right);
std::swap(root->left, root->right);
```

以上为两种方案的**独立代码片段**，不可直接先后连着执行，否则同一节点可能被重复翻转。

**面试专用回答：**

> 两种递归次序都正确。每个节点只要执行一次左右指针交换，并递归翻转其两棵子树，就能形成镜像；父节点交换与孩子子树内部翻转的先后顺序不影响最终结果。

### 理解题 3：空节点和叶子节点

**问题：** 当 `root == nullptr` 时应该返回什么，为什么叶子节点不需要特殊处理？

**我的回答（准确原话）：**

> 返回nullptr；因为叶子节点的两棵子树均为nullptr，翻转之后还是和原来一样，所以不会影响原先的翻转逻辑。

**订正：完全正确。** 空节点作为递归边界返回 `nullptr`；叶子节点的左右孩子都是空指针，交换两个空指针没有任何可见变化，再递归两次空节点也会立即返回。

**相关示例：** 对一个仅含节点 5 的单节点树，翻转前后完全相同，根节点指针本身仍需要返回。

**面试专用回答：**

> `root == nullptr` 时立即返回 `nullptr`，防止解引用空指针；无需单独判断叶子节点，因为叶子节点左右孩子都是空，正常交换和递归就会自然结束。

# 三、C++ Stage 2：LC226 独立代码与复杂度验收

## 3.1 我的实际提交代码

```cpp
class Solution {
public:
    TreeNode* invertTree(TreeNode* root) {
        if(root == nullptr){
            return nullptr;
        }
        swap(root -> left, root -> right);
        invertTree(root -> left);
        invertTree(root -> right);
        return root;
    }
};
```

**实测结果（用户报告）：**「提交正确」，即 LeetCode **Accepted**。未提供具体提交运行耗时或内存排名，不作编造。

代码审查：

1. 空节点边界正确。
2. 交换 `left`、`right` 两个节点指针正确。
3. 递归分别访问交换后的左右子树正确，两个子树都不会遗漏。
4. 返回原 `root` 指针，符合题目接口。
5. 在实际 C++ 源文件中，可明确使用 `std::swap` 并引入 `<utility>`；LeetCode 模板可能已预置所需声明。

## 3.2 复杂度问答

**问题：** 时间复杂度、空间复杂度是多少？树退化为链表时呢？

**我的回答（准确原话）：**

> 时间复杂度是O(n)，因为每个非空节点需要处理一次，每次仅是常数时间的交换操作。  
> 空间复杂度是O(h)，依据是递归的调用栈深度，递归调用栈中最多存放树高多个调用函数  
> 退化成链表后，树高即节点个数，所以O(h) = O(n)

**订正：全部正确。**

- 时间 `O(n)`：每个节点恰好经过一次非空节点调用、一次常数时间交换；对空孩子的调用总数也至多线性。
- 辅助空间 `O(h)`：由递归栈深度决定，`h` 为树高；不同树高定义（节点数或边数）只差常数。
- 平衡树 `O(log n)`；退化为链表的极端树 `O(n)`。
- 本算法原地交换指针，没有为每个节点创建新的二叉树副本。

**面试专用回答：**

> 递归翻转每个非空节点的左右孩子，时间复杂度为 `O(n)`；空间消耗主要来自递归调用栈，深度取决于树高，因此空间复杂度为 `O(h)`。平衡树为 `O(log n)`，最坏退化树为 `O(n)`。

# 四、Go Stage 1：error 接口、创建错误、包装错误

## 4.1 error 的本质

Go 内置的 `error` 接口可理解为：

```go
type error interface {
    Error() string
}
```

任何方法集符合这一接口的类型都能作为 `error` 使用。Go 的常规错误处理方式是函数显式返回 `error`，调用者判断是否为 `nil`：

```go
student, err := repo.GetByID(1001)
if err != nil {
    return err
}
// 成功后使用 student
```

**注意：** 返回 `nil` 是函数在成功时通常遵循的约定，不是 Go 运行时自动保证。接口值含有动态类型和动态值；若将一个「带类型的 nil 指针」直接装入 `error` 接口，接口可能不等于 `nil`。

## 4.2 errors.New 与 fmt.Errorf

```go
errors.New("student not found")
fmt.Errorf("student %d not found", 1001)
```

- `errors.New` 适合固定消息；
- `fmt.Errorf` 可以将变量格式化进错误消息；
- `fmt.Errorf(... %w ...)` 还能包装一个底层 `error`，使错误链可检查。

## 4.3 `%w` 和 `%v` 的关键区别

```go
original := sql.ErrNoRows

wrapped := fmt.Errorf("get student id=%d: %w", 1001, original)
formatted := fmt.Errorf("get student id=%d: %v", 1001, original)
```

打印出来的错误文本可能一样，但在**错误结构**上不同：

| 表达式 | 保留原始错误链 | `errors.Is(err, sql.ErrNoRows)` |
|---|---|---|
| `fmt.Errorf("... %w", original)` | 是 | `true` |
| `fmt.Errorf("... %v", original)` | 否 | `false` |

`%w` 使上层能继续检查底层错误；`%v` 仅把错误转换为格式化文本插入新错误消息。

## 4.4 理解题 1：error 为什么能用 `err != nil` 判断？

**我的回答（准确原话）：**

> 因为操作本身返回两个结果，一个是业务操作的结果，一个业务操作遇到的错误，再通过判断返回的错误是否为空就可以判断有没有出现错误，因为不出现错误的情况下，返回的错误为空。  
> error本质上是一个实现了Error() string方法的接口，因为不出现错误的情况下，返回的错误为空。

**订正：主要正确。** `error` 自身是**接口类型**，实现 `Error() string` 的**具体类型**可以实现此接口；按约定成功返回 `nil`，失败返回非 `nil`。注意接口中的 typed nil 陷阱。

**相关示例（讲解示例，非当天用户实验）：**

```go
type MyError struct{}
func (*MyError) Error() string { return "my error" }

func getError() error {
    var p *MyError = nil
    return p // error 接口的动态类型为 *MyError，不等于 nil
}
```

**面试专用回答：**

> `error` 是包含 `Error() string` 方法的内置接口；函数一般在成功时返回 `nil`，发生错误时返回非 `nil` 的错误值，由调用方显式处理。应注意接口里的 typed nil 指针不等于 nil 接口。

## 4.5 理解题 2：为什么 `%w` 能识别原始错误而 `%v` 不能？

**我的回答（准确原话）：**

> 因为%w是将错误进行包装，在原有的错误上包装发生错误的位置的各种相关信息，同时保留错误链，这样可以使得上层依然能通过错误链精准判断错误类型；而%v只是简单的格式化，即将原有的错误进行格式化后当成字符串插入进固定的字符串格式中，丢失了原有的错误链，不能再依靠原来的错误判断逻辑来判断错误类型。

**订正：正确。** 进一步区分 `errors.Is` 匹配特定**错误值**，`errors.As` 搜索能赋给目标**错误类型**的错误。

**相关示例：** `errors.Is(fmt.Errorf("repo: %w", sql.ErrNoRows), sql.ErrNoRows)` 为 `true`；改 `%v` 为 `false`。

**面试专用回答：**

> `%w` 包装原始错误，添加上下文同时保留链式检查能力；`%v` 只把错误写入格式化消息。上层应使用 `errors.Is`、`errors.As` 而不是比较错误字符串来识别错误。

## 4.6 理解题 3：Repository 包装 `sql.ErrNoRows` 后 Handler 判断结果

**我的回答（准确原话）：**

> 结果是true，因为虽然经过%w包装后的错误只是在原有的sql.ErrNoRows错误类型上加上包装信息，错误链依然存在，error.Is(err, sql.ErrNoRows)会沿着错误链一步步往下解包装，最终匹配到下层的原始错误类型sql.ErrNoRows。

**订正：结论正确，术语需修正。** 标准库函数写作 `errors.Is` 而非 `error.Is`；`sql.ErrNoRows` 是哨兵**错误值**，不是错误类型。

**相关示例：**

```go
err := fmt.Errorf("get student id=%d: %w", 1001, sql.ErrNoRows)
if errors.Is(err, sql.ErrNoRows) {
    // Handler 可以按业务策略返回 HTTP 404
}
```

**面试专用回答：**

> `%w` 保留原始错误链，`errors.Is(err, sql.ErrNoRows)` 可以沿链识别数据库无记录这一哨兵错误值；Handler 因此可以在添加上下文信息后仍正确返回 404。

# 五、Go Stage 2：errors.Is 与 errors.Unwrap 的独立实验

## 5.1 三个检查函数的核心区别

| 函数 | 返回/效果 | 核心目的 |
|---|---|---|
| `errors.Is(err, target)` | `bool` | 沿错误链检查是否匹配特定错误值；必要时还会使用错误自定义的匹配逻辑 |
| `errors.As(err, &target)` | `bool`，成功时给目标赋值 | 沿错误链搜索可赋值给目标类型的错误 |
| `errors.Unwrap(err)` | `error` | 获取**直接一层**包装的底层错误；无合适包装则返回 `nil` |

普通单链包装示例：

```go
err1 := sql.ErrNoRows
err2 := fmt.Errorf("query failed: %w", err1)
err3 := fmt.Errorf("repository failed: %w", err2)
```

结果：

```go
errors.Unwrap(err3)                    // err2
errors.Unwrap(errors.Unwrap(err3))     // err1
errors.Is(err3, sql.ErrNoRows)         // true
```

## 5.2 独立创建测试文件

文件：`day54_error_chain_test.go`。

**当天提交的 `TestDay54ErrorWrapping` 原始代码：**

```go
package main

import (
    "database/sql"
    "errors"
    "fmt"
    "testing"
)

func TestDay54ErrorWrapping(t *testing.T) {
    // TODO 1：定义原始错误 sql.ErrNoRows

        t.Fatalf("expected true, but got false")
    }
    if errors.Is(err3, sql.ErrNoRows) {
        t.Fatalf("expected false, but got true")
    }

    // TODO 5：验证 errors.Unwrap 的结果
    err4 := errors.Unwrap(err2)
    if err4 != sql.ErrNoRows {
        t.Fatalf("expected sql.ErrNoRows, but got %v", err4)
    }
}
```

注：代码块与提交内容逻辑一致，空白、缩进已按学习笔记标准格式整理。

这项测试检查三个互相独立的性质：

1. `%w` 保留底层哨兵错误。
2. `%v` 不保留底层错误链。
3. 单层 `errors.Unwrap` 得到原始 `sql.ErrNoRows`。

其中 `err4 != sql.ErrNoRows` 在此处可用，因为确知只有一层，且原始哨兵错误值可比较；真实跨层业务代码更推荐 `errors.Is`。

## 5.3 理解题 1：单层包装

**我的回答（准确原话）：**

> 返回sql.ErrNoRows；返回true

**订正：完全正确。** `errors.Unwrap(err2)` 取得一层底层错误 `sql.ErrNoRows`；`errors.Is(err2, sql.ErrNoRows)` 返回 `true`。

**相关示例：** `fmt.Errorf("query: %w", sql.ErrNoRows)` 仅增加一层包装。

**面试专用回答：**

> 单层 `%w` 包装后，`errors.Unwrap` 直接返回底层错误；`errors.Is` 能识别这个底层哨兵错误。

## 5.4 理解题 2：多层包装

**我的回答（准确原话）：**

> 返回的是err2，因为Unwrap直接得到的是下一层的错误值，不会直接得到最底层的原始错误值，需要一层层往下解包装。

**订正：完全正确。** `errors.Unwrap(err3)` 一次只返回 `err2`；`errors.Is(err3, sql.ErrNoRows)` 沿链匹配到底层。

**相关示例：** 上述 `err1 → err2 → err3` 三层示意。

**面试专用回答：**

# 六、Go Stage 3：errors.As、PathError 与测试假阳性

## 6.1 为什么需要 errors.As

`errors.Is` 回答「错误链中有没有特定错误值」，不能将一个具有字段的错误对象提取到变量里。

`errors.As` 回答「能不能在错误链中找到满足目标类型的错误，并赋给目标变量」，适合读取诸如 SQLite 错误码、文件路径等信息。

本次采用标准库 `*os.PathError` 实验，避免直接改动已有 SQLite Repository：

```go
pathErr := &os.PathError{
    Op:   "open",
    Path: "students.db",
    Err:  os.ErrNotExist,
}
err := fmt.Errorf("initialize database failed: %w", pathErr)
```

构成：

```text
err（error 接口，包含包装错误）
    │ %w
    ▼
*os.PathError { Op: "open", Path: "students.db", Err: os.ErrNotExist }
    │ PathError 自身的 Unwrap 关系
    ▼
os.ErrNotExist（哨兵错误值）
```

因此：

```go
errors.Is(err, os.ErrNotExist) // true

var target *os.PathError
errors.As(err, &target)       // true；target 指向 pathErr
```

## 6.2 独立编写的第一版 TestDay54ErrorsAs

**我的原始代码（提交时版本）：**

```go
func TestDay54ErrorsAs(t *testing.T) {
    pathErr := &os.PathError{
        Op:   "open",
        Path: "students.db",
        Err:  os.ErrNotExist,
    }

    err := fmt.Errorf("initialize database failed: %w", pathErr)

    var target *os.PathError
    if errors.As(err, &target) {
        if target.Op != "open" || target.Path != "students.db" {
            t.Fatalf("wrong variable")
        }
    }

    if !errors.Is(err, os.ErrNotExist) {
        t.Fatal("wrong error variable")
    }
}
```

**运行结果：** 第一次 Go Stage 3 专项测试 PASS，且 `TestDay54ErrorWrapping` 同时 PASS。

**代码审查发现的重要漏洞：**

```go
if errors.As(err, &target) {
    // 仅在匹配成功时才检查字段
}
```

如果 `errors.As` 返回 `false`，字段断言被跳过，测试未报告错误，可能出现**假阳性**。必须检查**匹配成功本身**，不能只在成功后检查字段。

## 6.3 正确的检查方式（教学修正示例）

```go
var target *os.PathError
if !errors.As(err, &target) {
    t.Fatalf("expected *os.PathError in error chain, got %v", err)
}

if target.Op != "open" || target.Path != "students.db" {
    t.Fatalf(
        "unexpected PathError: Op=%q, Path=%q",
        target.Op,
        target.Path,
    )
}
```

此处**先检查前提是否成立，再检查字段结果是否满足期望**。

**证据边界：** 用户最后执行了 `gofmt`、Day54 专项与完整回归且全部 PASS，但没有再次贴出修改后的 `day54_error_chain_test.go` 完整源代码。因此上面是明确教学使用的正确写法，**不能把它声称为已逐行核实的最终本机文件内容**。

## 6.4 理解题 1：Is 能否提取 Path 字段？

**我的回答（准确原话）：**

> 不能，因为errors.Is()只是判断其是否为特定的错误值，并不获取这个错误，如果需要获取到错误相关的具体字段值，需要使用errors.As()

**订正：正确。** `errors.Is` 返回 `bool`，需要读取 `*os.PathError.Path` 等字段时使用 `errors.As` 提取。

**相关示例：**

```go
var target *os.PathError
if errors.As(err, &target) {
    fmt.Println(target.Op, target.Path)
}
```

**面试专用回答：**

> `errors.Is` 负责错误值匹配，`errors.As` 负责从错误链中提取特定类型的错误，以便读取该具体类型的字段。

## 6.5 理解题 2：为什么传入 &target？

**我的回答（准确原话）：**

> target本身是一个类型为os.PathError的指针，它指向一个具体的os.PathError，wrapped本身也是一个指向os.PathError的指针，而不是一个具体的os.PathError类型。而传入函数时使用&target，其就变成了**os.PathError，这是因为As函数需要将特定的错误值赋值给target，所以需要传入target的地址，才能通过地址修改target的值。

**订正：后半部分正确，前半部分两处需明确。**

1. `var target *os.PathError` 初始时是 `nil`，**并未指向具体对象**。
2. `wrapped` 是 `fmt.Errorf` 返回的 `error` 接口值，其中含包装错误；并非本身就是一个 `*os.PathError` 指针。
3. `&target` 类型为 `**os.PathError`，把目标指针变量的地址交给 `errors.As`，才能在成功时写入匹配到的对象指针。

**相关示例：**

```go
var target *os.PathError
fmt.Println(target == nil) // true

ok := errors.As(err, &target)
// 对于本实验 ok 为 true，target 此时可访问 Op、Path、Err
```

**面试专用回答：**

> `target` 是类型为 `*os.PathError`、初始值为 `nil` 的指针变量。`errors.As` 匹配成功时需要给变量赋值，因此传入其地址 `&target`，类型为 `**os.PathError`，才能将找到的错误对象赋给 target。

## 6.6 最后的反例检查：为什么第一次测试可能假阳性

**题目：** 若错误构造从 `%w` 包装 `pathErr` 改成 `%w` 直接包装 `os.ErrNotExist`，第一次写的测试是否仍可能通过？`errors.As`、`errors.Is` 分别返回什么？

**我的回答（准确原话）：**

> 检查题：不能，因为我们使用error.As判断是否有具体的os.PathError能赋值给目标变量，但却只找到os.ErrNotExist，所以这一步就会失败。  
> 返回expected *os.PathError in error chain, got initialize database failed: file does not existh 和 true

**订正：`errors.As=false`、`errors.Is=true` 的判断方向正确，但「第一次写的测试不能通过」是错误的。**

若：

```go
err := fmt.Errorf("initialize database failed: %w", os.ErrNotExist)
```

第一次写的测试会发生：

1. `errors.As(err, &target)` 返回 `false`。
2. 外层 `if` 内所有字段检查**直接跳过**，没有调用 `t.Fatal`。
3. `errors.Is(err, os.ErrNotExist)` 返回 `true`，对应的失败分支不执行。
4. 测试结束，无失败断言，**可能显示 PASS（假阳性）**。

而改成 `if !errors.As(err, &target) { t.Fatalf(...) }` 后，遇到 `false` 就能正确失败。

**相关示例：** 单靠「条件成立后才做断言」不足以测试条件一定成立；测试要覆盖成功前提与成功后的具体结果。

**面试专用回答：**

> 错误匹配测试必须直接断言 `errors.As` 成功，否则匹配失败时跳过字段检查，会产生假阳性。应先 `if !errors.As(err, &target) { t.Fatal(...) }`，再检查 `target` 字段。
