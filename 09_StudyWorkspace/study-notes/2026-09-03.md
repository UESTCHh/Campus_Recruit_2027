## 2.1 Container Adaptor

今天学习的：

```cpp
std::stack
std::queue
std::priority_queue
```

更准确地属于：

```text
Container Adaptors
容器适配器
```

它们基于底层容器提供一种受到限制的数据访问方式。

核心思想：

```text
不是把底层容器的所有能力全部暴露出来，
而是根据数据结构的语义限制允许进行的操作。
```

例如：

```text
stack
→ 按照 LIFO 访问

queue
→ 按照 FIFO 访问

priority_queue
→ 按照 Priority 访问
```

# 三、`std::stack`

## 3.1 LIFO

`stack` 的核心规则：

```text
LIFO
= Last In First Out
= 后进先出
```

可以类比一摞盘子：

```text
最后放上去的盘子
最先被拿下来
```

例如：

```cpp
stack<int> s;

s.push(10);
s.push(20);
s.push(30);
```

逻辑结构：

```text
30 ← top
20
10
```

执行：

```cpp
s.pop();
```

首先删除：

```text
30
```

新的：

```cpp
s.top()
```

为：

```text
20
```

---

## 3.2 stack 常用 API

```cpp
push()
pop()
top()
empty()
size()
```

其中：

```cpp
top()
```

访问栈顶元素。

```cpp
pop()
```

删除栈顶元素。

---

## 3.3 `pop()` 不返回被删除元素

错误：

```cpp
int value = s.pop();
```

原因：

```text
stack::pop()
返回 void
```

如果需要读取并删除：

```cpp
int value = s.top();
s.pop();
```

即：

```text
top()
→ 读取

pop()
→ 删除
```

# 四、`std::queue`

## 4.1 FIFO

`queue` 核心规则：

```text
FIFO
= First In First Out
= 先进先出
```

可以类比排队或水管：

```text
最先进入的元素
最先出去
```

例如：

```cpp
queue<int> q;

q.push(10);
q.push(20);
q.push(30);
```

结构可以理解为：

```text
front              back
  ↓                  ↓
 10       20         30
 出口                 入口
```

---

## 4.2 queue 常用 API

```cpp
push()
pop()
front()
back()
empty()
size()
```

其中：

```cpp
q.front()
```

访问队头，也就是下一个要被删除的元素。

```cpp
q.back()
```

访问队尾，也就是最近进入的元素。

同样：

```cpp
q.pop()
```

返回：

```text
void
```

如果需要读取后删除：

```cpp
int value = q.front();
q.pop();
```

# 七、`std::priority_queue`

`priority_queue` 不根据：

```text
谁先进入
```

决定谁先出去，而是根据：

```text
Priority
优先级
```

决定：

```text
下一个被取出的元素是谁
```

---

## 7.1 默认 priority_queue

声明：

```cpp
priority_queue<int> pq;
```

例如：

```cpp
pq.push(10);
pq.push(30);
pq.push(20);
```

默认：

```text
最大元素拥有最高优先级
```

所以：

```cpp
pq.top()
```

得到：

```text
30
```

---

## 7.2 Max Heap

默认：

```cpp
priority_queue<int>
```

通常作为：

```text
Max Heap
大顶堆 / 最大堆
```

使用。

其重要性质：

```text
top()
→ 当前最大元素
```

注意：

```text
priority_queue
并不保证底层所有元素完整有序
```

不能理解为底层一定存成：

```text
50 40 30 20 10
```

真正保证的是：

```text
Heap Property
→ 最高优先级元素位于 top()
```

---

## 7.3 Min Heap

如果希望：

```text
最小元素拥有最高优先级
```

可以：

```cpp
priority_queue<
    int,
    vector<int>,
    greater<int>
> pq;
```

三个模板参数：

```text
int
→ 元素类型

vector<int>
→ 底层容器类型

greater<int>
→ Comparator / 优先级比较规则
```

此时：

```text
top()
→ 当前最小元素
```

通常称：

```text
Min Heap
小顶堆 / 最小堆
```

# 十三、为什么需要 RWMutex

普通：

```go
sync.Mutex
```

核心：

```text
同一时刻
只允许一个 goroutine 进入受保护的临界区
```

即使多个 goroutine 都只是 Reader：

```text
Reader A
Reader B
Reader C
```

使用普通 `Mutex` 时仍然需要串行。

而某些共享状态可能：

```text
Reader很多
Writer很少
```

这时可以考虑：

```go
sync.RWMutex
```

---

# 十四、RWMutex 基本 API

```go
RLock()
RUnlock()

Lock()
Unlock()
```

分别：

```text
RLock()
→ 获取读锁

RUnlock()
→ 释放读锁

Lock()
→ 获取独占写锁

Unlock()
→ 释放独占写锁
```

---

# 十五、RWMutex 核心并发规则

```text
Read + Read
→ 可以同时进行

Read + Write
→ 不可以同时进行

Write + Write
→ 不可以同时进行
```

表格：

| 当前访问 | 新 Reader | 新 Writer |
|---|---|---|
| Reader | 可以 | 等待 |
| Writer | 等待 | 等待 |

---

# 十六、为什么多个 Reader 可以同时进行

如果多个 goroutine：

```text
只读取共享状态
不修改共享状态
```

那么它们之间不需要相互排斥。

因此：

```text
多个 RLock()
→ 可以同时存在
```

但只要 Writer 需要进入：

```go
mu.Lock()
```

就必须等待所有 Reader：

```go
RUnlock()
```

完成。

---

# 十七、为什么 Get 只读也需要锁

错误理解：

```text
Get不修改数据
→ 所以Get不需要同步
```

实际上：

```text
Get自己不写
≠
其他goroutine不会写
```

例如：

```text
Reader
→ 正在读取共享状态

Writer
→ 同时修改共享状态
```

如果双方没有正确同步：

```text
可能发生 Data Race
```

因此：

```text
只要共享状态存在并发Write的可能
Reader也必须参与同一套同步协议
```

# 二十二、reader-writer-demo 中四个 Channel

# 二十五、为什么 main Receive 两次

```go
<-readersReady
<-readersReady
```

这里 Receive 的值本身不重要。

main 只关心：

```text

```

因此不用：


```go

```

两次 Receive 完成后，可以确定：

```text

Reader 2 已经获得 RLock
```

这样才启动 Writer。

否则 Writer 可能先于 Reader 获得锁，破坏实验想验证的执行状态。

# 三十七、`writerTrying`


main：

```go

```

这样 main 可以确保：

```text

```

否则 main 检查 Writer 状态时，Writer goroutine 可能还没有得到调度。

# 三十八、`writerAcquired`

Writer 成功：

```go

```

之后：

```go

```

```text

```

因此：

```text
writerAcquired是否ready
```

可以作为实验中判断：

```text

```

的信号。

# 三十九、`select + default`

代码：

```go
select {
case <-writerAcquired:
    fmt.Println("writer acquired while readers were active")

default:
    fmt.Println("writer is blocked while readers hold RLock")
}
```

作用：

```text
非阻塞检查 writerAcquired 当前是否 ready
```

如果 Writer 已获得锁：

```text
writerAcquired
→ 已close
→ Receive ready
→ 执行case
```

如果 Writer 仍被 Reader 阻塞：

```text
writerAcquired
→ 尚未close
→ Receive not ready
→ 立即执行default
```

非常重要：

```text
不是：
case先阻塞
↓
阻塞失败
↓
再执行default
```

而是：

```text
select检查当前ready状态
↓
没有Channel case ready
↓
存在default
↓
立即执行default
```

因此：

```text
select + default
→ Non-blocking Check
```

```text
   ≠ Mutex的无脑高级版

7. RWMutex不会让单次Read本身变快
   → 它只是允许多个Reader时间重叠

8. wg.Add()
   ≠ 创建goroutine

9. chan struct{}
   → 常用于只表达事件而不传业务数据

10. close(channel)
    → 可以用作广播通知

11. Closure
    → 函数可以访问定义位置外层变量

12. go func() {}()
    → 最后的()代表真正调用匿名函数

13. select + default
    → 没有case ready时立即default
    → 不是先阻塞再default

14. Sleep
    → 不能代替真正的同步机制
```
