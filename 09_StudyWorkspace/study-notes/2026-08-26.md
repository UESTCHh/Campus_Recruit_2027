# Part 1：C++ —— Rule of Zero

## 1. 从 Rule of Five 到 Rule of Zero

昨天为了学习资源所有权，我们使用了类似：

```cpp
class Student
{
public:
    int* age;

    Student(int a)
    {
        age = new int(a);
    }

    ~Student()
    {
        delete age;
    }

    Student(const Student& other)
    {
        age = new int(*other.age);
    }

    Student& operator=(const Student& other)
    {
        // ...
        return *this;
    }

    Student(Student&& other)
    {
        // ...
    }

    Student& operator=(Student&& other)
    {
        // ...
        return *this;
    }
};
```

这里之所以需要认真考虑 Rule of Five，是因为：

```cpp
int* age;
```

被当成一个：

```text
拥有型裸资源
```

也就是说：

```text
Student
自己负责
new
delete
copy
move
ownership
```

于是必须考虑：

```text
析构
拷贝构造
拷贝赋值
移动构造
移动赋值
```

# Part 3：为什么成员级拷贝仍然安全

编译器生成的 `Student` 拷贝构造会进行：

```text
成员级拷贝
```

但是：

```text
成员级拷贝
≠
所有成员都做裸字节复制
```

例如：

```cpp
int* age;
```

成员级拷贝时复制的是：

```text
指针值
```

也就是地址。

而：

```cpp
vector<int> scores;
```

成员级拷贝时会调用：

```text
vector 自己的拷贝语义
```

同理：

```cpp
string name;
```

会使用：

```text
string 自己的拷贝语义
```

因此：

```cpp
Student s2 = s1;
```

概念上是：

```text
s2.name
    ↓
调用 string 的拷贝逻辑

s2.scores
    ↓
调用 vector 的拷贝逻辑
```

而不是：

```text
直接把 vector 内部地址复制给另一个 vector
```

# Part 4：Rule of Zero 的核心思想

Rule of Zero 不是简单：

```text
不用写五个函数
```

真正的思想是：

```text
让专门的 RAII 类型负责底层资源管理
```

然后高层业务类通过组合这些 RAII 类型完成自己的资源语义。

例如：

```cpp
class Student
{
public:
    string name;
    vector<int> scores;
};
```

Student 不直接管理：

```text
裸内存
裸文件句柄
裸 socket
```

而是组合已经具有正确生命周期语义的类型。

于是：

```text
成员自己负责资源
    ↓
编译器生成的特殊成员函数
    ↓
自然组合成员自己的正确 copy / move / destructor
```

这就是 Rule of Zero。

# Part 5：Rule of Zero 闭卷题

## 问题 1

为什么：

```cpp
class Student
{
    int* age;
};
```

容易迫使我们考虑 Rule of Five？

### 我的回答

因为int* age是指针类型的裸资源，可能需要手动delete释放，而默认的构造函数和赋值函数一般都是值复制，容易造成double free问题，所以需要自定义五个资源管理函数。

### 订正

核心正确。

需要修正一个术语：

不是：

```text
默认构造函数一般进行值复制
```

而应该是：

```text
编译器生成的拷贝构造
和
拷贝赋值
会进行成员级复制
```

如果：

```cpp
int* age;
```

表示 Student 独占拥有的动态资源，那么成员级复制只会复制：

```text
age 指针值
```

导致两个对象可能指向同一资源。

可能产生：

```text
double free
悬空指针
资源所有权混乱
```

而默认拷贝赋值还可能覆盖原来拥有的指针，造成：

```text
memory leak
```

所以直接拥有裸资源的类必须认真设计：

```text
析构
拷贝构造
拷贝赋值
移动构造
移动赋值
```

即 Rule of Five。

# Part 6：std::vector —— size 与 capacity

## size()

```cpp
nums.size()
```

表示：

```text
当前 vector 中实际存在多少个元素
```

例如：

```cpp
vector<int> nums;

nums.push_back(10);
nums.push_back(20);
nums.push_back(30);
```

此时：

```text
size = 3
```

---

## capacity()

```cpp
nums.capacity()
```

表示：

```text
在不进行重新分配的前提下
当前存储区域最多可以容纳多少个元素
```

例如：

```text
[10][20][30][ ][ ][ ][ ][ ]
 ↑           ↑
实际元素      预留空间

size = 3
capacity = 8
```

注意：

```text
capacity 表示元素容量
```

不是：

```text
字节数
```

# Part 8：为什么 push_back 不一定重新分配

如果：

```text
size < capacity
```

说明当前分配的连续存储空间中仍有空位。

因此：

```cpp
push_back(...)
```

通常可以直接在已有存储空间中构造新元素。

只有当：

```text
size == capacity
```

而又要插入一个新元素时：

```text
当前空间已经没有空位
```

于是需要：

```text
扩大 capacity
+
重新分配存储
```

---

# Part 9：为什么 vector 要预留 capacity

如果每插入一个元素都只多申请一个元素的空间：

```text
插入第1个
→ 重新分配

插入第2个
→ 再重新分配

插入第3个
→ 再重新分配
...
```

每次可能需要：

```text
申请新内存
复制/移动旧元素
释放旧内存
```

如果连续插入 n 个元素：

```text
搬迁总成本大约：

1 + 2 + 3 + ... + n
```

会接近：

```text
O(n²)
```

所以 vector 通常采用：

```text
一次分配比当前需求更大的空间
```

使后续若干次 `push_back()` 不需要重新分配。

---

# Part 10：push_back 的均摊复杂度

`push_back()` 并不是：

```text
每一次都 O(1)
```

如果刚好触发扩容：

```text
需要搬迁已有元素
```

单次可能达到：

```text
O(n)
```

但因为扩容不是每次发生，而是隔一段时间发生一次，

所以大量连续 `push_back()` 的总成本平均下来：

```text
amortized O(1)
```

即：

```text
均摊常数时间
```

## 问题 1

`size()` 和 `capacity()` 分别表示什么？

### 我的回答

前者指当前容器已经存放的元素个数，后者指当前容器申请的内存空间中最多存放的元素个数。

### 订正

正确。

更严谨：

```text
size
=
当前实际元素数量

capacity
=
不重新分配当前存储的前提下

```

## 问题 2

为什么 `push_back()` 不一定每次重新分配内存？

### 我的回答

因为分配的内存空间一般会比当前存放的元素个数大，只有当存放的元素个数超过最大存放个数时才会重新分配内存。

### 订正

核心正确。

需要修正：

不是：

```text
已经超过 capacity 后才扩容
```

而是：

```text
size == capacity
```

时当前空间已满。

这时再执行下一次：

```cpp
push_back()
```

需要扩大 capacity。

所以：

```text
size < capacity
→ 通常不重新分配

size == capacity
且需要继续插入
→ 需要扩容
```

## 问题 3

为什么扩容时 `data()` 地址可能改变？

### 我的回答

因为原地址内存空间后方不一定有空闲未占用的连续空间，而vector要求存放元素的内存空间是必须连续的，故需要重新找一块满足要求的连续空间。

### 订正

正确。

vector 的重要性质：

```text
元素连续存储
```

如果原来存储区域后方没有足够连续空间：

```text
不能直接原地继续增长
```

只能：

```text
申请新的更大连续区域
    ↓
移动/复制旧元素
    ↓
释放旧存储
```

于是：

```cpp
nums.data()
```

可能改变。

## 问题 4

为什么 vector 不每增加一个元素就重新申请一次内存？

### 我的回答

如果每增加一次元素就重新分配内存，那么每增加一次元素就会触发内存重新分配、搬迁旧元素、添加新元素，效率很低

### 订正

正确。

如果每次只增加一个元素容量：

```text

```

会不断产生：

```text
allocate
move/copy
deallocate
```

导致总成本非常高。

通过几何增长 capacity，可以把连续插入的平均成本降低到：

```text

```

扩容前：


```text

↓
旧存储中的 nums[0]
```

```text

    ↓
元素被移动到新存储
    ↓
旧元素生命周期结束
    ↓
旧存储释放
```

但：

```text
p
```

仍然保存旧地址。

于是：

```text
p 成为悬空指针
```

此时：

```cpp
*p
```

属于：

```text
undefined behavior
```

# Part 15：iterator 为什么失效

对于 vector：

```cpp
auto it = nums.begin();
```

可以初步理解成：

```text
一个用来定位 vector 元素的位置对象
```

它的行为很像随机访问指针。

但标准不要求：

```text
vector::iterator 必须就是裸指针
```

如果 vector 的存储区域搬迁：

```text
旧元素位置不存在
```

那么基于旧位置的 iterator 也失效。

# Part 17：vector 失效闭卷题

## 问题 1

为什么重新分配后：

```cpp

```

可能失效？

### 我的回答

因为重新分配存储空间后，可能元素被转移到了另一块内存空间中，原先的内存空间被释放掉了，但p还是指向原内存空间的首地址，如果再访问可能就是未定义行为了。

### 订正

正确。

vector 重新分配后：

```text
旧存储失效
```

而 `p` 仍然保存旧元素位置。

因此：

```text
p 成为悬空指针
```

继续解引用属于：

```text
undefined behavior
```

---

## 问题 2

为什么 iterator 也会失效？

# Part 18：vector 常见 iterator invalidation 规则

## push_back / emplace_back

如果发生 reallocation：

```text
所有 pointer
所有 reference
所有 iterator
全部失效
```

如果没有 reallocation：

```text
已有元素的 pointer/reference/iterator 保持有效
```

但是：

```text
旧 end() 失效
```

---

## insert / emplace

如果发生 reallocation：

```text
全部失效
```

如果没有 reallocation：

```text
插入位置及之后的 iterator/reference
可能失效
```

因为元素需要向后移动。

---

## reserve

如果 `reserve()` 导致 capacity 改变：

```text
所有旧 pointer/reference/iterator 失效
```

如果没有重新分配：

```text
原 iterator 等保持有效
```

---

## erase

被删除位置以及之后位置的 iterator/reference 通常失效。

因为：

```text
后续元素向前移动
```

---

## clear

所有元素被销毁。

因此：

```text
所有指向元素的 iterator/reference
失效
```

# Part 22：为什么 end() 不能解引用

不能简单说：


```text

capacity >= 10
```

```text

 ↑          ↑
```


```text
undefined behavior
```

```text
iterator 是否指向一个有效对象
```

而不是：


# Part 68：Go 今日核心结论

今天必须记住：

```text
1. Go的error本身是interface。

2. 任意实现Error() string的方法集合的类型，
   都可以满足error。

3. Go普通业务失败通常通过error返回。

4. panic不应该替代普通业务错误处理。

5. err == nil
   通常表示成功。

6. err != nil
   表示操作失败，
   应先处理失败再使用成功结果。

7. 错误处理不等于打印错误。

8. 错误可能被当前层处理，
   也可能继续向上返回。

9. 不推荐通过err.Error()字符串判断错误语义。

10. sentinel error是：
    有名字、有稳定身份、可供程序判断的预定义错误值。

11. ErrUserNotFound是错误值，
    不是错误类型。

12. %w用于error wrapping。

13. %w可以增加上下文，
    同时保留与底层error的包装关系。
```

# Part 72：今日面试级表达

## C++：什么是 Rule of Zero？

可以回答：

> Rule of Zero 的核心是尽量不要让高层业务类直接管理底层裸资源，而是通过 `std::string`、`std::vector`、智能指针等 RAII 类型作为成员，让这些成员自己负责资源的拷贝、移动和析构。这样类本身通常就不需要手写析构、拷贝构造、拷贝赋值、移动构造和移动赋值。

---

## C++：vector 的 size 和 capacity 区别？

可以回答：

> `size()` 表示当前实际存在的元素数量；`capacity()` 表示在当前已经分配的存储空间中，在不发生重新分配的情况下最多可以容纳多少个元素。

---

## C++：为什么 vector push_back 是均摊 O(1)？

可以回答：

> `vector` 不会每插入一个元素就重新分配一次内存，而是一次扩展出更多 capacity。普通 `push_back` 在剩余 capacity 内通常是 O(1)，只有触发扩容时需要重新分配并移动已有元素，单次可能是 O(n)。将大量连续插入的总成本平均后，`push_back` 的均摊复杂度是 O(1)。

---

## C++：为什么 vector 扩容会导致 iterator 失效？

可以回答：

> `vector` 要求元素连续存储。扩容时如果当前区域无法继续容纳元素，就会申请新的连续存储区域，并移动或复制旧元素。旧元素的位置和生命周期随之失效，因此指向旧存储的 pointer、reference 和 iterator 都不能继续使用。

---

## C++：end() 是什么？

可以回答：

> `end()` 返回尾后 iterator，也就是最后一个有效元素之后的位置。它不指向有效元素，因此不能解引用。STL 通常使用 `[begin, end)` 这样的半开区间表示元素范围。

---

## C++：为什么 STL algorithm 使用 iterator？

可以回答：

> STL 算法通过 iterator 范围访问元素，从而与具体容器类型解耦。算法不需要知道容器是不是 `vector`，只需要 iterator 提供算法所要求的操作能力。但不同算法对 iterator 的能力要求不同，例如 `std::sort` 需要随机访问能力。

---

## Go：什么是 sentinel error？

可以回答：

> Sentinel error 是预先定义、具有稳定身份、可以供程序判断特定错误条件的错误值。例如 `ErrUserNotFound`。程序应该通过 `errors.Is` 判断这种错误语义，而不是比较错误字符串。

---

## Go：为什么使用 `%w`？

可以回答：

> `%w` 用于错误包装。它可以在创建新错误时增加当前层的上下文，同时保留与原始错误之间的包装关系，因此上层仍然可以通过 `errors.Is` 识别底层错误。

---

## Go：`%v` 和 `%w` 区别？

可以回答：

> `%v` 只是把错误格式化进新的错误文本，不建立可供 `errors.Is` 追踪的包装关系；`%w` 会真正包装原错误，形成 error chain。

---

## Go：为什么推荐 `errors.Is` 而不是 `==`？

可以回答：

> 直接 `==` 只能比较当前错误值本身。错误经过 `%w` 包装后，外层已经是新的错误值，所以直接比较可能失败。`errors.Is` 可以沿错误链继续查找目标错误，因此更适合分层后端代码。

---

## Go：为什么测试错误分支？

可以回答：

> 函数契约不仅规定什么时候成功和返回什么，也规定什么时候应该失败以及为什么失败。所以单元测试不仅应该验证成功结果，还应该验证错误分支是否返回了预期的错误语义，即是否“以正确原因失败”。

---
