## 2. 拷贝构造与拷贝赋值的区别

已经理解：

```cpp
Student s2 = s1;
```

表示：

```text
使用已有对象 s1
初始化一个新的对象 s2
```

因此调用：

```cpp
Student(const Student& other)
```

即：

```text
拷贝构造函数
```

而：

```cpp
Student s2(10);

s2 = s1;
```

此时：

```text
s1 已经存在
s2 也已经存在
```

所以并不是创建新对象，而是在修改一个已有对象。

调用：

```cpp
Student& operator=(const Student& other)
```

即：

```text
拷贝赋值运算符
```

核心区别：

```text
Student s2 = s1;
        ↓
创建新对象
        ↓
拷贝构造


s2 = s1;
        ↓
两个对象都已经存在
        ↓
拷贝赋值
```

# Part 2：默认拷贝赋值为什么有问题

测试：

```cpp
Student s1(22);
Student s2(10);

s2 = s1;
```

如果没有自己定义：

```cpp
operator=
```

编译器生成的拷贝赋值会进行成员级复制。

对于：

```cpp
int* age;
```

复制的是：

```text
指针值 / 内存地址
```

因此：

赋值之前：

```text
s1.age
   |
   ↓
地址 A
   |
   22


s2.age
   |
   ↓
地址 B
   |
   10
```

默认：

```cpp
s2 = s1;
```

之后：

```text
s1.age ───→ 地址 A
              ↑
s2.age ───────┘
```

同时还有一个额外问题：

`s2` 原本拥有的：

```text
地址 B
```

被直接覆盖掉。

由于已经没有指针保存地址 B：

```text
地址 B 无法再 delete
```

产生：

```text
内存泄漏
```

之后两个对象析构时又可能分别：

```cpp
delete age;
```

都尝试释放地址 A：

```text
double delete / double free
```

这是未定义行为。

因此默认的成员级拷贝赋值不适合拥有裸指针资源的类。

# Part 3：自定义拷贝赋值 operator=

实现：

```cpp
Student& operator=(const Student& other)
{
    if (this == &other)
    {
        return *this;
    }

    delete age;

    age = new int(*other.age);

    cout << "copy assignment" << endl;

    return *this;
}
```

测试：

```cpp
Student s1(22);
Student s2(10);

s2 = s1;

cout << *s1.age << endl;
cout << *s2.age << endl;
```

实际输出：

```text
constructor
constructor
copy assignment
22
22
destructor
destructor
```

说明自定义拷贝赋值成功。

## 拷贝赋值的执行过程

赋值前：

```text
s1
 |
 ↓
地址 A
 |
22


s2
 |
 ↓
地址 B
 |
10
```

执行：

```cpp
delete age;
```

此时释放：

```text
s2 原来的地址 B
```

然后：

```cpp
age = new int(*other.age);
```

重新申请一块独立内存：

```text
s1
 |
 ↓
地址 A
 |
22


s2
 |
 ↓
地址 C
 |
22
```

两者：

```text
值相同
地址不同
```

因此析构时可以分别释放自己的资源。

## 为什么需要：

```cpp
if (this == &other)
{
    return *this;
}
```

用于处理：

```cpp
s1 = s1;
```

这种自赋值。

如果没有检查：

```cpp
delete age;
```

会先释放自己的资源。

而：

```cpp
other
```

其实就是自己。

之后再访问：

```cpp
*other.age
```

就会访问已经释放的资源，产生未定义行为。

所以简单的拷贝赋值实现需要自赋值保护。

## 一个后续需要知道的工程细节

当前实现：

```cpp
delete age;
age = new int(*other.age);
```

用于学习没有问题。

但从异常安全角度看：

如果：

```cpp
new int(...)
```

抛异常，那么原来的 `age` 已经被删除。

对象可能处于资源丢失状态。

更强的工程写法可以使用：

```text
copy-and-swap
```

等方式增强异常安全。

当前阶段知道这一点即可。

# Part 6：移动构造闭卷题

## 问题 1

为什么：

```cpp
Student s2 = s1;
```

调用拷贝构造？

### 我的回答

因为这是用一个已存在的对象初始化另一个新对象，属于创建新对象的时候调用，且没有move关键字，故这是拷贝构造。

### 订正

核心正确。

更准确地说：

```cpp
Student s2 = s1;
```

是在使用一个已有对象：

```text
s1
```

初始化新的对象：

```text
s2
```

所以进入构造过程。

`s1` 是一个左值，因此匹配：

```cpp
Student(const Student& other)
```

也就是拷贝构造。

关键不是简单地看“有没有写 move 关键字”，而是看右侧表达式的值类别以及哪些构造函数可以匹配。

---

## 问题 2

为什么：

```cpp
Student s2 = std::move(s1);
```

调用移动构造？

### 我的回答

因为这是用一个已存在的对象初始化另一个新对象，属于创建新对象的时候调用，且有move关键字，故这是移动构造。

### 订正

核心正确。

`Student s2 = ...` 表示正在创建新的 `s2`。

而：

```cpp
std::move(s1)
```

把 `s1` 转换成一个允许参与移动语义的 xvalue。

因此可以匹配：

```cpp
Student(Student&& other)
```

所以调用移动构造。

特别注意：

```cpp
std::move
```

本身并不移动资源。

它只是完成值类别转换。

真正执行：

```text
资源转移
```

的是：

```cpp
Student(Student&& other)
```

内部代码。

---

## 问题 3

移动构造为什么必须：

```cpp
other.age = nullptr;
```

### 我的回答

防止double free问题，现有资源已经转交给新对象了，原对象已经没有资源管理权了，故置空。

### 订正

正确。

执行：

```cpp
age = other.age;
```

之后，如果不清空 `other.age`：

```text
新对象.age
和
other.age
```

仍然指向同一个资源。

两个对象析构时都可能：

```cpp
delete age;
```

导致：

```text
double free
```

所以需要：

```cpp
other.age = nullptr;
```

明确表示：

```text
源对象已经放弃资源所有权
```

在当前自定义类型中，移动后的源对象状态被明确设置成：

```text
age == nullptr
```

更一般地说，标准库类型的 moved-from object 通常要求仍然是：

```text
valid but unspecified state
```

即：

```text
仍然合法、可以析构、可以重新赋值
但具体值不一定有固定含义
```

---

## 问题 4

移动构造为什么比拷贝构造效率高？

### 我的回答

因为移动构造是直接转交资源控制权，而不是复制资源再重新分配内存，所以不用重新申请内存空间，故效率高。

### 订正

正确。

对于当前拥有动态资源的 `Student`：

拷贝构造：

```cpp
age = new int(*other.age);
```

需要：

```text
申请新内存
+
复制资源内容
```

而移动构造：

```cpp
age = other.age;
other.age = nullptr;
```

主要是：

```text
复制一个指针值
+
清空源指针
```

因此对于大型动态资源而言通常便宜很多。

但不能绝对地说：

```text
所有类型的 move 都一定比 copy 快
```

具体成本取决于类型自己的移动实现。

# Part 7：为什么移动构造参数是 `Student&&`

## 问题

为什么移动构造参数一定是：

```cpp
Student&&
```

而不是：

```cpp
Student&
```

### 我的回答

不太清楚。

### 订正

移动构造的语义是：

```text
资源可以从源对象中被转移走
```

如果写成：

```cpp
Student(Student& other)
```

普通左值：

```cpp
Student s1(22);
```

也可以绑定。

那么：

```cpp
Student s2 = s1;
```

可能直接把 `s1` 的资源拿走。

用户只是进行了普通对象初始化，却导致：

```text
s1 被修改
s1 失去资源
```

这是非常危险的。

C++11 引入：

```cpp
T&&
```

使移动语义可以针对：

```text
右值 / 即将被放弃的对象
```

进行重载。

普通：

```cpp
s1
```

是左值。

移动：

```cpp
std::move(s1)
```

将其转换成可以匹配：

```cpp
Student&&
```

的表达式。

因此：

```cpp
Student(const Student&)
```

表达：

```text
复制资源
```

而：

```cpp
Student(Student&&)
```

表达：

```text
允许转移资源
```

# Part 9：Rule of Five

对于一个直接管理资源的类，如果需要自己定义特殊成员函数，通常要一起考虑：

```text
1. 析构函数
2. 拷贝构造函数
3. 拷贝赋值运算符
4. 移动构造函数
5. 移动赋值运算符
```

这五个组成：

```text
Rule of Five
```

注意：

```text
普通构造函数不属于 Rule of Five
```

## noexcept 补充

工程中移动构造和移动赋值通常会考虑声明：

```cpp

```

例如：

```cpp

```

以及：


原因之一是：

# Part 10：Rule of Zero

现代 C++ 更希望避免手动管理：

```cpp

```

如果成员本身已经使用 RAII 类型：


```text
Rule of Zero
```

现代 C++ 一般优先：

```text
Rule of Zero
```

# Part 11：RAII

RAII：

```text
Resource Acquisition Is Initialization
```

中文通常译为：

```text
资源获取即初始化
```

核心思想不是：

```text
自动管理内存
```

而是：

```text
把资源生命周期绑定到对象生命周期
```

即：

```text
对象构造
    ↓
获取/接管资源

对象析构
    ↓
释放资源
```

---

## RAII 可以管理的资源

不仅是：

```text
内存
```

还包括：

```text
文件句柄
Socket
mutex 锁
数据库连接
线程相关资源
操作系统句柄
```

# Part 13：unique_ptr

## 核心语义

```text
独占所有权
```

例如：

```cpp
auto p = std::make_unique<Student>(22);
```

表示：

```text
只有 p 拥有该 Student 对象
```

`p` 生命周期结束：

```text
unique_ptr 析构
    ↓
自动释放 Student
```

无需手动：

```cpp
delete
```

---

## 为什么 unique_ptr 不能拷贝

### 问题

为什么 `unique_ptr` 不能拷贝，但是可以移动？

### 我的回答

因为拷贝会造成double free问题，而移动不会。

### 订正

核心正确。

更本质的原因是：

```text
unique_ptr 的类型语义就是独占所有权
```

如果允许：

```cpp
auto p2 = p1;
```

那么两个 `unique_ptr` 都认为自己拥有同一资源：

```text
p1 ──┐
     ↓
  Student
     ↑
p2 ──┘
```

这违反：

```text
独占所有权
```

也会导致两个对象析构时产生重复释放风险。

因此：


# Part 14：unique_ptr 移动问题

## 问题

为什么：

```cpp

```

之后：

```cpp

```

？

### 我的回答

因为这是移动赋值，p1会将资源控制权转交给p2，而自己不再控制资源，故将其置空。

### 订正

核心理解正确，但操作类型判断错误。

这里：

```cpp

```

是在：

```text

```

因此属于：

```text

```

而不是：

```text
移动赋值
```


本身不会把 `p1` 置空。


移动完成后：

# Part 18：shared_ptr 控制块

# Part 22：shared_ptr 循环引用

例如：


如果：


形成：

# Part 23：为什么 weak_ptr 需要 lock()

## 问题

为什么 `weak_ptr` 访问对象需要：

```cpp
lock()
```

而不能直接：

```cpp
w->xxx
```

？

### 我的回答

因为weak_ptr只是观察对象，不拥有对象。

### 订正

方向正确，但还缺最关键的一点：

正因为：

```text
weak_ptr 不拥有对象
```

所以：

```text
weak_ptr 自己存在
```

不代表：

```text
它观察的对象还存在
```

对象可能已经因为：

```text
所有 shared_ptr 都消失
```

而析构。

因此不能直接：

```cpp
w->age
```

否则无法保证访问时对象仍然存活。

正确方式：

```cpp
if (auto p = w.lock())
{
    cout << p->age << endl;
}
```

`lock()`：

```text
如果对象仍然存在
    ↓
获得一个新的 shared_ptr
    ↓
临时取得共享所有权
    ↓
在 p 生命周期内保证对象继续存活
```

如果对象已经不存在：

```text
lock()
    ↓
返回空 shared_ptr
```

# Part 29：RAII 闭卷题

## 问题 1

为什么 `doWork()` 中没有写：

```cpp
m.unlock()
```

`main()` 仍然能够再次获取 mutex？

### 我的回答

因为mutex是全局变量，各个局部函数均可访问。

### 订正

这个回答没有命中真正原因。

`mutex` 是全局变量只说明：

```text
doWork()
和
main()
```

访问的是：

```text
同一个 mutex
```

但如果 `doWork()` 把 mutex 锁住以后没有释放：

```cpp
m.lock();

return;
```

`main()` 即使能访问这个全局变量：

```cpp
m.try_lock();
```

依然会失败。

真正原因是：

```cpp
lock_guard<mutex> guard(m);
```

是一个局部 RAII 对象。

执行：

```cpp
return;
```

离开 `doWork()` 时：

```text
guard 生命周期结束
    ↓
guard 析构
    ↓
mutex 自动解锁
```

因此 `main()` 才能再次：

```cpp
m.try_lock();
```

成功。

核心区别：

```text
全局 mutex
    ↓
保证访问的是同一个 mutex


lock_guard 析构
    ↓
真正保证 mutex 被释放
```

## 问题 2

如果 `doWork()` 中途 return，为什么 `lock_guard` 仍然能够释放锁？

### 我的回答

因为lock_guard类中定义了析构函数，在对象生命周期结束时自动调用析构函数释放资源。

### 订正

正确。

`guard` 是局部对象。

函数执行：

```cpp
return;
```

离开其作用域时，C++ 自动销毁局部对象。

因此：

```text
guard 析构
    ↓
mutex 被释放
```

同样，在正常的 C++ 异常栈展开过程中：

```text
局部 RAII 对象
```

也会被依次析构。

这也是 RAII 提升异常安全性的关键原因之一。

## 问题 3

为什么说 RAII 不只是用来管理内存？

### 我的回答

因为RAII还可以用来管理锁、文件、数据库等资源。

### 订正

正确。

RAII 管理的是：

```text
具有获取和释放生命周期的资源
```

而不是只管理内存。

例如：

```text
unique_ptr
构造 → 接管动态内存
析构 → delete


lock_guard
构造 → 获取锁
析构 → 解锁


文件对象
构造 → 打开文件
析构 → 关闭文件


Socket RAII wrapper
构造 → 获取 Socket
析构 → close


数据库连接对象
构造/获取 → 获得连接
析构 → 归还/释放连接
```

RAII 的核心定义应该记成：

```text
将资源生命周期绑定到对象生命周期，
利用 C++ 确定性的析构自动完成资源释放。
```

# Part 58：Go 今日核心结论

必须记住：

```text
1. interface 描述行为契约。

2. Go interface 是隐式实现。

3. 一个类型不需要声明 implements。

4. 类型的方法集合满足接口要求，
   就自动满足该 interface。

5. interface 参数可以接收不同具体类型，
   前提是这些类型满足接口。

6. value receiver：
   T 的 method set 包含该方法，
   *T 的 method set 也包含该方法。

7. pointer receiver：
   该方法属于 *T 的 method set，
   T 不因此满足对应 interface。

8. 对可取地址变量调用 pointer receiver 方法时，
   Go 的 selector 语法可以自动取地址。

9. “某方法可以调用”
   不等于
   “该值类型实现了 interface”。

10. 后端业务层应该尽量依赖所需行为，
    而不是被某一个具体实现绑定。

11. NewUserService(notifier)
    是最简单的一种依赖注入。

12. Dependency Injection 不等于 DI 框架。

13. FakeNotifier 可以替代真实 EmailNotifier，
    从而避免单元测试依赖真实外部服务。

14. interface 可以显著提高可测试性。

15. Go 常见设计思想：
    consumer-defined interface。

16. 接口通常应该围绕消费者真正需要的能力设计。

17. Go 倾向 small interfaces。

18. 小接口的核心不是“方法越少越好”，
    而是“不要求消费者不需要的方法”。
```

# Part 63：今日最重要的面试级表达

## C++：什么是 RAII？

可以回答：

> RAII 是把资源的获取和释放绑定到对象生命周期的一种 C++ 资源管理思想。对象构造或初始化时取得资源，对象析构时自动释放资源，因此即使函数提前 return 或在正常异常栈展开过程中退出，也能通过析构完成清理。RAII 不只用于内存，也可以管理文件、Socket、mutex、数据库连接等资源。

---

## C++：std::move 做了什么？

可以回答：

> `std::move` 本身不会移动资源，它主要把表达式转换成适合参与移动语义的值类别，使移动构造或移动赋值等重载有机会被选择。真正的资源转移由类型自己的移动操作完成。

---

## C++：unique_ptr / shared_ptr / weak_ptr 区别？

可以回答：

> `unique_ptr` 表示独占所有权，不能拷贝但可以移动；`shared_ptr` 表示共享所有权，通过共享控制信息判断对象什么时候可以销毁；`weak_ptr` 是非拥有型观察者，不增加 shared ownership，常用于打破循环引用或安全观察对象生命周期，需要通过 `lock()` 尝试获得 `shared_ptr` 后再访问对象。

---

## Go：什么是 interface？

可以回答：

> Go 的 interface 描述一组行为契约。一个类型不需要显式声明 implements，只要它的方法集合包含接口要求的所有方法，就会隐式满足该 interface。

---

## Go：为什么后端中使用 interface？

可以回答：

> interface 可以让业务代码依赖行为抽象而不是某个具体实现，从而降低耦合。不同生产实现或测试 Fake 只要满足同一接口，就可以替换使用，因此也能提高代码的扩展性和可测试性。

---

## Go：什么是依赖注入？

可以回答：

> 当一个对象需要其他组件才能工作时，不在对象内部把依赖写死，而是由外部通过构造函数或参数等方式传入，这就是依赖注入。比如 `NewUserService(notifier Notifier)` 就是最简单的构造函数依赖注入。

---

## Go：为什么 interface 通常由消费者定义？

可以回答：

> interface 表达的是消费者真正需要什么行为，因此 Go 中常由使用依赖的一侧定义最小接口。具体实现不需要提前知道接口存在，只要方法集合满足接口要求即可隐式实现，这样可以降低提供方和消费方之间的耦合。

---

## Go：为什么倾向小接口？

可以回答：

> Go 倾向让 interface 只包含消费者真正需要的最小方法集合。这样实现者不需要实现无关方法，可以降低耦合和实现成本，也更方便替换实现以及编写测试 Fake。
