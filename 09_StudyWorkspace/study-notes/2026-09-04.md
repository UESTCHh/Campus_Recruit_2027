# 三、`std::deque`

## 3.1 deque 是什么

`deque` 全称：

```text
double-ended queue
```

中文：

```text
双端队列
```

它是一个真正的：

```text
Container
容器
```

其核心特点：

```text
可以在序列前端和后端
高效插入和删除元素
```

主要接口：

```cpp
push_front()
pop_front()

push_back()
pop_back()

front()
back()

operator[]
at()

size()
empty()
```

---

## 3.2 双端操作

例如：

```cpp
deque<int> numbers;

numbers.push_back(20);
numbers.push_back(30);

numbers.push_front(10);
numbers.push_back(40);
numbers.push_front(0);
```

最终：

```text
0 10 20 30 40
```

所以：

```text
push_front()
→ 前端插入

push_back()
→ 后端插入

pop_front()
→ 删除前端元素

pop_back()
→ 删除后端元素
```

---

# 四、deque 与 vector

`vector` 的重要特点：

```text
整体连续内存
```

因此尾部：

```cpp
push_back()
pop_back()
```

非常适合。

但是如果在最前端插入或删除：

```text
前面元素发生变化
↓
后面大量元素需要移动
↓
通常 O(n)
```

例如：

```cpp
v.insert(v.begin(), value);
```

前端插入通常：

```text
O(n)
```

---

而 `deque` 不要求所有元素位于一整块连续内存中。

其内部组织方式更适合双端扩展。

因此常见复杂度：

```text
push_front()
→ O(1)

pop_front()
→ O(1)

push_back()
→ O(1)

pop_back()
→ O(1)
```

今天暂时不深入 `deque` 的具体分段存储结构。

---

# 五、deque 的随机访问

虽然 `deque` 不保证整体连续存储，但是仍然支持：

```cpp
numbers[0]
numbers[1]
numbers[2]
```

以及：

```cpp
numbers.at(1)
```

随机访问常见复杂度：

```text
O(1)
```

因此：

```text
vector
→ 随机访问 O(1)

deque
→ 随机访问 O(1)
```

但两者底层存储结构不同。

---

# 六、vector vs deque

| 特性 | `vector` | `deque` |
|---|---|---|
| 随机访问 | O(1) | O(1) |
| `push_back()` | 通常 O(1) | O(1) |
| `pop_back()` | O(1) | O(1) |
| 前端插入 | 通常 O(n) | O(1) |
| 前端删除 | 通常 O(n) | O(1) |
| 整体连续内存 | 是 | 不保证 |
| 双端操作 | 不擅长前端 | 擅长 |

核心模型：

```text
vector
→ 连续存储
→ 尾部增长

deque
→ 不保证整体连续
→ 支持随机访问
→ 前后双端增长
```

不能因为 `deque` 支持更多双端操作，就认为：

```text
deque一定比vector好
```

应该根据实际访问模式选择数据结构。

---

# 七、deque vs queue

这两个概念不能混淆。

```cpp
deque<int>
```

属于：

```text
Container
真正负责存储元素
```

而：

```cpp
queue<int>
```

属于：

```text
Container Adaptor
容器适配器
```

`queue` 故意只暴露 FIFO 需要的接口。

例如：

```text
push
front
back
pop
```

不能：

```cpp
q[0];
```

而 `deque` 可以：

```cpp
d[0];
```

---

# 八、为什么 queue 默认适合使用 deque

Queue 的核心规则：

```text
FIFO
First In First Out
```

需要：

```text
从 back 加入元素
从 front 删除元素
```

而 `deque`：

```text
front 操作高效
+
back 操作高效
```

正好符合 Queue 的需求。

因此：

```cpp
queue<int>
```

默认可以理解为使用：

```cpp
deque<int>
```

作为底层容器。

关系：

```text
queue
→ 提供 FIFO 使用规则

deque
→ 真正负责底层元素存储
```

---

# 九、`operator[]` vs `at()`

对于：

```cpp
deque<int> d;
```

可以：

```cpp
d[index]
```

也可以：

```cpp
d.at(index)
```

区别：

```text
d[index]
→ 不进行边界检查
→ 越界属于 Undefined Behavior
```

而：

```text
d.at(index)
→ 进行边界检查
→ 越界抛出 std::out_of_range
```

这个规则也适用于：

```text
vector
string
```

等支持这两个接口的类型。

# 四十七、错误分支中的 `return`

代码：

```go
if r.Method != http.MethodGet {
    w.Header().Set(
        "Allow",
        http.MethodGet,
    )

    w.WriteHeader(
        http.StatusMethodNotAllowed,
    )

    fmt.Fprintln(
        w,
        "405 - method not allowed",
    )

    return
}
```

`return` 的作用：

```text
错误Response已经处理完
↓
立即结束当前Handler
```

```text
程序仍然会继续执行后面的正常GET逻辑
```

可能导致 Body：

```text
405 - method not allowed

```

这显然不正确。

这种模式以后 Go Backend 会大量出现：

```text
检查错误
↓
构造错误Response
↓
return
↓
正常业务逻辑
```
