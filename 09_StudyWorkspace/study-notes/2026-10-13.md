# 第一部分：C++ Day39｜二叉树结构与动态对象生命周期

## 一、Stage 1：二叉树结构

### 1. 与链表的知识衔接

```cpp
struct ListNode {
    int val;
    ListNode* next;
};

struct TreeNode {
    int val;
    TreeNode* left;
    TreeNode* right;

    TreeNode(int x)
        : val(x), left(nullptr), right(nullptr) {}
};
```

- 链表主要用 `next` 保存下一节点地址。
- 二叉树用 `left`、`right` 分别保存左右孩子节点地址；每个节点最多两个孩子，可以只有一个孩子，也可以没有孩子。
- `root` 是根节点指针；`nullptr` 可表示空树或某个不存在的孩子。
- `root->right->left->val` 表示先找到右孩子、再找到其左孩子，最后访问 `val`。链式访问途中每一个待解引用的指针都必须有效。

示例树：

```text
        1
       / \
      2   3
     / \
    4   5
```

| 节点 | 左孩子 | 右孩子 |
|---|---|---|
| 1 | 2 | 3 |
| 2 | 4 | 5 |
| 3 | 无 | 无 |
| 4 | 无 | 无 |
| 5 | 无 | 无 |

### 3. Stage 1 原始检查与逐题订正

#### 检查 1：TreeNode 字段和指针类型

**问题：** `val`、`left`、`right` 分别保存什么？为什么 `left` 和 `right` 必须是 `TreeNode*` 而不是 `int`？

**我的回答（原文）：**

> 1. `val`、`left`、`right` 各自保存什么？val保存数据，left保存左孩子节点位置，right保存右孩子节点位置
> 2. 为什么 `left` 和 `right` 是 `TreeNode*`，而不是 `int`？因为left保存左孩子节点位置，right保存右孩子节点位置，节点的类型是TreeNode，其位置应当由一个TreeNode\*指针类型来接收。

**订正：** ✅ 正确。`left`、`right` 保存的是孩子节点的**地址**，不是节点本身，也不是简单的整数值。访问某孩子的字段时使用 `root->left->val`。

**相关示例：**

```cpp
TreeNode n2(5);
root->left = &n2;          // 存入n2地址
cout << root->left->val;   // 访问n2的值5
```

**面试专用回答：**

> 二叉树节点通常包含数据字段和指向左右子节点的两个指针。由于子节点同样是 TreeNode 类型，因此使用 TreeNode* 保存对应节点地址，通过这些指针建立树形结构。

#### 检查 2：多级指针访问

**问题树：**

```text
        10
       /  \
      5    15
          /
         12
```

**我的回答（原文）：**

> root->val 10
>
> root->left->val 5
>
> root->right->val 15
>
> root->right->left->val 12

**订正：** ✅ 全部正确。`->` 连续出现只是逐层解引用并访问指针成员。

**相关示例：** `root->right` 是节点 15 的地址；`root->right->left` 是节点 12 的地址；再 `->val` 得到 `12`。

**面试专用回答：**

> 连续箭头运算符表示沿节点指针逐级访问，例如 root->right->left->val 表示根节点右孩子的左孩子所保存的值。

#### 检查 3：空指针解引用

**问题：** 当 `n1.right == nullptr` 时，为什么 `cout << root->right->val;` 错误？

**我的回答（原文）：**

> 因为n1节点没有右孩子，即n1的right指向的是空指针，而cout << root->right->val;则是访问空指针的操作，这是未定义的行为，程序可能会得到意想不到的结果，应当避免。所以在访问指针变量时，应当先判断指针是否为空，即是否指向空指针if(root->right != nullptr)

**订正：** ✅ 正确。对空指针解引用是未定义行为，可能崩溃，也可能表现为其他不可预期结果。

**相关示例：**

```cpp
if (root != nullptr && root->right != nullptr) {
    cout << root->right->val << '\n';
}
```

**面试专用回答：**

> 在访问二叉树节点的成员之前，需要确认相应节点指针非空，以避免空指针解引用导致未定义行为。递归树算法也经常使用 root == nullptr 作为终止条件。

## 二、Stage 2 过渡检查：根指针与空树

#### 检查 4：为什么是 `TreeNode* root`？

**我的回答（原文）：**

> 因为root需要保存的是二叉树头节点的位置，而不是头节点整个结构，所以需要用同类型的指针来接受该节点的地址。

**订正：** ✅ 正确。术语建议说“根节点”，不是“头节点”。指针便于传递节点地址和表示空树，但并非创建树的唯一形式：局部 `TreeNode root(1)` 同样合法。

**相关示例：** `TreeNode n1(10); TreeNode* root = &n1;`，二者通过 `n1.val` 和 `root->val` 均可访问 10。

**面试专用回答：**

> 树算法中常用 TreeNode* 保存根节点地址，便于连接和访问其他节点，也能以 nullptr 表示空树，并且能够在函数之间传递而不复制整个节点对象。

#### 检查 5：`root == nullptr` 的含义

**我的回答（原文）：**

> 表示头节点为空，即二叉树为空，没有任何节点。因为要先判断二叉树是否为空，否则遍历就会访问无效对象即空指针造成未定义的行为问题，产生不可预期的结果。

**订正：** ✅ 正确。根指针为空时代表空树；在递归中也用它代表当前子树为空。

**相关示例：**

```cpp
void printRoot(TreeNode* root) {
    if (root == nullptr) {
        cout << "Empty tree\n";
        return;
    }
    cout << root->val << '\n';
}
```

**面试专用回答：**

> nullptr 可以表示一棵空树。树遍历前先检查节点是否为空，可防止访问不存在的对象，也是递归遍历的一种常见终止条件。

## 三、Stage 2：new/delete 与对象生命周期

### 1. 为什么不能返回局部节点地址？

错误写法：

```cpp
TreeNode* createTree() {
    TreeNode root(1);  // 自动存储期对象
    return &root;      // 错误：函数返回后对象生命周期结束
}
```

正确的基础练习：

```cpp
TreeNode* createTree() {
    TreeNode* root = new TreeNode(1);
    return root;       // 返回动态对象地址
}
```

区分两者：

| 对象 | 何时结束生命周期 |
|---|---|
| 函数中的普通局部 TreeNode 对象 | 通常在离开作用域时自动销毁 |
| `new TreeNode(...)` 动态创建的对象 | 不因函数返回自动销毁，需要由所有者正确释放 |
| 指向动态对象的局部指针变量 `root` | 函数退出时这个局部变量结束生命周期，但动态对象仍可能存在 |

重要订正：动态对象在**创建函数返回后**能继续存在，不等于**进程退出后还可跨进程持久存在**；文件数据库才是前一日学习的持久化例子。

### 2. 为什么删除根节点不会自动删除整个树？

```cpp
TreeNode* root = new TreeNode(1);
root->left = new TreeNode(2);
root->right = new TreeNode(3);

delete root; // 当前TreeNode没有负责释放子节点的析构逻辑
```

- `delete root` 销毁根节点对象；`left` 和 `right` 是普通指针成员。
- 销毁普通指针成员**不会自动 delete 指针指向的对象**。
- 若已失去唯一可达的子节点地址，就可能内存泄漏。
- 对于这个固定例子，应先删除左右子节点，再删除根节点；对于真实复杂树，后续可以学习递归销毁或基于 RAII/智能指针的所有权管理。
- `delete root; root = nullptr;` 中 `delete` 才是释放资源操作，置空只清理这一个指针变量的值。

```cpp
struct TreeNode {

    TreeNode* left;

    cout << boolalpha;

         << (root->right->left == nullptr) << '\n';

    // 当前固定结构专用的手动释放顺序：先孩子，后父亲
    delete root->left->left;
    delete root->left;
    delete root->right;
    delete root;
    root = nullptr;

    return 0;
}
```

### 4. Stage 2 原始检查与逐题订正

#### 检查 1：局部对象与动态对象

**问题：** 为什么 `TreeNode root(1); return &root;` 有问题，而 `new TreeNode(1)` 返回地址可以在函数返回后继续使用？

**我的回答（原文）：**

> 前面这个函数是在函数内创建了一个局部对象节点，再返回该节点地址，但是局部对象在函数返回后会自动销毁，所以返回的地址指向的对象被销毁了，这时指针变为悬空指针，访问它是错误的行为，也达不到创建树的这个要求。
>
> 后面这个函数可以正常返回一个在函数结束后仍然有效的节点是因为在函数内用new动态创建了一个节点，该节点内存存放在堆上，生命周期需要手动管理，因此函数返回后甚至程序结束后可能依然存在，所以此时函数返回后节点依然存在，可以被其他函数使用，但要注意使用完后需要手动释放相关资源，防止造成内存泄漏。

**订正：** ✅ 主体正确；需修正“程序结束后可能依然存在”的说法。动态对象不会因**函数返回**而自动销毁，但通常在**进程终止**时其进程内存由操作系统回收，不能作为跨运行持久化数据。局部指针变量与动态对象分别有不同的生命周期。

**相关示例：**

```cpp
TreeNode* createNode() {
    return new TreeNode(10);
}
int main() {
    TreeNode* p = createNode();
    cout << p->val << '\n';
    delete p;
    p = nullptr;
}
```

**面试专用回答：**

> 普通局部对象在作用域结束时自动销毁，返回其地址会产生悬空指针。通过 new 创建的动态对象不会随函数返回自动销毁，因此可返回对象指针，但需通过正确的所有权管理释放资源，避免内存泄漏。

#### 检查 2：`new`、指针与 `delete`

**我的回答（原文）：**

> 1. `new TreeNode(10)` 返回的是什么？返回的是指向存放数据10的节点的指针
> 2. `root` 保存的是什么？保存的是存放数据10的节点的地址
> 3. 为什么使用结束后需要 `delete root`？因为该节点创建在堆上，堆上的内存生命周期需要手动管理，否则会造成内存泄漏等问题，好处就是生命周期长。

**订正：** ✅ 正确。`new` 创建并初始化对象，返回 `TreeNode*`；`delete` 用于销毁并释放对应动态资源。`root = nullptr` 不等于 `delete root`。

**相关示例：**

```cpp
TreeNode* root = new TreeNode(10);
// 错误：若没有其他指针，直接 root = nullptr 会丢失对象地址
// root = nullptr;
delete root;
root = nullptr;
```

**面试专用回答：**

> new 动态创建对象并返回指针，使用完毕后应通过 delete 或其他正确的资源管理方式释放。现代 C++ 通常优先使用 RAII 与智能指针降低手工资源管理风险。

#### 检查 3：删除父节点与子节点

**我的回答（原文）：**

> 不会，root只会释放其所指的对象，即存放数据1的根节点，而根节点的左孩子和右孩子不会被释放，因为根节点只存储左孩子和右孩子的地址，而非左孩子和右孩子节点本身，所以释放的是它们的地址，这样非但没有释放孩子节点，还导致孩子节点的地址丢失，造成资源泄漏，正确的做法是先释放左右孩子节点，再释放根节点

**订正：** ✅ 正确，措辞补充：`delete root` 销毁的是根节点对象，而不是另行“释放地址”。如果 TreeNode 只包含原始指针成员且没有递归析构逻辑，就不会自动删除子节点。

**相关示例：**

```cpp
TreeNode* root = new TreeNode(1);
root->left = new TreeNode(2);
root->right = new TreeNode(3);
delete root->left;
delete root->right;
delete root;
root = nullptr;
```

**面试专用回答：**

> 对于只通过原始指针连接、没有自动清理子节点逻辑的二叉树，delete 根节点不会自动释放其左右子树，应显式销毁所有动态节点或采用智能指针管理节点所有权。

## 二、Stage 1：`QueryRow()` 和错误处理

### 1. 单行 vs 多行查询

| API | 返回 | 读取方式 | 典型用途 |
|---|---|---|---|
| `db.Query()` | `(*sql.Rows, error)` | `rows.Next()` + `rows.Scan()` | 多条记录 |
| `db.QueryRow()` | `*sql.Row` | `row.Scan()` | 预期最多一条记录 |

`QueryRow()` 把查询过程中的错误延迟到 `Scan()` 返回；没有行时 `Scan()` 返回 `sql.ErrNoRows`。

```go
row := db.QueryRow(
    "SELECT id, name, age FROM students WHERE id = ?",
    1002,
)
err := row.Scan(&id, &name, &age)
```

### 2. `sql.ErrNoRows` 的业务含义

`id = 9999` 不存在时，不等于“数据库连接失败”。SQL 可能正常执行，但没有匹配的数据。

```go
if errors.Is(err, sql.ErrNoRows) {
    // 数据不存在，可以在未来的HTTP Handler中转换成404
} else if err != nil {
    // 其他实际数据库查询错误
}
```

### 3. 为什么要使用参数化查询？

安全写法：

```go
rows, err := db.Query(
    "SELECT id FROM students WHERE name = ?",
    name,
)
```

不推荐直接拼接来自用户的字符串：

```go
query := "SELECT id FROM students WHERE name = '" + name + "'"
rows, err := db.Query(query)
```

示例恶意字符串（仅用于解释 SQL 注入风险）：

```text
Alice' OR 1=1 --
```

拼接后：

```sql
SELECT id FROM students WHERE name = 'Alice' OR 1=1 --'
```

原 SQL 逻辑被改变；而占位符会把整段输入当作一个参数值，不将 `OR` 等解释为原 SQL 代码。

**注意：** 占位符主要绑定**数据值**，不能直接将任意列名、表名、排序方向作为普通参数值使用。动态 SQL 标识符必须另用白名单等方式处理。

## 三、Stage 1 原始检查与订正

#### 检查 1：Query 和 QueryRow

**我的回答（原文）：**

> 查询全部学生时通常会返回多条记录，所以用db.Query(...)查询，返回多行结果
>
> 而根据主键查询单个学生时只需要返回一条记录，即一行，所以更适合db.QueryRow(...)，返回单独一行结果。

**相关示例：**

```go

// 多行查询后需关闭Rows，并用Next+Scan遍历
```

**面试专用回答：**

> Query 返回多行结果集 *sql.Rows，需要通过 Next 和 Scan 遍历读取；QueryRow 返回 *sql.Row，适用于单条记录查询，通过 Scan 读取，并在没有匹配记录时返回 sql.ErrNoRows。

#### 检查 2：无记录与数据库错误

**我的回答（原文）：**

> 1. `Scan()` 会返回什么？会返回sql.ErrNoRows
> 2. 这是否意味着数据库连接失败？不是，这意味着数据库中没有找到该记录，但是查询操作本身是成功的，所以数据库连接实际是成功的
> 3. 为什么需要单独处理这种情况？因为可以区分没有找到对应记录和其他数据库查询错误

**订正：** ✅ 正确。应用层可以将没有记录映射为 HTTP 404，其他数据库故障则另行处理。

**相关示例：**

```go

    fmt.Println("Student not found")
} else if err != nil {
    log.Print(err)
}
```

**面试专用回答：**

> QueryRow 的 Scan 返回 sql.ErrNoRows 表示无匹配记录，不等于数据库连接失败。通过 errors.Is 区分无记录与其他数据库异常，让业务层做正确的错误转换。

#### 检查 3：Open、Ping 和参数化查询

**我的回答（原文）：**

> 1. 已经调用 `sql.Open()`，为什么还可能需要调用 `db.Ping()`？sql.Open只是创建数据库连接池管理对象，并不保证数据库连接成功，所以通过调用 `db.Ping()`  来判断数据库是否连接成功
> 2. SQL 里的 `?` 是什么作用？占位符，用于动态替代所需的参数，类似于函数调用时传入的参数
> 3. 为什么不直接把学生 ID 拼接到 SQL 字符串中？直接拼接会导致不同学生ID拼接后的字符串分析难度增高，比如当学生1的ID拼接到字符串中后，后续拼接学生2的ID则需要先将之前拼接的字符串中的学生ID去除，再拼接新的ID。

**订正：** 第 1、2 问 ✅；第 3 问 ⚠️ 需要纠正。直接拼接不必然需要先移除旧 ID，可以每次重新生成字符串。主要问题是可能使用户输入进入 SQL 语法结构，导致 SQL 注入风险；参数化查询可安全绑定数据值，也简化类型与转义处理。`db.Ping()` 只证明当前连接检查成功。

**相关示例：**

```go
// 正确，用户输入作为参数值绑定
row := db.QueryRow("SELECT id FROM students WHERE name = ?", name)
```

**面试专用回答：**

> sql.Open 创建 sql.DB 管理对象，但不保证已经连接成功，故可用 Ping 验证当前连接可用性。使用 ? 占位符参数化查询能将 SQL 结构与数据值分离，避免字符串拼接导致的 SQL 注入问题。

#### 针对性补充检查：SQL 注入

**问题：** A 直接拼接 name，B 用占位符绑定 name，哪种更安全？SQL 注入是什么？为什么 B 能避免？

**我的回答（原文）：**

> 1. 哪一种写法更安全？写法B
> 2. 什么是 SQL 注入？SQL注入即将用户输入当作SQL语句的一部分执行，改变了原有的SQL语法逻辑
> 3. 为什么写法 B 可以避免这里的 SQL 注入问题？写法B采用参数化查询，通过占位符绑定参数，将 SQL 结构与实际数据分离，用户输入会被当作一个普通的字符串值，数据库不会把其当作原始SQL语句里的运算符，同时便于正确处理不同类型的参数。

**订正：** ✅ 全部正确。补充参数化查询不能直接绑定任意表名、字段名或排序关键字。

**相关示例：** 恶意姓名 `Alice' OR 1=1 --` 在拼接 SQL 中可能改变筛选条件；在 `WHERE name = ?` 中则只是一段普通姓名字符串。

**面试专用回答：**

> SQL 注入是用户输入经过不安全拼接后被解释成 SQL 代码，改变原本执行逻辑的安全问题。参数化查询通过占位符分离 SQL 结构与数据，可避免这种用户参数值引发的 SQL 注入。

### 5. Stage 2 原始检查与逐题订正

#### 检查 1：函数的参数与返回值

**我的回答（原文）：**

> 1. `db *sql.DB` 为什么由外部传入，而不是在函数内部 `sql.Open()`？因为函数只负责查询业务，不负责初始化数据库连接等操作，数据库连接池管理对象初始化操作应放在程序启动阶段，而不是内部函数调用阶段。
> 2. `studentID` 的作用是什么？指明要查询学生的Id
> 3. 为什么返回 `(Student, error)` 两个值？Student则记录查询到的学生信息，error记录本次查询的结果成功与否，后续可以根据error 是否等于 nil、sql.ErrNoRows来判断查询是否发生了错误，并且错误属于什么类型。

**订正：** ✅ 完全正确。`error` 表示操作状态，也能区分“未找到记录”与“其他查询失败”。函数不自行创建/关闭数据库管理对象，以便复用资源和职责分离。

**相关示例：**

```go
student1, err1 := findStudentByID(db, 1001)
student2, err2 := findStudentByID(db, 1002)
_, _, _, _ = student1, student2, err1, err2
```

**面试专用回答：**

> 数据访问函数接收外部创建的 *sql.DB 和业务查询参数，复用数据库连接池管理对象，返回业务实体与 error。调用者再根据错误类型进行业务处理，避免数据访问函数管理整个程序生命周期。

#### 检查 2：Scan 与结构体字段

**我的回答（原文）：**

> 1. `Scan()` 会将查询结果写到哪里？写到结构体的成员变量里，即student.ID student.Name student.Age
> 2. 为什么 `Scan()` 的参数要按照查询列顺序排列？因为scan无法根据结构体的结构自动判断字段代表的含义
> 3. 为什么这里传的是 `&student.ID`，而不是 `student.ID`？因为要实际修改结构体的成员变量值，所以需要传入其地址，通过指针来修改原对象的值，否则无法正确写入值。

**订正：** ✅ 完全正确。`Scan` 根据 SQL SELECT 列**顺序**映射，而不是自动认结构体成员名字；必须传递指针或其他可写目标。

**相关示例：**

```go
// 查询列顺序：name, id, age
err := db.QueryRow(
    "SELECT name, id, age FROM students WHERE id = ?", 1002,
).Scan(&student.Name, &student.ID, &student.Age)
```

**面试专用回答：**

> Scan 按查询结果列顺序把当前行数据写入 Go 变量，所以接收参数的顺序必须与 SELECT 字段一致，且需要提供可写地址，例如结构体字段指针。

#### 检查 3：错误处理应由谁决定？

**我的回答（原文）：**

> 数据库查询函数不应该自行决定整个程序退出，因为数据库查询函数应当专注于查询以及查询的结果，不负责决定是否退出程序，应当由调用数据库查询函数的函数来根据返回的查询结果自行决定下一步操作。

**订正：** ✅ 完全正确。底层查询函数返回 error，上层决定记录日志、重试、返回 404/500 或退出；直接调用 `log.Fatal()` 会终止整个进程，也不会执行当前程序中已经注册的 defer。

**相关示例：**

```go
func findStudentByID(db *sql.DB, id int) (Student, error) {
```

**面试专用回答：**

> 数据访问函数应通过返回 error 向上层报告执行结果，而不应自行调用 log.Fatal 结束整个程序。让调用方根据业务语义统一处理错误，更符合职责分离，也提高函数复用性和可测试性。

# 第三部分：今天常见易错点与纠正清单

| 易错点 | 正确理解 |
|---|---|
| `root->left` 保存左孩子对象本身 | 保存的是指向子节点的地址 |
| 函数内局部 `TreeNode` 可以返回地址供外部使用 | 局部对象生命周期结束后地址会悬空 |
| `new` 创建的对象程序退出后可以像数据库一样持久存在 | 它只是不因创建函数返回而销毁，进程退出并非持久化机制 |
| `delete root` 会自动递归删除左右子树 | 原始指针成员不会自动 delete 指向的对象 |
| `root = nullptr` 等同于释放资源 | 置空不释放动态对象，应先正确释放对象 |
| `sql.Open` 保证已经连接成功 | 仅创建 `*sql.DB` 管理对象，需要 Ping 或实际操作检验 |
| `QueryRow` 返回 `(Row, error)` | 它返回 `*sql.Row`，查询错误经由 `Scan()` 返回 |
| 查不到记录意味着数据库连接失败 | 通常是 `sql.ErrNoRows`，需要与其他错误区分 |
| `Scan` 自动根据结构体字段名匹配 | 按 SELECT 的列顺序绑定目标 |
| 可以把任意用户输入拼接 SQL | 可能造成 SQL 注入，数据值应参数化绑定 |
| `findStudentByID` 内部遇错 `log.Fatal` | 返回 `error` 给上层，让上层决定处理策略 |

# 第四部分：今日核心面试问答速记

**Q1：二叉树节点为什么需要指针？**

> 节点通过指针保存左右子节点的地址，以建立树形结构，也能通过 nullptr 表示不存在的孩子或空树。

**Q2：为什么不能返回局部对象地址？**

> 普通局部对象在作用域结束后销毁，返回其地址会使外部指针悬空，后续解引用属于未定义行为。

**Q3：new/delete 的生命周期管理要注意什么？**

> new 动态创建对象，delete 负责销毁与释放；原始指针不自动管理其所指对象。现代 C++ 优先使用 RAII 和智能指针减少泄漏风险。

**Q4：Query 和 QueryRow 有何不同？**

> Query 用于多行结果，返回 *sql.Rows，并用 Next/Scan 遍历；QueryRow 返回 *sql.Row，用 Scan 读取一行并报告无记录错误。

**Q5：`sql.ErrNoRows` 表示什么？**

> 表示 SQL 查询没有匹配记录，并不代表数据库连接必然失败；可用 errors.Is 区分它和其他数据库错误。

**Q6：SQL 参数化查询有什么价值？**

> 将 SQL 语句结构和用户输入的参数值分离，防止用户输入作为 SQL 运算符或语句片段执行，降低 SQL 注入风险。

**Q7：`Scan` 为什么传地址？**

> 因为它要把查询结果写入变量，必须传递可写目标；并且目标参数按查询列的顺序排列。

**Q8：Repository 为什么不直接调用 `log.Fatal`？**

> 数据访问层应返回 error 而不是终止进程，使上层能够按业务场景做合适处理，提高解耦性、复用性和测试性。
