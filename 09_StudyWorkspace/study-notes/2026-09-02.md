# 第五阶段：为什么 set 元素不能直接修改

假设：

```cpp
auto it = numbers.find(30);
```

不能直接：

```cpp
*it = 100;
```

原因并不是简单：

```text
C++规定不允许
```

而是：

```text
set元素本身就是Key
```

同时：

```text
set依赖Comparator
维护有序关联结构
```

如果：

```text
10 20 30 40 50
```

直接把：

```text
30
↓
100
```

改掉，

可能形成：

```text
10 20 100 40 50
```

从而破坏容器内部已经建立的有序关系。

---

## 问题 6

### 我的回答

> 因为set本身存储的元素就是key值，是唯一的，而且set本身维护一个有序的结构，如果肆意修改元素，可能会导致原有的有序结构被打乱。set 中元素既是数据本身，也是决定容器组织结构的 Key，因此不能通过普通 iterator 直接修改。

### 订正

完全正确。

核心：

```text
set element
=
data
=
Key
```

而：

```text
Key
→ 参与Comparator定义的有序结构
```

所以不能通过普通 iterator 随意修改。

如果想：

```text
30 → 35
```

当前最简单方式：

```text
erase(30)
↓
insert(35)
```

# 第七阶段：std::multiset

`multiset` 和 `set` 最大区别：

```text
set
→ Key唯一

multiset
→ Key允许重复
```

例如：

```cpp
multiset<int> numbers;

numbers.insert(20);
numbers.insert(20);
numbers.insert(20);
```

最终：

```text
20
20
20
```

都会保留。

---

# multiset::count

如果存在：

```text
20 20 20
```

那么：

```cpp
numbers.count(20);
```

返回：

```text
3
```

因此：

```text
set::count(k)
→ 0 / 1

multiset::count(k)
→ 可能 > 1
```

---

# multiset 的边界范围

默认升序：

```text
lower_bound(20)
→ 第一个 >= 20

upper_bound(20)
→ 第一个 > 20
```

因此：

```text
[lower_bound(20), upper_bound(20))
```

恰好表示：

```text
所有等于20的元素
```

这也是 STL 中：

```text
[first, last)
```

左闭右开区间的重要应用。

---

# multiset::erase(key)

如果：

```text
20 20 20
```

执行：

```cpp
numbers.erase(20);
```

则：

```text
删除全部3个20
返回3
```

Go Channel 可以通过类型限制使用方向。

---

```go

```

允许：

```text

+

```

```go

```

只能：

```text

```

不能：

```text

```

---

## Receive-only Channel

```go

```

只能：

```text

```

不能：

```text

```

---

# 双向 Channel 的视角收窄

例如：

```go
ch := make(chan int)
```

类型：

```text
chan int
```

传给：

```go
func produce(ch chan<- int)
```

以后：

```text
底层仍然是同一个Channel
```

但在 `produce` 内：

```text
只能使用Send能力
```

同理：

```go
func consume(ch <-chan int)
```

只能 Receive。

---

# Channel Direction 的真正价值

不是：

```text
提高性能
```

而是：

```text
接口职责表达
+
编译期约束
```

例如：

```go
func produce(ch chan<- int)
```

清楚表达：

```text
produce只负责生产数据
```

如果函数内部尝试：

```go
<-ch
```

编译器就会直接拒绝。

# 第三阶段：Data Race

考虑：

```go
counter++
```

在一个 goroutine 中看起来只是简单的：

```text
+1
```

但概念上可以分为：

```text
Read
↓
Modify
↓
Write
```

因此它不是多个 goroutine 可以随意同时执行的不可分割操作。

---

# Lost Update

假设：

```text
counter = 100
```

Goroutine A：

```text
Read 100
Modify → 101
```

Goroutine B 同时：

```text
Read 100
Modify → 101
```

之后：

```text
A Write 101
B Write 101
```

最终：

```text
counter = 101
```

但实际上进行了两次：

```text
counter++
```

其中一次更新丢失。

# Data Race

今天采用的实用定义：

> 多个 goroutine 并发访问同一份共享数据，至少一个访问是写操作，并且这些访问没有得到正确同步，就可能产生 Data Race。

核心条件：

```text
Concurrent Access
+
Shared State
+
At Least One Write
+
Missing Synchronization
```

---

# 第四阶段：WaitGroup vs Mutex

之前已经学习：

```text
WaitGroup
→ 等待一组工作完成
```

今天增加：

```text
Mutex
→ 保护共享状态的互斥访问
```

二者解决的是不同问题。

---

# sync.Mutex

```go
var mu sync.Mutex
```

然后：

```go
mu.Lock()

counter++

mu.Unlock()
```

模型：

```text
Lock
↓
取得进入临界区的权限
↓
Critical Section
↓
访问共享状态
↓
Unlock
↓
释放锁
```

---

# Critical Section

临界区：

> 访问共享状态、不能让多个 goroutine 无同步并发执行的代码区域。

今天代码里的核心临界区：

```go
counter++
```

# Mutex 闭卷题订正

## 问题 1

### 我的回答

> 因为可能多个goroutine中都对counter进行了读写的操作，而恰巧某次读写的操作是同时发生的，那么可能会忽略掉一次更新

### 订正

核心正确。

完整：

```text
counter++

Read
↓
Modify
↓
Write
```

两个 goroutine 可能同时读取旧值，

然后分别计算相同新值并写回，

导致：

```text
Lost Update
```

---

## 问题 2

### 我的回答

> 多个goroutine对同一块内存资源进行操作，且至少有一个是write操作时

### 订正

需要补充：

```text
并发访问
+
至少一个写
+
没有正确同步
```

完整：

> 多个 goroutine 并发访问同一份共享数据，至少一个操作是写，并且这些访问缺少正确同步，就可能产生 Data Race。

---

## 问题 3

### 我的回答

> 因为wg.wait只能解决并发任务之间的等待，而Mutex解决的是互斥保护共享资源的问题（这个题暂时不知道怎么回答）

### 订正

其实核心已经正确。

`wg.Wait()`：

```text
等待worker全部完成
```

但 worker 运行过程中依然可能：

```text
A同时访问counter
B同时访问counter
```

因此：

```text
WaitGroup
→ 什么时候所有任务都完成？

Mutex
→ 同一时刻谁可以访问共享状态？
```

WaitGroup 不负责让 worker 之间互斥。

---

## 问题 4

### 我的回答

> 先在该goroutine中尝试获得锁，获得锁后在安全的临界区域中修改共享内存资源，再释放掉锁，解除独占状态

### 订正

完全正确。

```text
Lock
↓
进入临界区
↓
修改共享数据
↓
Unlock
```

---

## 问题 5

### 我的回答

> 临界区域，counter++

### 订正

正确。

```go
counter++
```

是当前程序真正需要互斥保护的：

```text
Critical Section
```

---

## 问题 6

### 我的回答

> 不安全，多个goroutine使用同一个内存资源需要遵守同一个mutex规则

### 订正

完全正确。

Mutex 不是自动附着到某个变量上的保护罩。

而是：

```text
共享状态访问协议
```

所有并发访问同一共享状态的代码，都必须遵守同一套同步规则。

---

## 问题 7

### 我的回答

> 因为碰巧出现的结果不能代表程序就没有发生Data Race

### 订正

完全正确。

```text
某一次结果正确
≠
并发同步正确
```

即使：

```text
counter: 200000
```

也不能单凭结果证明不存在 Data Race。

# 第五阶段：Race Detector

Go 可以使用：

```powershell
go run -race ...
```

动态检测程序运行期间发生的 Data Race。

今天实际进行了两个对照实验。

---

# 实验 1：mutex-demo

执行：

```powershell
go run -race .\mutex-demo
```

今日实际结果：

```text
counter: 200000
```

并且没有：

```text
WARNING: DATA RACE
```

说明当前这次运行中：

```text
Mutex成功保护了counter临界区
```

---

# 实验 2：race-demo

执行：

```powershell
go run -race .\race-demo
```

今日实际观察到：

```text
WARNING: DATA RACE
```

Race Detector 报告中指出：

```text
goroutine 8
goroutine 9
```

对同一内存地址存在：

```text
Read
Previous write

以及

Write
Previous write
```

最终实际输出还出现：

```text
counter: 200000
Found 2 data race(s)
exit status 66
```

这个实验非常重要。

虽然：

```text
counter恰好等于200000
```

Race Detector 仍然明确检测到：

```text
2 data race(s)
```

因此再次证明：

```text
结果恰好正确
≠
程序没有Data Race
```

# Go Day10 易错点

```text
1. select没有ready case
   且没有default
   → 阻塞

2. select有default
   且没有ready case
   → 立即执行default

3. default
   ≠ 其他case执行后必定执行

4. 多个case同时ready
   → 不能依赖源码顺序

5. for + select + 空default
   → 可能造成Busy Waiting

6. time.After()
   → 返回Channel
   → select中仍是Channel Operation

7. chan T
   → 双向

8. chan<- T
   → Send-only

9. <-chan T
   → Receive-only

10. Channel Direction
    → 主要用于职责表达和编译期约束
    ≠ 性能优化

11. ctx.Done()
    → Receive-only Channel
    → 通过Channel Closure通知取消

12. counter++
    → 概念上是Read-Modify-Write
    → 不是并发安全原子操作

13. WaitGroup
    → 等任务完成

14. Mutex
    → 保护共享状态互斥访问

15. WaitGroup不能代替Mutex

16. Mutex必须成为所有共享状态访问者共同遵守的规则

17. Critical Section
    → 需要同步保护的共享状态访问区域

18. counter最终结果正确
    ≠ 没有Data Race

19. Race Detector
    → 动态检测实际运行路径中发生的Race

20. Windows -race还依赖正确的C/MinGW运行环境
```
