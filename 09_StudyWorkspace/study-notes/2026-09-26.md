# 三、问题场景：距离原点最近的 K 个点

有很多二维坐标：

```text
(1,3)
(-2,2)
(5,8)
(0,1)
...
```

现在要求：

> 找出距离原点 `(0,0)` 最近的 K 个点。

一个点：

```text
(x,y)
```

到原点的欧氏距离：

```text
sqrt(x² + y²)
```

但是仅为了比较距离大小，没有必要真正计算平方根。

因为：

```text
x² + y²
```

越小：

```text
sqrt(x² + y²)
```

也一定越小。

因此可以直接定义：

```text
priority
→ distance²
→ x² + y²
```

---

# 四、距离平方作为 priority

例如：

```text
A = (1,3)

distance²
= 1² + 3²
= 10
```

：

```text
B = (-2,2)

distance²
= (-2)² + 2²
= 8
```

：

```text
C = (0,1)

distance²
= 0² + 1²
= 1
```

因此：

```text
C
→ 最近

B
→ 第二近

A
→ 更远
```

不需要真的计算：

```text
sqrt(1)
sqrt(8)
sqrt(10)
```

---

# 五、K Closest 本质是什么 Top K？

要求：

```text
距离最小的 K 个点
```

本质：

```text
Top K Smallest Priority
```

根据之前的 Heap 模型：

```text
保留最小的K个
↓
这K个里面最容易被淘汰的是谁？
↓
最大的那个
↓
让最大priority位于top()
↓
Size-K Max Heap
```

所以：

```text
K Closest Points
→ Size-K Max Heap
```

而不是：

```text
Min Heap
```

。

---

# 六、为什么“最近”反而使用 Max Heap？

这是今天继续强化的 Heap 判断原则。

不能看到：

```text
最近
最小
```

就条件反射：

```text
Min Heap
```

应该先问：

```text
我要长期保留谁？
```

答案：

```text
距离最小的K个
```

然后：

```text
这K个里面谁最容易被淘汰？
```

答案：

```text
距离最大的那个
```

所以必须：

```text
heap.top()
→ 当前K个最近点中最远的点
```

而：

```text
最大priority位于top()
```

意味着：

```text
Max Heap
```

。

# 八、为什么 Heap 不能只保存 distance？

题目最后要求返回：

```text
point
```

而不是：

```text
distance
```

例如：

```text
distance² = 8
```

最终真正需要的是：

```text
(-2,2)
```

因此再次出现：

```text
排名依据
≠
最终业务对象
```

所以 Heap 中需要同时保存：

```text
priority
+
business object
```

概念：

```text
(distance², point)
```

例如：

```text
(8, (-2,2))
```

其中：

```text
8
→ Heap priority

(-2,2)
→ 最终返回对象
```

# 十一、C++ 预热问题 3

## 问题

比较：

```text
LC347 Top K Frequent
```

和：

```text
K Closest Points
```

分别指出：

```text
原始对象
priority
额外转换
```

## 我的回答

```text
LC347：

原始对象 = 原数组元素值

priority = 元素出现的次数

需要的额外转换 = (frequency, Value)


K Closest Points：

原始对象 = 二维点坐标值

priority = 坐标到原点的距离

需要的额外转换 = (distance, point)
```

## 订正

核心完全正确。

进一步增加一个很重要的区别：

### LC347

```text
原始对象
→ value

priority
→ frequency
```

但 frequency 不能只根据当前 value 单独算出来。

需要先：

```text
遍历整个数组
↓
unordered_map
↓
value → frequency
```

所以：

```text
priority的产生方式
→ 统计 / 映射
```

Heap 候选：

```text
(frequency, value)
```

---

### K Closest Points

```text
原始对象
→ point(x,y)

priority
→ distance²
```

这个 priority 可以根据当前对象直接计算：

```text
x²+y²
```

不需要扫描整个输入以后才能知道。

所以：

```text
priority的产生方式
→ 当前对象直接计算
```

Heap 候选：

```text
(distance², point)
```

---

两者共同结构：

```text
原始业务对象
↓
获得priority
↓
(priority, object)
↓
Heap
↓
按照priority维护Top K
↓
返回object
```

不同点：

```text
LC347
→ priority需要全局统计获得

K Closest
→ priority可以根据当前对象直接计算
```

## 相关示例

LC347：

```text
value = 8
```

单独看到一个：

```text
8
```

无法知道它总共出现几次。

必须看完整数组。

K Closest：

```text
point = (3,4)
```

马上就能计算：

```text
distance²
= 3² + 4²
= 25
```

。

## 面试专用回答

> LC347 和 K Closest Points 都属于原始对象与 Heap priority 不同的 Top K 问题。LC347 需要先通过哈希表统计 frequency，再将 `(frequency, value)` 放入 Heap；K Closest Points 可以直接由当前点计算 `x²+y²`，再以 `(distance², point)` 作为 Heap 候选。

# 二十、Go 预热问题 1

## 问题

为什么不直接把：

```go
log.Println("request started")
```

复制到每一个 Handler？

## 我的回答

> 因为这是一个重复逻辑，如果每个Handler都重复写一遍这个，当handler数量多时，会造成效率低的问题，而且若某个handler不记得写还会造成逻辑错误，所以可以把这个公共逻辑从业务逻辑里提取出来，放到专门处理公共逻辑的中间件Middleware中统一处理

## 订正

核心完全正确。

需要调整：

```text
效率低
```

这里主要不是：

```text
程序运行效率
```

问题。

一个请求进入某个 Handler 时，该日志仍然只执行一次。

真正的问题是：

```text
代码重复
维护成本高
容易遗漏
修改困难
行为可能不一致
```

例如原来只有：

```text
request started
```

以后统一要求增加：

```text
Method
Path
耗时
```

如果有 20 个 Handler，就需要修改 20 个位置。

Middleware：

```text
修改一个公共位置
↓
所有使用它的Handler统一生效
```

所以 Middleware 的价值主要是：

```text
抽取公共逻辑
+
降低维护成本
+
保持行为一致
```

。

## 相关示例

没有 Middleware：

```text
userHandler
→ Logging + User Logic

productHandler
→ Logging + Product Logic

orderHandler
→ Logging + Order Logic
```

加入 Middleware：

```text
Logging Middleware
↓
不同业务Handler
```

：

```text
Middleware
→ 公共逻辑

Handler
→ 具体业务逻辑
```

## 面试专用回答

> Middleware 适合承载多个 Handler 共享的横切逻辑，例如日志、认证和 Request ID。将这些逻辑从具体业务 Handler 中抽离，可以减少代码重复、降低维护成本，并保证不同 Handler 使用一致的处理规则。

```text
w
```

## 订正

核心理解正确。

最重要的一点：

```text
+

```

# 二十二、Go 预热问题 3

## 问题

如果 Middleware：

```text
打印日志
↓
没有调用next.ServeHTTP(w,r)
↓
函数结束
```

真正业务 Handler 会不会执行？

## 我的回答

> 不会，因为没有调用next.ServeHTTP(w,r)的话，真正的业务处理逻辑根本没有执行，请求链在执行完中间件的打印日志公共逻辑后就结束了，直接跳到了return的环节。

## 订正

完全正确。

即使函数中没有显式：

```go
return
```

执行到函数末尾：

```go
}
```

也会自然返回。

所以：

```text
Request
↓
Middleware
↓
公共逻辑
↓
函数结束
```

如果缺少：

```go
next.ServeHTTP(w,r)
```

请求链就不会继续。

因此：

```text
next.ServeHTTP(w,r)
→ 让请求继续向后处理
```

以后 Middleware 也可以利用这个能力主动：

```text
截断请求链
```

例如认证失败：

```text
检查Token
↓
非法
↓
写401 Response
↓
return
```

这时就不应该执行后续业务 Handler。

当前只建立这个基本概念，不展开认证实现。

## 相关示例

有：

```go
log.Println("before")

next.ServeHTTP(w, r)
```

流程：

```text
before
↓
后续Handler
```

删除：

```go
next.ServeHTTP(w, r)
```

后：

```text
before
↓
结束
```

## 面试专用回答

> 如果 Middleware 不调用 `next.ServeHTTP(w, r)`，请求处理链会在当前 Middleware 结束，后续 Handler 不会执行。因此 Middleware 可以选择让请求继续，也可以在满足某些条件时直接写 Response 并截断请求链。

# 二十三、追问：Middleware 到底是什么类型？

今晚进一步提出问题：

> Middleware 是什么类型？它自己也是 Handler 吗？

这是理解 Middleware 代码结构非常重要的一步。

---

# 二十四、Middleware 不是一个固定内置类型

Go `net/http` 并没有一个必须叫：

```go
Middleware
```

的固定内置类型。

Middleware 更准确说：

```text
一种设计角色 / 包装模式
```

Go HTTP 中非常常见的 Middleware 写法：

```go
func(
    next http.Handler,
) http.Handler
```

即：

```text
输入：
http.Handler

输出：
http.Handler
```

因此可以把 Middleware 理解成：

```text
Handler
↓
Middleware包装
↓
新的Handler
```

。

---

# 二十五、Middleware 函数本身是不是 Handler？

例如：

```go
func loggingMiddleware(
    next http.Handler,
) http.Handler
```

这里：

```text
loggingMiddleware
```

本身是一个普通 Go 函数。

它的函数类型可以理解为：

```text
func(http.Handler) http.Handler
```

因此严格来说：

```text
loggingMiddleware函数本身
≠
http.Handler
```

。

它做的是：

```text
接收一个Handler
↓
包装
↓
返回另一个Handler
```

。

---

# 二十六、Middleware 返回的东西是什么？

看：

```go
return http.HandlerFunc(
    func(
        w http.ResponseWriter,
        r *http.Request,
    ) {
        log.Println("request started")

        next.ServeHTTP(w, r)
    },
)
```

这里最终返回的是一个：

```text
http.Handler
```

。

因此：

```text
Middleware包装函数本身
→ 通常不是Handler

Middleware调用后的返回结果
→ 是Handler
```

。

---

# 二十七、为什么经常说“Middleware也是一层Handler”？

虽然严格类型上：

```text
Middleware函数
≠ Handler
```

但是：

```text
Middleware包装后返回的对象
```

本身就是：

```text
http.Handler
```

而真正处理 Request 的也是这个包装后的 Handler。

因此从请求处理链的概念层面，经常会说：

```text
Middleware也是一层Handler
```

更准确理解：

```text
Middleware通过返回一个新的Handler
把公共逻辑插入请求处理链
```

。

---

# 二十八、Handler → Handler 模型

例如原始：

```text
User Handler
```

传入：

```text
Logging Middleware
```

：

```text
User Handler
↓
Logging Middleware包装
↓
Wrapped Handler
```

然后 Request 实际先进入：

```text
Wrapped Handler
```

：

```text
Request
↓
Wrapped Handler
↓
Logging逻辑
↓
next.ServeHTTP(w,r)
↓
User Handler
```

这就是：

```text
“包住Handler”
```

的含义。

---

# 二十九、`next` 为什么必须是 `http.Handler`？

`http.Handler` 接口核心：

```go
type Handler interface {
    ServeHTTP(
        ResponseWriter,
        *Request,
    )
}
```

所以 Middleware 不需要知道：

```text
next到底是什么具体类型
```

它只关心：

> next 能不能 `ServeHTTP(w,r)`？

因此 next 可以是：

```text
业务Handler
Middleware包装后的Handler
ServeMux
其他满足http.Handler接口的对象
```

这也是 Middleware 可以连续组合的基础。

---

# 三十、Middleware 类型问题最终模型

今晚最重要的结论：

```text
Middleware
不是一个固定的Go内置类型
```

常见形式：

```text

```

：

```text
Middleware包装函数本身

输入

输出
→ 一个新的Handler
```

> Middleware 也是 Handler 吗？

最准确：

```text

→ 是Handler
```

而从请求链角色上：

```text

```

。
