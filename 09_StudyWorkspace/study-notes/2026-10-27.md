# 二、C++ Stage 1：BST 中序遍历的有序性

## 2.1 学习背景

此前已经完成：

- Day48：LC700《二叉搜索树中的搜索》。
- Day49：LC98《验证二叉搜索树》。

今天进一步利用 BST 的有序性质解决：

**LeetCode 230《二叉搜索树中第 K 小的元素》**

题目：https://leetcode.cn/problems/kth-smallest-element-in-a-bst/

函数签名：

```cpp
int kthSmallest(TreeNode* root, int k);
```

题目要求返回 BST 中第 k 小的节点值。

## 2.2 什么是中序遍历？

二叉树三种常见 DFS 遍历顺序：

| 类型 | 顺序 |
|---|---|
| 前序遍历 | 根 → 左 → 右 |
| 中序遍历 | 左 → 根 → 右 |
| 后序遍历 | 左 → 右 → 根 |

中序遍历的关键是：

```cpp
// 先处理左子树
midSearch(root->left);

// 再处理当前节点
// ...

// 最后处理右子树
midSearch(root->right);
```

这里的“处理当前节点”可以是：

- 打印当前节点值。
- 将当前节点值放入数组。
- 增加计数器。
- 判断是否到达第 k 个节点。

## 2.3 为什么 BST 中序遍历天然升序？

BST 要求：

- 左子树全部节点值小于根节点。
- 右子树全部节点值大于根节点。
- 左右子树自身也满足 BST 性质。

中序遍历恰好先访问左子树、再访问根、最后访问右子树。

因此，合法且节点值互不重复的 BST 经过中序遍历后，可以得到严格递增序列。

例如：

```text
         8
       /   \
      3     10
     / \      \
    1   6      14
       / \    /
      4   7  13
```

中序遍历：

```text
1 → 3 → 4 → 6 → 7 → 8 → 10 → 13 → 14
```

不需要额外排序。

第 k 小的元素就是中序遍历时第 k 个真正被访问的节点值。

## 3.3 问题 3：count++ 应该放在哪里？

**问题：**

递归中序遍历包含：

```text
① 递归左子树
② 处理当前节点
③ 递归右子树
```

如果要统计访问到第几个节点，`count++` 应放在哪里？找到第 k 个节点时记录什么？

**我的回答（准确原话）：**

> 放在2？这个问题我不理解
>
> 我提出一个问题：我看到第k小的元素，想到了用之前学的priority_queue，不知道是否适合。

**订正：**

选择②是正确的。

本题真正需要理解的是：

**进入一个递归函数，不代表当前节点已经在中序序列中被访问。**

例如：

```text
       5
      / \
     3   8
```

调用 `midSearch(5)` 时，先递归访问节点 3。

实际中序处理顺序：

```text
3 → 5 → 8
```

对应：

```text
访问 3：count = 1
访问 5：count = 2
访问 8：count = 3
```

所以 `++count` 应放在左递归返回之后、右递归调用之前。

**相关示例：**

```cpp
midSearch(root->left, k);

++count;  // 现在才轮到当前节点

midSearch(root->right, k);
```

若 k=2，则在访问节点 5 时记录答案。

还需要使用共享计数器，否则每一次递归都重新从 0 开始计数，无法正确判断全局中序排名。

**面试专用回答：**

中序遍历按照左、根、右顺序进行，因此在左子树处理完毕后才访问当前节点，此时增加计数器。当计数器等于 k 时，当前节点值就是第 k 小的元素。

# 四、补充讨论：priority_queue 能不能解决 LC230？

今天主动提出了使用优先队列寻找第 k 小元素的思路。

这个思路可行，但不是最适合 BST 的方法。

## 4.1 最小堆方案

将所有节点值插入最小堆。

然后取出前 k 个元素，第 k 个弹出的值就是答案。

如果逐个插入构建堆：

- 时间复杂度：`O(n log n)`。
- 堆空间复杂度：`O(n)`。

## 4.2 大小为 k 的最大堆方案

维护一个大小不超过 k 的最大堆。

堆中始终保留已经扫描过的最小 k 个值。

最终堆顶就是第 k 小的元素。

- 时间复杂度：`O(n log k)`。
- 堆本身空间复杂度：`O(k)`。

如果遍历树时采用递归，还需要额外的 `O(h)` 递归栈。

## 4.3 为什么今天优先使用中序遍历？

因为题目已经给出了 BST。

BST 的中序遍历本身就有序，无需用堆再次维护节点值的大小关系。

| 方法 | 时间复杂度 | 主要额外空间 |
|---|---|---|
| 最小堆，逐个插入 | O(n log n) | O(n) |
| 大小为 k 的最大堆 | O(n log k) | 堆 O(k) |
| 完整中序遍历 | O(n) | 递归栈 O(h) |
| 提前终止中序遍历 | O(h+k)，最坏 O(n) | 递归栈 O(h) |

**本日结论：**

能够联想到 `priority_queue` 是有效的算法知识迁移。但应结合输入数据结构的特殊性质选择方法。

# 五、C++ Stage 2：LC230 独立编码与错误定位

## 5.1 第一版：尝试通过递归返回值寻找答案

**我的原始代码：**

```cpp
class Solution {
public:
    int midSearch(TreeNode* root, int k){
        if(root == nullptr){
            return -1;
        }
        midSearch(root -> left, k);
        if(++count == k){
            return root -> val;
        }
        midSearch(root -> right, k);

        return -1;
    }
    int kthSmallest(TreeNode* root, int k) {
        return midSearch(root, k);
    }
private:
    int count = 0;
};
```

### 问题分析

第一版存在关键逻辑问题：

```cpp
midSearch(root->left, k);
midSearch(root->right, k);
```

调用了递归函数，却没有接收子递归返回的值。

假设：

```text
       3
      / \
     1   4
```

k=1。

节点 1 返回 1。

但父节点 3 没有接收这个结果。

随后父节点继续执行后续操作，最终可能返回 -1。

### 错误本质

**递归函数内部的 return 只结束当前函数调用，不会自动把结果一直返回到最外层。**

例如：

```cpp
int f() {
    return 100;
}

int g() {
    f();
    return -1;
}
```

调用 `g()` 返回 -1，而不是 100。

因为 `f()` 的返回值被忽略了。

### 本阶段订正

有两类解决方案：

1. 显式接收子递归返回值，并判断是否找到了答案。
2. 使用共享状态保存答案，再用 `found` 控制遍历。

本日选择第二种方式。

**实际记录：第一版由代码审查发现逻辑问题，没有提供这一版的 LeetCode 错误提交结果，因此不记录为实际提交失败。**

# 六、LC230 第二版：共享状态与提前终止

## 6.1 我的第二版代码

```cpp
class Solution {
public:
    void midSearch(TreeNode* root, int k) {
        // 1. 什么时候直接结束当前调用？
        if(root == nullptr){
            return;
        }
        // 2. 先递归左子树
        midSearch(root -> left, k);
        // 3. 如果左子树已经找到答案，应该怎么办？
        if(found == true) return;
        // 4. 处理当前节点：++count
        ++count;
        // 5. count == k 时保存答案
        if(count == k) {
            answer = root -> val;
            found = true;
        }
        // 6. 最后递归右子树
        midSearch(root -> right, k);
    }

    int kthSmallest(TreeNode* root, int k) {
        // 调用辅助函数并返回答案
        midSearch(root, k);
        return answer;
    }

private:
    int count = 0;
    int answer = 0;
    bool found = false;
};
```

## 6.2 第二版改进了什么？

将辅助函数从返回 `int` 改为返回 `void`。

使用三个成员变量：

```cpp
int count = 0;
int answer = 0;
bool found = false;
```

作用如下：

| 变量 | 作用 |
|---|---|
| count | 记录已经中序访问的节点数量 |
| answer | 保存第 k 小的节点值 |
| found | 表示是否已经找到答案 |

### 关键代码

```cpp
midSearch(root->left, k);

if (found) return;
```

左子树可能在递归过程中发现答案。

因此左递归返回到父节点后，必须重新判断 `found`。

如果已经找到，就不能继续处理当前节点和右子树。

## 6.3 第二版尚可优化的位置

```cpp
if(count == k) {
    answer = root->val;
    found = true;
}

midSearch(root->right, k);
```

保存答案之后，没有立即结束当前调用。

此时仍会进入一次右递归。

因此建议在记录答案后直接 `return`。

注意：第二版可以正确保存答案，但提前终止尚不够彻底。

## 7.3 对 found 的理解

用户原话：

作用：

# 八、LC230 课后深入复盘：三个优化版本

今天完成真实 CRUD 之后，又继续深入理解了 LC230 的递归提前终止。

这一部分是今天的重要学习成果，必须保留。

## 8.1 第一种：完整遍历版本

**我的代码：**

```cpp
class Solution {
public:
    void midSearch(TreeNode* root, int k){
        if(root == nullptr){
            return;
        }
        // 遍历左子树
        midSearch(root -> left, k);

        // 遍历当前节点
        if(++count == k){
            answer = root -> val;
        }

        // 遍历右子树
        midSearch(root -> right, k);
    }
    int kthSmallest(TreeNode* root, int k) {
        midSearch(root, k);
        return answer;
    }
private:
    int answer = -1;
    int count = 0;
};
```

### 特点

- 中序遍历顺序正确。
- 在第 k 个节点记录答案。
- 记录答案之后继续遍历剩余节点。
- 因为 `count` 不会再次等于 k，所以不会覆盖答案。

复杂度：

- 时间：`O(n)`。
- 额外空间：`O(h)`。

这是最基础、最容易写对的版本。

## 8.2 第二种：找到答案后只结束当前调用

**我的代码：**

```cpp
class Solution {
public:
    void midSearch(TreeNode* root, int k){
        if(root == nullptr){
            return;
        }
        // 遍历左子树
        midSearch(root -> left, k);

        // 遍历当前节点
        if(++count == k){
            answer = root -> val;
            //找到第k小后立刻返回，不再往遍历右子树了，所以这里优化的是不遍历右子树，但是返回还是返回给上层调用，而不是整个函数提前返回
            return;
        }

        // 遍历右子树
        midSearch(root -> right, k);
    }
    int kthSmallest(TreeNode* root, int k) {
        midSearch(root, k);
        return answer;
    }
private:
    int answer = -1;
    int count = 0;
};
```

### 本次独立理解

记录答案之后执行：

```cpp
return;
```

只结束当前节点对应的递归调用。

当前节点的右子树不再遍历。

但父节点仍然会从递归调用结束的位置继续执行后面的代码。

例如：

```text
       5
      / \
     3   8
```

k=1。

执行过程：

```text
midSearch(5)
    ↓
midSearch(3)
    ↓
找到 3，return
    ↓
回到 midSearch(5)
    ↓
继续处理节点 5
    ↓
继续处理节点 8
```

因此，这只是**局部提前返回**。

最坏时间复杂度仍然是 `O(n)`。

## 8.3 第三种：通过 found 实现完整提前终止

**我的代码：**

```cpp
class Solution {
public:
    void midSearch(TreeNode* root, int k){
        if(root == nullptr){
            return;
        }
        // 遍历左子树
        midSearch(root -> left, k);
        // 如果左子树找到答案了，直接返回，不再处理当前节点和右子树了，这里优化的是不遍历父节点以及父节点的右子树
        if(found == true) {
            return;
        }

        // 遍历当前节点
        if(++count == k){
            answer = root -> val;
            //代表当前已经找到值，需要将结果返回给上层，上层不需要再处理了。
            found = true;
            //找到第k小后立刻返回，不再往遍历右子树了，所以这里优化的是不遍历右子树，但是返回还是返回给上层调用，而不是整个函数提前返回
            return;
        }

        // 遍历右子树
        midSearch(root -> right, k);
    }
    int kthSmallest(TreeNode* root, int k) {
        midSearch(root, k);
        return answer;
    }
private:
    int answer = -1;
    int count = 0;
    //加一个判断值，用于返回上层
    bool found = false;
};
```

### 核心改进

```cpp
midSearch(root->left, k);

if (found) return;
```

左递归返回后，检查是否已经找到答案。

如果找到了：

- 不再增加当前节点计数。
- 不再访问当前节点右子树。
- 当前函数直接返回上层。

这实现了找到答案后逐层终止剩余遍历。

### 复杂度

- 时间上界：`O(h+k)`。
- 最坏时间：`O(n)`。
- 递归额外空间：`O(h)`。

这里的优化来源于提前停止，不是改变中序遍历原理。

### 验收说明

这一版代码逻辑已经检查正确。此前带函数开头 `found` 判断的版本有 LeetCode Accepted 反馈；没有另外提供这一份精简版本的独立提交输出，因此不虚构第二次提交记录。

# 九、重点复盘：到底要不要在函数开头判断 found？

## 9.1 今天的深入疑问

用户围绕以下问题进行了多轮思考：

> 函数开头加判断found是不是是为了在右子树发现答案时提前返回？这个有必要吗？给出具体的例子说明这种情况

随后要求：

> 你给的例子是在根节点的左子树中的某个右子树找到的，再给几个在在根节点的右子树中找到的例子

核心是弄清楚：

**答案在左子树或右子树中找到后，递归函数到底从哪里继续执行？**

## 9.2 最重要的结论

在目前的代码结构中：

```cpp
midSearch(root->left, k);

if (found) return;

if (++count == k) {
    answer = root->val;
    found = true;
    return;
}

midSearch(root->right, k);
```

由于右递归是最后一条语句：

**右递归返回后，当前函数已经没有后续操作，因此可以自然结束。**

所以此版本不需要为了正确提前终止而在函数开头额外判断 `found`。

但是：

**左递归返回后必须判断 found。**

因为左递归之后，还要处理当前节点和右子树。

### 牢记

判断是否需要 `found`，不是看答案位于整棵树的左边还是右边，而是看：

**对当前这一层递归而言，子函数返回后还有没有剩余操作。**

---

## 9.3 示例树

```text
            8
          /   \
         3     12
        / \   /  \
       1   6 10  15
            / \  / \
           9  11 14 16
```

中序遍历：

```text
1 → 3 → 6 → 8 → 9 → 10 → 11 → 12 → 14 → 15 → 16
```

下面分别分析四个答案都位于根节点 8 的右子树中的场景。

## 9.4 示例一：k=5，答案为 9

答案所在路径：

```text
8 → 12 → 10 → 9
```

节点 9 找到答案后：

```text
9：
找到答案，设置 found，return

10：
9 是 10 的左子树节点
左递归返回后检查 found
直接 return

12：
10 是 12 的左子树节点
左递归返回后检查 found
直接 return

8：
12 是 8 的右子树节点
右递归是最后一步
自然返回
```

因此：

- 节点 10 不再被访问计数。
- 节点 11 不再访问。
- 节点 12 不再被访问计数。
- 节点 15、14、16 都不再访问。

**虽然答案在根节点 8 的右子树中，但节点 10、12 仍需要左递归后的 found 判断。**

---

## 9.5 示例二：k=8，答案为 12

中序第 8 个节点是 12。

节点 12 找到答案：

```text
12 设置 found = true
    ↓
12 return
    ↓
回到 8
    ↓
8 的右递归已经完成
    ↓
8 自然返回
```

节点 12 的右子树不需要再遍历。

根节点 8 不需要额外判断。

---

## 9.6 示例三：k=9，答案为 14

路径：

```text
8 → 12 → 15 → 14
```

递归返回：

```text
14：找到答案，return
    ↓
15：左递归返回，if(found) return
    ↓
12：右递归结束，自然返回
    ↓
8：右递归结束，自然返回
```

这个例子说明：

- 节点 15 需要判断 `found`。
- 节点 12、8 不需要额外判断。

原因不是节点 15 属于整棵树的哪一边，而是**节点 14 属于节点 15 的左子树**。

---

## 9.7 示例四：k=10，答案为 15

路径：

```text
8 → 12 → 15
```

节点 15 找到答案并返回：

```text
15：设置 found，return
    ↓
12：右递归结束，自然返回
    ↓
8：右递归结束，自然返回
```

节点 15 的右子树 16 不会访问。

这种情况下，找到答案后的祖先调用甚至不需要再执行额外的 `found` 判断。

---

## 9.8 最终规律总结

| 情况 | 处理方式 |
|---|---|
| 当前节点为空 | `return` |
| 当前节点左子树发现答案 | 左递归返回后检查 `found` |
| 当前节点本身是答案 | 设置 `found=true` 并立即 `return` |
| 当前节点右子树发现答案 | 因右递归在最后，当前函数自然结束 |
| 函数开头增加 `if(found)` | 可以作为防御性判断，但目前并非必需 |

**本日最重要的递归收获：**

理解了 `return` 的作用范围，以及子递归返回后父函数具体从哪里继续执行。

这比单纯记住 LC230 的标准答案更重要。

# 十、LC230 最终推荐写法

基于今天的独立实现整理：

```cpp
class Solution {
public:
    void midSearch(TreeNode* root, int k) {
        if (root == nullptr) {
            return;
        }

        // 左
        midSearch(root->left, k);

        // 左子树可能已经找到答案
        if (found) {
            return;
        }

        // 根
        if (++count == k) {
            answer = root->val;
            found = true;
            return;
        }

        // 右
        midSearch(root->right, k);
    }

    int kthSmallest(TreeNode* root, int k) {
        // 支持同一个 Solution 对象重复查询
        count = 0;
        answer = -1;
        found = false;

        midSearch(root, k);
        return answer;
    }

private:
    int count = 0;
    int answer = -1;
    bool found = false;
};
```

这里最后补充了每次查询前的成员变量重置。

因为如果同一个 `Solution` 对象被用于多次独立查询，不重置成员状态可能影响后一次查询。

这是在用户正确的第三版基础上进行的代码整理，**不是声称这一整理版已经再次提交 LeetCode**。

### 面试专用回答

LC230 利用 BST 中序遍历天然递增的性质。递归时先处理左子树，再对当前节点计数，最后处理右子树。第 k 次访问时记录当前节点值。基础版完整中序遍历，时间复杂度 O(n)；可以通过 found 标记将找到答案的信息传递给祖先递归调用，提前终止后续遍历，使时间复杂度上界达到 O(h+k)，最坏仍为 O(n)。递归额外空间复杂度为 O(h)。

# 十八、今日易错点与重点复盘

## 18.1 C++：忽略递归返回值

错误形式：

```cpp
midSearch(root->left, k);
```

如果函数返回有效结果，却没有接收或向上传递，结果可能被丢弃。

## 18.2 C++：return 只结束当前调用

一个子递归 `return` 后，父函数会从调用语句之后继续执行。

不能误以为子函数返回会同时结束整条递归调用链。

## 18.3 C++：count++ 的位置

必须在中序遍历处理当前节点时增加计数器。

不能因为进入当前节点函数，就提前计数。

## 18.4 C++：找到答案后要通知祖先

完整提前终止需要让各层递归知道答案已经找到。

可以使用共享 `found` 状态。

## 18.5 C++：并非所有位置都需要 found 判断

左递归之后还有操作，所以必须检查。

右递归若位于函数最后，就可以自然结束。

## 18.6 C++：成员变量需要考虑重复调用

如果同一个 `Solution` 对象执行多次查询，应重置：

```cpp
count = 0;
answer = -1;
found = false;
```

## 18.7 Go：测试路由不要重复维护

如果生产代码与测试分别注册一套 HTTP 路由，就可能出现测试通过但实际服务路由错误的情况。

应尽量复用同一套注册函数。

## 18.8 Go：状态码不能只看是否为 2xx

需要根据接口语义检查预期状态码。

例如 DELETE 返回 204、删除后 GET 返回 404。

## 18.9 Go：真实 HTTP CRUD 必须完整闭环

应该验证：

```text
创建 → 查询 → 更新 → 重新查询 → 删除 → 删除后查询
```

而不是只看创建、更新、删除接口各自是否返回成功。
