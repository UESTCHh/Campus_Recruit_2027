# 六、Package 到底是什么？

这一步比 Module 更重要。

假设：

```text
calculator/
├── add.go
└── subtract.go
```

`add.go`：

```go
package calculator

func Add(a int, b int) int {
	return a + b
}
```

`subtract.go`：

```go
package calculator

func Subtract(a int, b int) int {
	return a - b
}
```

这不是两个独立小模块。

而是：

```text
add.go ───────┐
              │
              ├── package calculator
              │
subtract.go ──┘
```

也就是说：

> **Package 是 Go 真正重要的代码组织和编译单位之一，而 `.go` 文件更多是我们为了组织代码而拆开的源文件。**

# 七、一个非常关键的 Go 思维：文件之间不 import

这是 C/C++ 背景特别容易产生的误区。

假设：

```text
calculator/
├── add.go
└── subtract.go
```

两个文件都是：

```go
package calculator
```

`add.go` 可以定义：

```go
func Add(a int, b int) int {
	return a + b
}
```

然后 `subtract.go` 中可以直接使用这个 Package 内的东西。

你不会写：

```go
import "add.go"
```

Go 没这个思维。

真正的关系是：

```text
add.go ──────┐
             │
             ├── calculator Package
             │
subtract.go ─┘
```

所以：

> **Go 的 import 是 Package import Package，不是文件 import 文件。**

这是非常重要的一句话。

```text
Module: example.com/todo-service

├── package main
├── package user
└── package todo
```

---

# 十一、第 2 层：Package

目录：

```text
user/
```

里面：

```text
user.go
service.go
service_test.go
```

前两个可能：

```go
package user
```

所以：

```text
user.go ─────┐
             ├── package user
service.go ──┘
```

而它的 import path：

```text
example.com/todo-service/user
```

---

目录：

```text
todo/
```

对应：

```text
package todo
```

import path：

```text
example.com/todo-service/todo
```

---

# 十二、第 3 层：`.go` 文件

例如：

```text
user/user.go
```

可能负责定义数据：

```go
package user

type User struct {
	Name string
	Age  int
}
```

而：

```text
user/service.go
```

负责业务函数：

```go
package user

func IsAdult(user User) bool {
	return user.Age >= 18
}
```

虽然分成两个文件：

```text
user.go
service.go
```

但它们仍然属于：

```text
同一个 package user
```

因此 `service.go` 可以直接使用：

```go
User
```

不需要：

```go
import "user.go"
```

---

# 十三、Package 之间才需要 import

例如：

```text
cmd/server/main.go
```

属于：

```go
package main
```

它要使用：

```text
package user
```

那么：

```go
package main

import (
	"fmt"

	"example.com/todo-service/user"
)

func main() {
	u := user.User{
		Name: "hui",
		Age:  20,
	}

	fmt.Println(user.IsAdult(u))
}
```

注意这里：

```go
import "example.com/todo-service/user"
```

导入的是：

```text
user Package
```

不是：

```text
user.go
```

也不是：

```text
service.go
```

所以编程模型变成：

```text
package main
      │
      │ import
      ↓
package user
      │
      ├── user.go
      └── service.go
```

---

# 十四、为什么 Go 要这么设计？

因为调用方根本不应该关心：

```text
User 定义在哪个文件？
IsAdult 写在 service.go 还是 logic.go？
```

调用方只关心：

```text
我需要 package user 提供的 API
```

例如：

```go
user.User
user.IsAdult(...)
```

以后我们甚至可以把：

```text
service.go
```

改名：

```text
business.go
```

只要 Package API 不变：

```go
user.IsAdult(...)
```

调用者通常不用关心。

这就是：

> **文件是 Package 的内部组织细节，Package 才是对外协作边界。**

---

# 十五、为什么 Go 标识符有大小写区别？

这就开始和 Package 连接起来了。

例如：

```go
func IsAdult(user User) bool
```

`IsAdult`：

```text
I 大写
```

意味着可以被其他 Package 使用。

例如：

```go
user.IsAdult(...)
```

但如果写：

```go
func isAdult(user User) bool
```

小写：

```text
isAdult
```

它通常只能在：

```text
package user
```

内部使用。

因此 Go 很大程度通过：

```text
首字母大写 → exported
首字母小写 → unexported
```

控制 Package API。

这也进一步说明：

> **Package 才是 Go 很重要的封装边界。**

---

# 十六、`package main` 到底特殊在哪里？

普通 Package：

```go
package user
```

主要给其他 Package 使用。

特殊 Package：

```go
package main
```

表示它是一个可执行程序 Package。

如果其中有：

```go
func main()
```

那么：

```text
package main
+
func main()
    ↓
可以生成可执行程序
```

例如：

```text
cmd/server/
└── main.go
```

```go
package main

func main() {
	// application starts here
}
```

以后真实 Go 后端经常出现：

```text
cmd/
└── server/
    └── main.go
```

意思大致就是：

> 这里放一个可执行程序入口。

---

# 十七、一个 Module 可以有多个 `package main` 吗？

可以。

例如：

```text
my-tools/
├── go.mod
└── cmd/
    ├── server/
    │   └── main.go
    │
    └── migration/
        └── main.go
```

两个目录：

```text
cmd/server
cmd/migration
```

都可以分别是：

```go
package main
```

于是：

```text
一个 Module

├── server 可执行程序
└── migration 可执行程序
```

可以分别：

```bash
go run ./cmd/server
```

和：

```bash
go run ./cmd/migration
```

这也说明：

```text
Module
≠
一个可执行文件
```

一个 Module 可以产生多个不同的程序。

---

# 十八、这时候 `.` 就更容易理解了

假设我们站在：

```text
my-tools/cmd/server
```

执行：

```bash
go run .
```

`.`：

```text
当前目录
   ↓
当前目录对应的 Package
   ↓
package main
   ↓
运行 server
```

如果你站在：

```text
my-tools/cmd/migration
```

再：

```bash
go run .
```

运行的是另一个 Package：

```text
migration 的 package main
```

所以现在应该彻底避免：

```text
go run .
=
运行整个 Module
```

正确是：

> **运行 `.` 所匹配的当前 Package。**

---

# 十九、那 `./...` 又是什么？

这个以后你会经常看到。

例如：

```bash
go test ./...
```

这里和：

```bash
go test .
```

完全不同。

```text
.
→ 当前目录 Package
```

而：

```text
./...
→ 当前目录以及下面匹配到的所有 Packages
```

例如：

```text
todo-service/
├── package main
├── package user
└── package todo
```

在 Module 根目录：

```bash
go test .
```

可能主要测试：

```text
根目录 Package
```

而：

```bash
go test ./...
```

则会遍历：

```text
package main
package user
package todo
...
```

所以以后工程 CI 经常：

```bash
go test ./...
```

现在你应该能理解为什么是三个点了：

```text
.      → 一个当前 Package
./...  → 下面的一系列 Packages
```

---

# 二十、`_test.go` 文件到底是什么？

现在进入测试。

假设：

```text
calculator/
├── calculator.go
└── calculator_test.go
```

普通源码：

```go
package calculator

func Add(a int, b int) int {
	return a + b
}
```

测试：

```go
package calculator

import "testing"

func TestAdd(t *testing.T) {
	got := Add(2, 3)
	want := 5

	if got != want {
		t.Fatalf("got %d, want %d", got, want)
	}
}
```

关键点：

```text
calculator_test.go
```

不是一个新的 Module。

也不是正常运行程序需要的普通生产源文件。

它是：

> **Go 测试工具根据 `_test.go` 文件名约定识别的测试源码文件。**

---

# 二十一、普通 `.go` 与 `_test.go` 在什么时候参与？

例如：

```text
calculator/
├── add.go
├── subtract.go
└── calculator_test.go
```

运行：

```bash
go build .
```

主要构建：

```text
add.go
subtract.go
```

测试文件不会像普通生产文件那样成为最终库/程序的一部分。

而：

```bash
go test .
```

则大致可以理解：

```text
正常 Package 源码
+
_test.go 测试代码
    ↓
生成测试程序
    ↓
执行 TestXxx
```

所以：

```text
_test.go
```

是：

> **测试阶段参与构建的特殊 Go 源文件。**

---

# 二十二、为什么 `_test.go` 还写 `package calculator`？

例如：

```go
package calculator
```

这叫“同包测试”的一种典型方式。

优点是测试代码和被测代码处于相同 Package 视角。

甚至可以测试一些未导出的内部函数。

例如：

```go
package calculator

func normalize(value int) int {
	...
}
```

虽然：

```text
normalize
```

是小写，其他 Package 不能使用。

但是同包测试：

```go
package calculator
```

可以直接调用：

```go
normalize(...)
```

---

# 二十三、你以后还会看到另一种 `_test` Package

比如项目：

```text
calculator/
├── calculator.go
└── calculator_test.go
```

测试文件可能写：

```go
package calculator_test
```

而不是：

```go
package calculator
```

然后：

```go
import (
	"testing"

	"example.com/demo/calculator"
)

func TestAdd(t *testing.T) {
	got := calculator.Add(2, 3)
	...
}
```

这叫外部测试风格。

结构变成：

```text
package calculator
        ↑
        │ import
        │
package calculator_test
```

这种测试更像一个真正的外部用户：

> 我只能通过公开 API 使用 calculator。

所以它不能随便碰：

```text
calculator 内部小写未导出实现
```

---

# 二十四、两种测试方式的区别

先认识即可：

```text
package calculator

优点：
可以测试 Package 内部实现
可以访问未导出的标识符
```

而：

```text
package calculator_test

优点：
从外部调用者视角测试
更能验证公开 API 是否好用
不能依赖内部细节
```

以后写正式项目时我们再练。

今天知道：

```text
_test.go 不一定必须和生产代码写完全一样的 package 声明
```

这一点就够了。

# 二十六、`go.sum` 又是什么？

你问到了 Module，那么顺手认识它。

当项目依赖第三方 Module 时，经常出现：

```text
go.mod
go.sum
```

简单理解：

```text
go.mod
→ 我需要哪些 Module / 版本与模块配置
```

而：

```text
go.sum
→ 记录下载依赖相关内容的校验信息
```

帮助 Go 验证下载到的模块内容。

目前不要手改 `go.sum`。

通常交给 Go 工具管理。

---

# 二十七、第三方依赖为什么也是 Module？

比如以后使用某个第三方库。

你的代码写：

```go
import "github.com/someone/library/foo"
```

注意这里 import 的通常是一个：

```text
Package
```

但这个 Package 属于某个：

```text
第三方 Module
```

因此关系很容易看错：

```text
你的代码
   ↓ import
第三方 Package
   ↓ 属于
第三方 Module
```

所以：

> **代码 import Package，依赖管理主要以 Module 为单位。**

这句话很重要。

不是：

```text
import Module
```

严格意义上一般是导入某个 Package 路径。

---

# 二十八、为什么要分 Module 和 Package 两层？

因为它们解决的是两个不同的问题。

### Package 解决

```text
代码怎么组织？
哪些 API 对外暴露？
不同功能怎么分包？
代码之间怎么 import？
```

### Module 解决

```text
这些 Packages 属于哪个版本管理单位？
它们的 import path 前缀是什么？
工程依赖哪些外部 Modules？
应该使用什么版本？
```

所以可以记成：

```text
Module
→ 依赖、版本、模块身份层

Package
→ 代码组织、封装、复用层
```

这是非常核心的区别。

# 三十、最值得你建立的工程直觉

以后打开一个陌生 Go 项目，不要先问：

> main.go 在哪里？

而是按这个顺序看：

```text
① go.mod 在哪里？
      ↓
这个 Module 的根在哪里？

② module path 是什么？
      ↓
这个 Module 的身份是什么？

③ 有哪些目录？
      ↓
有哪些 Packages？

④ 每个目录里的 package 声明是什么？
      ↓
这个 Package 负责什么？

⑤ 哪些地方是 package main？
      ↓
有哪些可执行入口？

⑥ *_test.go 在哪里？
      ↓
哪些 Package 有测试？

⑦ Package 之间怎样 import？
      ↓
工程依赖关系是什么？
```

这才是比较接近 Go 工程师的看代码方式。

# 三十一、你现在可以把几个概念浓缩成这张表

| 概念 | 最核心的问题 |
|---|---|
| Module | “这一组 Packages 属于哪个模块/版本管理单位？” |
| `go.mod` | “这个 Module 的身份和依赖配置是什么？” |
| Package | “这一组代码作为一个什么功能单元协作和对外暴露？” |
| Directory | “一个 Package 通常物理上放在哪里？” |
| `.go` | “这个 Package 的代码怎样拆分成源文件？” |
| `package xxx` | “这个文件属于哪个 Package？” |
| `import` | “当前 Package 依赖哪个其他 Package？” |
| Function | “这个 Package 中的一段可调用逻辑是什么？” |
| `package main` | “这是可执行程序 Package。” |
| `func main()` | “可执行程序从哪里开始？” |
| `_test.go` | “这是测试阶段使用的 Go 源文件。” |
| `TestXxx` | “这是 `go test` 可以发现的测试函数。” |
| `go.sum` | “第三方模块内容的校验信息。” |

# 三十二、最后用一句更准确的话重新解释层级

以后面试或者自己复习时，你可以这样说：

> **Go Module 是由 `go.mod` 定义边界和 module path、并作为依赖版本管理单位的一组 Packages。一个 Module 可以包含多个 Packages；一个 Package 通常对应一个目录，由多个声明相同 package 的 `.go` 文件共同组成。`.go` 文件只是 Package 内部组织代码的物理文件，其中可以定义函数、类型、变量等；不同 Package 之间通过 import 协作，而同一 Package 的多个文件不需要互相 import。`*_test.go` 是测试阶段参与构建的特殊 Go 源文件，由 `go test` 根据约定发现并运行其中的测试。**

你现在要真正掌握的核心不是背这个长定义，而是下面五句话：

```text
Module 不是 go.mod，go.mod 只是描述 Module。

Module 管理的是一组 Packages。

Package 才是 Go 非常重要的代码组织和封装边界。

.go 文件属于 Package，同 Package 文件之间不互相 import。

代码 import Package；依赖版本主要由 Module 管理。
```

明天再开始正式学习时，我建议先用 **一个包含 `main + calculator` 两个 Package 的 15～20 行小实验**验证今天这套模型，而不是继续纯讲概念。这样你会第一次真正执行出：

```text
一个 Module
     ↓
两个 Packages
     ↓
main import calculator
     ↓
calculator 由多个 .go 文件组成
     ↓
calculator_test.go 测试 calculator
```

这会把今天的抽象理解彻底落到工程上。

这两个问题正好击中了 **Module 和 Package 最容易混淆的两个地方**。尤其第二个问题，也说明我前面用

```text
todo-service/
├── package main
├── package user
└── package todo
```

这种“逻辑图”容易让你误以为 Package 是目录树里真实存在的东西。我们现在把它彻底改成真实工程视角。

# 1. 一个项目为什么会有多个 Module？

首先要把“项目”这个词放松一点。

**项目并不是 Go 语言里的严格技术概念。**

我们平时说：

> 这个商城项目。

可能是指一个 Git 仓库，也可能是指一整套系统。

而 `Module` 是 Go 的明确技术概念。

所以完全可以出现：

```text
一个业务项目
    ↓
一个 Git 仓库
    ↓
多个 Go Module
```

例如一个公司的仓库：

```text
shop-project/
│
├── user-service/
│   ├── go.mod
│   └── ...
│
├── order-service/
│   ├── go.mod
│   └── ...
│
└── admin-tool/
    ├── go.mod
    └── ...
```

这里从业务角度看：

```text
shop-project
= 一个商城项目
```

但从 Go 的角度看：

```text
user-service   → Module A
order-service  → Module B
admin-tool     → Module C
```

因为存在三个独立的：

```text
go.mod
```

---

# 2. `go.mod` 实际上会形成 Module 边界

例如：

```text
shop-project/
│
├── user-service/
│   ├── go.mod
│   └── main.go
│
└── order-service/
    ├── go.mod
    └── main.go
```

`user-service/go.mod`：

```go
module example.com/shop/user-service

go 1.26.5
```

`order-service/go.mod`：

```go
module example.com/shop/order-service

go 1.26.5
```

那么：

```text
user-service/
    ↓
Module:
example.com/shop/user-service
```

和：

```text
order-service/
    ↓
Module:
example.com/shop/order-service
```

是两个独立 Module。

它们可以有：

```text
不同的 module path
不同的 dependencies
不同的依赖版本
不同的发布版本
不同的构建过程
```

这就是多个 Module 最实质的意义。

---

# 3. 为什么不直接做成一个 Module？

当然也可以。

比如：

```text
shop-project/
├── go.mod
├── user/
├── order/
└── admin/
```

只有最上面：

```text
go.mod
```

那么就是：

```text
一个 Module
│
├── package user
├── package order
└── package admin
```

这往往比多 Module 更简单。

所以：

> **不是项目稍微大一点就应该拆 Module。**

很多大型 Go 项目仍然可以只有一个 Module。

---

# 4. 那什么时候可能使用多个 Module？

一个很典型的原因是：

> 几个部分需要独立管理。

例如：

```text
company-platform/
│
├── sdk/
│   └── go.mod
│
├── server/
│   └── go.mod
│
└── cli/
    └── go.mod
```

可能：

```text
SDK
→ 给其他人引用
→ 单独发布 v1.2.0

Server
→ 公司服务器程序
→ 不需要和 SDK 同版本

CLI
→ 命令行工具
→ 有自己的依赖
```

于是：

```text
一个 Repository

├── Module SDK
├── Module Server
└── Module CLI
```

会比较合理。

另一个典型场景是 monorepo：

```text
company/
│
├── payment-service/
│   └── go.mod
│
├── user-service/
│   └── go.mod
│
└── notification-service/
    └── go.mod
```

业务上：

```text
一个公司大项目
```

Go 工程上：

```text
三个相对独立 Module
```

# 5. 一个 Module 能依赖另一个 Module 吗？

当然可以。

例如：

```text
shop/
├── common/
│   ├── go.mod
│   └── ...
│
└── server/
    ├── go.mod
    └── ...
```

假设：

```text
common Module
= example.com/shop/common
```

server 里的代码可以 import common 中的 Package。

概念关系是：

```text
server Module
      │
      │ dependency
      ↓
common Module
      │
      └── 某个 Package
```

注意这里又出现我们之前的重要区别：

> **依赖版本管理是 Module 层面的，而代码真正 `import` 的通常是 Package。**

例如：

```go
import "example.com/shop/common/logger"
```

这里代码使用的是：

```text
logger Package
```

它属于：

```text
example.com/shop/common Module
```

所以：

```text
Module A
   ↓ dependency
Module B
   ↓ contains
Package B1

Package A1
   ↓ import
Package B1
```

这两个层次同时存在。

# 6. 多 Module 本地一起开发怎么办？

你以后会看到一个文件：

```text
go.work
```

例如：

```text
shop/
├── go.work
│
├── user-service/
│   └── go.mod
│
└── order-service/
    └── go.mod
```

`go.work` 是 Go Workspace 相关的东西。

它可以把多个本地 Module 放进一个开发工作区。

逻辑上类似：

```text
Go Workspace
│
├── Module A
├── Module B
└── Module C
```

不过这个今天只需要认识名字。

**不要把 `go.work` 和 `go.mod` 混起来：**

```text
go.mod
→ 定义一个 Module

go.work
→ 可以帮助同时开发多个 Module
```

以后遇到真实多 Module 工程时再正式学。

---

# 7. 还有一种特别重要的情况：嵌套 Module

例如：

```text
project/
├── go.mod
├── main.go
│
└── tools/
    ├── go.mod
    └── tool.go
```

这并不是：

```text
外层 Module
└── 内层 Module 仍然普通属于外层
```

一旦：

```text
tools/go.mod
```

存在，`tools` 就建立了新的 Module 边界。

逻辑上更像：

```text
project/
│
├── Module A
│
│   ├── go.mod
│   └── main.go
│
└── Module B
    ├── go.mod
    └── tool.go
```

所以：

> **遇到新的 `go.mod`，通常意味着进入另一个 Module。**

这句话非常实用。

# 8. 现在回答第二个问题：什么叫“根目录 Package”？

这个问题非常好。

先把我之前的抽象写法：

```text
todo-service/
├── package main
├── package user
└── package todo
```

扔掉。

因为真实磁盘上根本不会有一个叫：

```text
package main
```

的文件。

真实工程应该长这样：

```text
todo-service/
│
├── go.mod
├── main.go
├── main_test.go
│
├── user/
│   ├── user.go
│   └── user_test.go
│
└── todo/
    ├── todo.go
    └── todo_test.go
```

假设 `go.mod`：

```go
module example.com/todo-service
```

---

# 9. 现在逐个目录看 Package

## 根目录

```text
todo-service/
├── main.go
└── main_test.go
```

`main.go`：

```go
package main

func main() {
}
```

所以：

```text
todo-service 这个目录
    ↓
对应 package main
```

这个就是我说的：

> **根目录 Package**

所谓“根目录”，就是：

```text
go.mod 所在目录
```

这里就是：

```text
todo-service/
```

因为这个目录里面存在普通 Go 源文件：

```text
main.go
```

并且它声明：

```go
package main
```

所以**根目录本身形成了一个 Package**。

---

# 10. `user/` 又是另一个 Package

```text
todo-service/user/
└── user.go
```

假设：

```go
package user
```

那么：

```text
user/
   ↓
package user
```

它的 import path 是：

```text
example.com/todo-service/user
```

---

# 11. `todo/` 又是一个 Package

```text
todo-service/todo/
└── todo.go
```

声明：

```go
package todo
```

于是：

```text
todo/
   ↓
package todo
```

import path：

```text
example.com/todo-service/todo
```

所以整个工程应该理解成：

```text
Module:
example.com/todo-service
│
├── 根目录
│   ├── main.go
│   └── main_test.go
│       ↓
│   package main
│
├── user/
│   ├── user.go
│   └── user_test.go
│       ↓
│   package user
│
└── todo/
    ├── todo.go
    └── todo_test.go
        ↓
    package todo
```

现在“根目录 Package”应该就清楚了：

> **它不是特殊种类的 Package，只是碰巧这个 Package 位于 Module 根目录。**

# 12. `go test .` 到底测试谁？

现在假设终端在：

```text
todo-service/
```

也就是：

```text
go.mod
```

所在目录。

执行：

```bash
go test .
```

其中：

```text
.
```

表示：

```text
当前目录
```

而当前目录对应：

```text
package main
```

所以：

```bash
go test .
```

测试的是：

```text
todo-service 根目录的 Package
```

也就是：

```text
package main
```

以及相应的：

```text
main_test.go
```

可以画成：

```text
当前目录 .
    ↓
todo-service/
    ↓
package main
    ↓
main.go + main_test.go
    ↓
go test
```

它**不会因为 user 和 todo 在子目录里，就自动测试它们**。

# 13. 所以 `go test .` 不测试 `user/`？

对。

在：

```text
todo-service/
```

执行：

```bash
go test .
```

主要针对：

```text
todo-service/
```

这个目录对应的 Package。

不会自动递归：

```text
user/
todo/
```

如果你要测试 user：

```bash
go test ./user
```

测试 todo：

```bash
go test ./todo
```

而想测试当前 Module 下的一系列 Packages：

```bash
go test ./...
```

这就是：

```text
.
```

和：

```text
./...
```

的巨大区别。

# 15. 一个非常关键的问题：Module 根目录一定有 Package 吗？

**不一定。**

这就是你第二个问题真正深入下去以后必须知道的地方。

假设：

```text
todo-service/
├── go.mod
│
├── cmd/
│   └── server/
│       └── main.go
│
├── user/
│   └── user.go
│
└── todo/
    └── todo.go
```

注意：

```text
todo-service/
```

根目录里只有：

```text
go.mod
```

没有：

```text
普通 .go 源文件
```

那么：

> **Module 根目录本身并没有一个普通 Go Package。**

因为 Package 是由目录里的 Go 源文件形成的。

也就是说：

```text
Module root
≠
必然有 root package
```

这非常重要。

指的是：

考虑：

```text
todo-service/
├── go.mod
├── cmd/server/
├── user/
└── todo/
```

Module 是：

```text
example.com/todo-service
```

它的边界从：

```text
go.mod
```

开始。

而 Package：

```text
cmd/server

```

分散在 Module 里的不同目录。

所以：

```text
Module
不是某个 Package

Module root
也不必是 Package

一个 Module
可以含 0/1/很多个 Package
```

# 21. 一个特别容易误解的表达

以后看到：

```text
Module root
```

和：

```text
root package
```

一定不要认为一样。

### Module root

指：

> `go.mod` 所在目录。

例如：

```text
/home/hui/shop/
```

有：

```text
/home/hui/shop/go.mod
```

所以：

```text
/home/hui/shop
```

是：

```text
Module root
```

---

### root package

指：

> 如果 Module 根目录本身包含组成某个 Package 的 `.go` 文件，那么这个目录对应的 Package，可以俗称 root package。

所以：

```text
Module root
```

一定存在。

但：

```text
root package
```

不一定存在。

这两个概念现在必须分开。

# 22. 再来看多 Module + Package，会彻底统一起来

假设一个真实 monorepo：

```text
shop/
│
├── user-service/
│   ├── go.mod
│   ├── cmd/
│   │   └── server/
│   │       └── main.go
│   └── user/
│       └── user.go
│
└── order-service/
    ├── go.mod
    ├── cmd/
    │   └── server/
    │       └── main.go
    └── order/
        └── order.go
```

我们从最外面开始看。

```text
shop/
```

只是：

```text
项目 / repository / monorepo
```

不一定是 Go Module。

---

里面：

```text
user-service/go.mod
```

定义：

```text
Module A
```

包含：

```text
package main
package user
```

---

而：

```text
order-service/go.mod
```

定义：

```text
Module B
```

包含：

```text
package main
package order
```

完整关系：

```text
一个业务项目 / Git Repository
│
├── Module A
│   │
│   ├── Package main
│   │   └── main.go
│   │
│   └── Package user
│       └── user.go
│
└── Module B
    │
    ├── Package main
    │   └── main.go
    │
    └── Package order
        └── order.go
```

这就是：

> **一个项目多个 Module**

最直观的工程形式。

# 23. 再多走一步：`go test ./...` 会跨另一个 Module 吗？

这个问题你现在已经有能力理解了。

假设：

```text
shop/
├── go.mod              ← Module A
├── main.go
│
└── tools/
    ├── go.mod          ← Module B
    └── tool.go
```

在 Module A 根目录执行：

```bash
go test ./...
```

不要简单理解成：

> 把硬盘下面所有目录都递归到底。

`tools/` 里面出现了新的：

```text
go.mod
```

它已经是另一个 Module 边界。

所以外层 Module 的 `./...` **不会把嵌套的另一个 Module 当成自己普通的 Package 来统一处理**。

这也进一步说明：

```text
go.mod
=
真正的 Module 边界
```

# 24. 用一句话分别回答你两个问题

### 问题 1：一个项目多个 Module 怎么理解？

> “项目”可以是业务或仓库层面的概念，而 Module 是 Go 的依赖和版本管理单位。因此一个项目/仓库完全可以包含多个独立 `go.mod`，每个 `go.mod` 定义一个独立 Module，每个 Module 再包含自己的 Packages。

---

### 问题 2：根目录 Package 是什么？

> Module 根目录就是 `go.mod` 所在目录。如果这个目录本身有普通 `.go` 文件组成某个 Package，那么这个 Package 就可以称为根目录 Package；如果根目录只有 `go.mod`、代码都在子目录，那么根目录本身根本没有 Package。

---

# 最后给你一张现在最值得记住的图

```text
项目 / Git Repository
│
│  这不是 Go 必须规定的层次
│
├── Module A
│   │
│   ├── go.mod
│   │
│   ├── Package A1
│   │   ├── a.go
│   │   └── a_test.go
│   │
│   └── Package A2
│       └── b.go
│
└── Module B
    │
    ├── go.mod
    │
    ├── Package B1
    │   └── c.go
    │
    └── Package B2
        └── d.go
```

然后命令是作用在不同范围：

```text
go test .
        ↓
当前目录对应的 Package


go test ./user
        ↓
指定 user 目录对应的 Package


go test ./...
        ↓
当前 Module 范围内，从当前目录向下匹配的一系列 Packages
```

而**不是**：

```text
.     = Module
./... = 整个电脑上的所有 Go 文件
```

这两个错误直觉现在可以彻底删掉了。
