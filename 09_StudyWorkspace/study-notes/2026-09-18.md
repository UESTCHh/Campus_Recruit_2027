# 三、Stage 1：为什么需要 Priority Queue？

## 1. 从动态最大值问题开始

假设不断加入：

```text
5
1
8
3
10
```

每次要求知道：

```text
当前最大值
```

普通 Queue：

```text
FIFO
First In First Out
```

关注：

```text
谁最早进入
```

Stack：

```text
LIFO
```

关注：

```text
谁最近进入
```

而 Priority Queue：

```text
谁的优先级最高
→ 谁优先处理
```

默认：

```cpp
priority_queue<int>
```

中：

```text
数值越大
→ 优先级越高
```

因此：

```cpp
pq.top()
```

始终得到当前最大值。

---

## 2. `maximum` 变量是否已经足够？

今天主动提出了一个非常重要的问题：

> 用一个常数变量 maximum 记录最大值，每次有新元素进入就跟其比较，这样不也能时刻获得最大元素吗？为什么还要用大顶堆？

答案：

如果需求真的只有：

```text
不断加入元素
+
查询历史最大值
```

那么：

```cpp
maximum = max(maximum, value);
```

完全足够。

复杂度：

```text
插入：O(1)
查询最大值：O(1)
额外空间：O(1)
```

甚至比 Heap 更简单。

Heap 真正解决的是：

```text
最大值被删除以后
还能快速获得新的最大值
```

例如：

```text
5 1 8 3 10
```

若：

```text
maximum = 10
```

删除 10 后：

```text
新的最大值 = 8
```

单独的 `maximum` 并不知道 8。

而 Max Heap：

```text
top = 10
↓
pop
↓
重新调整
↓
top = 8
```

因此 Heap 真正适合：

```text
动态加入元素
+
频繁查询最大 / 最小值
+
频繁删除最大 / 最小值
```

---

## 3. Priority Queue 基础接口

```cpp
priority_queue<int> pq;

pq.push(5);
pq.push(1);
pq.push(8);
pq.push(3);
```

得到：

```cpp
pq.top()
```

：

```text
8
```

不断：

```cpp
top()
pop()
```

得到：

```text
8 5 3 1
```

常见复杂度：

```text
top()  = O(1)
push() = O(log n)
pop()  = O(log n)
```

### 我的回答

### 订正

```text
Queue

Priority Queue

```

```cpp

```


```text

出去：

```

```text
进入：

出去：
8 5 1
```

### 面试专用回答

> `std::queue` 维护 FIFO 语义，最早进入的元素最先处理；`std::priority_queue` 根据优先级选择元素，默认 `priority_queue<int>` 中最大的元素具有最高优先级，因此 `top()` 始终得到当前最大值。

# 七、Stage 3：Binary Heap 的内部结构

## 1. Heap Property

一个 Max Heap：

```text
        10
       /  \
      8    9
     / \   /
    1   3 5
```

满足：

```text
10 >= 8
10 >= 9

8 >= 1
8 >= 3

9 >= 5
```

即：

```text
Parent >= Direct Children
```

注意：

Heap 并不要求全局完全排序。

---

## 2. Complete Binary Tree

Binary Heap 通常是一棵：

```text
Complete Binary Tree
完全二叉树
```

特点：

```text
从上到下
从左到右
依次填充
```

最后一层可以不满，但必须优先填左侧。

---

## 3. 数组表示 Heap

逻辑上的：

```text
        10
       /  \
      8    9
     / \   /
    1   3 5
```

可以存成：

```text
Index:
0  1  2  3  4  5

Value:
10 8  9  1  3  5
```

因此 Heap 不需要：

```cpp
Node* left;
Node* right;
```

也可以直接使用：

```cpp
vector
```

保存。

---

## 4. Parent / Child 下标关系

对于 0-based index：

```text
当前节点：
i
```

左孩子：

```text
2 * i + 1
```

右孩子：

```text
2 * i + 2
```

父节点：

```text
(i - 1) / 2
```

其中父节点公式要求：

```text
i > 0
```

---

# 八、为什么 `top()` 是 O(1)

Heap 始终维护：

```text
最高优先级元素
→ Root
```

数组实现：

```text
Root
→ Index 0
```

所以：

```cpp
top()
```

只是直接访问：

```text
index 0
```

无需遍历。

因此：

```text
O(1)
```

# 九、为什么 `push()` 是 O(log n)

加入新元素：

```text
先放到Complete Binary Tree最后一个位置
↓
与Parent比较
↓
违反Heap Property
↓
交换
↓
继续向上
```

该过程：

```text
Sift Up
```

最坏：

```text
Leaf
↓
Root
```

移动整棵树高度。

Complete Binary Tree：

```text
Height = O(log n)
```

所以：

```text
push = O(log n)
```

# 十、Push 最坏情况示例

原 Max Heap：

```text
        50
       /  \
     40    45
    / \    / \
   20 30  35 10
```

插入：

```text
100
```

先放最后：

```text
        50
       /  \
     40    45
    / \    / \
   20 30  35 10
  /
100
```

然后：

```text
100 > 20
→ swap
```

继续：

```text
100 > 40
→ swap
```

继续：

```text
100 > 50
→ swap
```

最终：

```text
       100
       /  \
     50    45
    / \    / \
   40 30  35 10
  /
20
```

移动：

```text
Leaf
→ Parent
→ Parent
→ Root
```

即 Sift Up 最坏情况。

# 十一、为什么 `pop()` 是 O(log n)

删除的是：

```text
Root
```

步骤：

```text
删除Root
↓
将最后一个元素移动到Root
↓
与Children比较
↓
违反Heap Property
↓
和优先级最高的Child交换
↓
继续向下
```

这个过程：

```text
Sift Down
```

最坏：

```text
Root
↓
Leaf
```

所以：

```text
pop = O(log n)
```

---

删除：


```text

```

```text
Root
↓
Leaf
```

# 十三、Stage 3 检查题

## 问题 1

为什么：

```text
        10
       /  \
      8    9
     / \   /
    1   3 5
```

是合法 Max Heap？

### 我的回答

> 因为每个父子局部关系都满足父节点大于等于所有子节点，并且节点紧凑，结构类似完全二叉树

### 订正

核心正确。

两个地方需要更精确：

第一：

不是：

```text
父节点 >= 所有子节点
```

而是：

```text
父节点 >= 自己的直接子节点
```

第二：

不是：

```text
类似完全二叉树
```

而是：

```text
Binary Heap 本身就是 Complete Binary Tree
```

### 相关示例

只需要检查：

```text
10 >= 8
10 >= 9

8 >= 1
8 >= 3

9 >= 5
```

不要求：

```text
10 9 8 5 3 1
```

这种全局顺序。

### 面试专用回答

> Binary Heap 通常是一棵 Complete Binary Tree。对于 Max Heap，每个父节点都不小于其直接子节点，因此最大元素位于根节点；Heap 只维护这种局部父子关系，并不要求所有元素整体有序。

## 问题 3

为什么 `push()` 是 O(log n)？

### 我的回答

> 新元素放在最后，然后比对和父节点的优先级关系，若不满足就替换，最多向上sift up整颗树的高度，即最多替换到root节点，而整棵树的高度即logn层，故O(logn)

### 订正

理解正确。

术语上：

```text
替换
```

更准确地说是：

```text
交换
```

完整：

```text
末尾插入
↓
与Parent比较
↓
必要时交换
↓
Sift Up
↓
最坏到Root
↓
O(log n)
```

### 面试专用回答

> 插入元素时先将其放在完全二叉树的最后一个位置，然后通过 Sift Up 与父节点不断比较并在必要时交换。最坏情况下新元素从叶节点一路移动到根节点，移动次数受树高限制，因此为 O(log n)。

---

## 问题 4

为什么 `pop()` 是 O(log n)？

### 我的回答

> 每次删除的是堆顶的元素即root，这时用最底下最后的元素来补充root，再依次判断其与子节点的关系，若不满足则将其替换成优先级最高的子节点，层层判断，最多sift down整棵树，而整棵树的高度即logn层，故O(logn)

### 订正

完全正确。

同样：

```text
替换
```

更准确是：

```text
交换
```

Max Heap：

```text
选择两个Child中更大的
```

Min Heap：

```text
选择两个Child中更小的
```

### 面试专用回答

> 删除堆顶时，通常先用最后一个元素替代 Root，然后通过 Sift Down 与优先级最高的子节点不断比较和交换，直到重新满足 Heap Property。最坏情况下该元素从 Root 移动到最底层，因此时间复杂度为 O(log n)。

# 十五、LeetCode 1046：Last Stone Weight

## 1. 题目核心

每轮：

```text
取得最大石头 y
↓
删除

取得第二大石头 x
↓
删除
```

如果：

```text
y == x
```

如果：

```text

```

```text

```

```text

```

块石头。

## 2. 为什么适合 Max Heap？

每轮都需要：

```text
取得最大值
↓
删除最大值
↓
再取得新的最大值
↓
删除
↓
可能插入新值
```

正好对应：

```text

pop

```

因此：

```cpp
priority_queue<int>
```

非常适合。

# 十六、LeetCode 1046 我的代码

```cpp
class Solution {
public:
    int lastStoneWeight(vector<int>& stones) {
        int n = static_cast<int>(stones.size());

        if (n == 1) {
            return stones[0];
        }

        priority_queue<int> pq;

        for (int i = 0; i < n; i++) {
            pq.push(stones[i]);
        }

        while (!pq.empty()) {
            int first = pq.top();
            pq.pop();

            if (pq.empty()) {
                return first;
            }

            int second = pq.top();
            pq.pop();

            if (first != second) {
                pq.push(abs(first - second));
            }
        }

        return 0;
    }
};
```

# 十七、代码订正

该实现逻辑正确。

由于：

```text
first
```

是第一次：

```cpp
pq.top()
```

得到的当前最大值，

删除以后：

```text
second
```

是剩余元素中的最大值，

因此一定：

```text
first >= second
```

所以：

```cpp
abs(first - second)
```

可以直接写成：

```cpp
first - second
```

此外循环也可以更直观写成：

```cpp
while (pq.size() >= 2)
```

因为题目的规则本身就是：

```text
至少还有两块石头
→ 才继续碰撞
```

一种更常见写法：

```cpp
class Solution {
public:
    int lastStoneWeight(vector<int>& stones) {
        priority_queue<int> pq;

        for (int stone : stones) {
            pq.push(stone);
        }

        while (pq.size() >= 2) {
            int first = pq.top();
            pq.pop();

            int second = pq.top();
            pq.pop();

            if (first != second) {
                pq.push(first - second);
            }
        }

        if (pq.empty()) {
            return 0;
        }

        return pq.top();
    }
};
```

# 二十五、C++ 今日易错点

1. Heap 不等于完整排序。

2. Max Heap 只要求：

```text
Parent >= Direct Children
```

不是所有节点全局有序。

3. Min Heap 的：

```text

```

是最小值。

4. 默认：

```cpp

```

是 Max Heap。

5. Min Heap：

```cpp

    int,
    vector<int>,
    greater<int>
```

> 一个是显示将普通函数转换成HandlerFunc类型并作为一个Handler传给Handle函数，而mux.HandleFunc( "/hello", helloHandler, )是直接隐式地将helloHandler转换成handler接口并注册路由

### 订正

前半句正确。

后半句需要更准确：

不是 Go 自动：

```text
普通函数
→ Handler interface
```

而是：

```text
HandleFunc
→ 接收符合签名的函数
→ 内部进行类似HandlerFunc的适配
→ 注册为Handler
```

显式：

```go
mux.Handle(
    "/hello",
    http.HandlerFunc(
        helloHandler,
    ),
)
```

方便写法：

```go
mux.HandleFunc(
    "/hello",
    helloHandler,
)
```

### 相关示例

```text
Handle
→ “给我的必须已经是Handler”

HandleFunc
→ “给我符合签名的函数，我帮你适配”
```

### 面试专用回答

> `ServeMux.Handle` 接收一个已经实现 `http.Handler` 的对象，因此普通函数通常需要显式使用 `http.HandlerFunc` 进行适配；`ServeMux.HandleFunc` 则是便捷方法，可以直接接收符合签名的函数，并在内部完成相应的 HandlerFunc 适配和路由注册。

## 问题 4

解释：

```text
Request
↓
ServeMux
↓
Handler.ServeHTTP(w, r)
↓
HandlerFunc.ServeHTTP(w, r)
↓
helloHandler(w, r)
```

### 我的回答

> 请求进入Server后先通过路由分发器ServeMux找到对应的Handler，而此时对应的Handler是被转换后的HandlerFunc类型，所以调用Handler.ServeHTTP(w, r)即先调用HandlerFunc.ServeHTTP(w, r)，而HandlerFunc.ServeHTTP(w, r)中则实际调用helloHandler(w, r)

### 订正

完全正确。

更加完整：

```text
Request
↓
ServeMux进行Route Matching
↓
找到Route对应的Handler
↓
调用Handler.ServeHTTP
↓
实际对象是HandlerFunc
↓
执行HandlerFunc.ServeHTTP
↓
内部f(w, r)
↓
f = helloHandler
↓
helloHandler(w, r)
```

### 面试专用回答

> `ServeMux` 匹配路由后会以 `http.Handler` 的形式调用对应处理器的 `ServeHTTP`。如果该 Handler 实际是由普通函数转换得到的 `http.HandlerFunc`，那么 `HandlerFunc.ServeHTTP` 内部会继续调用原始函数，因此最终执行具体的 Handler Function。

# 三十八、什么叫“符合签名的函数”？

今天继续提出：

> 符合签名的函数是什么样的函数？

`http.HandlerFunc` 对应的函数形式：

```go
func(
    http.ResponseWriter,
    *http.Request,
)
```

因此必须满足：

```text
第1个参数：
http.ResponseWriter

第2个参数：
*http.Request

返回值：
无
```

例如：

```go
func helloHandler(
    w http.ResponseWriter,
    r *http.Request,
) {
}
```

符合。

参数名字无所谓：

```go
func abc(
    x http.ResponseWriter,
    y *http.Request,
) {
}
```

也符合。

因为类型和顺序相同。

```go
func helloHandler(
```

少参数：

```go
func helloHandler(

) {
}
```

不符合。

多返回值：

```go
func helloHandler(
    w http.ResponseWriter,

    return nil
```

也不符合。

# 三十九、ServeMux 匹配的准确过程

今天提出：

> 所以ServeMux最先匹配到的是适配器类型HandlerFunc，再调用HandlerFunc.ServeHTTP来实际调用helloHandler(w, r)

核心方向正确，但需要更精确。

ServeMux 首先匹配的不是：

```text
HandlerFunc类型
```

而是：

```text
Route
```

例如：

```text
Path = /hello
```

ServeMux：

```text
匹配 /hello
↓
取得这条Route注册的Handler
```

这个 Handler 的具体类型恰好可能是：

```text
http.HandlerFunc
```

然后：

```text
Handler.ServeHTTP(w, r)
↓
HandlerFunc.ServeHTTP(w, r)
↓
helloHandler(w, r)
```

所以顺序：

```text
Request
↓
Route Matching
↓
找到Route对应Handler
↓
调用Handler
↓
HandlerFunc适配层
↓
普通helloHandler
```

# 四十五、Go 今日易错点

1. Server 和 ServeMux 不是同一个东西。

```text
Server
→ 监听端口、接Request

ServeMux
→ Routing
```

2. `ListenAndServe(":8080", nil)` 中：

```text
nil
```

不是“没有 Handler”，而是使用：

```text
DefaultServeMux
```

3. 包级：

```go
http.HandleFunc(...)
```

注册到：

```text
DefaultServeMux
```

4. 普通函数本身不直接实现：

```text
http.Handler
```

因为它没有：

```text
ServeHTTP
```

方法。

5. `HandlerFunc` 是适配器类型。

6. `HandleFunc` 是方便注册符合签名函数的方法。

7. ServeMux 首先匹配的是 Route，不是先寻找“HandlerFunc 类型”。

8. Handler Function 签名要求：

```go
func(
    http.ResponseWriter,
    *http.Request,
)
```

9. `log.Println`：

```text
Server终端
```

不是 HTTP Response。

10. `fmt.Fprintln(w, ...)`：

```text
HTTP Response
```

不是 Server 普通日志。

11. `log.Fatal`：

```text
记录错误
+
退出程序
```

12. Go 标识符区分大小写：

```text
ServeHTTP
```

不能写成：

```text
serveHttp
```
