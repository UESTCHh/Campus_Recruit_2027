# 十三、关于 right 的重要理解

最初曾使用：

```cpp
left = 1;
right = maxPile + 1;
```

这属于：

```text
[left,right)
```

半开区间 lower_bound 风格。

其中：

```text

```

更像：

```text
one-past-the-end哨兵
```

而不是一个实际答案。

为了让：

```text
right = 当前已知可行上界
```

这一语义从初始化开始就成立，最终采用：

```cpp
int left = 1;
int right = maxPile;
```

维护：

```text
真正答案 ∈ [left,right]
```

并且：

```text
right始终是已知可行上界
```

# 十四、关于半开区间的疑问

## 问题

```cpp
right = mid;
```

以后 `[left,right)` 已经不包含 mid，为什么还说 mid 没有被排除为答案？

## 结论

必须区分：

```text
不再需要搜索mid
```

和：

```text
证明mid不可能是答案
```

这是两件不同的事情。

当：

```text
canFinish(mid) == true
```

时：

```text
mid已经确认可行
```

所以不需要再次检查。

通过：

```cpp
right = mid;
```

把它保存成：

```text
当前已知可行边界
```

继续搜索左侧是否还有更小的可行答案。

如果左侧全部失败：

```text
left最终会推进到right
```

于是：

```text
left == right == mid
```

最终仍然返回 mid。

> 新的 [left,right) =[4, 5)，虽然 `5` 不在这个半开区间里了 ，但是此时right保存的就是5，即上次找到的可行边界，所以新的搜索空间可以从left开始一直搜索到right - 1，如果全部不符合条件这时left会最终== right，返回的刚好是上次找到的可行边界，所以right不仅是当前搜索空间的边界，还保存了上次搜索的可行答案。

## 订正

理解正确。

```text
对于right = maxPile + 1的最初状态，
right还只是排他右边界。

当right = mid发生后，
mid则是已经确认过的可行边界。
```

最终正式代码采用：

```text
[left,right]
```

模型：

```text
right从初始化开始就属于已知可行上界
```

### 面试专用回答

> 当 mid 可行时，令 `right = mid` 是把 mid 保存为当前可行上界，然后继续搜索左侧。如果左侧候选最终全部不可行，left 会推进到 right，此时返回的仍然是之前保存的可行边界。

# 十八、LeetCode 875 独立实现

## 我的代码

```cpp
class Solution {
public:
    int minEatingSpeed(vector<int>& piles, int h) {
        int n = static_cast<int> (piles.size());

        int maxPile =
            *max_element(
                piles.begin(),
                piles.end()
            );

        int left = 1;
        int right = maxPile;

        while(left < right){
            int mid =
                left + (right - left) / 2;

            long long int time = 0;

            for(int pile : piles){
                int hour =
                    (pile + mid - 1) / mid;

                time += hour;

                if(time > h) break;
            }

            if(time > h){
                left = mid + 1;
            }
            else{
                right = mid;
            }
        }

        return left;
    }
};
```

复杂度：

```text
时间复杂度 = O(n log M)
额外辅助空间复杂度 = O(1)
```

# 二十三、Stage 1：为什么需要 writeError

昨天每个错误分支直接：

```go
http.Error(
    w,
    message,
    status,
)
return
```

如果很多 Handler 都这样写：

```text
Handler A
Handler B
Handler C
...
```

错误响应实现细节就会散落整个项目。

因此先封装：

```go
func writeError(
    w http.ResponseWriter,
    status int,
    message string,
) {
    http.Error(
        w,
        message,
        status,
    )
}
```

目的：

```text
不是少写几行

而是：
统一错误响应实现
降低Handler耦合
提高维护性
```

# 二十五、Stage 1 检查 1

# 三十、错误顺序预测

错误：

```go
json.NewEncoder(w).Encode(...)

w.WriteHeader(status)
```

## 我的回答

> 1. JSON Body还能不能正常写出去？能
>
> 2. 客户端最终很可能看到的Status Code是400还是200？200
>
> 3. 为什么？因为在w.WriteHeader(status)之前已经显式地写了响应body已经默认提交了200 ok以及现有的header
>

全部正确。


```text
Header
→ WriteHeader
→ Encode
```

> `Encode` 会写 Response Body，而第一次写 Body 会隐式提交 200 和当前 Header，所以状态码必须在 Encode 前显式写入，Content-Type 又必须在响应提交前设置。

# 三十六、错误响应结构

```go
type errorResponse struct {
    Code    string `json:"code"`
    Message string `json:"message"`
}
```

Helper：

```go
func writeError(
    w http.ResponseWriter,
    status int,
    code string,
    message string,
) {
    w.Header().Set(
        "Content-Type",
        "application/json",
    )

    w.WriteHeader(status)

    json.NewEncoder(w).Encode(
        errorResponse{
            Code:    code,
            Message: message,
        },
    )
}
```
