### 1. C++：std::set

`std::set` 是一种有序关联容器，可以理解为：

> `set` 只保存元素本身，元素本身就是用于排序和查找的 Key，不存在独立的 mapped value。

与之前学习的 `map` 对比：

```text
map
Key → Value

set
Key
例如：
set<int> numbers;

numbers.insert(30);
numbers.insert(10);
numbers.insert(20);
numbers.insert(20);
最终集合中的元素为：
10
20
30
虽然 20 插入了两次，但普通 set 中元素必须唯一，因此最终只有一个 20。
2. set 的有序性
默认情况下，set 使用升序 Comparator 维护元素顺序。
因此即使按照：
30
10
20
的顺序插入，遍历时仍然得到：
10
20
30
需要注意：
真正决定排序规则的是 Comparator，而不是 set 这个名字本身。

默认情况下通常是升序，但可以通过传入自定义 Comparator 改变排序规则。
3. set 的查找
可以使用：
auto it = numbers.find(20);
如果找到：
it != numbers.end()
并可以通过：
*it
得到元素本身。
如果没有找到：
it == numbers.end()
因此：
auto it = numbers.find(20);

if (it != numbers.end())
{
    cout << *it << endl;
}
可以用于判断元素是否存在。
4. set 的 count()
普通 set 中元素唯一，因此：
numbers.count(20);
结果只能是：
0
1
含义分别是：
0 → 不存在
1 → 存在
这与之后会学习的 multiset 有区别。
5. set 的查找复杂度
set 内部维护有序结构，因此查找可以利用有序结构进行高效搜索。
通常：
find
→ O(log n)
与之前学习的：
unordered_map
→ 平均 O(1)
→ 最坏 O(n)
形成对比。
当前阶段可以先记住：
set
→ 有序
→ 元素唯一
→ O(log n) 查找

unordered_map
→ 无序
→ Key 唯一
→ 平均 O(1) 查找
三、Go：select
1. select 的基本作用
select 用于让一个 goroutine 同时等待多个 Channel 操作。
例如：
select {
case <-ch1:
    ...
case <-ch2:
    ...
}
可以理解为：
同时等待 ch1 和 ch2
        ↓
哪个 Channel 操作先 ready
        ↓
执行对应 case
它不是简单按照代码从上到下依次检查。
2. Channel ready
例如：
go func() {
    time.Sleep(300 * time.Millisecond)
    ch1 <- "message from ch1"
}()

go func() {
    time.Sleep(600 * time.Millisecond)
    ch2 <- "message from ch2"
}()
然后：
select {
case message := <-ch1:
    fmt.Println(message)

case message := <-ch2:
    fmt.Println(message)
}
由于 ch1 大约 300ms 后就可以接收，而 ch2 大约 600ms 后才可以接收，因此通常会先执行：
case <-ch1
3. select 与 Context cancellation
之前学习过：
select {
case <-ctx.Done():
    return ctx.Err()

case <-time.After(500 * time.Millisecond):
    // work finished
}
这里实际上是在同时等待两个事件：
ctx.Done()
→ Context cancellation

time.After(...)
→ 500ms 时间到达
哪个 case 先 ready，就先执行哪个。
因此，如果 Context 在 100ms 时取消：
100ms
→ ctx.Done() ready
→ 立即响应 cancellation
而不是必须等待 500ms。
4. 为什么 select 比 time.Sleep 更及时？
单独使用：
time.Sleep(500 * time.Millisecond)
时，当前 goroutine 会阻塞在 Sleep 上。
即使 Context 在 Sleep 中途已经取消，也不能直接通过这个 Sleep 操作响应取消信号。
通常需要等：
Sleep结束
↓
继续执行
↓
下一次检查ctx
↓
发现已经取消
而：
select {
case <-ctx.Done():
    ...
case <-time.After(500 * time.Millisecond):
    ...
}
可以同时等待：
Context cancellation
        或
500ms 到达
因此 cancellation 可以更及时地打断等待逻辑。
5. ctx.Done() 的本质
ctx.Done()
返回一个 Channel。
它主要不是用来传递业务数据，而是用于：
传递 Context 已经结束/取消的通知。

因此：
case <-ctx.Done():
中的：
<-
表示从 Channel 接收。
Context 被取消后，Done() 对应的 Channel 会关闭，从而让等待它的 goroutine 能够感知 cancellation。
