# 二、C++ Day41 Stage 1：二叉树 BFS 广度优先搜索

## 1. 回顾：昨天的 DFS 与今天的 BFS 有什么不同？

昨天我们学习了二叉树的三种递归遍历。

对于下面这棵二叉树：

昨天的前序遍历（DFS）：

```
1 → 2 → 4 → 5 → 3
```

会先沿着左子树深入，再返回处理其他节点。

而今天的 BFS（Breadth-First Search，广度优先搜索）：

```
1 → 2 → 3 → 4 → 5
```

会先处理距离根节点较近的节点，再向下一层扩展。

也就是：

```
第一层：1

第二层：2 3

第三层：4 5
```

因此，BFS 在二叉树中也经常被称为层序遍历。

## 2. 为什么 BFS 要使用队列？

你之前已经学过 `queue`。

队列的特点：

FIFO：First In, First Out，先进先出。

假设我们有一个队列：

```
queue<int> q;
```

执行：

```
q.push(1);
q.push(2);
q.push(3);
```

队列中：

```
队头                  队尾
 1       2       3
```

此时：

```
q.front(); // 1
```

然后：

```
q.pop();
```

队列变为：

```
队头          队尾
 2       3
```

BFS 正是利用这个特点：

> 谁先被发现，谁就先被处理。处理当前节点时，把它的左右孩子追加到队尾。

这样就可以保证上一层的节点先于下一层的节点被处理。

# 三、BFS 的执行过程

仍然使用这棵树：

```
        1
       / \
      2   3
     / \
    4   5
```

注意，我们要把节点指针放进队列，而不是只保存节点的值。

因此队列类型是：

```
queue<TreeNode*> q;
```

原因很简单：

如果只保存 `int val`，就无法通过该值继续访问节点的左右孩子。

但是如果保存 `TreeNode*`：

```
TreeNode* node = q.front();
```

就能够继续访问：

```
node->left;
node->right;
```

下面看完整过程。

| 步骤  | 处理的节点       | 处理后队列（队头 → 队尾） |
| --- | ----------- | -------------- |
| 初始化 | 尚未处理        | `[1]`          |
| 1   | 访问 1，加入 2、3 | `[2, 3]`       |
| 2   | 访问 2，加入 4、5 | `[3, 4, 5]`    |
| 3   | 访问 3，没有孩子   | `[4, 5]`       |
| 4   | 访问 4，没有孩子   | `[5]`          |
| 5   | 访问 5，没有孩子   | `[]`           |

队列为空，遍历结束。

最终：

```
1 2 3 4 5
```

这里有一个非常重要的理解：

BFS 并不是直接判断某个节点位于第几层，而是通过队列的先进先出顺序，自然实现逐层向外扩展。

## 2. 完整代码

```

#include <iostream>
#include <queue>

using namespace std;

// 二叉树节点
struct TreeNode {
    int val;
    TreeNode* left;
    TreeNode* right;

    TreeNode(int x)
        : val(x), left(nullptr), right(nullptr) {}
};

// BFS：使用队列实现层序遍历
void bfs(TreeNode* root) {
    // 空树直接返回
    if (root == nullptr) {
        return;
    }

    // 队列保存节点指针
    queue<TreeNode*> q;

    // 根节点首先进入队列
    q.push(root);

    // 队列不为空，就继续遍历
    while (!q.empty()) {
        // 获取队头节点
        TreeNode* current = q.front();

        // 移除队头
        q.pop();

        // 处理当前节点
        cout << current->val << " ";

        // 左孩子存在，就加入队列
        if (current->left != nullptr) {
            q.push(current->left);
        }

        // 右孩子存在，就加入队列
        if (current->right != nullptr) {
            q.push(current->right);
        }
    }
}

int main() {
    /*
            1
           / \
          2   3
         / \
        4   5
    */

    TreeNode n1(1);
    TreeNode n2(2);
    TreeNode n3(3);
    TreeNode n4(4);
    TreeNode n5(5);

    // 建立节点连接关系
    n1.left = &n2;
    n1.right = &n3;

    n2.left = &n4;
    n2.right = &n5;

    TreeNode* root = &n1;

    cout << "BFS: ";
    bfs(root);
    cout << '\n';

    return 0;
}

```

### 为什么这里没有使用 `new`？

因为本次实验中的五个节点都是在 `main()` 内创建的局部对象：

```
TreeNode n1(1);
```

在 `main()` 执行期间，这些节点都有效。

我们只是把它们的地址连接起来，所以不需要手动 `delete`。

这与之前 Day39 使用 `new TreeNode(...)` 动态创建节点的方式不同。

对于本次固定的局部对象实验，这样也能避免不必要的手动内存管理。

## 核心代码分析

```
while (!q.empty()) {
    TreeNode* current = q.front();
    q.pop();

    cout << current->val << " ";

    if (current->left != nullptr) {
        q.push(current->left);
    }

        q.push(current->right);

你要能够理解三件事：

第一，为什么先 `front()` 再 `pop()`？

因为要先保存当前队头节点的地址，才能移除队头并继续使用该节点。

第二，为什么需要判断左右孩子是否为空？

因为我们只希望把实际存在的节点加入队列。如果把 `nullptr` 加进去，后续直接执行 `current->val` 就可能发生空指针访问。

第三，为什么左孩子先入队、右孩子后入队？

因为题目要求每一层按照从左到右的顺序访问。

# 六、BFS 的时间与空间复杂度

这里要联系昨天晚间加练中订正的复杂度知识。

对于有 `n` 个节点的二叉树：

时间复杂度：`O(n)`

每个节点最多入队一次、出队一次，访问每个节点的操作总体为线性规模。

空间复杂度：`O(w)`

其中 `w` 表示二叉树的最大宽度，即节点最多的一层所包含的节点数。

因为 BFS 队列在遍历过程中需要保存尚未处理的节点。

最坏情况下：

```
O(w) = O(n)
```

所以 BFS 的最坏额外空间复杂度是 `O(n)`。

与昨天的 DFS 对比：

| 算法     | 时间复杂度  | 额外空间复杂度      |
| ------ | ------ | ------------ |
| 递归 DFS | `O(n)` | `O(h)`，递归调用栈 |
| 队列 BFS | `O(n)` | `O(w)`，队列    |

这里 `h` 表示树高，`w` 表示最大宽度。

这两个算法都是线性时间，但额外空间开销取决于不同的树形结构。

## 检查 3：BFS 的复杂度分析

### 问题

为什么时间复杂度是 `O(n)`？为什么空间复杂度不是 `O(1)`？`O(w)` 与 `O(h)` 分别代表什么？

### 我的回答

> 1. 为什么时间复杂度是 `O(n)`？因为每个节点入队一次，出队一次，处理时间都是O(1)，所以n个节点的复杂度就是O(1 \* n) = O(n)
> 2. 为什么空间复杂度不是一定为 `O(1)`？因为额外的空间负责度是依据队列的存储元素来决定的，当n=1时，队列最多存储一个元素，自然是O(1)，当n>1时，需要根据树的最大宽度来计算队列的最坏存储元素数量，即O(w)
> 3. BFS 的 `O(w)` 与递归 DFS 的 `O(h)` 分别代表什么？二叉树的最大宽度，二叉树的最大深度。

### 订正

✅ 核心全部正确。

这里补充两个细节。

第一，`w` 表示最大层宽，`h` 表示树高。

```
BFS：O(w) —— 队列空间

递归 DFS：O(h) —— 递归调用栈空间
```

你的答案正确。

第二，`O(w)` 并不意味着队列中的最大元素数量一定刚好等于最宽一层的节点数量。

因为遍历某一层的过程中，队列可能同时保存：

- 当前层尚未处理的节点。
- 下一层已经加入队列的节点。

但是队列规模仍然是 `O(w)`，最大不会超过最大层宽的常数倍。

此外，`n > 1` 的二叉树也可能只有宽度 1，例如退化为链表，此时 BFS 的额外队列空间仍是 `O(1)`。

因此严格的说法是：

> BFS 额外空间复杂度为 `O(w)`，最坏情况下为 `O(n)`，但具体使用多少空间取决于树的宽度。

### 相关示例

对于一棵退化为链表的二叉树：

```
1
 \
  2
   \
    3
     \
      4
```

每次队列中最多保存一个待处理节点：

```

```

对于一棵较为平衡的二叉树：

```

       /     \
      2       3
     / \     / \
    4   5   6   7
```

```
BFS 队列空间：O(w)，最坏 O(n)
DFS 递归栈空间：O(log n)
```

> 二叉树 BFS 使用队列实现，每个节点最多入队、出队一次，因此时间复杂度为 O(n)。额外空间用于保存待处理节点，与树的最大宽度有关，为 O(w)，最坏为 O(n)。递归 DFS 则依靠函数调用栈，其额外空间与树高有关，为 O(h)。

# 三、C++ Day41 Stage 2：LeetCode 102 二叉树的层序遍历

## 1. 题目要求

给定二叉树：

```
          3
         / \
        9   20
           /  \
          15   7
```

普通 BFS 输出：

```
3 9 20 15 7
```

但 LeetCode 102 要求：

按照层数，将每一层的节点分别放入一个数组中。

因此最终答案是：

```
{
    {3},
    {9, 20},
    {15, 7}
}
```

对应返回类型：

```
vector<vector<int>>
```

为什么是二维 `vector`？

因为：

```
vector<int>
```

只能表示一层：

```
{9, 20}
```

而：

```
vector<vector<int>>
```

能够表示多层：

```
{
    {3},
    {9, 20},
    {15, 7}
}
```

所以这道题和 Stage 1 最明显的区别是：

不仅要知道 BFS 的遍历顺序，还需要区分每一层的节点。

## 2. 问题来了：怎么知道当前层有多少个节点？

观察 BFS 的队列。

初始：

```
队列：[3]
```

第一层只有一个节点：

```
3
```

处理节点 3 后，将它的左右孩子入队：

```
队列：[9, 20]
```

此时队列中的两个节点，就是第二层需要处理的节点。

所以我们可以在每一层开始时，记录：

```
int levelSize = static_cast<int>(q.size());
```

它代表：

> 在这一层开始处理之前，队列里有多少个需要处理的节点。

接下来只处理这么多节点。

处理过程中，新加入队列的孩子节点属于下一层，不能混入当前层的遍历结果。

## 3. 关键：为什么要提前保存 `q.size()`？

假设：

```
队列：[9, 20]
```

我们先记录：

```
int levelSize = 2;
```

然后：

```
for (int i = 0; i < levelSize; i++) {
    // 处理当前层节点
}
```

循环处理：

```
第1次：处理9
第2次：处理20
```

处理节点 20 时，它的两个孩子 15、7 会进入队列：

```
队列：[15, 7]
```

但是因为：

```
levelSize == 2
```

当前层循环已经执行完两次，因此不会继续处理 15 和 7。

下一轮外层循环，再将 `[15, 7]` 视为新的一层。

这就是按层分组的核心。

# 四、通过可交互演示理解层序遍历

按层遍历过程

步骤 1/4

当前队列（队头 → 队尾）

3

已完成的层

尚未处理

根节点入队，准备开始第一层

&#x20;上一步下一步&#x20;

通过这个过程，可以明确二层循环的不同职责。

外层 `while`：控制一共有多少层。

```
while (!q.empty()) {
    // 处理当前层
}
```

内层 `for`：只处理当前层的节点。

```
int levelSize = static_cast<int>(q.size());

for (int i = 0; i < levelSize; i++) {
    // 取出当前层的节点
    // 把它的孩子加入队列
}
```

这就是 LeetCode 102 相比普通 BFS 新增的主要技巧。

### 订正

✅ 完全正确。

你已经抓住了 LeetCode 102 与普通 BFS 的本质区别：

当前层处理过程中，队列会不断发生变化，但当前层应该处理的节点数量必须保持固定。

例如：

```
        1
       / \
      2   3
     / \
    4   5
```

处理第二层时：

```
当前队列：[2, 3]
```

记录：

```
int levelSize = 2;
```

在内层循环中：

- 处理节点 2，加入节点 4、5。
- 处理节点 3，没有孩子。
- 当前层处理结束。

此时队列变成：

```
[4, 5]
```

但节点 4、5 属于第三层，不能放入第二层结果。

另外，动态使用 `q.size()` 不仅可能错误处理下一层，也可能因为队列变短而提前结束当前层循环。

### 相关示例

错误的写法：

```
for (int i = 0; i < q.size(); i++) {
    // 处理节点并添加孩子
}
```

这里 `q.size()` 每次判断循环条件时都可能变化，而且 `i` 与 `q.size()` 的类型也不同，容易引入问题。

正确写法：

```
int levelSize = static_cast<int>(q.size());

for (int i = 0; i < levelSize; i++) {
    // 只处理当前层的节点
}
```

### 面试专用回答

> 二叉树层序遍历需要在每一层开始时记录当前队列大小，作为本层需要处理的节点数量。因为处理当前节点时会将下一层节点加入队列，导致队列大小动态变化。如果直接使用变化的队列大小控制循环，可能导致层级混乱，因此必须提前固定当前层节点数量。

```
class Solution {
public:
    vector<vector<int>> levelOrder(TreeNode* root) {
        vector<vector<int>> answer;

        if (root == nullptr) {
            return answer;
        }

        queue<TreeNode*> q;

                }
                if (current->right != nullptr) {
                    q.push(current->right);
                }

        }

    }
};

### 相关示例

输入：

```
        3
       / \
      9   20
         /  \
        15   7
```

执行过程：

| 层数 | levelSize | 当前层结果    |
| -- | --------- | -------- |
| 1  | 1         | `[3]`    |
| 2  | 2         | `[9,20]` |
| 3  | 2         | `[15,7]` |

最终：

```
{{3}, {9, 20}, {15, 7}}
```

关于空间复杂度，你的分析尤其准确：

- `queue`：最多保存 `O(w)` 个待处理节点。
- `levelVals`：当前层最多 `O(w)` 个节点值。
- `answer`：总共保存 `n` 个节点值。

所以不计算返回结果时，辅助空间为 `O(w)`；计算返回结果时，总空间为 `O(n)`。

### 可以进一步优化的地方

当前：

```
vector<int> levelVals{};
```

完全正确。

如果我们知道当前层有 `levelSize` 个节点，可以提前预留空间：

```
vector<int> levelVals;
levelVals.reserve(levelSize);
```

这可以减少 `vector` 在追加元素时可能发生的动态扩容。

但这只是可选优化，不是必需修改，你当前提交通过的代码已经足够好。

### 面试专用回答

> 二叉树层序遍历可以使用 BFS 和队列实现。首先将根节点入队，每次外层循环开始时记录当前队列大小，确定这一层的节点数量。然后通过内层循环依次处理这些节点，将节点值保存到当前层数组，并将其非空左右孩子加入队列。当前层结束后，将该层数组加入二维结果。每个节点访问一次，时间复杂度为 O(n)；辅助空间为 O(w)，如果计入保存全部节点的返回结果，总空间复杂度为 O(n)。

## 1. 回顾 `Exec()` 的返回值

你之前写的是：

```
_, err := r.db.Exec(...)
```

为什么使用 `_`？

因为 `Exec()` 实际返回两个值：

```
(sql.Result, error)
```

第一个返回值 `sql.Result` 被你忽略了。

今天我们要把它保存下来：

```
result, err := r.db.Exec(...)
```

其中：

- `result`：SQL 执行结果。
- `err`：SQL 执行是否发生错误。

`sql.Result` 是一个接口，主要提供两个方法：

| 方法               | 作用                          |
| ---------------- | --------------------------- |
| `RowsAffected()` | 获取 SQL 操作影响的行数              |
| `LastInsertId()` | 获取最近插入记录的 ID，具体是否支持取决于数据库驱动 |

今天重点学习 `RowsAffected()`。

## 2. `RowsAffected()` 是什么？

例如，执行：

```
UPDATE students
SET age = 22
WHERE id = 1002;
```

如果学生 1002 存在，通常会有一条记录受到影响。

在 Go 中：

```
result, err := db.Exec(
    "UPDATE students SET age = ? WHERE id = ?",
    22,
    1002,
)
```

然后：

```
affected, err := result.RowsAffected()
```

就可以取得数据库驱动报告的受影响行数。

例如：

```
affected = 1
```

表示有一条记录受到本次 SQL 操作影响。

但是如果：

```
result, err := db.Exec(
    "UPDATE students SET age = ? WHERE id = ?",
    22,
    9999,
)
```

由于数据库中没有这个学生：

```
affected = 0
```

这里要理解一个重要区别：

SQL 执行成功，并不意味着一定有记录被修改。

例如：

```
DELETE FROM students WHERE id = 9999;
```

语句可以成功执行，但如果数据库没有该 ID，受影响行数就是 0。

这并不必然代表 SQL 执行错误。

### 执行错误与受影响行数

执行成功

`err == nil`

继续检查 RowsAffected()

执行失败

`err != nil`

直接处理或返回错误

当执行成功时，`RowsAffected()` 可能返回 0、1 或更多，取决于实际匹配情况、SQL 操作及驱动行为。

# 一、为什么动态使用 `q.size()` 可能提前结束当前层？

考虑下面这棵只有三个节点的二叉树：

```
       1
      / \
     2   3
```

正确的层序遍历结果应该是：

```
{
    {1},
    {2, 3}
}
```

假设你错误地写成：

```
for (int i = 0; i < static_cast<int>(q.size()); i++) {
    TreeNode* current = q.front();
    q.pop();

    levelVals.push_back(current->val);

    if (current->left != nullptr) {
        q.push(current->left);
    }

    if (current->right != nullptr) {
        q.push(current->right);
    }
}
```

问题在于，`q.size()` 每次判断循环条件时都会重新计算。

## 具体执行过程

第一层节点 1 处理完成后，队列为：

```
队头 → [2, 3] ← 队尾
```

此时准备处理第二层。

| 步骤     | `i` | `q.size()` | 条件          | 发生什么           |
| ------ | --- | ---------- | ----------- | -------------- |
| 开始     | 0   | 2          | `0 < 2`，成立  | 进入循环           |
| 处理节点 2 | 0   | 1          | —           | 节点 2 出队，没有孩子入队 |
| 下一次判断  | 1   | 1          | `1 < 1`，不成立 | 循环提前结束         |

此时队列还剩下：

```
[3]
```

但是当前层的结果已经变成：

```
[2]
```

下一次外层 `while` 又会把节点 3 当成新的一层。

错误结果

[[1], [2], [3]]

同一层的 2 和 3 被错误地拆开。

正确结果

[[1], [2, 3]]

第二层的两个节点一起处理。

### 为什么提前保存 `levelSize` 就能解决？

```
int levelSize = static_cast<int>(q.size());

for (int i = 0; i < levelSize; i++) {
    // 处理当前层
}
```

即使处理节点 2 后，队列大小从 2 变成 1，`levelSize` 仍然是 2。

于是：

```
i = 0：处理节点 2
i = 1：处理节点 3
```

第二层就能完整处理。

因此，动态使用 `q.size()` 有两类风险：

1. 当前节点没有孩子，队列变短，循环可能提前结束。
2. 当前节点有孩子，队列新增下一层节点，循环可能错误地继续处理下一层。

这也是 LeetCode 102 必须在每一层开始时固定队列大小的根本原因。

但检查的正确顺序应该是：

```
执行 Exec()
      ↓
检查 err
      ├── 非 nil → SQL 执行发生错误
      └── nil → 继续获取 RowsAffected()
                         ↓
                   检查其 error
                         ↓
                   判断受影响行数
```

当 `Exec()` 与 `RowsAffected()` 都没有返回错误，且结果为 0 时，通常说明操作没有影响记录，而不是重新将它解释为 SQL 执行失败。

对于按主键进行的 `DELETE`，影响 0 行一般表示没有匹配的记录；对于其他 SQL，则需要结合具体语句和驱动语义解释。

### 相关示例

```

    9999,
)
if err != nil {
    return err
}

affected, err := result.RowsAffected()
if err != nil {
    return err
}

    fmt.Println("学生不存在，未删除任何记录")
}
```

### 面试专用回答

> 数据库写操作需要先检查 Exec 返回的 error，确保 SQL 没有发生执行错误。如果还需要判断实际操作结果，则通过 RowsAffected 获取受影响行数，并检查该方法的错误。受影响行数为 0 不一定是数据库异常，可能只是没有匹配记录，具体处理取决于业务需求。

## 2. `repository.go`

```

package main

import "database/sql"

type Student struct {
	ID   int
	Name string
	Age  int
}

type StudentRepository struct {
	db *sql.DB
}

func NewStudentRepository(db *sql.DB) *StudentRepository {
	return &StudentRepository{db: db}
}

// 查询单个学生
func (r *StudentRepository) GetByID(id int) (Student, error) {
	var student Student

	err := r.db.QueryRow(
		"SELECT id, name, age FROM students WHERE id = ?",
		id,
	).Scan(
		&student.ID,
		&student.Name,
		&student.Age,
	)

	if err != nil {
		return Student{}, err
	}
	return student, nil
}

// 查询所有学生
func (r *StudentRepository) List() ([]Student, error) {
	rows, err := r.db.Query(
		"SELECT id, name, age FROM students ORDER BY id",
	)
	if err != nil {
		return nil, err
	}
	defer rows.Close()

	students := make([]Student, 0)

	for rows.Next() {
		var student Student

		if err := rows.Scan(
			&student.ID,
			&student.Name,
			&student.Age,
		); err != nil {
			return nil, err
		}

		students = append(students, student)
	}

	if err := rows.Err(); err != nil {
		return nil, err
	}

	return students, nil
}

// 新增学生
func (r *StudentRepository) Create(student Student) error {
	_, err := r.db.Exec(
		"INSERT INTO students (id, name, age) VALUES (?, ?, ?)",
		student.ID,
		student.Name,
		student.Age,
	)
	return err
}

// 根据ID修改学生信息
func (r *StudentRepository) Update(student Student) (int64, error) {
	result, err := r.db.Exec(
		"UPDATE students SET name = ?, age = ? WHERE id = ?",
		student.Name,
		student.Age,
		student.ID,
	)
	if err != nil {
		return 0, err
	}

	return result.RowsAffected()
}

// 根据ID删除学生
func (r *StudentRepository) Delete(studentID int) (int64, error) {
	result, err := r.db.Exec(
		"DELETE FROM students WHERE id = ?",
		studentID,
	)
	if err != nil {
		return 0, err
	}

	return result.RowsAffected()
}

	// 初始化学生表
	_, err = db.Exec(`
		CREATE TABLE students (
			id INTEGER PRIMARY KEY,
			name TEXT NOT NULL,
			age INTEGER NOT NULL
		)
	`)
	if err != nil {
		log.Fatal(err)
	}

	repo := NewStudentRepository(db)

	// 1. Create：新增学生
	err = repo.Create(Student{
		ID:   1004,
		Name: "David",
		Age:  23,
	})
	if err != nil {
		log.Fatal(err)
	}

	student, err := repo.GetByID(1004)
	if err != nil {
		log.Fatal(err)
	}

	fmt.Printf("After Create: %d | %s | %d\n",
		student.ID, student.Name, student.Age)

	// 2. Update：修改年龄
	affected, err := repo.Update(Student{
		ID:   1004,
		Name: "David",
		Age:  24,
	})
	if err != nil {
		log.Fatal(err)
	}

	fmt.Printf("Update affected: %d\n", affected)

	student, err = repo.GetByID(1004)
	if err != nil {
		log.Fatal(err)
	}

	fmt.Printf("After Update: %d | %s | %d\n",
		student.ID, student.Name, student.Age)

	// 3. Update：尝试修改不存在的学生
	affected, err = repo.Update(Student{
		ID:   9999,
		Name: "Nobody",
		Age:  20,
	})
	if err != nil {
		log.Fatal(err)
	}

	fmt.Printf("Update missing affected: %d\n", affected)

	// 4. Delete：删除存在的学生
	affected, err = repo.Delete(1004)
	if err != nil {
		log.Fatal(err)
	}

	fmt.Printf("Delete affected: %d\n", affected)

	// 5. Delete：再次删除同一学生
	affected, err = repo.Delete(1004)
	if err != nil {
		log.Fatal(err)
	}

	fmt.Printf("Delete again affected: %d\n", affected)

	// 6. 验证删除结果
	_, err = repo.GetByID(1004)

	if errors.Is(err, sql.ErrNoRows) {
		fmt.Println("Student 1004 not found")
	} else if err != nil {
		log.Fatal(err)
	} else {
		log.Fatal("Student 1004 should have been deleted")
	}
}

```

这里的 `:memory:` 表示数据库只存在于当前进程的内存中，程序结束后数据就消失。

设置：

```
db.SetMaxOpenConns(1)
```

是为了保证本实验中的数据库操作复用同一个底层 SQLite 连接，避免多个连接各自访问不同的内存数据库。

## 检查 4：`Update()`、`Delete()` 和受影响行数

### 1. 问题

为什么返回 `(int64, error)`？为什么更新不存在的学生可能不报错？为什么 `UPDATE`、`DELETE` 必须注意 `WHERE` 条件？

### 2. 我的回答

> 1. 为什么这次不再只返回 `error`，而是返回 `(int64, error)`？因为这次需要知道受到影响的行数，调用的RowsAffected返回值即(int64, error)
> 2. 当修改一个不存在的学生时，为什么 `Exec()` 可能返回 `nil` 错误，而 `RowsAffected()` 返回 0？因为本身SQL语句执行成功，修改一个不存在的学生在SQL语句执行层面也算成功，修改一个不存在的学生等于修改0个学生成功。所以RowsAffected()返回 0，nil,受到影响的记录行数为0
> 3. 为什么执行 `UPDATE` 和 `DELETE` 时尤其需要注意 `WHERE` 条件？因为不加where字段判断条件的话，UPDATE和DELETE会在数据库中的所有记录上执行，造成毁灭性的错误。

### 3. 订正

✅ 三问全部正确。

第一问： `RowsAffected()` 返回 `(int64, error)`，所以可以将受影响行数以及错误继续返回给调用者。

```
func (r *StudentRepository) Update(student Student) (int64, error) {
    result, err := r.db.Exec(
        "UPDATE students SET name = ?, age = ? WHERE id = ?",
        student.Name,
        student.Age,
        student.ID,
    )
    if err != nil {
        return 0, err
    }

    return result.RowsAffected()
}
```

第二问： 你已经正确区分了“SQL 执行成功”和“实际更新到记录”。

当执行：

```
UPDATE students SET age = 20 WHERE id = 9999;
```

而数据库中没有 ID 为 9999 的学生时，语句仍然可以成功执行，只是没有匹配的记录，因而在当前 SQLite 示例中受影响行数为 0。

第三问： 你的理解完全正确。需要记住，`WHERE` 不是 `UPDATE` 和 `DELETE` 在语法上必须具备的部分，但在根据特定学生操作数据时，它是至关重要的安全条件。

### 4. 相关示例

假设数据库有 100 名学生。

```
UPDATE students SET age = 20 WHERE id = 1002;
```

只针对 ID 为 1002 的记录。

而：

```
UPDATE students SET age = 20;
```

会针对表中所有记录执行更新。

删除操作同理：

```
DELETE FROM students WHERE id = 1002;
```

和：

```
DELETE FROM students;
```

含义完全不同。后者会删除表中全部记录。

### 5. 面试专用回答

> `Update()` 和 `Delete()` 可以通过 `Exec()` 执行 SQL，并通过 `RowsAffected()` 返回受影响行数，同时返回 `error` 报告执行异常。SQL 执行成功不一定代表存在匹配记录，例如按主键更新不存在的数据时，影响行数可以为 0。此外，UPDATE 和 DELETE 必须根据业务需求正确设置 WHERE 条件，否则可能误操作整张表。

## 检查 5：CRUD 与内存数据库、文件数据库

### 1. 问题

Repository 中的五个方法如何对应 CRUD？为什么使用不同的数据库 API？内存型和文件型 SQLite 有什么区别？

### 2. 我的回答

> 1. 它们分别对应 CRUD 中的什么操作？Create()对应增，Delete()Delete()对应删，Update()对应改，GetByID()和List()对应查，总体就是增删改查。
> 2. 为什么 `GetByID()` 和 `List()` 使用查询 API，而 `Create()`、`Update()`、`Delete()` 通常使用 `Exec()`？因为一般`GetByID()` 和 `List()`需要返回单行或多行结果集，而Create()`、`Update()`、`Delete()\`通常不需要返回结果集。
> 3. 当前 `:memory:` 数据库与之前文件型 `students.db` 有什么区别？前者是内存型数据库，生命周期绑定程序的生命周期，程序结束后就会被销毁，程序启动则会重新创建，而后者是文件型数据库，其生命周期实现了持久化，数据一般保存在硬盘内存中，不会随着程序的关闭而被销毁，且其他程序也可以共同访问该数据库，实现了数据的持久化。

### 3. 订正

✅ 核心全部正确，有两处表述值得规范。

第一，CRUD 对应关系：

| CRUD       | Repository 方法        | SQL 操作        |
| ---------- | -------------------- | ------------- |
| Create（创建） | `Create()`           | `INSERT INTO` |
| Read（读取）   | `GetByID()`、`List()` | `SELECT`      |
| Update（更新） | `Update()`           | `UPDATE`      |
| Delete（删除） | `Delete()`           | `DELETE`      |

第二，API 的选择：

你的理解正确。普通的 `SELECT` 查询需要读取行结果，通常使用 `QueryRow()` 或 `Query()`；不需要返回行结果集的普通写操作通常使用 `Exec()`。

需要补充：这不是绝对规则，例如某些数据库支持 `INSERT ... RETURNING`，此时也可能使用查询 API 读取返回的数据。但对于我们目前的 SQLite CRUD 实验，你的选型完全正确。

第三，数据库生命周期：

你提到“硬盘内存”，这里应该区分：

- 内存（RAM）：保存 `:memory:` 数据库的数据。
- 磁盘存储（例如 SSD、硬盘）：保存 `students.db` 数据库文件。

另外，`:memory:` 数据库的生命周期更严格地说是与创建它的 SQLite 底层连接关联，而不单纯是与整个程序生命周期绑定。

一个新的 SQLite 连接使用 `:memory:`，通常会创建自己的独立内存数据库；对应连接关闭后，该数据库就会消失。

这也是我们之前使用：

```
db.SetMaxOpenConns(1)
```

的重要原因：确保实验操作复用同一个底层连接，避免意外访问不同的内存数据库。

### 4. 相关示例

内存数据库：

```
db, err := sql.Open("sqlite3", ":memory:")
```

适合学习实验或需要隔离数据的简单测试，重启程序后重新初始化。

文件数据库：

```
db, err := sql.Open("sqlite3", "students.db")
```

数据存入数据库文件，程序退出后通常仍然保留，下次重新打开可以继续读取。

文件型 SQLite 也可以由其他进程访问，但并发读写仍然受到 SQLite 事务和锁机制的约束，并不是所有操作都能无限制同时执行。

### 5. 面试专用回答

> CRUD 分别对应数据库的新增、查询、更新和删除操作。普通查询通常通过 QueryRow 或 Query 获取结果，普通写操作通常通过 Exec 执行，并可结合 RowsAffected 判断受影响行数。SQLite 的内存数据库主要将数据保存在内存中，生命周期与底层连接相关；文件数据库将数据持久化保存到磁盘文件中，程序退出后仍可重新打开并读取。
